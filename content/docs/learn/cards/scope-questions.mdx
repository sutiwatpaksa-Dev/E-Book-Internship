## ความหมาย

**ขอบเขตงาน (scope)** คือเส้นแบ่งที่เขียนไว้ว่ารอบนี้ **ทำอะไร และไม่ทำอะไร** ส่วน **ถามให้ได้คำตอบ** คือเขียนคำถามแบบที่คนตอบตอบได้เร็ว และตอบครั้งเดียวจบ

**นึกภาพ:** รับจ้างทาสีห้องนอน 1 ห้อง ถ้าไม่ได้ตกลงกันว่า "ไม่รวมเพดานและประตู" วันสุดท้ายเจ้าของบ้านจะถามว่า "เพดานด้วยนะ" ช่างไม่มีอะไรให้อ้าง ต้องทำฟรีหรือทะเลาะกัน

## ที่มา

งานไม่ได้ใหญ่ขึ้นทีเดียว มันงอกทีละนิด "เพิ่มปุ่มนี้อีกนิดเดียว" "ทำให้ส่งอีเมลได้ด้วยได้ไหม" แต่ละข้อดูเล็ก รวมกันแล้วไม่ทันกำหนด เรียกว่า [scope creep](/glossary#scope-creep) ทางกันคือเขียนรายการ "ไม่ทำ" ตั้งแต่วันแรก ให้ทุกคนเห็นตรงกัน คำขอใหม่จะได้เป็น **การตัดสินใจ** (เพิ่มแล้วตัดอะไรออก หรือเลื่อนไปรอบหน้า) ไม่ใช่งานที่แอบเพิ่มเข้ามา

ส่วนคำถาม ถ้าถามกว้าง ("ตรงนี้ทำยังไงดีครับ") จะได้คำตอบกว้างกลับมา หรือต้องคุยกันอีกหลายรอบ ระหว่างนั้นงานหยุด

## การใช้งาน

ทำไฟล์ `NOTES.md` ไว้ที่ root ของโปรเจกต์ (ขึ้น Git ด้วย) มี 3 หัวข้อ ตัวอย่างนี้ต่อจาก story ห้องสมุดในการ์ด [User story](/learn/cards/user-stories)

**1. ไม่ทำรอบนี้** บอกเหตุผล และบอกว่าจะได้ทำเมื่อไร

```md
## ไม่ทำรอบนี้
- สมาชิกต่ออายุการยืมเอง (story 8): ต้องมีระบบ login ของสมาชิก ซึ่งใหญ่กว่างานทั้งรอบ → รอบหน้า
- เตือนผ่าน LINE (story 9): ต้องสมัคร LINE Official Account และตั้ง webhook → รอบหน้า
- ค่าปรับคืนช้า: ห้องสมุดไม่เก็บเงิน (ตาม brief) → ไม่ทำ
- สมาชิกจองหนังสือเองผ่านเว็บ: brief บอกว่าไม่มี → ไม่ทำ
- แบ่งหนังสือเป็นหมวด: Requirement ข้อ 6 ยกตัวอย่างหมวดไว้ แต่ไม่มีหน้าจอหรือกฎไหนใช้หมวด (คำถามข้อ 3 ในการ์ดอ่าน Requirement) → รอบหน้า ถ้าบรรณารักษ์ขอ
- สมาชิกระดับทอง (ข้อ 7): ตัดออกตามคำตอบคำถามข้อ 1 ข้างล่าง → รอบหน้า
```

**2. ข้อสมมติ** คือสิ่งที่เราเดาไว้และจะทำตามนี้ ถ้าไม่มีใครค้าน เขียนไว้เพื่อให้คนอื่นเห็นแล้วค้านได้ตั้งแต่วันนี้

```md
## ข้อสมมติ
- หนังสือ 1 ชื่อมี 1 เล่ม (ไม่มีหลายฉบับ) ตาราง books 1 แถว = 1 เล่มบนชั้น
- บรรณารักษ์ทุกคนมีสิทธิ์เท่ากัน ไม่แยกระดับ
```

ข้อสมมติแรกเปลี่ยนแบบตารางทั้งหมด ถ้าห้องสมุดมี "แฮร์รี่ พอตเตอร์" 3 เล่ม ต้องแยกตาราง "ชื่อหนังสือ" กับ "เล่มจริง" ออกจากกัน รู้วันนี้แก้บนกระดาษ รู้วันที่ 8 ต้องรื้อตาราง API และหน้าจอ

**3. คำถามและคำตอบ** คำถามที่ดีมี 4 ส่วน: **อ้างที่มา + ทางเลือก + สิ่งที่เราเสนอ + ผลถ้ายังไม่มีคำตอบ**

```md
## คำถาม

### 1. ระดับทองยืมได้กี่เล่ม (ถาม 27 ต.ค.)
- อ้างถึง: Requirement ข้อ 7 "สมาชิกระดับทองยืมได้มากกว่าปกติ" ไม่บอกตัวเลข
- ทางเลือก: (ก) 5 เล่ม (ข) ไม่จำกัด (ค) ตัดข้อนี้ออกรอบนี้
- ผมเสนอ: (ค) เพราะต้องเพิ่มคอลัมน์ระดับสมาชิก และหน้าจัดการระดับ
- ถ้ายังไม่มีคำตอบภายในพรุ่งนี้: ทำ 3 เล่มเท่ากันทุกคนไปก่อน
- คำตอบ: (ค) · พี่ไบต์ · 27 ต.ค.
```

ใช้หัวข้อย่อย 1 อันต่อ 1 คำถามแทนตาราง เพราะคำถามที่ดีมีหลายบรรทัด และตาราง markdown ขึ้นบรรทัดใหม่ในช่องไม่ได้

เทียบกับคำถามที่ไม่ดี: "ระดับทองยืมได้กี่เล่มครับ" คนตอบต้องไปคิดเองว่ามีทางเลือกอะไร และต้องถามกลับว่า "แล้วถ้าไม่จำกัดจะทำทันไหม" เสียไปอีกรอบ

**4. ส่งคำถามรวมทีเดียว** วันละ 1–2 รอบ ไม่ใช่ทีละข้อ และพอได้คำตอบ จดในบรรทัด "คำตอบ" ของคำถามนั้นทันที พร้อมชื่อคนตอบและวันที่

**5. เมื่องานหลุดแผน แจ้งภายในวันนั้น** ข้อความ 4 บรรทัดพอ

> - **วันนี้:** ทำ story 5 (บันทึกการยืม) ยังไม่เสร็จ ช้ากว่าแผน 1 วัน
> - **เพราะ:** เกณฑ์ "ยืมเกิน 3 เล่มไม่ได้" ต้องนับเล่มที่ยังไม่คืน ผมเพิ่งเข้าใจ query นี้วันนี้
> - **พรุ่งนี้:** ทำ story 5 ให้เสร็จก่อนเที่ยง แล้วเริ่ม story 6
> - **ต้องการ:** ขอให้พี่ช่วยดู query ตอนบ่าย 15 นาที (ถ้าไม่ต้องการอะไร เขียนว่า "ไม่ต้องการอะไรเพิ่ม")

4 บรรทัดนี้ตอบสิ่งที่พี่เลี้ยงต้องรู้ครบ: ช้าแค่ไหน, ช้าเพราะอะไร (จะได้ช่วยถูกจุด), แผนใหม่, และต้องช่วยอะไรไหม

**ควรได้:** `NOTES.md` ที่มีทั้ง 3 หัวข้อ ส่งพร้อม brief และ story

## ทริคที่แนะนำ

1. **รายการ "ไม่ทำ" ต้องตกลงกัน ไม่ใช่ตัดเอง:** ถ้าเราตัดเงียบๆ วันส่งงานลูกค้าจะเห็นว่าขาด ส่งรายการให้พี่เลี้ยงเห็นด้วยก่อน ข้อที่ไม่ผ่านจะได้ย้ายกลับไปอยู่ในงาน
2. **คำถามแบบเลือกตอบเร็วกว่าคำถามเปิด:** คนตอบตอบ "(ค)" ได้ในไม่กี่วินาที คำถามเปิดต้องคิดแทนเรา ยิ่งคนตอบยุ่ง ยิ่งต่างกันมาก
3. **ทุกคำตอบจดว่าใครตอบ วันที่เท่าไร:** วัน Review ถ้ามีคนถามว่า "ทำไมไม่มีระดับทอง" เราเปิด `NOTES.md` ให้ดูได้เลย ไม่ต้องจำ และไม่ต้องเถียงจากความจำของแต่ละคน

## ปรับไปใช้จริง

**ในงาน STARTER:** ขอบเขตหลายข้อมีให้แล้วใน Requirement (ลิงก์ PDF ต้อง login): **ห้ามมีตะกร้าสินค้าหรือจ่ายเงิน** และไม่เกิน 3 หน้า ([หน้า 2](/api/files/requirement.pdf#page=2)), **รูปใช้ URL ไม่ต้องทำระบบอัปโหลด** ([หน้า 6](/api/files/requirement.pdf#page=6)), **bonus ทำได้เมื่องานหลักครบแล้วเท่านั้น** ([หน้า 13](/api/files/requirement.pdf#page=13)) และกฎ **"ถ้าวันไหนหลุด ต้องแจ้งพี่เลี้ยงภายในวันนั้น"** ([หน้า 11](/api/files/requirement.pdf#page=11)) วันที่ 5 (Review รอบ 1) Requirement ให้ "สรุปปัญหาที่เจอมาให้ชัดก่อนคุยกับพี่เลี้ยง" ซึ่งใช้วิธีเขียนคำถามแบบเดียวกับข้อ 3

**เว็บคู่มือนี้:** หน้า /learn ที่กำลังอ่านอยู่ก็มีขอบเขตเขียนไว้ก่อนเริ่ม ใน [MAINTAINING.md บน GitHub](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/MAINTAINING.md) หัวข้อเลขเวอร์ชัน บอกว่างานปรับหน้าเรียนต้อง "เสร็จครบตามเกณฑ์ที่ตกลงกันไว้ก่อนเริ่ม" ถึงจะขึ้นเว็บจริงได้ ของที่ยังไม่ครบจึงอยู่บนเว็บทดสอบก่อน

ลองคิด: วันที่ 7 พี่เลี้ยงบอกว่า "เพิ่มระบบจองคิวให้ลูกค้าด้วยนะ" ควรตอบกลับว่าอะไร (ลองเขียนเป็นคำถามแบบมี 4 ส่วน)

## ตัวเลือกอื่นที่คล้ายกัน

| ที่จด | ข้อดี | ข้อเสีย |
|---|---|---|
| **`NOTES.md` ใน repo (การ์ดนี้)** | อยู่กับโค้ด มีประวัติใน Git ทุกคนเปิดได้ | ต้องมีวินัยจดเอง |
| GitHub Issues + label | คุยใต้คำถามได้ ปิดเมื่อได้คำตอบ | กระจายหลายใบ หาภาพรวมยากกว่า |
| หัวข้อ "การตัดสินใจ" ใน README | คนที่ clone ไปเห็นทันที | README ยาวขึ้นเรื่อยๆ |
| แชท LINE / Slack | เร็วที่สุด | ข้อความเลื่อนหาย หาย้อนหลังไม่เจอ ใช้ถามได้ แต่คำตอบต้องจดลงที่อื่น |

## ลองเอง

**โจทย์:** เขียน `NOTES.md` ของงาน STARTER ให้มี **ไม่ทำรอบนี้** อย่างน้อย 3 ข้อ, **ข้อสมมติ** อย่างน้อย 2 ข้อ และ **คำถาม** อย่างน้อย 3 ข้อที่มีครบ 4 ส่วน (ใช้คำถามจากการ์ด [อ่าน Requirement](/learn/cards/reading-requirements) ได้)

<Hint level={1}>เริ่มรายการ "ไม่ทำ" จากข้อห้ามที่ Requirement เขียนไว้แล้ว แล้วเพิ่มของที่ brief บอกว่า "ไม่มี"</Hint>
<Hint level={2}>หาข้อสมมติด้วยคำถาม "ถ้าคำตอบเป็นอีกแบบ แบบตารางต้องเปลี่ยนไหม" เช่น หนึ่งบริการอยู่ได้กี่หมวด, ร้านมีกี่สาขา</Hint>
<Hint level={3}>ตรวจคำถามของตัวเอง: อ่านแล้วตอบได้ด้วยตัวอักษรตัวเดียวหรือคำว่า "ได้/ไม่ได้" ไหม และทุกข้อบอกว่าถ้ายังไม่มีคำตอบจะทำอะไรต่อ ถ้ายังต้องถามกลับ แปลว่ายังขาดส่วนใดส่วนหนึ่ง</Hint>
