> ต่อจากการ์ด [Migration และ Seed](/learn/cards/migration) และการ์ดขึ้นเว็บ ([VPS](/learn/cards/vps-deployment) ข้อ 7 สอน `pg_dump` ครั้งเดียวไว้แล้ว การ์ดนี้ทำให้เป็นอัตโนมัติ เก็บนอกเครื่อง และซ้อมกู้) หรือ [Vercel + Neon](/learn/cards/vercel-deployment) ข้อมูลแผนฟรีตรวจเมื่อ 3 พ.ย. 2569

## ความหมาย

พูดง่ายๆ: **[backup](/glossary#backup)** คือสำเนาข้อมูลทั้งหมด ณ เวลาหนึ่ง ส่วน **กู้คืน (restore)** คือเอาสำเนานั้นกลับมาใช้ได้จริง สองอย่างนี้ต้องมาคู่กัน **backup ที่ไม่เคยลองกู้ = ยังไม่มี backup** เพราะไม่รู้ว่าไฟล์อ่านได้ไหม ครบไหม และกู้แล้วใช้เวลาเท่าไหร่

นึกภาพ: สมุดทะเบียนยืมหนังสือของห้องสมุด

- **backup** = ถ่ายเอกสารสมุดทุกคืน
- **เก็บนอกเครื่อง** = เอาสำเนาไปไว้อีกตึกหนึ่ง ถ้าเก็บไว้ในตู้เดียวกับสมุดจริง ไฟไหม้ทีเดียวหายทั้งคู่
- **ซ้อมกู้** = หยิบสำเนามาลองอ่านว่าครบทุกหน้า ไม่ใช่กระดาษเปล่าเพราะเครื่องถ่ายหมึกหมด

จุดที่ไม่ตรง: สำเนากระดาษเปิดดูแล้วรู้เลยว่าอ่านได้ แต่ไฟล์ backup มองจากชื่อไฟล์ไม่ออก ไฟล์ขนาด 0 หรือมีแต่ error ก็ชื่อเหมือนไฟล์ดี ต้องกู้ลงฐานจริงแล้วนับแถวเท่านั้นถึงจะรู้

ตัวเลข 2 ตัวที่ลูกค้าจะถาม (และอยู่ใน "คำถามที่ต้องตอบได้" ของขั้น 7):

| คำถาม | ชื่อเรียกในวงการ | ระบบห้องสมุดในการ์ดนี้ |
|---|---|---|
| ข้อมูลหายย้อนหลังได้มากสุดกี่ชั่วโมง | RPO | backup ทุกคืนตี 2 = เสียได้สูงสุดราว 24 ชั่วโมง |
| พังแล้วกู้กลับมาใช้ได้ในกี่นาที | RTO | ได้จากการซ้อมกู้ (ข้อ 4) ไม่ใช่การเดา |

## ที่มา

เรื่องจริงที่เกิดบ่อย: น้องแก้ schema ลบคอลัมน์ `returned_at` ผิดตัว แล้ว migrate บนฐานจริง ประวัติการคืนหนังสือทั้งปีหายในวินาทีเดียว [rollback](/glossary#rollback) โค้ดย้อนได้ แต่**ข้อมูลที่ลบไปแล้วย้อนเองไม่ได้**

สาเหตุอื่นที่เจอ: ดิสก์ VPS เสีย, ผู้ให้บริการปิดบัญชี, กด `docker compose down -v` (ลบ volume = ลบฐานทั้งก้อน), รหัสฐานหลุดแล้วโดนลบข้อมูล ทุกกรณีทางรอดทางเดียวคือมีสำเนาที่**อยู่ที่อื่น**และ**เคยกู้ได้จริง**

## การใช้งาน

### ตั้งค่าครั้งแรก

ทาง VPS ไม่ต้องติดตั้งอะไรเพิ่ม (`pg_dump` อยู่ในกล่อง Postgres แล้ว) ทาง Neon ใช้ Docker บนเครื่องเรา รัน `pg_dump` แทนการติดตั้ง Postgres (ไม่ต้องลงโปรแกรมเพิ่ม และได้รุ่นตรงกับฐานเสมอ)

ข้อ 1–4 สำหรับทาง VPS ข้อ 5 สำหรับทาง Vercel + Neon

### 1. สคริปต์ backup (`deploy/backup.sh`)

เขียนเป็นไฟล์แทนพิมพ์คำสั่งทุกครั้ง เพราะจะให้เครื่องรันเองทุกคืน (ข้อ 2) และต้องแน่ใจว่า**ถ้าพัง ต้องพังเสียงดัง** ไม่ใช่ได้ไฟล์เปล่าเงียบๆ:

```bash
#!/usr/bin/env bash
# สำรองฐานข้อมูลห้องสมุด 1 ไฟล์ แล้วลบไฟล์ที่เก่ากว่า 14 วัน
set -euo pipefail
cd "$(dirname "$0")/.."                       # ไปโฟลเดอร์โปรเจกต์ (ที่มี compose.yaml) ไม่ว่าจะรันจากที่ไหน
mkdir -p backups
file="backups/library-$(date +%F-%H%M).sql.gz"
trap 'rm -f "$file.part"' EXIT                 # ถ้าล้มกลางทาง ลบไฟล์ครึ่งๆ ทิ้ง
docker compose exec -T db pg_dump -U postgres postgres | gzip > "$file.part"
mv "$file.part" "$file"                        # ถึงบรรทัดนี้ได้ = dump สำเร็จจริง
find backups -name 'library-*.sql.gz' -mtime +14 -delete
echo "สำรองเสร็จ: $file ($(du -h "$file" | cut -f1))"
```

อ่านจุดสำคัญ:

- **`set -euo pipefail`** สั่งให้หยุดทันทีเมื่อคำสั่งไหนล้ม `pipefail` สำคัญที่สุด: ใน `pg_dump | gzip` ถ้า `pg_dump` ล้มแต่ `gzip` ทำงานต่อ ปกติ bash ถือว่าผ่าน แล้วได้ไฟล์ `.gz` ขนาดเล็กที่ข้างในว่างเปล่า (ตัวเลือกนี้มีใน bash จึงขึ้นต้นด้วย `#!/usr/bin/env bash` และรันด้วย `bash` ไม่ใช่ `sh`)
- **`.part` แล้วค่อย `mv`:** ไฟล์ชื่อ `library-*.sql.gz` จะมีเฉพาะที่ dump สำเร็จ ไฟล์ที่ล้มกลางทางไม่หลงมาให้เราเข้าใจผิดตอนกู้
- **`-T`** ส่งผลออกมาตรงๆ ไม่ผ่านจอ (ไม่ใส่จะมีตัวอักษรควบคุมปนในไฟล์ ใช้กู้ไม่ได้)
- **`gzip`** ไฟล์ SQL เป็นตัวอักษรล้วน บีบแล้วเล็กลงหลายเท่า
- **`find ... -mtime +14 -delete`** ลบไฟล์ที่เก่ากว่า 14 วัน ไม่งั้นดิสก์เต็มสักวัน

เพิ่ม `backups/` ใน `.gitignore` ก่อน (ไฟล์ backup มีข้อมูลสมาชิกและ hash รหัสผ่าน ห้ามขึ้น GitHub เด็ดขาด) แล้ว commit สคริปต์ ดึงลง VPS ด้วย `git pull` และลองรันบน VPS:

```bash
cd ~/library
bash deploy/backup.sh
```

**ควรเห็น:** `สำรองเสร็จ: backups/library-2026-11-03-0200.sql.gz (4.0K)` ขนาดขึ้นกับข้อมูล ถ้ามีแค่ข้อมูลจาก seed จะได้ราว `4.0K` (ลองแล้ว) (ลองแล้วกับข้อมูลสมาชิก 2,000 หนังสือ 5,000 การยืม 20,000 แถว ได้ `144K`)

**ลองให้มันพัง:** `docker compose stop db` แล้วรันสคริปต์อีกครั้ง ต้องเห็น `service "db" is not running` และ `echo $?` ได้ `1` (`echo $?` พิมพ์ผลของคำสั่งล่าสุด เรียกว่า **exit code**: `0` = สำเร็จ เลขอื่น = ล้ม) ใน `backups/` ต้องไม่มีไฟล์ใหม่ (ลองแล้ว) จากนั้น `docker compose start db`

### 2. ให้เครื่องรันเองทุกคืน (cron)

[cron](/glossary#cron) คือนาฬิกาปลุกของ Linux สั่งให้รันคำสั่งตามเวลาที่ตั้ง เปิดตารางของ cron บน VPS:

```bash
crontab -e
```

ครั้งแรกจะถามว่าใช้โปรแกรมแก้ไฟล์ตัวไหน เลือก `nano` (ง่ายสุด) แล้วเพิ่มบรรทัดนี้ท้ายไฟล์ บันทึกด้วย `Ctrl+O` Enter ออกด้วย `Ctrl+X`:

```text
0 2 * * * bash /root/library/deploy/backup.sh >> /root/library/backups/backup.log 2>&1
```

- **`0 2 * * *`** = นาทีที่ 0 ของตี 2 ทุกวัน ทุกเดือน ทุกวันในสัปดาห์ (ตี 2 ตามเวลาของเครื่อง ดูด้วย `date` ถ้าเป็น UTC ตี 2 ของเครื่องคือ 9 โมงเช้าไทย แก้เลข 2 เป็น 19 ถ้าอยากได้ตี 2 ไทย)
- **ใช้ path เต็ม** `/root/library/...` เพราะ cron ไม่ได้เริ่มที่โฟลเดอร์เดียวกับเรา ถ้า login ด้วยชื่ออื่นที่ไม่ใช่ `root` (เช่น `ubuntu` ในการ์ด VPS) ให้ใช้ path ที่ได้จาก `cd ~/library && pwd` แทน
- **`>> backup.log 2>&1`** เก็บทั้งข้อความปกติและ error ลงไฟล์ cron ไม่มีจอให้เห็น ถ้าไม่เก็บ พังก็ไม่มีใครรู้
- เรียกสคริปต์ ไม่เขียนคำสั่งยาวใน crontab ตรงๆ เพราะใน crontab ตัว `%` (ใน `date +%F`) มีความหมายพิเศษ ต้อง escape ทุกตัว ลืมทีเดียวบรรทัดนั้นไม่ทำงานเงียบๆ

**ควรเห็น:** `crontab -l` แสดงบรรทัดที่เพิ่ม เช้าวันรุ่งขึ้น `tail backups/backup.log` ต้องมีบรรทัด `สำรองเสร็จ:` ของตี 2 ถ้าไม่มีอะไรเลย ตรวจว่า cron ทำงานด้วย `systemctl status cron` (ต้องขึ้น `active (running)`)

### 3. เก็บอีกชุดไว้นอกเครื่อง

backup ที่อยู่บน VPS เครื่องเดียวกับฐาน ช่วยได้เฉพาะตอนข้อมูลถูกลบผิด แต่ถ้าเครื่องเสียหรือบัญชีถูกปิด หายทั้งคู่ วิธีง่ายที่สุดคือดึงลงเครื่องเราสัปดาห์ละครั้ง (พิมพ์**บนเครื่องเรา** ไม่ใช่บน VPS ใช้ได้ทั้ง Mac และ Git Bash):

```bash
mkdir -p ~/library-backups
scp "root@203.0.113.10:/root/library/backups/library-*.sql.gz" ~/library-backups/
```

แทน `203.0.113.10` ด้วย IP ของ VPS เรา (และ `root` ด้วยชื่อที่ใช้ ssh) ใส่เครื่องหมายคำพูดรอบที่อยู่บน VPS เพราะ `*` ต้องให้ฝั่ง VPS เป็นคนขยาย ไม่ใช่เครื่องเรา

**ควรเห็น:** ไฟล์ทุกไฟล์ใน `backups/` ของ VPS ถูกคัดลอกมาที่ `~/library-backups` (แต่ละไฟล์มีบรรทัด `100%`) งานจริงของบริษัทมักส่งขึ้นที่เก็บไฟล์บน cloud อัตโนมัติ (ดู "ตัวเลือกอื่น") แต่หลักเดียวกัน: **อย่างน้อย 2 ที่ และ 1 ในนั้นอยู่นอกเครื่องที่รันฐาน**

### 4. ซ้อมกู้จริง และจับเวลา

กู้ลง**ฐานใหม่** (`restore_check`) เสมอ ห้ามกู้ทับฐานที่เว็บใช้อยู่ ถ้าไฟล์เสีย ฐานจริงจะพังตามไปด้วย และถ้ากู้ลงฐานที่มีตารางอยู่แล้ว จะเจอ `ERROR: relation "books" already exists` (ลองแล้ว):

```bash
cd ~/library
date                                                              # จดเวลาเริ่ม
docker compose exec -T db createdb -U postgres restore_check
gunzip -c backups/library-2026-11-03-0200.sql.gz \
  | docker compose exec -T db psql -q -v ON_ERROR_STOP=1 -U postgres -d restore_check
docker compose exec -T db psql -U postgres -d restore_check \
  -c "select (select count(*) from members) as members, (select count(*) from books) as books, (select count(*) from loans) as loans;"
date                                                              # จดเวลาจบ
```

`-v ON_ERROR_STOP=1` ให้ `psql` หยุดทันทีที่เจอ error แรก (ค่าเริ่มต้นคือข้ามแล้วทำต่อ ได้ฐานครึ่งๆ กลางๆ ที่ดูเหมือนสำเร็จ)

**ควรเห็น:** ตัวเลข 3 ตัวตรงกับฐานจริง (เปิดเทียบใน pgAdmin หรือรันคำสั่งเดียวกันกับ `-d postgres`) ลองแล้วข้อมูลราว 27,000 แถวกู้เสร็จใน 1 วินาที ฐานจริงที่ใหญ่ขึ้นจะนานขึ้น ตัวเลขนี้แหละคือ RTO จดลง README ส่วน "ดูแลระบบ" ซ้อมเสร็จลบทิ้งด้วย `docker compose exec -T db dropdb -U postgres restore_check`

**ถ้าวันหนึ่งต้องกู้จริง:** ทำเหมือนการซ้อมทุกขั้น (กู้ลงฐานใหม่ชื่อ เช่น `library_restored` แล้วนับแถว) จากนั้นแก้ `DATABASE_URL` ใน `compose.yaml` ให้ชี้ `.../library_restored` แล้ว `docker compose up -d app` ฐานเก่ายังอยู่ ถ้ากู้ผิดไฟล์ก็สลับกลับได้ ก่อนเริ่มให้ backup ฐานที่พังเก็บไว้อีกชุดด้วย เผื่อต้องดึงข้อมูลบางส่วนที่เกิดหลัง backup ล่าสุด

### 5. ทาง Vercel + Neon

Neon เก็บ**ประวัติการเปลี่ยนแปลง**ของฐานไว้ให้เอง ย้อนไปจุดเวลาไหนก็ได้ในช่วงที่เก็บ แผน Free เก็บ **6 ชั่วโมง** (Launch สูงสุด 7 วัน) มี 2 วิธีใช้:

- **ดูหรือดึงข้อมูลเก่ามาเทียบ (ปลอดภัย):** เมนู **Branches** → **New branch** → เลือก parent เป็น branch หลัก → เลือก **Past data** แล้วใส่วันเวลาก่อนเกิดเรื่อง → **Create** ได้ฐานแยกที่ข้อมูลเป็นแบบเวลานั้น ต่อด้วย connection string ของ branch ใหม่ (ปุ่ม Connect) ฐานจริงไม่ถูกแตะ
- **ย้อนฐานจริงทั้งก้อน:** เลือก branch หลัก → **Backup & Restore** → **Restore from history** → เลือกเวลา → **Next** → **Restore** Neon สร้าง branch สำรองของสถานะก่อนย้อนให้เอง (ชื่อลงท้าย `_old_...`) ถ้าย้อนผิดเวลายังกลับได้

6 ชั่วโมงสั้นมาก ถ้าเพิ่งรู้ตัวพรุ่งนี้เช้าว่าข้อมูลหายเมื่อวาน ย้อนไม่ทันแล้ว จึงต้องมี backup ของเราเองด้วย ใช้ `pg_dump` ผ่าน Docker บนเครื่องเรา ด้วย connection string แบบ **direct** (วิธี `read -rs` เดียวกับการ์ด Vercel ข้อ 3 ไม่ให้ค่าลับค้างในประวัติ Terminal):

```bash
# Mac (zsh) และ Windows (Git Bash) พิมพ์เหมือนกัน
mkdir -p ~/library-backups
set -o pipefail                 # ให้ทั้งบรรทัดล้มถ้า pg_dump ล้ม (เหตุผลเดียวกับข้อ 1)
read -rs DIRECT                 # วางค่าแบบ direct จาก Neon แล้วกด Enter
docker run --rm postgres:17-alpine pg_dump --no-owner --no-privileges "$DIRECT" | gzip > ~/library-backups/neon-$(date +%F).sql.gz
echo $?                         # ต้องได้ 0
```

`--no-owner --no-privileges` ตัดบรรทัดที่บอกว่าตารางเป็นของผู้ใช้ชื่อ `neondb_owner` ออก ถ้าไม่ตัด ตอนกู้ลงฐานในเครื่องจะล้มด้วย `ERROR: role "neondb_owner" does not exist` เพราะในเครื่องไม่มีผู้ใช้ชื่อนี้ (ลองแล้ว)

`postgres:17-alpine` ต้องเป็นรุ่นเดียวกับ Postgres ของ Neon หรือใหม่กว่า (`pg_dump` รุ่นต่ำกว่าฐานจะไม่ยอมทำงาน) ดูรุ่นได้ที่ **SQL Editor** ของ Neon พิมพ์ `SHOW server_version;` ถ้าขึ้น 18.x ให้ใช้ `postgres:18-alpine`

**ควรเห็น:** `echo $?` ได้ `0` และมีไฟล์ `neon-2026-11-03.sql.gz` ถ้ารหัสผิดจะขึ้น `password authentication failed` และ `echo $?` ไม่ใช่ `0` (ลองแล้วกับฐานในเครื่อง)

ซ้อมกู้ลงกล่อง Postgres ที่ใช้ตอนพัฒนา (กล่อง `pg` จากการ์ด [Postgres](/learn/cards/postgres)) ลงฐานใหม่ ไม่ใช่ฐานที่ใช้พัฒนา:

```bash
docker exec pg createdb -U postgres restore_check
gunzip -c ~/library-backups/neon-2026-11-03.sql.gz | docker exec -i pg psql -q -v ON_ERROR_STOP=1 -U postgres -d restore_check
docker exec pg psql -U postgres -d restore_check -c "select (select count(*) from members) as members, (select count(*) from books) as books, (select count(*) from loans) as loans;"
```

ใช้ `-i` (ไม่ใช่ `-it`) เพราะส่งไฟล์เข้าทาง pipe ไม่ได้พิมพ์โต้ตอบ (ใน Git Bash `-t` จะขึ้น `not a TTY`) **ควรเห็น:** ตัวเลขตรงกับที่ดูใน SQL Editor ของ Neon ซ้อมเสร็จลบด้วย `docker exec pg dropdb -U postgres restore_check`

## ทริคที่แนะนำ

1. **backup ก่อนทุกครั้งที่ migrate บนฐานจริง:** migration คือจังหวะที่ข้อมูลหายบ่อยที่สุด รัน `bash deploy/backup.sh` (หรือ `pg_dump` ของ Neon) ก่อน `drizzle-kit migrate` ทุกครั้ง แค่ 1 บรรทัด แต่ช่วยได้ทั้งวัน
2. **ใส่ซ้อมกู้ในปฏิทิน:** ตั้งเตือนเดือนละครั้ง "ซ้อมกู้ backup ล่าสุด" สคริปต์ backup ที่เคยทำงานอาจพังเงียบๆ ได้ (รหัสเปลี่ยน ดิสก์เต็ม cron ไม่ทำงาน) ซ้อมจะเจอก่อนวันที่ต้องใช้จริง
3. **ไฟล์ backup คือข้อมูลลูกค้า:** มีชื่อสมาชิกและ hash รหัสผ่านอยู่ข้างใน อย่าส่งในแชท อย่าใส่ในโฟลเดอร์ที่แชร์ทั้งบริษัท อย่าขึ้น GitHub (`backups/` อยู่ใน `.gitignore`) เก็บนอกเครื่องในที่ที่ต้อง login

## ปรับไปใช้จริง

**ในโจทย์ฝึกงาน:** [Requirement หน้า 1](/api/files/requirement.pdf?sec=overview) (ต้อง login) บอกว่างานนี้คือ "งานที่ต้องส่งมอบให้ลูกค้าใช้ต่อได้จริง" ถ้าทำ Bonus ขึ้นเว็บจริง ([หน้า 13](/api/files/requirement.pdf?sec=bonus)) ข้อมูลที่ลูกค้ากรอก (ข้อความติดต่อ ข้อมูลร้าน) คือของที่ลูกค้าจะโกรธที่สุดถ้าหาย งานของขั้นนี้: ตั้ง backup อัตโนมัติ ซ้อมกู้ 1 ครั้ง แล้วเขียนใน README ส่วน "ดูแลระบบ" ว่า backup อยู่ไหน ทุกกี่ชั่วโมง เก็บนอกเครื่องที่ไหน และซ้อมกู้แล้วใช้เวลาเท่าไหร่ ถ้ายังไม่ได้ขึ้นเว็บจริง ซ้อมกับฐานใน Docker บนเครื่องเรา

**เว็บคู่มือนี้:** ฐานอยู่บน Neon และ Vercel รัน migrate ก่อน build ทุกครั้งที่ขึ้น `main` ([vercel.json](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/vercel.json)) แปลว่าทุก deploy แตะฐานจริง migration จึงเขียนแบบ "เพิ่มอย่างเดียว" เช่น [0021_post_feed.sql](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/server/db/migrations/0021_post_feed.sql) มีแต่ `CREATE TABLE` กับ `ADD COLUMN` ไม่มีการลบ ถ้าพังยังย้อนโค้ดได้โดยข้อมูลไม่หาย

ลองคิด: ถ้าลูกค้าบอกว่า "ข้อมูลหายได้ไม่เกิน 1 ชั่วโมง" ต้องเปลี่ยนอะไรในการ์ดนี้บ้าง และทาง Neon แผนฟรีพอไหม

## ตัวเลือกอื่นที่คล้ายกัน

| ทาง | ตัวอย่าง | เหมาะกับ |
|---|---|---|
| `pg_dump` + cron (การ์ดนี้) | สคริปต์ในข้อ 1–2 | ฐานเล็กถึงกลาง ดูแลเอง เข้าใจทุกขั้น |
| ฐานบน cloud ที่ย้อนเวลาได้เอง | Neon, Supabase, AWS RDS | ไม่อยากดูแลเอง แต่ต้องดูว่าแผนที่ใช้ย้อนได้กี่ชั่วโมงกี่วัน |
| เครื่องมือ backup เฉพาะ Postgres | pgBackRest, WAL-G | ฐานใหญ่ ต้องการย้อนได้ทุกวินาที (ไม่ใช่แค่ทุกคืน) |
| ส่งไฟล์ backup ออกนอกเครื่องอัตโนมัติ | rclone ไป Google Drive / S3, ที่เก็บไฟล์แบบ [S3-compatible](/glossary#s3-compatible) | แทน `scp` ด้วยมือในข้อ 3 |

## ลองเอง

**โจทย์:** เขียน `deploy/restore-drill.sh` ที่ซ้อมกู้ให้อัตโนมัติ: หยิบไฟล์ backup **ล่าสุด** กู้ลงฐานใหม่ชื่อ `restore_drill` พิมพ์จำนวนแถวของ members, books, loans และเวลาที่ใช้เป็นวินาที แล้วลบฐานทิ้ง ถ้าไฟล์เสีย สคริปต์ต้องจบด้วย exit code ที่ไม่ใช่ 0

<Hint level={1}>ไฟล์ล่าสุดหาได้ด้วย `ls -t backups/library-*.sql.gz | head -1` (`-t` เรียงจากใหม่ไปเก่า) จับเวลาด้วย `start=$(date +%s)` ตอนเริ่ม แล้ว `$(( $(date +%s) - start ))` ตอนจบ</Hint>
<Hint level={2}>เริ่มด้วย `dropdb --if-exists restore_drill` กันกรณีรอบก่อนล้มแล้วฐานค้าง ใช้ `set -euo pipefail` กับ `psql -v ON_ERROR_STOP=1` เหมือนข้อ 1 และ 4 ไฟล์เสียจะทำให้สคริปต์หยุดเอง</Hint>
<Hint level={3}>ตรวจผล: รันกับไฟล์ดี ต้องได้บรรทัดเดียวแบบ `ซ้อมกู้ backups/library-....sql.gz: members=... books=... loans=... ใช้ 1 วินาที` และ exit `0` แล้วทำไฟล์เสียด้วย `echo garbage | gzip > backups/library-2099-01-01-0000.sql.gz` (ชื่อวันที่อนาคตให้เป็นไฟล์ล่าสุด) รันอีกครั้ง ต้องเห็น `syntax error at or near "garbage"` และ `echo $?` ไม่ใช่ `0` (ลองแล้วได้ `3`) ลบไฟล์เสียทิ้งหลังทดสอบ</Hint>
