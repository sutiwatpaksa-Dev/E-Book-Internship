> ต่อจากการ์ด [เทสต์อัตโนมัติ](/learn/cards/unit-testing) (เทสต์คือตาข่ายกันตกตอนอัปเดต) คำสั่งในการ์ดนี้ลองกับ Bun 1.4.0 เมื่อ 3 พ.ย. 2569

## ความหมาย

พูดง่ายๆ: โปรเจกต์เราใช้โค้ดที่คนอื่นเขียน ([dependency](/glossary#dependency)) เช่น Hono, Drizzle, Zod, React คนเขียนเหล่านั้นแก้บั๊กและอุดช่องโหว่ออกรุ่นใหม่ตลอด แต่โปรเจกต์เราจะ**ไม่ได้ของใหม่เอง** จนกว่าเราจะสั่งอัปเดต การ์ดนี้คือวิธีตรวจว่ามีอะไรต้องอัปเดต และอัปเดตแบบไม่ทำเว็บพัง

นึกภาพ: รถยนต์ 1 คันประกอบจากชิ้นส่วนหลายโรงงาน

- **dependency** = ชิ้นส่วนจากโรงงานอื่น (เบรก ยาง ถุงลม)
- **ประกาศช่องโหว่ (security advisory)** = ประกาศเรียกคืนรถ "ถุงลมรุ่นนี้อาจไม่พอง ให้เข้าศูนย์เปลี่ยน"
- **อัปเดตรุ่นเล็ก** = เปลี่ยนชิ้นเดิมเป็นล็อตใหม่ที่แก้แล้ว ใส่ตรงที่เดิมได้เลย
- **อัปเดตรุ่นใหญ่** = เปลี่ยนเป็นถุงลมแบบใหม่ ช่องเสียบไม่เหมือนเดิม ต้องแก้รถบางส่วนก่อนใส่ได้

จุดที่ไม่ตรง: รถที่ถูกเรียกคืน เจ้าของได้จดหมายแจ้งถึงบ้าน แต่ library ไม่มีใครมาบอกเรา **ต้องเป็นฝ่ายไปตรวจเอง** (ข้อ 1) หรือตั้งให้มีคนตรวจแทน (ข้อ 5)

เลขรุ่นของ library อ่านแบบ [semver](/glossary#semver) คือ `ใหญ่.กลาง.เล็ก` เช่น Hono `4.13.16`:

| ส่วนที่เปลี่ยน | ตัวอย่าง | แปลว่า | อัปเดตแล้วโค้ดเราต้องแก้ไหม |
|---|---|---|---|
| เล็ก (patch) | 4.13.15 → 4.13.16 | แก้บั๊ก | ไม่ต้อง |
| กลาง (minor) | 4.12.x → 4.13.0 | เพิ่มของใหม่ ของเดิมยังใช้ได้ | ไม่ต้อง |
| ใหญ่ (major) | Zod 3.x → 4.x | **เปลี่ยนแบบใช้ของเดิมไม่ได้** | อาจต้องแก้ ต้องอ่านคู่มือย้ายรุ่น |

ใน `package.json` เขียน `"hono": "^4.6.0"` เครื่องหมาย `^` แปลว่า "รับรุ่นใหม่ได้ ตราบที่เลขใหญ่ยังเป็น 4" (`bun add` ใส่ `^` ให้เอง) ส่วนรุ่นที่ติดตั้งจริงถูกจดไว้ใน `bun.lock` ([lockfile](/glossary#lockfile)) ทุกเครื่องจึงได้รุ่นเดียวกัน จนกว่าจะสั่งอัปเดต

## ที่มา

ระบบห้องสมุดขึ้นเว็บจริงตั้งแต่ต้นปี ไม่มีใครแตะ `package.json` อีกเลย 10 เดือนต่อมา Hono รุ่นที่ใช้มีช่องโหว่ที่ประกาศแล้วหลายสิบข้อ บางข้อเป็นเรื่อง login และ cookie ใครอ่านประกาศก็รู้วิธีโจมตี ส่วนเราไม่รู้ด้วยซ้ำว่ามีประกาศ

พอรู้ตัวแล้วสั่งอัปเดตทุกอย่างรวดเดียว (`--latest` ทุกตัว) Zod ข้ามรุ่นใหญ่ โค้ดตรวจข้อมูลพังทั้งโปรเจกต์ เว็บล่มครึ่งวัน การ์ดนี้คือทางกลาง: **ตรวจเป็นรอบ อัปเดตทีละน้อย ทดสอบทุกครั้ง**

## การใช้งาน

### ตั้งค่าครั้งแรก

ไม่ต้องติดตั้งอะไร `bun audit` และ `bun outdated` มากับ Bun แล้ว ทำทีละโฟลเดอร์ (`server/` แล้วค่อย `client/`) เพราะแต่ละโฟลเดอร์มี `package.json` และ `bun.lock` ของตัวเอง

### 1. ตรวจช่องโหว่ (`bun audit`)

`bun audit` เอารายชื่อ library ใน `bun.lock` ไปเทียบกับฐานข้อมูลช่องโหว่ของ npm แล้วบอกว่าตัวไหนมีประกาศอะไร:

```bash
cd server
bun audit
```

ถ้าเพิ่งติดตั้ง library เมื่อไม่นาน มักได้ `No vulnerabilities found` และ `bun outdated` ว่าง (ดีแล้ว) ตัวอย่างข้างล่างมาจากโปรเจกต์ที่ตั้งใจใช้รุ่นเก่า ถ้าอยากเห็นของจริงในเครื่อง ให้ลองบน branch ทดลองที่ทิ้งได้: `git switch -c try-old-hono` แล้ว `bun add hono@4.6.0` ลองข้อ 1–3 เสร็จแล้ว `git switch -` กลับ และ `bun install` (ห้ามทำบน `main`)

**ควรเห็น** (ลองแล้วกับโปรเจกต์ที่ตั้งใจใช้ Hono 4.6.0 รุ่นเก่า ตัดมาบางส่วน):

```text
hono@4.6.0
  (direct dependency)
  high: Hono JWT Middleware's JWT Algorithm Confusion via Unsafe Default (HS256) Allows Token Forgery and Auth Bypass (<4.11.4) - https://github.com/advisories/GHSA-f67f-6cw9-8mq4
  high: Hono vulnerable to arbitrary file access via serveStatic vulnerability  (<4.12.4) - https://github.com/advisories/GHSA-q5qw-h33p-qvwr
  moderate: Hono: Cookie helper does not sanitize sameSite and priority, allowing Set-Cookie injection (<4.12.21) - https://github.com/advisories/GHSA-3hrh-pfw6-9m5x
  ...

esbuild@0.19.12, 0.18.20
  drizzle-kit > esbuild
  moderate: esbuild enables any website to send any requests to the development server and read the response (<=0.24.2) - ...

45 vulnerabilities (6 high, 37 moderate, 2 low)
```

อ่านทีละส่วน:

- **บรรทัดชื่อ** `hono@4.6.0` คือรุ่นที่เราใช้ **`(direct dependency)`** = เราติดตั้งเอง ส่วน **`drizzle-kit > esbuild`** = เราไม่ได้ติดตั้ง esbuild เอง แต่ drizzle-kit ดึงมาให้
- **ระดับ** `high` / `moderate` / `low` บอกว่าร้ายแรงแค่ไหน
- **วงเล็บท้าย** `(<4.11.4)` = รุ่นที่ต่ำกว่านี้มีปัญหา อัปเดตถึงรุ่นนี้ก็หาย
- **ลิงก์** อ่านว่าช่องโหว่นี้เกี่ยวกับเราไม่ (เช่น ข้อของ `serveStatic` เกี่ยวเพราะการ์ด Build ใช้ ส่วนข้อของ `hono/jsx` ไม่เกี่ยวเพราะเราไม่ได้ใช้ JSX ฝั่ง server แต่ก็อัปเดตทิ้งไว้ดีกว่าต้องมานั่งไล่)

ตัวเลือกที่ใช้บ่อย:

| คำสั่ง | ทำอะไร |
|---|---|
| `bun audit --prod` | ดูเฉพาะของที่ขึ้นเว็บจริง (ไม่นับ devDependencies เช่น drizzle-kit ที่รันแค่ในเครื่องเรา) |
| `bun audit --audit-level=high` | แสดงเฉพาะระดับ high ขึ้นไป |

`bun audit` จบด้วย exit code `1` เมื่อเจอช่องโหว่ (`0` เมื่อไม่เจอ ดูได้ด้วย `echo $?` หลังรัน: `0` = สำเร็จ เลขอื่น = ล้ม) จึงเอาไปใส่ในสคริปต์ตรวจอัตโนมัติได้ (โจทย์ลองเอง)

### 2. ดูว่ามีรุ่นใหม่อะไรบ้าง (`bun outdated`)

```bash
bun outdated
```

**ควรเห็น** (ลองแล้ว):

```text
|----------------------------------------|
| Package  | Current | Update  | Latest  |
|----------|---------|---------|---------|
| hono     | 4.6.0   | 4.13.16 | 4.13.16 |
|----------|---------|---------|---------|
| zod      | 3.23.8  | 3.25.76 | 4.6.7   |
|----------------------------------------|
```

- **Current** = ที่ติดตั้งอยู่ (ตาม `bun.lock`)
- **Update** = รุ่นใหม่สุดที่ `^` ใน `package.json` ยอมให้ = **อัปเดตได้โดยไม่ต้องแก้โค้ด**
- **Latest** = รุ่นใหม่สุดที่มี ถ้าเลขใหญ่ต่างจาก Current (Zod 3 → 4) = **รุ่นใหญ่ อาจต้องแก้โค้ด**

### 3. อัปเดตรุ่นเล็กและกลาง (ทำได้บ่อย)

ทำบน branch `dev` (หรือ branch ใหม่) เสมอ ไม่ใช่บน `main`:

```bash
bun update            # อัปเดตทุกตัวไปถึงคอลัมน์ Update (ไม่ข้ามรุ่นใหญ่)
bun test              # เทสต์จากการ์ดเทสต์อัตโนมัติต้องผ่านทั้งหมด
bun audit --prod      # ดูว่าเหลืออะไร
```

**ควรเห็น:**

```text
^ hono 4.6.0 -> 4.13.16
^ zod 3.23.8 -> 3.25.76 (v4.6.7 available)
```

หลังอัปเดต ช่องโหว่ของ Hono หายหมด (ลองแล้ว) ส่วนที่เหลือคือ `zod@3.25.76` มี `high: Zod can exhaust memory ... (<4.6.6)` = **แก้แล้วเฉพาะในรุ่นใหญ่ 4** อัปเดตในรุ่น 3 แก้ไม่ได้ ต้องไปข้อ 4

จากนั้นไล่เช็กลิสต์ทดสอบด้วยมือแบบสั้นๆ (login, ยืม, คืน, หน้าหลังบ้าน) แล้ว commit **ทั้ง `package.json` และ `bun.lock`** (ถ้าลืม `bun.lock` เครื่องอื่นและเว็บจริงจะยังได้รุ่นเก่า):

```bash
git add package.json bun.lock        # ยังอยู่ในโฟลเดอร์ server/ จากขั้นก่อน
git commit -m "chore: update server dependencies (hono 4.13.16)"
```

`bun audit fix` ทำงานคล้าย `bun update` แต่เลือกอัปเดตเฉพาะตัวที่มีช่องโหว่ ถ้าไม่มีรุ่นที่แก้ได้ในช่วง `^` มันจะบอกว่า `Fixed 0 vulnerabilities` (ลองแล้วกับ esbuild ใน drizzle-kit 0.30.0)

### 4. อัปเดตรุ่นใหญ่ (ทีละตัว อ่านคู่มือก่อน)

รุ่นใหญ่**ทำทีละ library ทีละ commit** ถ้าพังจะรู้ทันทีว่าเพราะตัวไหน:

1. หาคู่มือย้ายรุ่นของ library นั้น ส่วนมากชื่อ "Migration guide" หรือ "Upgrading to v4" ในเว็บทางการ หรืออ่าน [changelog](/glossary#changelog) ในหน้า Releases บน GitHub ของเขา
2. อัปเดตตัวเดียว:

   ```bash
   bun update zod --latest
   ```

   **ควรเห็น:** `^ zod 3.23.8 -> 4.6.7` และ `package.json` เปลี่ยนเป็น `"zod": "^4.6.7"`
3. รัน `bun test` และ `bunx tsc --noEmit` (ตรวจ type ทั้งโปรเจกต์ ของที่ถูกเปลี่ยนชื่อหรือเลิกใช้มักขึ้นเป็นเส้นแดงตรงนี้) แก้ตามคู่มือจนผ่าน
4. ทดสอบด้วยมือ commit แยก แล้วค่อยไปตัวถัดไป

ถ้าแก้ไม่ทันหรือยังไม่เข้าใจคู่มือ ให้ย้อนด้วย `git checkout -- package.json bun.lock && bun install` แล้วจดไว้เป็นงาน ไม่ต้องรีบ ช่องโหว่ที่เหลือให้ดูว่าเกี่ยวกับเราไหม (ข้อ 1) ถ้าเกี่ยว ให้บอกพี่เลี้ยง

### 5. ให้มีคนเตือนแทนเรา (Dependabot)

GitHub มีบริการชื่อ Dependabot เปิด **Pull Request (PR)** อัปเดต library ให้ตามรอบที่ตั้ง (PR = คำขอรวมโค้ดจาก branch หนึ่งเข้า branch หลัก ที่เปิดให้ดูการเปลี่ยนแปลงและรันเทสต์ก่อน แล้วค่อยกด **merge** รวมเข้าไป) เราแค่อ่าน รันเทสต์ แล้วกด merge สร้างไฟล์ `.github/dependabot.yml` ที่โฟลเดอร์บนสุดของ repo:

```yaml
version: 2
updates:
  - package-ecosystem: "bun"
    directories:
      - "/server"
      - "/client"
    schedule:
      interval: "weekly"
    groups:
      minor-and-patch:              # รวมรุ่นเล็กและกลางเป็น PR เดียวต่อสัปดาห์ ไม่ท่วม
        update-types: ["minor", "patch"]
```

- **`package-ecosystem: "bun"`** บอกว่าอ่าน `bun.lock` (GitHub รองรับ Bun ตั้งแต่ 1.1.39 ขึ้นไป)
- **`groups`** ไม่งั้นได้ PR แยกตัวละ 1 อัน สัปดาห์ละหลายสิบอัน จนไม่มีใครอ่าน ส่วนรุ่นใหญ่ยังแยกเป็น PR ละตัว ตรงกับข้อ 4

**ควรเห็น:** push ไฟล์ขึ้น GitHub แล้วไปที่แท็บ **Insights** → **Dependency graph** → **Dependabot** จะเห็นรายการ `server` และ `client` พร้อมเวลาที่ตรวจล่าสุด ไม่กี่นาทีถึงไม่กี่ชั่วโมง PR แรกจะขึ้นในแท็บ Pull requests

ข้อควรรู้: สำหรับ Bun ตอนนี้ Dependabot ทำได้แค่ **เปิด PR อัปเดตตามรอบ** ยังไม่ส่ง PR อุดช่องโหว่ทันทีแบบ npm จึงยังต้องรัน `bun audit` เองเป็นรอบ (ทริคข้อ 1)

**ทาง VPS ต้องอัปเดตอีก 2 ชั้น** (Vercel และ Neon ทำส่วนนี้ให้แล้ว):

```bash
# ถ้า login ด้วยชื่ออื่นที่ไม่ใช่ root ให้ใส่ sudo หน้า apt และ docker (เหมือนการ์ด VPS)
apt update && apt upgrade -y           # ระบบปฏิบัติการของเครื่อง (ช่องโหว่ของ Linux, OpenSSH)
docker compose pull db                 # image ของ Postgres รุ่นย่อยล่าสุดในรุ่น 17
docker compose build --pull app        # สร้างกล่อง app ใหม่บน image ของ Bun ล่าสุด
docker compose up -d
```

ทำหลัง backup เสมอ (การ์ด [Backup และกู้คืน](/learn/cards/backup-restore)) และดู `/api/health` หลังเสร็จ (การ์ด [Log และเฝ้าเว็บ](/learn/cards/log-monitoring))

## ทริคที่แนะนำ

1. **รอบเดียวกันทุกเดือน:** ตั้งเตือนวันที่ 1 ของเดือน "audit + update รุ่นเล็ก" ใช้ไม่เกิน 30 นาที อัปเดตทีละนิดสม่ำเสมอ ง่ายกว่าอัปเดต 10 เดือนรวดเดียวมาก เพราะรุ่นที่ห่างกันยิ่งไกล ยิ่งมีของเปลี่ยนเยอะ
2. **อย่าลบ `bun.lock` เพื่อ "แก้ปัญหา":** ลบแล้ว `bun install` ใหม่ = อัปเดตทุกตัวพร้อมกันแบบไม่ได้ตั้งใจ ถ้าพังหลังจากนั้นจะหาไม่เจอว่าตัวไหน ใช้ `bun update <ชื่อ>` ทีละตัวแทน
3. **ไม่ต้องรีบตามรุ่นที่เพิ่งออกวันนี้:** รุ่นใหญ่ที่ออกไม่ถึงสัปดาห์มักมีบั๊กให้แก้ตามมา (แล้วออกเป็น .0.1 .0.2) ยกเว้นเป็นการอุดช่องโหว่ระดับ high ที่เกี่ยวกับเรา อันนั้นรีบ

## ปรับไปใช้จริง

**ในโจทย์ฝึกงาน:** [Requirement หน้า 10](/api/files/requirement.pdf?sec=nfr) (ต้อง login) ข้อ Security (hash รหัสผ่าน, JWT ใน cookie, middleware) ปลอดภัยได้แค่เท่ากับ library ที่ใช้ ถ้า Hono มีช่องโหว่เรื่อง JWT หรือ cookie อย่างในข้อ 1 โค้ดเราเขียนถูกก็ยังโดน ก่อนส่งงาน (วันที่ 10) และก่อนขึ้นเว็บจริง ให้รัน `bun audit --prod` ทั้ง `server/` และ `client/` แล้วจดผลลง README ส่วน "ดูแลระบบ" ว่าตรวจวันไหน เหลือข้อไหน เพราะอะไร

**เว็บคู่มือนี้:** ใช้ npm (Next.js) ไม่ใช่ Bun ตรวจด้วย `npm audit` และก่อนแก้โค้ดที่ใช้ Next.js จะอ่านคู่มือของรุ่นที่ติดตั้งอยู่จริงใน `node_modules/next/dist/docs/` ก่อนเสมอ เพราะรุ่นใหญ่เปลี่ยนวิธีเขียนหลายอย่าง ตามหลักข้อ 4

ลองคิด: `bun audit` บอกว่า library ตัวหนึ่งมีช่องโหว่ระดับ high แต่ยังไม่มีรุ่นที่แก้ ต้องคิดอะไรบ้างก่อนตัดสินใจว่าจะรอ เลิกใช้ฟังก์ชันนั้น หรือเปลี่ยน library

## ตัวเลือกอื่นที่คล้ายกัน

| ทาง | ตัวอย่าง | เหมาะกับ |
|---|---|---|
| ตรวจช่องโหว่เองจาก Terminal | `bun audit`, `npm audit`, `pnpm audit` | ทุกโปรเจกต์ ใช้ตัวที่ตรงกับ package manager |
| บอทเปิด PR อัปเดตให้ | Dependabot (GitHub), Renovate | repo บน GitHub ที่อยากได้ PR ตามรอบ Renovate ตั้งค่าได้ละเอียดกว่า |
| ตรวจลึกขึ้น (แยกว่าโค้ดเราเรียกส่วนที่มีช่องโหว่จริงไหม) | Snyk, Socket | งานบริษัทที่มี library เยอะ |

## ลองเอง

**โจทย์:** เพิ่ม script `check` ใน `server/package.json` ให้รันคำสั่งเดียวแล้วรู้ว่า "พร้อมขึ้นเว็บไหม" คือเทสต์ผ่านทั้งหมด **และ** ไม่มีช่องโหว่ระดับ high ใน library ที่ขึ้นเว็บจริง ถ้าข้อใดไม่ผ่าน `bun run check` ต้องจบด้วย exit code ที่ไม่ใช่ 0

<Hint level={1}>script ใน `package.json` เขียนคำสั่ง shell ต่อกันด้วย `&&` ได้ (คำสั่งแรกผ่านถึงรันคำสั่งถัดไป) ส่วนตัวเลือกของ `bun audit` ดูตารางในข้อ 1</Hint>
<Hint level={2}>`"check": "bun test && bun audit --prod --audit-level=high"` เรียงให้เทสต์ก่อน เพราะเร็วกว่าและไม่ต้องใช้เน็ต</Hint>
<Hint level={3}>ตรวจผล: รัน `bun run check` แล้ว `echo $?` ตอนทุกอย่างปกติต้องได้ `0` จากนั้นทำให้ไม่ผ่านทีละข้อ: (1) แก้เทสต์ให้พังชั่วคราว ต้องได้ไม่ใช่ `0` และ `bun audit` ไม่ถูกรัน (2) แก้เทสต์กลับ แล้ว `bun add hono@4.6.0` (รุ่นที่มีช่องโหว่ high) ต้องได้ไม่ใช่ `0` พร้อมรายการช่องโหว่ เสร็จแล้ว `bun add hono@latest` กลับ และรันเทสต์อีกรอบ</Hint>
