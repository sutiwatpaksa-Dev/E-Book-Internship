## ความหมาย

**เทสต์อัตโนมัติ** คือโค้ดที่เรียกโค้ดของเรา แล้วเทียบผลกับค่าที่ควรได้ ถ้าไม่ตรง เครื่องฟ้องทันทีว่าข้อไหนผิด **[Unit test](/glossary#unit-test)** คือเทสต์แบบเล็กที่สุด ตรวจชิ้นเดียว (เช่น schema 1 ตัว หรือฟังก์ชัน 1 ตัว) ไม่ต่อฐานข้อมูล ไม่เปิด server จึงรันเสร็จในเสี้ยววินาที

**นึกภาพ:** เครื่องชั่งบนสายพานโรงงาน ตั้งไว้ครั้งเดียวว่ากล่องต้องหนัก 1 กิโล ทุกกล่องที่ผ่านถูกชั่งเองโดยไม่ต้องมีคนยก กล่องไหนเบาไปเครื่องก็ดีดออกและบอกว่าเบาไปเท่าไหร่

จับคู่: เครื่องชั่ง = ไฟล์เทสต์ · "ต้องหนัก 1 กิโล" = `expect(...).toBe(...)` · กล่องบนสายพาน = ผลจากโค้ดของเรา (เช่น `newBookSchema.safeParse(...)`) · ดีดออกพร้อมบอกว่าเบาไปเท่าไหร่ = เทสต์ไม่ผ่าน บอกค่าที่คาดกับค่าที่ได้

```text
bun test
   │ newBookSchema.safeParse(
   │   { title: "" }
   │ )
   ▼
ได้ r.success = false
   │ expect(r.success).toBe(false)
   ▼
ตรงกับที่คาด = ผ่าน
ไม่ตรง = ฟ้องว่าข้อไหน
คาดอะไร แต่ได้อะไร
```

จุดที่ไม่ตรง: เครื่องชั่งรู้แค่น้ำหนัก ไม่รู้ว่าของข้างในถูกชิ้นไหม unit test ก็ตรวจได้แค่สิ่งที่เราเขียน `expect` ไว้ และตรวจทีละชิ้น ไม่รู้ว่าชิ้นต่างๆ ต่อกันถูกไหม จึงยังต้องยิงทดสอบ API และทดสอบด้วยมือคู่กัน

## ที่มา

การ์ด [ทดสอบด้วยมือแบบมีแผน](/learn/cards/manual-testing) ได้ `TESTING.md` ที่ใช้เวลาเป็นชั่วโมง ทำทุกครั้งที่แก้โค้ดไม่ไหว สุดท้ายก็ข้าม แล้ววันหนึ่งการแก้เล็กๆ ไปทำให้กฎอื่นพังโดยไม่มีใครรู้ เทสต์อัตโนมัติไม่เหนื่อย ไม่ลืม 5 ข้อในการ์ดนี้รันเสร็จใน 20 มิลลิวินาที รันได้ทุกครั้งที่กดบันทึก

แต่เครื่องตรวจได้แค่สิ่งที่ตัดสินด้วยค่า เช่น "ชื่อว่างต้องไม่ผ่าน" หรือ "ต้องได้ `409`" ส่วน "ปุ่มเด่นพอไหม" หรือ "อ่านเข้าใจไหม" ยังต้องใช้ตาคน สองแบบจึงใช้คู่กัน: **กฎที่ต้องตรวจซ้ำทุกรอบให้เครื่องทำ ที่เหลือใช้มือ**

## การใช้งาน

### ตั้งค่าครั้งแรก

ไม่ต้องติดตั้งอะไรเพิ่ม Bun มีตัวรันเทสต์มาในตัว (`bun:test`) ใช้ได้กับโปรเจกต์ `server/` (สร้างในการ์ด [Drizzle](/learn/cards/drizzle-orm) แล้วต่อ Hono ในการ์ด [Hono](/learn/cards/hono)) ทันที ส่วน type ของ `bun:test` มากับ `@types/bun` ที่ `bun init -y` ใส่ไว้ให้ตั้งแต่การ์ด [Drizzle](/learn/cards/drizzle-orm) VS Code จึงไม่ขึ้นเส้นแดง

### 1. เขียนเทสต์ของ schema

ต่อจาก `newBookSchema` ในการ์ด [ตรวจข้อมูลด้วย Zod](/learn/cards/validation) สร้างไฟล์ใหม่ `server/src/validators/book.validator.test.ts` ไว้ข้างไฟล์ที่จะทดสอบ ชื่อต้องลงท้าย `.test.ts` Bun จะหาไฟล์แบบนี้เองทั้งโปรเจกต์

```ts
import { describe, expect, test } from "bun:test";
import { z } from "zod";
import { newBookSchema } from "./book.validator";

describe("newBookSchema", () => {                    // กลุ่มของเทสต์ ชื่อ = สิ่งที่ทดสอบ
  test("ชื่อปกติผ่าน และตัดช่องว่างหัวท้ายให้", () => {  // 1 test = 1 กฎ
    const r = newBookSchema.safeParse({ title: "  ฮอบบิท 2  " });
    expect(r.success).toBe(true);                    // expect(ค่าที่ได้).toBe(ค่าที่ควรได้)
    expect(r.data?.title).toBe("ฮอบบิท 2");
  });

  test("ชื่อว่างไม่ผ่าน และบอกว่าผิดช่อง title", () => {
    const r = newBookSchema.safeParse({ title: "" });
    expect(r.success).toBe(false);
    expect(z.flattenError(r.error!).fieldErrors.title).toEqual(["ต้องมีชื่อหนังสือ"]);
  });

  test("ช่องว่างล้วนนับเป็นชื่อว่าง", () => {
    expect(newBookSchema.safeParse({ title: "   " }).success).toBe(false);
  });

  test("ชื่อยาว 200 ตัวผ่าน 201 ตัวไม่ผ่าน", () => {
    expect(newBookSchema.safeParse({ title: "ก".repeat(200) }).success).toBe(true);
    expect(newBookSchema.safeParse({ title: "ก".repeat(201) }).success).toBe(false);
  });

  test("ไม่ส่ง title หรือส่งเป็นตัวเลข ไม่ผ่าน", () => {
    expect(newBookSchema.safeParse({}).success).toBe(false);
    expect(newBookSchema.safeParse({ title: 123 }).success).toBe(false);
  });
});
```

- `toBe` เทียบค่าเดี่ยว (ตัวเลข ข้อความ true/false) ส่วน `toEqual` เทียบ array หรือ object ทีละช่อง เพราะ array 2 ตัวที่หน้าตาเหมือนกันไม่ใช่ตัวเดียวกัน `toBe` จะบอกว่าไม่เท่ากัน
- `r.data?.title` ใส่ `?.` เพราะ TypeScript ไม่รู้ว่าบรรทัดก่อนตรวจแล้วว่าผ่าน ถ้าไม่ผ่านจริง `r.data` จะไม่มี และเทสต์ก็ fail ตรงบรรทัดก่อนหน้าอยู่แล้ว ส่วน `r.error!` ก็เหตุผลเดียวกัน

### 2. รัน

```bash
cd server
bun test
```

Mac และ Windows (Git Bash) พิมพ์เหมือนกัน

**ควรเห็น:**

```text
bun test v1.4.0

 5 pass
 0 fail
 9 expect() calls
Ran 5 tests across 1 file. [21.00ms]
```

### 3. พิสูจน์ว่าเทสต์จับได้จริง

เทสต์ที่ไม่เคย fail เลย อาจไม่ได้ตรวจอะไรเลยก็ได้ ลองทำให้โค้ดผิดโดยตั้งใจ: ใน `book.validator.ts` แก้เลข 200 ใน `.max(...)` ของ `title` เป็น 300 (ถ้าใส่ข้อความไทยตามการ์ดทดสอบด้วยมือแล้ว ก็แก้แค่ตัวเลข) แล้วรัน `bun test` อีกครั้ง

**ควรเห็น:** (ตัดบางบรรทัดออก)

```text
src/validators/book.validator.test.ts:
24 |     expect(newBookSchema.safeParse({ title: "ก".repeat(201) }).success).toBe(false);
                                                                             ^
error: expect(received).toBe(expected)

Expected: false
Received: true

(fail) newBookSchema > ชื่อยาว 200 ตัวผ่าน 201 ตัวไม่ผ่าน

 4 pass
 1 fail
```

อ่านจากบนลงล่าง: ไฟล์และบรรทัดที่พัง, ค่าที่ควรได้ (`Expected`) กับค่าที่ได้จริง (`Received`) และชื่อเทสต์ที่บอกว่ากฎไหนเสีย แก้เลขกลับเป็น 200 แล้วรันอีกครั้ง ต้องกลับมา `5 pass`

### 4. คำสั่งที่ใช้บ่อย

| คำสั่ง | ทำอะไร |
|---|---|
| `bun test` | รันทุกไฟล์ `.test.ts` ในโปรเจกต์ |
| `bun test book` | รันเฉพาะไฟล์ที่ชื่อมีคำว่า `book` |
| `bun test --watch` | รันใหม่เองทุกครั้งที่กดบันทึกไฟล์ เปิดทิ้งไว้ข้างๆ ตอนเขียนโค้ด (หยุดด้วย `Ctrl+C`) |

## ทริคที่แนะนำ

1. **ตั้งชื่อเทสต์เป็นประโยคบอกกฎ:** "ชื่อยาว 200 ตัวผ่าน 201 ตัวไม่ผ่าน" ดีกว่า "test 4" เพราะวันที่มันพัง ชื่อจะขึ้นในบรรทัด `(fail)` อ่านแล้วรู้ทันทีว่ากฎไหนเสีย โดยไม่ต้องเปิดไฟล์
2. **ทดสอบที่ขอบ:** บั๊กชอบอยู่ที่ค่าพอดีเส้น (200 กับ 201, 3 เล่มกับ 4 เล่ม) และค่าแปลกๆ (ช่องว่างล้วน, ส่งตัวเลขมาแทนข้อความ) ค่ากลางๆ อย่าง "ฮอบบิท" แทบไม่เคยพัง
3. **โค้ดที่เทสต์ง่ายคือโค้ดที่ไม่แตะของภายนอก:** schema รับค่าเข้า คืนผลออก ไม่ต่อฐานข้อมูล จึงเทสต์ได้ในบรรทัดเดียว ถ้ากฎไหนเทสต์ยากเพราะผูกกับฐานข้อมูลหรือเวลาปัจจุบัน ลองแยกส่วนคำนวณออกมาเป็นฟังก์ชันเล็กๆ (โจทย์ลองเองข้างล่าง) นี่คือเหตุผลเดียวกับที่การ์ด [แบ่งชั้น](/learn/cards/layers) แยกกฎไว้ใน service

## ปรับไปใช้จริง

**ในงาน STARTER:** Bonus ข้อสุดท้าย ([Requirement หน้า 13](/api/files/requirement.pdf#page=13), ต้อง login) คือ "เขียน test อย่างน้อยให้ครอบคลุม validator และ auth middleware" ส่วน validator ทำได้ด้วยการ์ดนี้ เริ่มจาก schema ที่มีกฎเยอะที่สุด คือฟอร์มติดต่อ (เบอร์โทร 9–10 หลัก, ข้อความไม่เกิน 1,000 ตัวอักษร ตามหน้า 10) ส่วน auth middleware ใช้ `app.request()` จากการ์ด [Hono](/learn/cards/hono) ยิงเข้าแอปตรงๆ ไม่ต้องเปิด server ทดสอบแค่ทางที่ไม่ต้องต่อฐานข้อมูล คือไม่มีบัตรกับบัตรปลอม (ตัวอย่างของห้องสมุดบิต ไฟล์ `server/src/auth.test.ts`)

```ts
import { describe, expect, test } from "bun:test";
import app from "./index";

describe("ด่าน login ของหลังบ้าน", () => {
  test("ไม่มีบัตร ได้ 401", async () => {
    const res = await app.request("/api/admin/books");
    expect(res.status).toBe(401);
    expect((await res.json()).error.code).toBe("UNAUTHORIZED");
  });
  test("บัตรปลอม ได้ 401", async () => {
    const res = await app.request("/api/admin/books", { headers: { Cookie: "session=not.a.jwt" } });
    expect(res.status).toBe(401);
  });
});
```

ค่าใน header ต้องเป็นตัวอังกฤษ ตัวเลข และเครื่องหมายเท่านั้น (ใส่ภาษาไทยแล้ว `Request` จะโยน `TypeError: Header 'Cookie' has invalid value` ก่อนถึง server ลองแล้ว) · Bun อ่าน `server/.env` ให้เองตอน `bun test` ด่านจึงมี `JWT_SECRET` ใช้ตรวจบัตร (ชื่อ `session` มาจาก `SESSION_COOKIE` ในการ์ด [JWT ใน cookie](/learn/cards/jwt-cookie)) แต่จำไว้ว่า bonus นับเมื่องานหลักครบแล้วเท่านั้น

**เว็บคู่มือนี้:** กฎว่าหน้าไหนต้อง login และหน้าไหนเฉพาะพี่เลี้ยง มีเทสต์อยู่ที่ [src/lib/page-access.test.ts บน GitHub](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/src/lib/page-access.test.ts) อ่านชื่อเทสต์อย่างเดียวก็รู้กฎครบ เช่น "หน้า STARTER ต้อง login" และ "หน้า Dev เฉพาะพี่เลี้ยง" ทุกเวอร์ชันของเว็บนี้ต้องผ่าน `bun test` ก่อนออก

ลองคิด: ถ้าเทสต์ผ่านครบทุกข้อ แปลว่าโค้ดไม่มีบั๊กใช่ไหม

## ตัวเลือกอื่นที่คล้ายกัน

| ตัวรันเทสต์ | เหมาะกับ | หมายเหตุ |
|---|---|---|
| **`bun test` (การ์ดนี้)** | โปรเจกต์ที่ใช้ Bun อยู่แล้ว | มาในตัว ไม่ต้องติดตั้ง เขียนแบบเดียวกับ Jest |
| [Vitest](https://vitest.dev) | ฝั่ง `client/` ที่ใช้ Vite | ใช้ค่าตั้งของ Vite ร่วมกัน เหมาะกับเทสต์ component React |
| [Jest](https://jestjs.io) | โปรเจกต์ Node รุ่นเก่า | ใช้กันมานานที่สุด ตัวอย่างบนเน็ตเยอะ ตั้งค่า TypeScript เพิ่ม |
| `node:test` | Node ล้วน ไม่อยากเพิ่มแพ็กเกจ | มากับ Node ตั้งแต่รุ่น 18 |

ทั้ง 4 ตัวใช้คำ `describe` / `test` / `expect` คล้ายกันมาก ย้ายไปใช้ตัวอื่นได้โดยแก้ไม่กี่บรรทัด

## ลองเอง

**โจทย์:** ใน `loan.repository.ts` (การ์ดแบ่งชั้น) วันครบกำหนดคืนคำนวณอยู่ในบรรทัด `insert` ซึ่งเทสต์ไม่ได้ถ้าไม่ต่อฐานข้อมูล แยกการคำนวณนี้ออกเป็นฟังก์ชัน `dueDate(from: Date): Date` ในไฟล์ใหม่ `server/src/lib/due-date.ts` ให้ repository เรียกใช้ แล้วเขียนเทสต์ของมัน พร้อมเทสต์ `newLoanSchema` อีกอย่างน้อย 3 ข้อ

<Hint level={1}>ฟังก์ชันรับวันยืมเข้าไป คืนวันที่บวก 14 วัน ฝั่ง repository เปลี่ยนจาก `new Date(Date.now() + ...)` เป็น `dueDate(new Date())` ส่วนเทสต์ส่งวันที่ตายตัวเข้าไป เช่น `new Date("2026-01-01T10:00:00Z")` แล้วเทียบกับวันที่ที่ควรได้</Hint>
<Hint level={2}>`toBe` ใช้เทียบ `Date` 2 ตัวไม่ได้ (เป็นคนละ object) ลองเทียบด้วย `.getTime()` หรือใช้ `toEqual` ส่วน `newLoanSchema` คิดขอบของมัน: `memberId` เป็น 0, ติดลบ, ทศนิยม, ส่งเป็นข้อความ `"1"` ควรผ่านหรือไม่ผ่าน</Hint>
<Hint level={3}>ตรวจผล: แก้ 14 เป็น 15 ใน `due-date.ts` แล้ว `bun test` ต้องมี 1 fail ที่ชื่อเทสต์บอกว่ากฎครบกำหนดคืนเสีย แก้กลับแล้วผ่านหมด และยิง `POST /api/loans` ด้วย `memberId: 2` (สมาชิก 1 ยืมครบ 3 เล่มแล้ว จะได้ `409`) ต้องได้ `dueAt` ห่างจากวันนี้ 14 วันเท่าเดิม</Hint>
