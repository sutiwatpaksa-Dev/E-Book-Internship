> ต่อจากการ์ด [จัดการ error](/learn/cards/error-handling) ข้อ 1–2 (logger กับ `/api/health`) ทำได้ทันทีในเครื่องเรา ส่วนข้อ 3–4 (อ่าน log บนเครื่องจริง และ monitor) ทำหลังขึ้นเว็บจริงแล้วอย่างน้อยหนึ่งทาง: [Build สำหรับขึ้นระบบ](/learn/cards/production-build) + [VPS](/learn/cards/vps-deployment) หรือ [Vercel + Neon](/learn/cards/vercel-deployment) ข้อมูลแผนฟรีตรวจจากเว็บทางการเมื่อ 3 พ.ย. 2569

## ความหมาย

พูดง่ายๆ: **[log](/glossary#log)** คือสมุดจดว่าระบบทำอะไรไปบ้าง ใครขออะไร ได้ผลอะไร พังตรงไหน ส่วน **การเฝ้าเว็บ ([monitor](/glossary#monitor))** คือมีคนหรือโปรแกรมคอยเปิดเว็บเราทุกไม่กี่นาที ถ้าเปิดไม่ได้ก็ส่งข้อความเตือนทันที

นึกภาพ: ร้านสะดวกซื้อ 24 ชั่วโมง

- **log** = กล้องวงจรปิดกับสมุดบันทึกกะ ไว้ย้อนดูว่า "เมื่อคืนตี 2 เกิดอะไรขึ้น" ดูได้แค่หลังเกิดเรื่อง
- **[health check](/glossary#health-check)** = ไฟสถานะหน้าตู้แช่ เขียวคือเย็นปกติ แดงคือมีปัญหา ใครเดินผ่านก็รู้ในไม่กี่วินาที
- **monitor** = บริษัท รปภ. ที่ขับรถผ่านทุก 5 นาที เห็นไฟแดงก็โทรหาเจ้าของ ไม่ต้องรอลูกค้ามาบอก

จุดที่ไม่ตรง: กล้องวงจรปิดจับได้ทุกอย่างที่เกิดหน้ากล้อง แต่ log จดแค่**สิ่งที่โค้ดเราสั่งให้จด** ถ้าไม่เคยเขียนให้จด ตอนพังก็ไม่มีอะไรให้ดู

```text
ลูกค้า ──► เว็บ ──► server (Hono) ──► ฐานข้อมูล
                        │
                        ├── จดทุกคำขอลง log (logger)
                        └── /api/health ตอบ "ยังดีอยู่" ไหม
                                  ▲
          monitor (UptimeRobot) ──┘ เปิดดูทุก 5 นาที ไม่ตอบ 200 = ส่งอีเมลเตือนเรา
```

## ที่มา

วันจันทร์บรรณารักษ์โทรมาว่า "ตั้งแต่เมื่อวานกดยืมหนังสือไม่ได้เลย" เราเปิดเว็บดูตอนนั้นก็ใช้ได้ปกติ ไม่รู้ว่าเมื่อวานเกิดอะไร เพราะ:

1. **ไม่มีใครรู้ว่าพัง** จนลูกค้าเจอเองแล้วโทรมา เสียไปทั้งวัน
2. **ไม่มีหลักฐาน** server ไม่ได้จดอะไรไว้ หรือจดไว้แต่ log บน Vercel แผนฟรีเก็บแค่ 1 ชั่วโมง หายไปแล้ว
3. **เดาไม่ถูกว่าพังที่ชั้นไหน** เว็บ API หรือฐานข้อมูล

การ์ดนี้แก้ทั้ง 3 ข้อ: จดทุกคำขอ, มีปุ่ม "ยังดีอยู่ไหม" ที่ตรวจถึงฐานข้อมูล, และให้โปรแกรมเฝ้ามันแทนเรา

## การใช้งาน

### ตั้งค่าครั้งแรก

ไม่ต้องติดตั้งอะไรเพิ่ม `logger` มากับ Hono อยู่แล้ว ส่วนบริการเฝ้าเว็บสมัครฟรีที่ [uptimerobot.com](https://uptimerobot.com) (ทำในข้อ 4)

### 1. จดทุกคำขอ (`server/src/index.ts`)

เพิ่ม `logger()` เป็นด่านแรกของ `app` ทุกคำขอจะถูกจด 2 บรรทัด: ตอนเข้ามา และตอนตอบกลับพร้อม status กับเวลาที่ใช้ เพิ่มแค่ 2 บรรทัด ส่วนที่เหลือของไฟล์เหมือนเดิม:

```ts
import { logger } from "hono/logger";          // เพิ่มบนสุด

const app = new Hono().basePath("/api");
app.use(logger());                              // เพิ่มบรรทัดนี้ต่อจากบรรทัดสร้าง app ก่อน route ทุกตัว
```

ต้องอยู่**ก่อน** route ทุกตัว เพราะ middleware ทำงานตามลำดับที่เขียน ถ้าวางท้ายไฟล์ คำขอจะถูกตอบไปก่อนถึงด่านนี้ ไม่ถูกจด

**ควรเห็น:** รัน `bun run dev` แล้วเปิด `/api/books` กับ `/api/nope?q=1` ใน Terminal ของ server ขึ้น:

```text
<-- GET /api/books
--> GET /api/books 200 4ms
<-- GET /api/nope?q=1
--> GET /api/nope?q=1 404 1ms
```

`<--` คือคำขอเข้ามา `-->` คือตอบออกไป ตัวเลขท้ายคือเวลาที่ server ใช้ ถ้าคำขอไหนมีแต่ `<--` ไม่มี `-->` ตามมา แปลว่าค้างอยู่ข้างใน

ใน Terminal ตัวเลข status มีสี (เขียว 2xx, เหลือง 4xx, แดง 5xx) แต่ใน log ของ Docker และ Vercel สีจะกลายเป็นตัวอักษรแปลกๆ อย่าง `[32m200[0m` ให้ปิดสีด้วยค่า `NO_COLOR=1` ตอนขึ้นระบบ (ข้อ 3)

**ห้ามจดของลับ:** logger จด method, path **และ query string** (เห็น `?q=1` ข้างบน) จึงห้ามส่งค่าลับทาง URL เช่น `?token=...` ส่วน `console.log` ที่เขียนเอง อย่าพิมพ์ body ของ login, cookie, token หรือ `DATABASE_URL` เพราะใครเข้าถึง log ได้ก็เห็นรหัสหมด

### 2. ปุ่ม "ยังดีอยู่ไหม" (`GET /api/health`)

ถ้าทำโจทย์ลองเองของการ์ด Build ไว้แล้ว จะมี `/api/health` ที่ตอบ `ok: true` เสมอ (**ลบ route นั้นออกก่อน** คือ `app.get("/health", ...)` ที่ตอบ `ok: true` ซึ่งวางเหนือ `const site = new Hono()` ถ้ามี 2 ตัว Hono ใช้ตัวที่ลงทะเบียนก่อน แล้วจะได้ `200` ตลอดแม้ฐานปิด) แบบนั้นบอกได้แค่ว่า server ยังเปิดอยู่ แต่บอกไม่ได้ว่า**ต่อฐานข้อมูลได้ไหม** ซึ่งเป็นสาเหตุที่เว็บพังบ่อยที่สุด (รหัสฐานเปลี่ยน, Neon หยุด, ดิสก์เต็ม) ให้แทนด้วยแบบที่ถามฐานข้อมูลจริง 1 คำถามเล็กที่สุด:

```ts
// server/src/index.ts เพิ่ม import บนสุด
import { sql } from "drizzle-orm";
import { db } from "./db";
import { fail, ok } from "./lib/response";   // บรรทัดเดิมมีแค่ { fail } ให้เติม ok (ไม่งั้น ok ไม่มี → catch จับแล้วตอบ DB_DOWN ทั้งที่ฐานปกติ)

// วางก่อน app.notFound(...)
app.get("/health", async (c) => {
  try {
    await db.execute(sql`select 1`);                       // คำถามที่เล็กที่สุด ตอบได้ = ฐานข้อมูลยังคุยได้
    return ok(c, { ok: true, db: "ok" });
  } catch (err) {
    console.error("health: ต่อฐานข้อมูลไม่ได้", err);       // รายละเอียดอยู่ใน log ของเรา
    return fail(c, 500, "DB_DOWN", "ต่อฐานข้อมูลไม่ได้");   // คนนอกเห็นแค่นี้ (Requirement: 500 ห้ามส่ง stack trace)
  }
});
```

- **``sql`select 1` ``** (backtick ติดชื่อ `sql`) คือวิธีของ Drizzle ที่ส่ง SQL ดิบ 1 คำสั่งไปที่ฐาน เหมือนที่พิมพ์ใน pgAdmin
- **`select 1`** ไม่อ่านตารางไหนเลย เร็วมาก เรียกทุก 5 นาทีไม่หนักฐาน
- **ตอบ `500` ตอนพัง:** monitor ดูแค่เลข status ถ้าตอบ `200` พร้อมข้อความ "พัง" monitor จะคิดว่าทุกอย่างปกติ
- **route นี้ไม่ต้อง login** และไม่บอกอะไรลับ (ไม่บอกชื่อฐาน ไม่บอกเวอร์ชัน) เพราะ monitor จากข้างนอกต้องเรียกได้

**ควรเห็น** (ลองแล้ว: รัน `bun run dev` แล้วปิดกล่อง Postgres ของการ์ด [Postgres](/learn/cards/postgres) ด้วย `docker stop pg` แล้วเปิดกลับด้วย `docker start pg` server ไม่ล่มระหว่างนั้น):

| สถานะฐาน | `curl -i http://localhost:3000/api/health` | Terminal ของ server |
|---|---|---|
| เปิดอยู่ | `200` `{"success":true,"data":{"ok":true,"db":"ok"}}` | `--> GET /api/health 200 17ms` |
| ปิดไปแล้ว | `500` `{"success":false,"error":{"code":"DB_DOWN","message":"ต่อฐานข้อมูลไม่ได้"}}` | `health: ต่อฐานข้อมูลไม่ได้ ...` ตามด้วย `ECONNREFUSED` แล้ว `--> GET /api/health 500 2ms` |
| เปิดกลับ | `200` อีกครั้ง ไม่ต้องรีสตาร์ต server | `--> GET /api/health 200 12ms` |

ตอนฐานปิด `/api/books` ก็ได้ `500` `INTERNAL_ERROR` จาก `errorHandler` (การ์ด [จัดการ error](/learn/cards/error-handling)) เหมือนกัน แต่ health บอกชัดว่าเป็นเพราะ**ฐานข้อมูล** ไม่ต้องเดา

### 3. อ่าน log บนเครื่องจริง

**ทาง VPS (Docker Compose):** log อยู่ในเครื่องเรา ดูได้ย้อนหลังตราบที่ไฟล์ยังไม่ถูกลบ

```bash
docker compose logs -t --since 1h app         # ย้อนหลัง 1 ชั่วโมง
docker compose logs -t --tail 50 -f app       # 50 บรรทัดล่าสุด แล้วดูสดต่อ (Ctrl+C ออก กล่องไม่หยุด)
docker compose logs -t app | grep " 500 "     # หาเฉพาะบรรทัดที่มี " 500 " (คำขอที่ server พัง)
```

- **`-t`** ให้ Docker ใส่เวลาหน้าทุกบรรทัด จำเป็นเพราะ logger ของ Hono ไม่พิมพ์เวลาเอง ถ้าไม่ใส่จะไม่รู้ว่าบรรทัดไหนเกิดตอนไหน
- **`|` (pipe)** ส่งผลของคำสั่งซ้ายไปให้คำสั่งขวา `grep " 500 "` กรองให้เหลือแต่บรรทัดที่มีข้อความนั้น ถ้าอยากหาบรรทัด error ที่ `console.error` พิมพ์ด้วย ใช้ `grep -i error`

ค่าเริ่มต้นของ Docker **ไม่จำกัดขนาด log** เว็บเปิดไปหลายเดือน ไฟล์ log โตจนดิสก์เต็ม แล้วฐานข้อมูลเขียนไม่ได้ (เว็บล่มเพราะ log!) ให้เพิ่ม `logging` ให้ทุก service ใน `compose.yaml` และปิดสีของ logger:

```yaml
services:
  app:
    # ...ของเดิม...
    environment:
      # ...ของเดิม...
      NO_COLOR: "1"
    logging:
      options:
        max-size: "10m"   # ไฟล์ละไม่เกิน 10 MB
        max-file: "3"     # เก็บ 3 ไฟล์ล่าสุด ไฟล์เก่าสุดถูกลบเอง = log ไม่เกิน 30 MB ต่อ service
```

ใส่ก้อน `logging` แบบเดียวกันให้ `db` และ `caddy` ด้วย แล้ว `docker compose up -d` (Compose สร้างกล่องใหม่ให้เองเมื่อค่าเปลี่ยน)

**ควรเห็น:** `docker inspect $(docker compose ps -q app) --format '{{.HostConfig.LogConfig}}'` ขึ้น `{json-file map[max-file:3 max-size:10m]}` (ลองแล้วด้วยขนาดเล็ก: กล่องพิมพ์ 30,000 บรรทัด แต่เก็บไว้แค่ราว 3,500 บรรทัดล่าสุดตามเพดาน)

**ทาง Vercel:**

- เมนู **Logs** ของโปรเจกต์ กรอง **Level** = Error หรือพิมพ์ `/api/health` ในช่องค้นหา `console.error` ขึ้นเป็นระดับ error คำขอที่ได้ 5xx มีป้ายแดงให้เอง
- **แผน Hobby เก็บ log แค่ 1 ชั่วโมง** (Pro 1 วัน) ถ้ามีคนแจ้งปัญหาเมื่อวาน log หายไปแล้ว นี่คือเหตุผลที่ต้องมี monitor ในข้อถัดไป ให้รู้ภายในไม่กี่นาที ไม่ใช่รอคนมาบอก
- ใส่ `NO_COLOR` = `1` ใน Environment Variables แล้ว Redeploy

### 4. ให้โปรแกรมเฝ้าแทนเรา (UptimeRobot)

1. สมัคร [uptimerobot.com](https://uptimerobot.com) แผน Free (50 จุดเฝ้า เปิดดูทุก 5 นาที ใช้กับงานเชิงพาณิชย์ได้)
2. **New monitor** → แบบ **HTTP(s)** → URL = `https://<เว็บเรา>/api/health` (ต้องเป็นเว็บจริงบนเน็ต `localhost` ใช้ไม่ได้ เพราะ UptimeRobot อยู่ข้างนอก)
3. ช่องแจ้งเตือนเลือกอีเมลของเรา และ**อีเมลของพี่เลี้ยง** (คนเดียวเฝ้าไม่พอ ถ้าเราไม่ว่างจะไม่มีใครรู้)

**ควรเห็น:** สถานะ **Up** สีเขียว จากนั้นทดสอบว่าเตือนจริง: VPS ใช้ `docker compose stop db` / Vercel เปลี่ยน `DATABASE_URL` ให้ผิดชั่วคราวแล้ว Redeploy ภายในราว 5 นาทีต้องได้อีเมลว่า **Down** แก้กลับแล้วต้องได้อีเมลว่า **Up** ถ้ายังไม่เคยเห็นอีเมล Down ด้วยตาตัวเอง ถือว่ายังไม่ได้ตั้งเตือน

บน Neon แผนฟรี ฐานหยุดเองเมื่อไม่มีคนใช้ 5 นาที การเปิด `/api/health` ทุก 5 นาทีทำให้ฐานตื่นบ่อยขึ้นและกินเวลาเครื่องของแผนฟรี ถ้าเว็บไม่ได้มีคนใช้จริง (แค่ส่งงาน) ตั้งรอบเฝ้าให้ห่างขึ้นได้ หรือหยุด monitor ไว้ก่อน

## ทริคที่แนะนำ

1. **ไล่จากนอกเข้าใน:** เว็บเข้าไม่ได้ ให้ถามทีละชั้น เปิดหน้าแรกได้ไหม (DNS, https) → `/api/health` ได้อะไร (server, ฐาน) → log ว่ายังไง แต่ละชั้นตอบได้ใน 1 นาที ดีกว่าเปิดโค้ดเดาไปเรื่อย
2. **จด "เวลา" ทุกครั้งที่มีคนแจ้งปัญหา:** log ที่ดูผ่าน `docker compose logs -t` และของ Vercel มีเวลาทุกบรรทัด ถ้ารู้ว่าพังตอน 14:05 จะหาเจอในไม่กี่วินาที (log ของ Vercel และ Docker แสดงเวลาเป็น [UTC](/glossary#utc) = เวลาไทยลบ 7 ชั่วโมง 14:05 ของไทยคือ 07:05 ใน log)
3. **error ที่รู้จักแล้วไม่ต้องตะโกน:** `409` หนังสือถูกยืมอยู่ ไม่ใช่เรื่องที่ต้องตื่นมาแก้ ส่วน `500` คือเรื่องที่ต้องดูทุกครั้ง ถ้าใน log มีแต่ `console.error` ของเรื่องปกติ ตอนมีเรื่องจริงจะมองไม่เห็น

## ปรับไปใช้จริง

**ในโจทย์ฝึกงาน (ตัวอย่างจาก STARTER):** [Requirement หน้า 10](/api/files/requirement.pdf?sec=nfr) (ต้อง login) ข้อ Security "Error 500 ห้ามส่ง stack trace กลับไปให้ client" คือครึ่งหนึ่งของการ์ดนี้: รายละเอียดอยู่ใน log ฝั่ง server คนนอกเห็นแค่ข้อความสั้น ถ้าทำ Bonus ขึ้นเว็บจริง ([หน้า 13](/api/files/requirement.pdf?sec=bonus)) แล้ว ให้ทำข้อ 2–4 ด้วย และใส่ใน README ส่วน "ดูแลระบบ" (หน้าตาดูที่การ์ด [Feedback](/learn/cards/feedback-loop)) ว่า log ดูที่ไหน และ monitor เตือนไปที่อีเมลใคร

**เว็บคู่มือนี้:** มี `/api/health` ใน [server/app.ts](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/server/app.ts) ใช้ตรวจหลัง deploy ทุกครั้ง ต่างจากในการ์ด 3 จุด: ถามตาราง `users` จริง (`select 1 from users limit 1`) จึงจับได้ด้วยว่า "ต่อได้แต่ยังไม่ได้ migrate" · log จดรหัส error กับชื่อเครื่องฐานข้อมูล (ไม่มีรหัสผ่าน) ไว้เทียบว่าต่อถูกฐานไหม · ตอบ `503` และ `{ ok, db }` แบบสั้นตามรูปแบบเดิมของเว็บนี้ ไม่ใช่ `{ success, data }` ตาม Requirement

ลองคิด: ถ้า `/api/health` ตอบ `200` แต่บรรณารักษ์บอกว่ากดยืมไม่ได้ ปัญหาน่าจะอยู่ชั้นไหน และจะหาใน log ด้วยคำค้นอะไร

## ตัวเลือกอื่นที่คล้ายกัน

| ทาง | ตัวอย่าง | เหมาะกับ |
|---|---|---|
| เฝ้าว่าเว็บเปิดได้ (uptime) | UptimeRobot, Better Stack, Uptime Kuma (ติดตั้งเองบน VPS) | ทุกเว็บที่มีคนใช้จริง เริ่มจากตรงนี้ |
| เก็บ error พร้อมรายละเอียดให้ (error tracking) | Sentry | เว็บที่มีคนใช้เยอะ อยากรู้ว่า error ไหนเกิดบ่อย เกิดกับใคร |
| ส่ง log ไปเก็บที่อื่นให้นานขึ้น (log drain) | Vercel Drains, Better Stack Logs, Axiom | บน Vercel ที่ log หายใน 1 ชั่วโมง แต่อยากย้อนดูได้หลายวัน |
| จด log เป็น JSON ให้ค้นง่าย | pino | log เยอะจนต้องกรองตาม field เช่น userId |

## ลองเอง

**โจทย์:** ทำให้ `/api/health` บอกได้ด้วยว่า**ฐานข้อมูลตอบช้า** ไม่ใช่แค่พังหรือไม่พัง: วัดเวลาที่ `select 1` ใช้ ถ้าเกิน 1 วินาทีให้ `console.warn` ลง log พร้อมตัวเลข แต่ยังตอบ `200` แล้วพิสูจน์ด้วยการทำให้ฐานช้าจริง

<Hint level={1}>จดเวลาก่อนและหลัง `await` ด้วย `performance.now()` ลบกันได้เป็นมิลลิวินาที</Hint>
<Hint level={2}>ทำให้ช้าได้ด้วยการเปลี่ยน `select 1` ชั่วคราวเป็น `select pg_sleep(1.5)` (ให้ Postgres รอ 1.5 วินาทีก่อนตอบ) ทดสอบเสร็จแล้วเปลี่ยนกลับ</Hint>
<Hint level={3}>ตรวจผล: ตอน `pg_sleep(1.5)` คำขอได้ `200` แต่ใน Terminal มีบรรทัดเตือนพร้อมตัวเลขราว 1500 (ลองแล้วได้ `1530ms`) และบรรทัด `-->` ของ logger แสดง `2s` (logger ปัดเป็นวินาทีเมื่อเกิน 1 วินาที) พอเปลี่ยนกลับเป็น `select 1` บรรทัดเตือนต้องหายไป</Hint>
