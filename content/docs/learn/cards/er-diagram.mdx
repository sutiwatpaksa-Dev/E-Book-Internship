## ความหมาย

[ER diagram](/glossary#er-diagram) (Entity-Relationship) คือภาพของ **ตารางทั้งหมดในระบบ** แต่ละกล่องคือ 1 ตาราง ข้างในเป็นรายชื่อคอลัมน์ และ **เส้นเชื่อม** บอกว่าแถวในตารางหนึ่งชี้ไปหาแถวในอีกตารางยังไง (1 ต่อ 1, 1 ต่อหลาย, หลายต่อหลาย)

**นึกภาพ:** ผังครอบครัว กล่องคือคน เส้นคือความเกี่ยวข้อง ดูแผ่นเดียวก็รู้ว่าใครเป็นลูกใคร โดยไม่ต้องอ่านทะเบียนบ้านทีละใบ

จุดที่ไม่ตรง: ในผังครอบครัว 1 กล่องคือคน 1 คน แต่ใน ER diagram 1 กล่องคือ **ทั้งตาราง** (สมาชิกทุกคน) เส้นจึงไม่ได้บอกว่าใครเกี่ยวกับใคร แต่บอกว่า "1 แถวฝั่งนี้ มีได้กี่แถวฝั่งโน้น"

ระบบห้องสมุดเขียนเป็นภาพคร่าวๆ ได้แบบนี้ (ภาพจริงจาก pgAdmin อยู่ในข้อ 3):

```text
members (สมาชิก)
   │
   │ 1 คน ยืมได้หลายครั้ง
   ▼
loans (การยืม)
มี member_id และ book_id
   ▲
   │ 1 เล่ม ถูกยืมได้หลายครั้ง
   │
books (หนังสือ)
```

## ที่มา

การ์ด [จากหน้าจอสู่ข้อมูล](/learn/cards/screen-to-data) ให้รายการคอลัมน์ของแต่ละตารางมาแล้ว แต่รายการไม่บอกว่า **ตารางต่อกันตรงไหน** ถ้าข้ามขั้นนี้ไปเขียน schema เลย ปัญหาที่เจอบ่อยคือ ใส่ [foreign key](/glossary#foreign-key) (คอลัมน์ที่เก็บ id ของแถวในอีกตาราง) ผิดฝั่ง (เช่น เก็บ `loan_id` ไว้ใน `books` ซึ่งทำให้หนังสือ 1 เล่มมีประวัติยืมได้ครั้งเดียว) หรือลืมว่าความสัมพันธ์หลายต่อหลายต้องมีตารางกลาง ภาพเดียวทำให้เห็นเรื่องพวกนี้ก่อนเขียนโค้ด และพี่เลี้ยงตรวจได้ในนาทีเดียว

## การใช้งาน

**1. อ่านสัญลักษณ์ที่ปลายเส้น** (แบบ "ตีนกา" ที่ pgAdmin ใช้)

| ปลายเส้น | แปลว่า |
|---|---|
| ขีดตั้ง 1 เส้น | ฝั่งนี้มี **1** แถว |
| ขา 3 แฉก (ตีนกา) | ฝั่งนี้มี **หลาย** แถว |

ความสัมพันธ์ 3 แบบ และวิธีทำในตาราง (ใส่ foreign key ฝั่งไหน, ตารางกลาง) อยู่ในบทเดิม [ความสัมพันธ์ 3 แบบ](/06-sql-nosql#ความสัมพันธ์-3-แบบ-er-diagram)

**2. วาดเองก่อน จากรายการต่อตาราง** ถามทีละคู่ตาราง 2 คำถาม: "สมาชิก 1 คน มีการยืมได้กี่ครั้ง" (หลาย) และ "การยืม 1 ครั้ง เป็นของสมาชิกกี่คน" (1) ได้ **1 ต่อหลาย** foreign key จึงอยู่ฝั่ง "หลาย" คือ `loans.member_id`

| คู่ตาราง | ฝั่งนี้ 1 แถว มีอีกฝั่งได้ | ความสัมพันธ์ | foreign key |
|---|---|---|---|
| `members` – `loans` | สมาชิก 1 คน ยืมได้หลายครั้ง · การยืม 1 ครั้งเป็นของ 1 คน | 1 ต่อหลาย | `loans.member_id` |
| `books` – `loans` | หนังสือ 1 เล่ม ถูกยืมได้หลายครั้ง (คนละช่วงเวลา) · การยืม 1 ครั้งเป็นหนังสือ 1 เล่ม | 1 ต่อหลาย | `loans.book_id` |
| `members` – `books` | สมาชิก 1 คนเคยยืมหลายเล่ม · หนังสือ 1 เล่มเคยถูกยืมโดยหลายคน | **หลายต่อหลาย** | ไม่มีตรงๆ ใช้ `loans` เป็นตารางกลาง |
| `librarians` (สร้างในการ์ด [เก็บรหัสผ่านด้วย hash](/learn/cards/password-hash)) | ไม่มีตารางไหนชี้มา | ไม่เชื่อมกับใคร | |

แถวที่ 3 คือเหตุผลที่ `loans` มีอยู่: ความสัมพันธ์หลายต่อหลายเก็บในคอลัมน์เดียวไม่ได้ ต้องแตกเป็น 1 ต่อหลาย 2 เส้นผ่านตารางกลาง และตารางกลางนี้เก็บข้อมูลของ "การยืมครั้งนั้น" ได้ด้วย (`due_at`, `returned_at`) ส่วนตารางที่ไม่เชื่อมกับใครก็ไม่ผิด แค่ให้ถามว่าตั้งใจไหม

วาดบนกระดาษก็พอ: กล่องละตาราง เขียนคอลัมน์ ขีดเส้นใต้ primary key และลากเส้นจาก foreign key ไปหา `id` ที่มันชี้

**3. หลังทำการ์ด [Migration](/learn/cards/migration) แล้ว ให้ pgAdmin วาดจากฐานข้อมูลจริงมาเทียบ** (ตรวจกับ pgAdmin 9.18)

1. ใน Object Explorer ด้านซ้าย เปิด Servers → ชื่อ server → Databases
2. คลิกขวาที่ฐานข้อมูลของโปรเจกต์ (ในการ์ด [Postgres](/learn/cards/postgres) คือ `postgres`) → **ERD For Database**
3. pgAdmin เปิดแท็บใหม่ที่วาดทุกตารางและเส้นเชื่อมจาก foreign key ให้เอง (ปุ่ม **Auto align** บนแถบเครื่องมือช่วยจัดกล่องใหม่ถ้าซ้อนกัน)
4. กดปุ่ม **Download image** (ไอคอนรูปภาพบนแถบเครื่องมือ) ได้ไฟล์ `.png`

**ควรเห็น:** กล่อง `books`, `members`, `loans` และเส้น 2 เส้นจาก `members` และ `books` ไปที่ `loans` โดยฝั่ง `loans` เป็นตีนกา มีกล่องที่ 4 ชื่อ `__drizzle_migrations` (schema `drizzle`) ด้วย เป็นตารางที่ drizzle-kit ใช้จดว่า migration ไฟล์ไหนรันไปแล้ว ไม่ใช่ตารางของเรา ไม่ต้องวาดในภาพของตัวเอง ส่วน `librarians` จะโผล่หลังทำการ์ดเก็บรหัสผ่าน

![ERD ของห้องสมุดใน pgAdmin มีตาราง __drizzle_migrations books members loans และเส้นเชื่อม members กับ books ไปที่ loans](/img/learn-er-pgadmin.png)
*ภาพจริงจาก pgAdmin 9.18 หลังทำการ์ด Migration ขีดตั้งอยู่ฝั่ง books และ members ตีนกาอยู่ฝั่ง loans*

ถ้าภาพของ pgAdmin ไม่ตรงกับที่วาดไว้ อย่ารีบแก้ภาพให้ตรง ให้ถามก่อนว่าอันไหนผิด ส่วนใหญ่ภาพที่วาดถูก แต่ schema ลืม `.references()` ทำให้ไม่มีเส้น

## ทริคที่แนะนำ

1. **เปิดไฟล์ png ดูก่อนส่งทุกครั้ง:** ตอนทดสอบการ์ดนี้ (pgAdmin 9.18) ไฟล์ที่ได้จาก Download image มีกล่องครบ แต่เส้นเชื่อมหายเหลือแค่จุดปลายเส้น ถ้าเจอแบบนั้น ให้แคปหน้าจอแทน (Windows: `Win + Shift + S`, Mac: `Cmd + Shift + 4`) เพราะเส้นคือส่วนที่สำคัญที่สุดของภาพ
2. **ตารางที่ไม่มีเส้นเลย ให้ถามว่าตั้งใจไหม:** `librarians` ไม่มีเส้นเพราะห้องสมุดไม่ได้เก็บว่าใครบันทึกการยืม ถ้าวันหนึ่งต้องรู้ จะต้องเพิ่ม `loans.librarian_id` ภาพทำให้เห็นคำถามนี้
3. **ภาพต้องตรงกับฐานข้อมูลเสมอ:** แก้ schema ทีไร ให้สร้าง ERD ใหม่ ภาพเก่าที่ไม่ตรงแย่กว่าไม่มีภาพ เพราะคนอ่านจะเชื่อมัน

## ปรับไปใช้จริง

**ในโจทย์ฝึกงาน** (ตัวอย่างจาก STARTER)**:** วันที่ 2 ต้องส่ง "รูป ER Diagram (export จาก pgAdmin หรือวาดเองก็ได้)" ([Requirement หน้า 7](/api/files/requirement.pdf?sec=database), ต้อง login) ตาราง 6 ตารางมีเส้นที่ต้องเห็นอย่างน้อย 1 เส้น: `categories` 1 ต่อหลาย `services` (foreign key `services.category_id`) และหน้า 7 บอกว่า **ห้ามลบหมวดที่ยังมีบริการอยู่** ซึ่งเป็นกติกาของเส้นนี้ ส่วน `admins`, `site_settings`, `pages`, `contact_messages` ไม่มีเส้นเชื่อม ภาพจะช่วยตอบตอน Review รอบที่ 1 (วันที่ 5) ว่าทำไมเป็นแบบนั้น

**เว็บคู่มือนี้:** ตาราง `thread_messages` ชี้ไปที่ `threads` (1 เรื่องมีหลายข้อความ) ด้วย `onDelete: "cascade"` แปลว่าลบเรื่องแล้วข้อความหายตาม ต่างจากห้องสมุดที่ไม่ใส่ จึงลบหนังสือที่มีประวัติยืมไม่ได้ (รหัส `23503` ในการ์ด [หน้าจัดการข้อมูล](/learn/cards/crud-ui)) ดูได้ที่ [server/db/schema.ts บน GitHub](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/server/db/schema.ts)

ลองคิด: ถ้าห้องสมุดอยากให้หนังสือ 1 เล่มมีได้หลายหมวด (เช่น "นิยาย" และ "หนังสือเด็ก") ภาพต้องเปลี่ยนยังไง

## ตัวเลือกอื่นที่คล้ายกัน

| เครื่องมือ | ข้อดี | ข้อเสีย |
|---|---|---|
| **pgAdmin ERD Tool** | สร้างจากฐานข้อมูลจริง ไม่มีทางวาดไม่ตรง ติดตั้งมาพร้อม pgAdmin แล้ว | ต้องมีตารางในฐานข้อมูลก่อน ใช้ตอนวางแผนยังไม่ได้ |
| กระดาษ + ปากกา | เร็วที่สุด ใช้ตอนยังไม่มีโค้ด | ต้องวาดใหม่ทุกครั้งที่ schema เปลี่ยน |
| [dbdiagram.io](https://dbdiagram.io) | พิมพ์เป็นข้อความแล้ววาดให้ แก้ง่าย | ข้อความแยกจาก schema จริง ต้องคอยแก้ให้ตรงเอง |
| [Mermaid](https://mermaid.js.org/syntax/entityRelationshipDiagram.html) `erDiagram` | เขียนใน README ได้ GitHub วาดภาพให้เอง | จัดตำแหน่งกล่องเองไม่ได้ ตารางเยอะแล้วอ่านยาก |

## ลองเอง

**โจทย์:** วาด ER diagram ของ 6 ตารางในโจทย์ STARTER (โจทย์อื่นใช้ส่วนที่เทียบกันได้) บนกระดาษ จากรายการต่อตารางในการ์ดก่อน แล้วเขียนข้างทุกเส้นว่าเป็นความสัมพันธ์แบบไหน และ foreign key อยู่คอลัมน์ไหน

<Hint level={1}>ถาม 2 คำถามกับทุกคู่ตารางที่น่าจะเกี่ยวกัน เช่น "หมวด 1 หมวด มีบริการได้กี่รายการ" และ "บริการ 1 รายการ อยู่ได้กี่หมวด"</Hint>
<Hint level={2}>`site_settings` "มีแถวเดียวทั้งระบบ" (หน้า 7) และ `contact_messages` มาจากคนทั่วไปที่ไม่ได้ login จึงไม่มีตารางไหนให้ชี้ไป ถ้าวาดเส้นไปหา `admins` ลองถามว่าเก็บไว้เพื่อตอบคำถามอะไร</Hint>
<Hint level={3}>ตรวจก่อนส่ง: ทุกเส้นมี foreign key จริง 1 คอลัมน์อยู่ฝั่ง "หลาย", ทุกตารางที่ไม่มีเส้นอธิบายได้ว่าทำไม และหลังทำการ์ด Migration แล้ว ภาพจาก ERD For Database ของ pgAdmin มีเส้นตรงกับที่วาดทุกเส้น</Hint>
