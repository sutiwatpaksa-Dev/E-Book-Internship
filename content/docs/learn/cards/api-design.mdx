## ความหมาย

รายการ API คือ **สัญญา** ระหว่างหน้าเว็บกับ server ว่ามีทางเรียกอะไรบ้าง แต่ละทางเขียน 5 อย่าง: **method + URL**, **ใครเรียกได้**, **ส่งอะไรมา**, **ตอบอะไรเมื่อสำเร็จ** และ **ผิดได้แบบไหน (status + code)**

**นึกภาพ:** เมนูร้านอาหารที่เขียนให้ครัวกับพนักงานเสิร์ฟใช้ร่วมกัน ชื่อจาน (URL), ใครสั่งได้ (เมนูเด็ก/เมนูพนักงาน), ต้องบอกอะไรตอนสั่ง (เผ็ดไหม), จานที่ได้หน้าตาแบบไหน และถ้าวัตถุดิบหมดจะบอกลูกค้าว่าอะไร ทั้งสองฝ่ายทำงานแยกกันได้เพราะยึดเมนูเดียวกัน

พื้นฐานของ method, URL และ status code อยู่ในการ์ด [HTTP และ REST](/learn/cards/http-rest) การ์ดนี้ใช้ของพวกนั้นออกแบบทั้งระบบ

## ที่มา

ในงาน STARTER ทำ API วันที่ 3–4 แต่ทำหน้าเว็บวันที่ 6–8 (Checklist หน้า 14–15) ถ้าไม่มีสัญญา พอเริ่มทำหน้าเว็บ จะเจอว่า API ตอบชื่อฟิลด์ไม่ตรงที่หน้าเว็บใช้ กรองตามหมวดไม่ได้เพราะไม่ได้ทำ query นั้นไว้ หรือหน้าเว็บไม่รู้ว่า "ยืมเกินกำหนด" ตอบมาเป็น status อะไร จึงเขียนข้อความให้ผู้ใช้ไม่ได้ ต้องกลับไปแก้ API ที่ทดสอบผ่านไปแล้ว สัญญาที่เขียนวันที่ 1 ทำให้รู้เรื่องพวกนี้ตั้งแต่ยังไม่มีโค้ด

## การใช้งาน

**1. ไล่หน้าจอทีละหน้า ว่าต้องเรียกอะไร** ทุกแถวในการ์ด [จากหน้าจอสู่ข้อมูล](/learn/cards/screen-to-data) ที่ "มาจาก" ฐานข้อมูล ต้องมีทางเรียกรองรับ ตัวอย่างห้องสมุด (ตรงกับที่การ์ดช่วง Coding สร้าง)

| หน้าจอ | ต้องเรียก | ใครเรียกได้ | การ์ดที่สร้าง |
|---|---|---|---|
| `/books` รายการ + ค้นหา | `GET /api/books?q=` | ทุกคน | [แบ่งชั้น](/learn/cards/layers) |
| `/books/:id` | `GET /api/books/:id` | ทุกคน | แบ่งชั้น |
| `/admin/login` | `POST /api/admin/login` · `POST /api/admin/logout` | ทุกคน | [JWT ใน cookie](/learn/cards/jwt-cookie) |
| ทุกหน้า `/admin/*` (ยัง login อยู่ไหม) | `GET /api/admin/me` | บรรณารักษ์ | [Middleware](/learn/cards/auth-middleware) |
| `/admin/books` | `GET /api/admin/books?q=&page=` · `POST /api/admin/books` · `PATCH` และ `DELETE /api/admin/books/:id` | บรรณารักษ์ | [หน้าจัดการข้อมูล](/learn/cards/crud-ui) |
| บันทึกการยืม (story 5) | `POST /api/loans` | ควรเป็นบรรณารักษ์ | แบ่งชั้น |

**2. แบ่ง "ทุกคน" กับ "ต้อง login" ด้วย URL** กติกาง่ายๆ: อ่านอย่างเดียวและไม่มีข้อมูลส่วนตัว = ทุกคน · เพิ่ม แก้ ลบ หรือดูข้อมูลของคนอื่น = ต้อง login ของที่ต้อง login ทั้งหมดขึ้นต้นด้วย `/api/admin/` จึงใช้ด่านตรวจตัวเดียวคุมได้ทั้งหมด (`app.use("/admin/*", requireLibrarian)` ในการ์ด Middleware) ไม่ต้องจำใส่ทีละทาง

แถวสุดท้ายของตารางผิดกติกานี้: การ์ดแบ่งชั้นทำ `POST /api/loans` ไว้ก่อนมีระบบ login ใครก็ยิงยืมแทนคนอื่นได้ การ์ด Middleware จึงชวนย้ายไปหลังด่าน ถ้าออกแบบตั้งแต่ขั้นนี้ จะได้ `POST /api/admin/loans` ตั้งแต่แรก

**3. เขียนสัญญาของแต่ละทาง ให้ครบทุกผลที่เกิดได้** ตัวอย่างการยืม (ตรงกับการ์ด [จัดการ error](/learn/cards/error-handling))

| | `POST /api/loans` |
|---|---|
| ส่งมา | `{ "memberId": 1, "bookId": 2 }` |
| สำเร็จ | `201` `{ success: true, data: { id, memberId, bookId, dueAt, returnedAt: null } }` |
| ข้อมูลไม่ครบหรือผิดชนิด | `400` `VALIDATION_ERROR` พร้อม `details` รายช่อง |
| ไม่มีหนังสือเล่มนั้น | `404` `BOOK_NOT_FOUND` |
| ยืมค้างครบ 3 เล่มแล้ว | `409` `LOAN_LIMIT` |
| เล่มนี้ยังไม่ถูกคืน (เกณฑ์ข้อ 3 ของ story 5) | `409` รหัสใหม่ เช่น `BOOK_NOT_AVAILABLE` · **ยังไม่มีในโค้ด** เป็นโจทย์ 1 ของการ์ดแบ่งชั้น |
| ไม่มีสมาชิกคนนั้น | ควรเป็น `404` `MEMBER_NOT_FOUND` · **ตอนนี้ได้ `500`** เพราะการ์ดแบ่งชั้นตรวจแค่หนังสือ แล้วไปชน foreign key ตอนบันทึก |

สัญญานี้เขียนตามโค้ดที่การ์ดแบ่งชั้นทำ 2 แถวสุดท้ายคือสิ่งที่การเขียนสัญญาทำให้เห็น: เกณฑ์ที่ยังไม่มีโค้ดรองรับ และช่องโหว่ที่ผู้ใช้จะได้ "เกิดข้อผิดพลาด" แทนข้อความที่บอกว่าผิดอะไร ถ้าย้ายไปเป็น `POST /api/admin/loans` ตามข้อ 2 ต้องเพิ่มแถว "ยังไม่ login → `401` `UNAUTHORIZED`" ด้วย

ทุกแถวที่ผิดได้ คือข้อความที่หน้าเว็บต้องเตรียมไว้ (การ์ด [User flow](/learn/cards/user-flow)) และคือกรณีที่ต้องยิงทดสอบ (การ์ด [ยิงทดสอบ API](/learn/cards/api-testing)) สัญญาแผ่นเดียวจึงใช้ได้ 3 งาน

**4. ใช้ชื่อเดียวกันทั้งระบบ** ฐานข้อมูลใช้ `member_id` แต่ JSON ที่ส่งไปมาใช้ `memberId` (schema จับคู่ชื่อไว้ให้ เช่น `memberId: integer("member_id")` ในการ์ด [Drizzle](/learn/cards/drizzle-orm)) ตัดสินครั้งเดียวแล้วใช้ทุกทาง และรูปแบบคำตอบเหมือนกันทุกทาง (`{ success, data }` / `{ success: false, error }`) หน้าเว็บจะได้เขียนตัวอ่านคำตอบแค่ชุดเดียว

**ควรได้:** ตาราง "หน้าจอ → ต้องเรียก" ที่ไม่มีหน้าจอไหนไม่มีทางเรียก และสัญญาของทุกทางที่เขียนผลผิดพลาดครบ

## ทริคที่แนะนำ

1. **กรองและค้นหาใช้ `?` ไม่ใช่ URL ใหม่:** `GET /api/books?q=ฮอบ&page=2` ดีกว่า `GET /api/books/search/ฮอบ` เพราะ URL ยังหมายถึง "รายการหนังสือ" เหมือนเดิม แค่บอกเงื่อนไขเพิ่ม และเงื่อนไขหลายตัวรวมกันได้โดยไม่ต้องเพิ่มทาง
2. **เขียนเฉพาะ error ที่ผู้ใช้ทำให้เกิดได้:** `400`, `401`, `404`, `409` คือสิ่งที่หน้าเว็บต้องบอกผู้ใช้ว่าทำอะไรต่อ ส่วน `500` คือโค้ดเราพังเอง ไม่ต้องเขียนในสัญญาทุกทาง เพราะหน้าเว็บทำได้อย่างเดียวคือบอกว่า "ลองใหม่"
3. **ตอบเท่าที่หน้าจอใช้ ไม่ตอบทั้งแถว:** `GET /api/admin/me` ตอบชื่อและอีเมล ไม่ใช่ทั้งแถวของ `librarians` ซึ่งมี `password_hash` การ์ด Middleware จึงให้ repository เลือกเฉพาะคอลัมน์ที่ตอบออกไปได้ ถ้าสัญญาเขียนไว้ว่าตอบอะไร จะเห็นตั้งแต่แรกว่ามีอะไรห้ามหลุด

## ปรับไปใช้จริง

**ในงาน STARTER:** Requirement ให้รายการ API มาครบแล้ว ([หน้า 8–9](/api/files/requirement.pdf#page=8), ต้อง login) แบ่ง Public กับ Admin และให้รูปแบบคำตอบกับ status ที่ต้องใช้ งานของเราจึงเป็น 2 อย่าง

- **ตรวจกลับกับ wireframe:** ทุกหน้าจอเรียกได้ครบไหม ทุกทางมีหน้าจอที่ใช้ไหม เช่น Dashboard ต้องการ "ข้อความล่าสุด 5 รายการ" (หน้า 5) ได้จาก `GET /api/admin/dashboard` หรือต้องเรียก `/api/admin/messages` อีกที
- **เขียนผลผิดพลาดของแต่ละทาง** ซึ่ง Requirement ไม่ได้เขียนให้ครบ เช่น `DELETE /api/admin/categories/:id` ตอบ `409` เมื่อหมวดยังมีบริการ (หน้า 9 ยกตัวอย่างไว้) ส่วน `POST /api/contact` ถ้าส่งเกิน 5 ครั้งใน 10 นาที (หน้า 10) ควรตอบอะไร

สัญญานี้คือสิ่งที่พี่เลี้ยงดูใน Review รอบที่ 1 (วันที่ 5, โครงสร้าง DB + API)

**เว็บคู่มือนี้:** แยกทางเรียกเป็นกลุ่มตามของ (`/api/auth`, `/api/admin`, `/api/threads`, `/api/progress`) และกลุ่ม `/api/admin` ทั้งหมดผ่านด่านตรวจสิทธิ์ตัวเดียว ดูได้ที่ [server/app.ts บน GitHub](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/server/app.ts) (เว็บนี้ตอบ error แบบสั้น `{ error: "..." }` ซึ่งต่างจาก Requirement เพราะทำก่อน งาน STARTER ต้องใช้รูปแบบใน Requirement)

ลองคิด: Requirement หน้า 9 ให้ status ที่ต้องใช้ 7 ตัว ไม่มีตัวไหนแปลว่า "ส่งบ่อยเกินไป" ถ้าฟอร์มติดต่อโดนกันสแปม ควรตอบด้วยตัวไหนในนั้น หรือควรเข้ารายการคำถามในการ์ด [ขอบเขตงาน](/learn/cards/scope-questions)

## ตัวเลือกอื่นที่คล้ายกัน

| วิธี | ข้อดี | ข้อเสีย |
|---|---|---|
| **ตาราง markdown (การ์ดนี้)** | เขียนเร็ว อยู่ใน README ได้ อ่านง่าย | ไม่มีอะไรตรวจว่าโค้ดตรงกับตาราง |
| OpenAPI (Swagger) | มาตรฐานที่ใช้กันกว้าง สร้างหน้าเอกสารที่กดลองยิงได้ และ Hono มี [`@hono/zod-openapi`](https://hono.dev/examples/zod-openapi) สร้างจาก Zod schema | ต้องเรียนรูปแบบของมัน หนักไปสำหรับงาน 10 วัน |
| [Hono RPC](https://hono.dev/docs/guides/rpc) | หน้าเว็บได้ type ของ API จาก server โดยตรง ชื่อฟิลด์ผิดแล้ว TypeScript เตือน | ใช้ได้เฉพาะเมื่อหน้าเว็บกับ server เป็น TypeScript ใน repo เดียวกัน และไม่ใช่เอกสารให้คนอ่าน |
| Postman collection | เป็นทั้งเอกสารและชุดทดสอบ | เปิดอ่านต้องใช้ Postman ไม่เห็นใน repo |

## ลองเอง

**โจทย์:** เขียนสัญญาแบบข้อ 3 ของ 4 ทางในงาน STARTER: `GET /api/services`, `POST /api/contact`, `DELETE /api/admin/categories/:id` และ `PATCH /api/admin/services/:id`

<Hint level={1}>เริ่มจากถามทีละทางว่า "ส่งอะไรมาได้บ้างที่ทำให้มันผิด" ข้อมูลหาย, id ที่ไม่มีอยู่, ชนกับของที่มีอยู่แล้ว, ยังไม่ login แต่ละแบบคือ 1 แถว</Hint>
<Hint level={2}>`GET /api/services` เป็นทางของทุกคน จึงต้องตอบเฉพาะบริการที่เปิดแสดงผล (`is_active`) และรับ `?category=&featured=` (หน้า 8) ส่วนทางที่ขึ้นต้น `/api/admin/` ทุกทางมีแถว `401` เหมือนกัน เขียนครั้งเดียวไว้หัวตารางได้</Hint>
<Hint level={3}>ตรวจก่อนส่ง: ทุกแถวที่ผิดมี status และ code (เช่น `VALIDATION_ERROR`), ใช้แค่ status 7 ตัวในหน้า 9, ชื่อฟิลด์ใน JSON เหมือนกันทุกทาง และทุกแถวที่ผิด หาได้ว่าหน้าเว็บแสดงข้อความอะไร</Hint>
