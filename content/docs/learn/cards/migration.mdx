## ความหมาย

**[Migration](/glossary#migration)** คือไฟล์ที่จดว่า **โครงตารางเปลี่ยนอะไร ทีละครั้ง เรียงตามลำดับ** ใครรันไฟล์ชุดเดียวกันตามลำดับ ก็ได้ฐานข้อมูลหน้าตาเดียวกัน

**[Seed](/glossary#seed)** คือสคริปต์ใส่ **ข้อมูลตั้งต้น** ลงตาราง เช่น บัญชี admin คนแรก หมวดหมู่ตัวอย่าง เปิดระบบมาจะได้ไม่ว่างเปล่า

**นึกภาพ:** migration = สมุดบันทึกการต่อเติมบ้าน (ห้องที่ 1 สร้างเมื่อไร ห้องที่ 2 ต่อเติมเมื่อไร) ส่วน seed = เฟอร์นิเจอร์ชุดแรกที่ขนเข้าบ้าน

## ที่มา

ทีมหนึ่งมีฐานข้อมูลหลายที่: เครื่องของทุกคน เครื่องพี่เลี้ยงที่ตรวจงาน และเว็บจริง ถ้าแก้ตารางด้วยมือใน pgAdmin สักวันต้องมีคนลืมแก้สักที่ แล้วโค้ดที่รันผ่านในเครื่องหนึ่งก็พังในอีกเครื่อง migration ทำให้การเปลี่ยนตารางเป็นไฟล์ที่ commit ลง Git ได้ ตรวจได้ และรันซ้ำได้เหมือนกันทุกที่ ส่วน seed ทำให้ทุกคนได้ข้อมูลทดสอบชุดเดียวกันด้วยคำสั่งเดียว

## การใช้งาน

ต่อจากการ์ด [Drizzle ORM](/learn/cards/drizzle-orm) (มี `schema.ts`, `db/index.ts` และ `drizzle.config.ts` แล้ว) ทุกคำสั่งพิมพ์ในโฟลเดอร์ `server/` เหมือนกันทั้ง Windows และ Mac

**1. สร้างไฟล์ migration จาก schema**

```bash
bunx drizzle-kit generate
```

**ควรเห็น:**
```text
books 3 columns 0 indexes 0 fks
loans 5 columns 0 indexes 2 fks
members 3 columns 0 indexes 0 fks
[✓] Your SQL migration file ➜ drizzle/0000_xxxx.sql 🚀
```

เปิดไฟล์ `.sql` ที่ได้ดู จะเห็น `CREATE TABLE` แบบเดียวกับที่เขียนเองในการ์ด SQL ขั้นนี้ **ยังไม่แตะฐานข้อมูล**

**2. รัน migration ลงฐานจริง**

```bash
bunx drizzle-kit migrate
```

**ควรเห็น:** `[✓] migrations applied successfully!` แล้วใน pgAdmin คลิกขวาที่ฐาน `postgres` → Refresh แล้วเปิด Schemas → public → Tables จะเห็นตาราง `members`, `books`, `loans` และตาราง `__drizzle_migrations` ที่จดว่ารันไฟล์ไหนไปแล้ว (อยู่ใต้ schema ชื่อ `drizzle` คำว่า schema ใน pgAdmin หมายถึง "กลุ่มตาราง" ในฐานข้อมูล เช่น `public` คนละเรื่องกับไฟล์ `schema.ts`)

> **ขึ้น `relation "members" already exists`?** แปลว่าเคยสร้างตารางเองในฐาน `postgres` (การ์ด SQL รุ่นก่อนให้ทำแบบนั้น) ใน Query Tool ของฐาน `postgres` รัน `DROP TABLE loans, books, members;` (ต้องลบสามตารางในคำสั่งเดียว ถ้าลบ `members` ตัวเดียว จะติด foreign key ที่ `loans` ชี้มา) แล้ว `bunx drizzle-kit migrate` ใหม่ ข้อมูลที่ลองใส่ไว้จะหายไป ซึ่งไม่เป็นไร seed ขั้นถัดไปใส่ให้ใหม่

**3. Seed ข้อมูลตั้งต้น** `server/src/db/seed.ts`

```ts
import { db } from "./index";
import { books, members } from "./schema";

await db.insert(members).values([{ name: "มานี" }, { name: "ปิติ" }]);
await db.insert(books).values([{ title: "เจ้าชายน้อย" }, { title: "ฮอบบิท" }]);
console.log("seed เสร็จ");
process.exit(0);   // ปิด connection ที่ค้างอยู่ ไม่งั้นคำสั่งไม่จบ
```

เพิ่ม `"scripts"` ใน `server/package.json` เป็น key ระดับเดียวกับ `"dependencies"` (อยู่ใน `{ }` นอกสุด) และคั่นกับ key ข้างๆ ด้วย `,` แล้วรัน `bun run seed`

```json
{
  "name": "server",
  "type": "module",
  "scripts": {
    "seed": "bun run src/db/seed.ts"
  },
  "dependencies": { ... }
}
```

**ควรเห็น:** `seed เสร็จ` และใน pgAdmin ตาราง `members` มี 2 แถว (คลิกขวาที่ตาราง → View/Edit Data → All Rows)

## ทริคที่แนะนำ

1. **อ่านไฟล์ SQL ทุกครั้งก่อน migrate:** เปลี่ยนชื่อคอลัมน์อาจถูกเข้าใจว่า "ลบแล้วสร้างใหม่" (`DROP` + `ADD`) ข้อมูลเดิมหาย drizzle-kit จะถามตอน generate ให้ตอบว่าเป็นการเปลี่ยนชื่อ (rename)
2. **ไฟล์ที่ push ไปแล้วห้ามแก้** เพื่อนหรือพี่เลี้ยงอาจรันไปแล้ว อยากเปลี่ยนให้แก้ schema แล้ว generate ใหม่ จะได้ไฟล์ migration ใบถัดไปต่อท้าย (ไฟล์เดิมไม่ถูกแตะ)
3. **seed รันซ้ำแล้วข้อมูลเบิ้ล** ถ้าจะให้รันซ้ำได้ ให้ลบข้อมูลเก่าก่อนใส่ใหม่ หรือเช็กก่อนว่ามีแล้วหรือยัง ส่วน `drizzle-kit push` (ดัน schema เข้าฐานตรงๆ ไม่สร้างไฟล์) ใช้ได้แค่ตอนทดลองกับฐานของตัวเอง

## ปรับไปใช้จริง

**ในงาน STARTER:** วันที่ 2 ต้องส่ง `schema.ts`, migration ที่รันได้ และ seed script (admin 1, หมวด 2, service 6, settings 1, pages 3) ตรวจผ่านเมื่อ "`bun run seed` แล้วมีข้อมูลใน pgAdmin" และจำไว้ว่ารหัสผ่าน admin ใน seed ต้อง hash ก่อนเก็บ (เกณฑ์ไม่ผ่านทันทีถ้าเก็บรหัสผ่านตรงๆ)

**เว็บคู่มือนี้:** Vercel รัน migrate ก่อน build ทุกครั้ง ตารางบนเว็บจริงจึงตามโค้ดทันเสมอ เคยพังครั้งหนึ่งด้วยรหัส `42P07` (ตารางมีอยู่แล้ว) เพราะตารางถูกสร้างไปแล้วแต่ `__drizzle_migrations` ไม่ได้จดไว้ ระบบจึงพยายามสร้างซ้ำ **สมุดกับของจริงต้องตรงกันเสมอ**

ลองคิด: ถ้าแก้ตารางใน pgAdmin ด้วยมือ แล้วค่อย generate migration ทีหลัง จะเกิดอะไรตอนพี่เลี้ยงรัน migrate บนเครื่องของเขา

## ลองเอง

**โจทย์:** เพิ่มเบอร์โทรให้สมาชิก โดยสมาชิก 2 คนที่ seed ไว้ต้องไม่พัง และสมาชิกใหม่ต้องกรอกเบอร์ทุกคน

<Hint level={1}>ถ้าเพิ่มคอลัมน์ที่ห้ามว่างทันที แถวเก่าที่ไม่มีเบอร์จะทำให้ migrate ไม่ผ่าน ต้องคิดว่าแถวเก่าจะได้ค่าอะไร</Hint>
<Hint level={2}>มีสองทาง: ให้ค่าเริ่มต้น (`.default(...)`) หรือแบ่งเป็น 2 migration (เพิ่มแบบว่างได้ → เติมข้อมูล → ค่อยเปลี่ยนเป็นห้ามว่าง)</Hint>
<Hint level={3}>เลือกทางหนึ่ง แก้ schema → generate → **อ่านไฟล์ SQL** → migrate แล้วลองเพิ่มสมาชิกใหม่ใน pgAdmin โดยไม่ใส่เบอร์ ต้องเจอ error</Hint>
