## ความหมาย

Migration คือ **ไฟล์ที่จดว่าโครงตารางเปลี่ยนอะไร ทีละครั้ง เรียงตามลำดับ** เหมือนสมุดบัญชีที่จดทุกรายการ ใครเปิดสมุดเล่มเดียวกันแล้วทำตามทีละบรรทัด ก็ได้ฐานข้อมูลหน้าตาเดียวกัน

## ที่มา

ทีมหนึ่งมีฐานข้อมูลหลายที่: เครื่องของทุกคน, preview และเว็บจริง ถ้าแก้ตารางด้วยมือ สักวันต้องมีคนลืมแก้สักที่ แล้วโค้ดที่รันผ่านในเครื่องหนึ่งก็พังในอีกเครื่อง migration ทำให้การเปลี่ยนตารางเป็นไฟล์ที่ commit ลง Git ได้ ตรวจได้ และรันซ้ำได้เหมือนกันทุกที่

## การใช้งาน

วงจรมี 3 จังหวะ:

1. แก้ schema (เช่น เพิ่มคอลัมน์ใน `server/db/schema.ts`)
2. `npx drizzle-kit generate` → เครื่องมือเทียบ schema กับครั้งก่อน แล้วสร้าง **ไฟล์ SQL ใหม่** (ยังไม่แตะฐานข้อมูล)
3. `npx drizzle-kit migrate` → รันไฟล์ที่ฐานข้อมูลนั้นยังไม่เคยรัน แล้วจดไว้ในตาราง `__drizzle_migrations` ว่ารันไปแล้ว

ตัวอย่างไฟล์ที่ได้เมื่อเพิ่มคอลัมน์ `due_date` ในตาราง `loans`:

```sql
ALTER TABLE "loans" ADD COLUMN "due_date" timestamp with time zone;
```

คำสั่งเหมือนกันทั้ง Windows และ Mac (เว็บนี้ตั้งชื่อย่อไว้เป็น `npm run db:generate` และ `npm run db:migrate`)

## ทริคที่แนะนำ

1. **อ่านไฟล์ SQL ทุกครั้งก่อน migrate:** เปลี่ยนชื่อคอลัมน์อาจถูกเข้าใจว่า "ลบแล้วสร้างใหม่" (`DROP` + `ADD`) ข้อมูลเดิมหาย ที่ปลอดภัยคือ `RENAME COLUMN`
2. **ไฟล์ที่ push ไปแล้วห้ามแก้** เพื่อนอาจรันไปแล้ว อยากเปลี่ยนให้สร้างไฟล์ใหม่ทับ
3. **commit ไฟล์ migration คู่กับ schema เสมอ** และ `drizzle-kit push` (ดัน schema เข้าฐานตรงๆ ไม่สร้างไฟล์) ใช้ได้แค่กับฐานส่วนตัวตอนทดลอง

## ปรับไปใช้จริง

เว็บคู่มือนี้เก็บไฟล์ไว้ที่ `server/db/migrations/` และให้ Vercel รัน migrate ก่อน build ทุกครั้ง ตารางบนเว็บจริงจึงตามโค้ดทันเสมอ เคยพังครั้งหนึ่งด้วยรหัส `42P07` (ตารางมีอยู่แล้ว) เพราะตารางถูกสร้างไปแล้ว แต่สมุด `__drizzle_migrations` ไม่ได้จดไว้ ระบบจึงพยายามสร้างซ้ำ **สมุดกับของจริงต้องตรงกันเสมอ**

ลองคิด: ในโปรเจกต์ของเรา ตารางไหนน่าจะต้องเปลี่ยนบ่อยที่สุด และถ้ามีข้อมูลจริงอยู่แล้ว จะเพิ่มคอลัมน์ที่ "ห้ามว่าง" ยังไง

## ลองเอง

**โจทย์:** เพิ่มเบอร์โทรให้สมาชิกห้องสมุด โดยสมาชิกเก่าที่มีอยู่แล้วต้องไม่พัง และสมาชิกใหม่ต้องกรอกเบอร์ทุกคน

<Hint level={1}>ถ้าเพิ่มคอลัมน์ที่ห้ามว่างทันที แถวเก่าที่ไม่มีเบอร์จะทำให้ migrate ไม่ผ่าน ต้องคิดว่าแถวเก่าจะได้ค่าอะไร</Hint>
<Hint level={2}>มีสองทาง: ให้ค่าเริ่มต้น (`default`) หรือแบ่งเป็น 2 migration (เพิ่มแบบว่างได้ → เติมข้อมูล → ค่อยเปลี่ยนเป็นห้ามว่าง)</Hint>
<Hint level={3}>เลือกทางหนึ่ง แก้ schema → generate → **อ่านไฟล์ SQL** → migrate แล้วลองเพิ่มสมาชิกใหม่โดยไม่ใส่เบอร์ ต้องเจอ error</Hint>
