> ต่อจากการ์ด [Log และเฝ้าเว็บ](/learn/cards/log-monitoring) และใช้ของจากขั้น 1 ([User story](/learn/cards/user-stories), [ขอบเขตงาน](/learn/cards/scope-questions)) เพราะการ์ดนี้คือจุดที่วงจร 7 ขั้นวนกลับไปเริ่มใหม่

## ความหมาย

พูดง่ายๆ: หลังเว็บเปิดใช้ จะมีคนบอกเราตลอดว่า "ตรงนี้พัง" "ตรงนี้ใช้ยาก" "อยากได้ปุ่มนี้" การ์ดนี้คือวิธีรับเรื่องพวกนี้ให้ไม่หล่นหาย แยกว่าเรื่องไหนด่วน แล้วเปลี่ยนเป็นงานที่ทำเสร็จได้ และมีขั้นตอนพร้อมใช้สำหรับวันที่เว็บล่มจริง

นึกภาพ: ร้านอาหารที่มีบัตรความเห็นบนโต๊ะ

- **feedback** = บัตรความเห็นที่ลูกค้าเขียน ("ต้มยำเค็มไป" "อยากให้มีเมนูเจ")
- **[issue](/glossary#issue)** = ใบสั่งงานที่แปะในครัว 1 เรื่องต่อ 1 ใบ มีคนรับผิดชอบ
- **จัดลำดับ** = เชฟตัดสินว่าใบไหนทำก่อน "แก๊สรั่ว" มาก่อน "อยากได้เมนูใหม่" เสมอ
- **ปิดงาน + แจ้งกลับ** = บอกลูกค้าคนนั้นว่า "ปรับสูตรแล้วครับ" ครั้งหน้าเขาจะเขียนบัตรอีก

จุดที่ไม่ตรง: บัตรความเห็นมีคนเขียนเพราะวางอยู่บนโต๊ะ แต่ผู้ใช้เว็บส่วนมาก**ไม่บอกอะไรเลย** เจอปัญหาแล้วเลิกใช้ เรื่องที่มาถึงเราจึงเป็นส่วนน้อย ต้องถือเป็นของมีค่า และต้องดู log กับ monitor ประกอบด้วย

```text
ผู้ใช้ / monitor / log
      │ แจ้งเรื่อง
      ▼
จดเป็น issue (1 เรื่อง 1 ใบ) ──► จัดลำดับ: 🔴 ต้องแก้ทันที · 🟠 ควรแก้ · ⚪ เก็บกวาด
      │
      ├── บั๊ก ──► แก้ ──► ทดสอบ ──► ขึ้นเว็บ ──► ปิด issue + แจ้งคนที่บอก
      │
      └── ของใหม่ ──► กลับไปขั้น 1: เขียน user story, ถามขอบเขต, ใส่แผน
```

## ที่มา

สัปดาห์แรกหลังเปิดระบบห้องสมุด บรรณารักษ์ส่ง LINE มา 4 เรื่อง: ปุ่มคืนหนังสือบนมือถือกดไม่โดน, รายการเกินกำหนดเรียงผิด, อยากให้ส่ง SMS เตือนสมาชิก, และ "เมื่อเช้าเข้าไม่ได้" เราตอบ "รับทราบครับ" ทุกเรื่อง แล้ว:

- 2 สัปดาห์ต่อมาจำไม่ได้ว่ามีเรื่องไหนบ้าง เพราะอยู่ในแชทปนกับเรื่องอื่น
- เรื่อง SMS ซึ่งไม่อยู่ในขอบเขตงาน เราทำให้ไปครึ่งวัน (ไม่มีใครถามพี่เลี้ยงก่อน) ส่วนเรื่องรายการเกินกำหนดที่กระทบงานทุกวันยังไม่ได้แก้
- "เมื่อเช้าเข้าไม่ได้" ไม่มีใครถามต่อว่ากี่โมง เห็นอะไร log ก็หายไปแล้ว

ทุกข้อแก้ได้ด้วยนิสัยเดียว: **จดทุกเรื่องเป็น issue ทันที พร้อมข้อมูลพอให้คนอื่นทำซ้ำได้**

## การใช้งาน

### ตั้งค่าครั้งแรก

ใช้แท็บ **Issues** ของ repo บน GitHub (เปิดอยู่แล้วโดยค่าเริ่มต้น ถ้าไม่เห็นแท็บ ไปที่ Settings → General → ติ๊ก **Issues**) ไม่ต้องติดตั้งอะไรเพิ่ม

### 1. ฟอร์มรายงานบั๊ก (`.github/ISSUE_TEMPLATE/bug.yml`)

ปัญหาใหญ่ของบั๊กที่มีคนแจ้งคือ**ข้อมูลไม่พอ** "กดแล้วไม่ได้" ไม่รู้ว่ากดตรงไหน บนอะไร เมื่อไร ทำฟอร์มให้ต้องกรอกช่องที่จำเป็น สร้างไฟล์นี้ที่โฟลเดอร์บนสุดของ repo:

```yaml
name: รายงานบั๊ก
description: มีอะไรใช้ไม่ได้ หรือทำงานไม่ตรงที่ควรเป็น
title: "[บั๊ก] "
labels: ["bug"]
body:
  - type: textarea
    id: steps
    attributes:
      label: ทำอะไรบ้าง (ทีละขั้น)
      placeholder: |
        1. เข้า /admin/loans บนมือถือ
        2. กดปุ่ม "คืน" ของรายการแรก
    validations:
      required: true
  - type: textarea
    id: expected-actual
    attributes:
      label: คาดว่าจะเกิดอะไร และเกิดอะไรจริง
      placeholder: คาดว่ารายการหายไปจากหน้า แต่กดแล้วไม่มีอะไรเกิดขึ้น
    validations:
      required: true
  - type: input
    id: when
    attributes:
      label: เกิดเมื่อไร (วันที่ เวลา)
      description: ใช้หาใน log ซึ่งเก็บไว้ไม่นาน
      placeholder: 3 พ.ย. 14:05
    validations:
      required: true
  - type: dropdown
    id: device
    attributes:
      label: ใช้อุปกรณ์อะไร
      options: ["มือถือ", "แท็บเล็ต", "คอมพิวเตอร์"]
    validations:
      required: true
  - type: textarea
    id: screenshot
    attributes:
      label: รูปหน้าจอ (ลากรูปมาวางได้)
```

ทุกช่องมีเหตุผล: **ขั้นตอน** ให้เรา[ทำซ้ำ](/glossary#repro)ได้ (ทำซ้ำไม่ได้ = แก้ไม่ได้), **คาด vs จริง** บางทีระบบทำถูกแต่ผู้ใช้เข้าใจต่าง, **เวลา** ใช้ค้น log (Vercel แผนฟรีเก็บ log แค่ 1 ชั่วโมง ยิ่งแจ้งเร็วยิ่งดี), **อุปกรณ์** บั๊กจำนวนมากเกิดเฉพาะมือถือ

**ควรเห็น:** push ไฟล์ขึ้น `main` แล้วกด **New issue** บน GitHub จะมีตัวเลือก "รายงานบั๊ก" กดแล้วได้ฟอร์มที่ช่องมีดอกจันสีแดง ส่งโดยเว้นช่องบังคับไม่ได้ ชื่อเรื่องขึ้นต้นด้วย `[บั๊ก]` และติดป้าย `bug` ให้เอง

ผู้ใช้ทั่วไป (บรรณารักษ์) ไม่มีบัญชี GitHub ก็ไม่เป็นไร เขาแจ้งทาง LINE หรือฟอร์มติดต่อตามปกติ **เราเป็นคนเปิด issue ให้** โดยถามข้อมูลตามช่องในฟอร์มนี้กลับไป ฟอร์มจึงเป็นทั้งที่จดและรายการคำถามที่ต้องถาม

### 2. จัดลำดับ: อะไรก่อน

ทุก issue ใหม่ ติด label ระดับ 1 อัน (label = ป้ายสีบน issue ไว้กรองและจัดกลุ่ม สร้างครั้งแรกที่ Issues → **Labels** → **New label**):

| ป้าย | เมื่อไร | ตัวอย่างในห้องสมุด | ทำเมื่อไร |
|---|---|---|---|
| 🔴 ต้องแก้ทันที | ใช้งานหลักไม่ได้ ข้อมูลผิด/หาย หรือไม่ปลอดภัย | ยืมไม่ได้ทั้งระบบ, ใครก็เข้าหลังบ้านได้ | วันนี้ หยุดงานอื่น |
| 🟠 ควรแก้ | ใช้ได้แต่ผิดหรือลำบาก มีทางเลี่ยง | รายการเกินกำหนดเรียงผิด, ปุ่มบนมือถือกดยาก | รอบนี้หรือรอบหน้า |
| ⚪ เก็บกวาด | ไม่กระทบการใช้งาน | ตัวสะกดผิด, สีไม่ตรง brief | ว่างเมื่อไรค่อยทำ |

ส่วน**คำขอของใหม่** (ป้าย `enhancement`) เช่น "อยากให้ส่ง SMS เตือน" **ไม่ใช่บั๊ก** อย่าเริ่มทำทันที ให้วนกลับไปขั้น 1: เขียนเป็น [user story](/learn/cards/user-stories) แล้วถามพี่เลี้ยงหรือลูกค้าว่าอยู่ใน[ขอบเขต](/learn/cards/scope-questions)ไหม ถ้าอยู่ ค่อยใส่แผนแบบ[แบ่งงานครึ่งวัน](/learn/cards/task-breakdown)

### 3. แก้แล้วปิดงาน และแจ้งกลับ

เขียนเลข issue ใน commit ที่แก้ แล้ว GitHub จะผูกกันให้ และปิด issue เองเมื่อ commit นั้นเข้า branch หลัก:

```bash
git commit -m "fix: ปุ่มคืนหนังสือบนมือถือสูง 44px (fixes #12)"
```

คำว่า `fixes #12` (หรือ `closes #12`) คือคำสั่งให้ปิด issue หมายเลข 12 ถ้าเขียนแค่ `#12` จะผูกลิงก์แต่ไม่ปิด (ใช้ตอนแก้ไปบางส่วน)

**ควรเห็น:** หลัง merge เข้า `main` issue #12 เปลี่ยนเป็น **Closed** และในหน้า issue มีบรรทัดบอกว่าปิดด้วย commit ไหน จากนั้น**บอกคนที่แจ้ง**ว่าแก้แล้ว ขอให้ลองใหม่ คนที่ได้ยินว่าเรื่องที่บอกถูกแก้จริง จะบอกเรื่องต่อไปอีก

### 4. วันที่เว็บล่ม: ทำตามลำดับนี้

ตอนเว็บล่มสมองไม่ค่อยทำงาน ลูกค้าโทรตาม พี่เลี้ยงถาม จึงเขียนขั้นตอนไว้ล่วงหน้า แปะไว้ใน README ส่วน "ดูแลระบบ" (หรือ `docs/incident.md`):

1. **ยืนยัน (2 นาที):** เปิดเว็บจาก 4G ของมือถือ (ไม่ใช่เน็ตออฟฟิศ) และเปิด `/api/health` ดูว่าพังที่ชั้นไหน ([การ์ด Log](/learn/cards/log-monitoring) ทริคข้อ 1) จดเวลาที่เริ่มพัง
2. **แจ้ง (5 นาที):** บอกพี่เลี้ยงและลูกค้าก่อนเริ่มแก้ ข้อความสั้นๆ: "ระบบยืมคืนใช้ไม่ได้ตั้งแต่ 14:05 กำลังตรวจ จะแจ้งอีกครั้งภายใน 30 นาที" ลูกค้ารับได้ถ้ารู้ว่ามีคนดูอยู่ ที่รับไม่ได้คือเงียบ
3. **หยุดความเสียหายก่อน แก้ทีหลัง:** ถ้าเพิ่ง deploy แล้วพัง ให้[ย้อนกลับ](/glossary#rollback)ทันที (VPS: `git checkout` ไปที่ git tag ของรุ่นก่อน ตามการ์ด VPS ข้อ 7 · Vercel: Instant Rollback) ถ้าข้อมูลหาย กู้จาก backup ([การ์ด Backup](/learn/cards/backup-restore)) **อย่าแก้โค้ดสดบนเว็บจริงใต้ความกดดัน**
4. **แก้จริง:** เว็บกลับมาแล้วค่อยหาต้นเหตุจาก log อย่างใจเย็น บน branch ปกติ ทดสอบ แล้วขึ้นใหม่
5. **สรุป 5 บรรทัด (วันเดียวกัน):** เปิด issue ป้าย 🔴 ใส่ตามนี้ แล้วแจ้งลูกค้าว่าจบแล้ว

```text
เกิดอะไร:   ระบบยืมคืนตอบ 500 ทุกคำขอ 14:05–14:40 (35 นาที)
ต้นเหตุ:     migration ลบคอลัมน์ due_at ที่โค้ดรุ่นเก่ายังใช้อยู่
แก้ยังไง:   ย้อนโค้ด 14:20, เพิ่มคอลัมน์กลับและกู้ข้อมูลจาก backup ตี 2 เสร็จ 14:40
ข้อมูลหาย:  การยืม 3 รายการระหว่าง 02:00–14:05 บรรณารักษ์บันทึกใหม่ให้แล้ว
กันไม่ให้เกิดอีก: migration ใหม่ทุกตัวต้องเป็นแบบ "เพิ่ม" และ backup ก่อน migrate
```

ข้อ "กันไม่ให้เกิดอีก" สำคัญที่สุด สรุปนี้ไม่ใช่การหาคนผิด แต่หาว่า**ระบบหรือขั้นตอน**ตรงไหนที่ปล่อยให้เกิดได้

## ทริคที่แนะนำ

1. **1 เรื่อง 1 issue:** "ปุ่มคืนกดยาก และอยากได้ SMS" แยกเป็น 2 ใบเสมอ ใบหนึ่งเป็นบั๊ก อีกใบเป็นของใหม่ ถ้ารวมกัน แก้ข้อแรกเสร็จก็ปิดไม่ได้เพราะข้อสองยังค้าง
2. **ถามกลับทันทีที่ได้เรื่อง:** ข้อมูลที่ขาด (เวลา อุปกรณ์ ขั้นตอน) ถามวันนั้นยังจำได้ ถามสัปดาห์หน้าเขาลืมแล้ว และ log ก็หายแล้ว
3. **บั๊กที่เจอซ้ำ = เทสต์ที่ขาด:** แก้บั๊กแล้วเพิ่มเทสต์ 1 ข้อที่จะพังถ้าบั๊กนี้กลับมา ([การ์ดเทสต์อัตโนมัติ](/learn/cards/unit-testing)) บั๊กเดิมจะไม่กลับมาโดยไม่มีใครรู้ (เรียกว่า [regression](/glossary#regression))

## ปรับไปใช้จริง

**ในโจทย์ฝึกงาน** (ตัวอย่างจาก STARTER)**:** หลังบ้านของ STARTER มีหน้าข้อความติดต่อที่เปลี่ยนเป็น "อ่านแล้ว" เมื่อเปิดดู ([Requirement หน้า 6](/api/files/requirement.pdf?sec=admin-detail) ต้อง login) นี่คือช่องรับ feedback ของลูกค้าร้าน ส่วน Bonus "แจ้งเตือนเข้า LINE หรืออีเมลเมื่อมีข้อความติดต่อใหม่" ([หน้า 13](/api/files/requirement.pdf?sec=bonus)) คือการทำให้เรื่องไม่ค้างในกล่องโดยไม่มีใครเห็น (โจทย์อื่นใช้ส่วนที่เทียบกันได้) ระหว่างฝึกงาน ผู้ใช้คนแรกคือ**เพื่อนที่ทดสอบงานเรา**และพี่เลี้ยงตอน Review ให้จดทุกข้อที่เขาเจอเป็น issue ติดป้ายระดับ แล้วปิดด้วย `fixes #` ก่อนส่งงาน พี่เลี้ยงจะเห็นว่าเรื่องไหนแก้แล้ว เรื่องไหนตั้งใจไม่ทำเพราะอะไร

**เว็บคู่มือนี้:** น้องแจ้งปัญหาและขอเนื้อหาผ่านปุ่ม "ถามพี่เลี้ยง" และ "ขอเนื้อหาเพิ่ม" คำขอเนื้อหาเข้าบอร์ดในหลังบ้านที่มีสถานะ (ใหม่ → รับเรื่อง → กำลังทำ → เสร็จ หรือไม่ทำ) และแจ้งเตือนกลับหาน้องทุกครั้งที่พี่เลี้ยงตอบหรือเปลี่ยนสถานะ ([thread.service.ts](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/server/services/thread.service.ts)) หลักเดียวกับการ์ดนี้: ทุกเรื่องเป็น 1 รายการที่ติดตามได้ และคนแจ้งรู้ผลเสมอ ส่วนผลรีวิวงานใช้ป้ายระดับชุดเดียวกับข้อ 2

ลองคิด: บรรณารักษ์ขอ "ปุ่มลบสมาชิก" ฟังดูง่าย แต่สมาชิกที่ยังยืมหนังสือค้างอยู่ล่ะ ก่อนรับเป็นงาน ต้องถามอะไรกลับไปบ้าง

## ตัวเลือกอื่นที่คล้ายกัน

| ทาง | ตัวอย่าง | เหมาะกับ |
|---|---|---|
| issue คู่กับโค้ด (การ์ดนี้) | GitHub Issues, GitLab Issues | ทีมเล็ก งานที่โค้ดอยู่บน GitHub อยู่แล้ว ผูก commit กับ issue ได้ |
| บอร์ดงานเต็มรูปแบบ | Jira, Linear, Trello | ทีมหลายคน มีรอบงาน (sprint) และผู้จัดการโปรเจกต์ |
| รับเรื่องจากผู้ใช้ทั่วไป | ฟอร์มติดต่อในเว็บ, Google Forms, LINE OA | ผู้ใช้ที่ไม่มีบัญชี GitHub แล้วเราจดต่อเป็น issue |
| หน้าแจ้งสถานะระบบ | Better Stack Status Page, UptimeRobot Status Page | ระบบที่มีผู้ใช้เยอะ ให้คนเช็กเองได้ว่าล่มอยู่ไหม ลดสายโทรตาม |

## ลองเอง

**โจทย์:** บรรณารักษ์ส่งข้อความมาในแชทเดียว: "ปุ่มคืนหนังสือในมือถือกดไม่ค่อยติด แล้วก็หน้ารายการเกินกำหนดเรียงชื่อ ไม่ได้เรียงวันที่ อยากให้ส่ง SMS เตือนคนที่เลยกำหนดด้วยค่ะ อ้อ เมื่อเช้าตอนเปิดร้านเข้าระบบไม่ได้ ตอนนี้ได้แล้ว" ให้สร้างฟอร์มรายงานบั๊กตามข้อ 1 ใน repo ของเรา แล้วเปิด issue จากข้อความนี้ให้ครบทุกเรื่อง ติดป้ายระดับ และเขียนข้อความตอบบรรณารักษ์ 1 ข้อความ

<Hint level={1}>ในข้อความมีกี่เรื่อง? นับให้ครบก่อนเปิด issue (ทริคข้อ 1) และแยกว่าเรื่องไหนเป็นบั๊ก เรื่องไหนเป็นของใหม่</Hint>
<Hint level={2}>เรื่อง "เมื่อเช้าเข้าไม่ได้" ข้อมูลไม่พอให้ทำซ้ำ ต้องถามอะไรกลับ (ดูช่องในฟอร์มข้อ 1) และควรไปดูอะไรของเราเองก่อนถาม (monitor ส่งอีเมลไหม, log ช่วงเช้ายังอยู่ไหม) ส่วน SMS ไม่ต้องติดป้ายระดับ ติด `enhancement` แล้วเขียนเป็น user story</Hint>
<Hint level={3}>ตรวจผล: ต้องได้ 4 issue: บั๊กปุ่มคืนบนมือถือ (🟠 มีทางเลี่ยงคือใช้คอมพิวเตอร์), บั๊กการเรียง (🟠), เข้าระบบไม่ได้ตอนเช้า (ระดับขึ้นกับข้อมูลที่ถามกลับ ถ้ายังเกิดซ้ำทุกเช้า = 🔴) และคำขอ SMS (`enhancement` พร้อม user story) ข้อความตอบบรรณารักษ์ต้องบอกว่าได้รับกี่เรื่อง ถามข้อมูลที่ขาดของเรื่องเข้าระบบไม่ได้ และบอกตรงๆ ว่าเรื่อง SMS ต้องคุยขอบเขตก่อน ไม่ใช่ตอบ "รับทราบครับ" คำเดียว</Hint>
