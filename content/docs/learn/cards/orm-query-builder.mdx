## ความหมาย

เครื่องมือที่ให้โค้ด TypeScript คุยกับฐานข้อมูล มี 3 ระดับ ยิ่งสูงยิ่งเขียนน้อย แต่ยิ่งมองไม่เห็นว่าข้างล่างเกิดอะไร

| ระดับ | เขียนแบบไหน | นึกภาพ |
|---|---|---|
| [Driver](/glossary#driver) | พิมพ์ SQL เป็นข้อความเอง | เขียนจดหมายภาษาต่างประเทศเองทุกคำ |
| [Query Builder](/glossary#query-builder) | เรียกฟังก์ชันหน้าตาคล้าย SQL แล้วมันประกอบ SQL ให้ | กรอกแบบฟอร์มที่มีช่องให้เติม |
| [ORM](/glossary#orm) | มองตารางเป็น object เรียกต่อกันได้ | บอกเลขาว่าอยากได้อะไร เลขาไปจัดการเอง |

ในงาน Todo ที่ผ่านมา **Prisma คือ ORM** ส่วนงาน STARTER ใช้ **Drizzle** ซึ่งอยู่ระหว่าง Query Builder กับ ORM

## ที่มา

การพิมพ์ SQL เป็นข้อความในโค้ดมีปัญหา 3 อย่าง: พิมพ์ชื่อคอลัมน์ผิดก็รู้ตอนรัน, editor ช่วยเติมคำไม่ได้ และถ้าเอาข้อความจากผู้ใช้ไปต่อเป็นคำสั่งผิดวิธี จะโดน [SQL Injection](/glossary#sql-injection) จึงเกิด ORM ตั้งแต่ต้นทศวรรษ 2000 ส่วนเครื่องมือรุ่นใหม่ยุค TypeScript เน้นให้ **[type](/glossary#type) ในโค้ดตรงกับตารางจริง** พิมพ์ผิดก็เห็นตั้งแต่ตอนเขียน

## การใช้งาน

งานเดียวกัน "หาหนังสือเล่มที่ id = 5" เขียนได้ 3 แบบ (ดูความต่างก่อน ยังไม่ต้องรัน การ์ดถัดไปพาตั้งค่า Drizzle ทีละขั้น)

```ts
// Driver (pg): SQL เป็นข้อความ ค่าแยกส่งด้วย $1 กัน SQL Injection
await pool.query("SELECT * FROM books WHERE id = $1", [5]);

// Drizzle แบบ Query Builder (ส่วนที่ทีมใช้): หน้าตาเหมือน SQL แต่เป็นฟังก์ชันที่มี type
await db.select().from(books).where(eq(books.id, 5));

// ORM (Prisma ที่ใช้ในงาน Todo): บอกสิ่งที่อยากได้เป็น object
await prisma.book.findUnique({ where: { id: 5 } });
```

ทั้งสามแบบสุดท้ายส่ง SQL หน้าตาเดียวกันไปที่ฐานข้อมูล: `SELECT ... FROM books WHERE id = 5`

| เทียบ | Prisma (งาน Todo) | Drizzle (งาน STARTER) |
|---|---|---|
| ประกาศตาราง | ไฟล์ `schema.prisma` ภาษาของ Prisma เอง | ไฟล์ `schema.ts` เป็น TypeScript ธรรมดา |
| ก่อนใช้งาน | ต้องรัน `prisma generate` สร้างโค้ด | ไม่ต้องสร้างโค้ด type มาจาก schema ทันที |
| หน้าตาคำสั่ง | `findMany({ where })` | `select().from().where()` ใกล้ SQL |

## ทริคที่แนะนำ

1. **เข้าใจ SQL ก่อนใช้เครื่องมือ** เครื่องมือแค่ช่วยเขียน เวลาช้าหรือผิดต้องกลับไปดู SQL ที่มันสร้าง
2. **เปิด log ดู SQL ที่ส่งจริงตอนพัฒนา** (Drizzle: `drizzle(url, { logger: true })`) จะเห็นว่าคำสั่งสั้นๆ อาจกลายเป็น SQL หลายคำสั่ง
3. **ระวังปัญหา [N+1](/glossary#n-plus-one):** ดึงรายการ 100 แถว แล้ววนดึงข้อมูลที่โยงกันทีละแถว = ยิงฐานข้อมูล 101 ครั้ง ให้ดึงพร้อมกันด้วย `JOIN` แทน

## ปรับไปใช้จริง

**ในงาน STARTER:** Requirement เขียนไว้ว่า "จาก Prisma → Drizzle ORM (ได้เห็นว่า ORM คนละตัวคิดต่างกันยังไง)" ตอน review วันที่ 5 ให้เตรียมตอบได้ว่า schema ของ Drizzle ต่างจาก Prisma ตรงไหน (ใช้ตารางเทียบข้างบนเป็นจุดเริ่ม)

ลองคิด: ถ้าทีมหนึ่งใช้ Prisma อีกทีมใช้ Drizzle คนที่ "รู้ SQL" ย้ายทีมได้ง่ายกว่าคนที่ "รู้แค่เครื่องมือ" เพราะอะไร

## ลองเอง

**โจทย์:** เปิดโปรเจกต์ Todo ของตัวเอง เลือกคำสั่ง Prisma มา 3 จุด (หาทั้งหมด, หาตาม id, เพิ่ม) แล้วเขียนว่าแต่ละจุดส่ง SQL อะไรไปที่ฐานข้อมูล

<Hint level={1}>`findMany` = `SELECT` หลายแถว, `findUnique` = `SELECT ... WHERE` แถวเดียว, `create` = `INSERT`</Hint>
<Hint level={2}>ตรวจคำตอบได้จริง: เปิด log ของ Prisma ด้วย `new PrismaClient({ log: ["query"] })` แล้วรันโปรเจกต์ SQL ที่ส่งจริงจะขึ้นใน Terminal</Hint>
<Hint level={3}>เทียบ SQL ที่เดากับที่ log ขึ้นทีละจุด ตรงไหนต่างกัน (เช่น Prisma เลือกทุกคอลัมน์ทีละชื่อ ไม่ใช่ `*`) จดไว้ เป็นคำตอบที่ดีตอนพี่เลี้ยงถาม</Hint>
