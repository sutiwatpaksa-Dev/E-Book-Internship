## ความหมาย

**[HTTP](/glossary#http)** คือภาษาที่หน้าเว็บกับ [server](/glossary#server) ใช้คุยกัน ทุกครั้งเป็นคู่ **คำขอ (request) → คำตอบ (response)**

**นึกภาพ:** สั่งอาหารในร้าน ลูกค้า (หน้าเว็บ) ยื่นใบสั่ง (request) บอกว่าอยากได้อะไร พนักงาน (server) ส่งอาหารกลับมาพร้อมบอกผล (response) เช่น "ได้แล้วครับ" หรือ "เมนูนี้หมด"

**[REST](/glossary#rest)** คือวิธีตั้งชื่อ [API](/glossary#api) ให้คนอื่นเดาได้: ให้ URL เป็น **สิ่งของ** (คำนาม) แล้วใช้ **[method](/glossary#method)** ของ HTTP เป็น **คำกริยา**

| อยากทำ | method + URL | ตอบเมื่อสำเร็จ |
|---|---|---|
| ดูหนังสือทั้งหมด | `GET /api/books` | `200` + รายการ |
| ดูเล่มเดียว | `GET /api/books/7` | `200` + หนังสือ |
| เพิ่มหนังสือ | `POST /api/books` | `201` + หนังสือที่สร้าง |
| แก้บางช่อง | `PATCH /api/books/7` | `200` + หนังสือที่แก้แล้ว |
| ลบ | `DELETE /api/books/7` | `200` |

## ที่มา

ถ้าไม่มีแบบแผน ทุกคนตั้งชื่อเอง: `/getBook`, `/book_list`, `/deleteBookById?id=7` คนเรียกต้องเปิดเอกสารทุกครั้ง REST มาจากวิทยานิพนธ์ของ Roy Fielding (ปี 2000) ที่อธิบายว่าเว็บใหญ่โตได้เพราะทุกอย่างมี "ที่อยู่" และใช้คำกริยาชุดเดียวกัน พอทุกทีมทำแบบเดียวกัน เห็น `POST /api/loans` ก็เดาได้ทันทีว่าคือ "สร้างการยืม"

## การใช้งาน

**คำขอ** มี 4 ส่วน

```http
POST /api/books?draft=1 HTTP/1.1      ← method + path + query (?ตัวกรอง)
Content-Type: application/json         ← header: บอกว่า body เป็น JSON

{ "title": "เจ้าชายน้อย" }              ← body: ข้อมูลที่ส่งไป
```

**คำตอบ** บอกผลด้วย **[status code](/glossary#status-code)** ตัวเลขหลักแรกบอกว่าเป็นความผิดของใคร

| กลุ่ม | ความหมาย | ที่งาน STARTER ต้องใช้ให้ถูก |
|---|---|---|
| `2xx` | สำเร็จ | `200` ได้แล้ว · `201` สร้างใหม่แล้ว |
| `4xx` | **คนขอ**ส่งมาผิด | `400` ข้อมูลไม่ผ่านการตรวจ · `401` ยังไม่ login · `404` ไม่พบ · `409` ขัดกับของที่มีอยู่ (ซ้ำ, ลบของที่ยังถูกใช้) |
| `5xx` | **server** พังเอง | `500` โค้ดเราพัง |

**รูปแบบ body ของคำตอบ** ต้องเหมือนกันทุก endpoint (ตาม Requirement STARTER) หน้าเว็บจะได้เขียนโค้ดอ่านผลแบบเดียวใช้ได้ทุกที่

```json
{ "success": true, "data": { "id": 7, "title": "เจ้าชายน้อย" } }

{ "success": true, "data": [ ... ], "meta": { "page": 1, "limit": 10, "total": 42 } }

{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "ข้อมูลไม่ถูกต้อง", "details": { } } }
```

## ทริคที่แนะนำ

1. **URL เป็นคำนามพหูพจน์ ไม่มีคำกริยา:** `POST /api/loans` ไม่ใช่ `POST /api/createLoan`
2. **status กับ body ต้องพูดเรื่องเดียวกัน:** ตอบ `200` พร้อม `"success": false` = ผิด เพราะโค้ดหน้าเว็บที่เช็ก `res.ok` จะคิดว่าสำเร็จ ข้อมูลผิดแล้วตอบ `500` ก็ผิด เพราะคนเรียกจะคิดว่า server พัง ไปแก้ผิดที่
3. **`GET` ห้ามเปลี่ยนข้อมูล:** browser และโปรแกรมเก็บข้อมูลเว็บยิง `GET` เองได้ ถ้า `GET /api/books/7/delete` ลบหนังสือได้ สักวันจะมีอะไรไปกดมัน

## ปรับไปใช้จริง

**ในงาน STARTER:** หน้า 7–8 ของ Requirement มีรายการ API ครบทุกตัวแล้ว ลองอ่านทีละบรรทัดแล้วถามว่า "ตัวนี้ทำอะไร กับอะไร" จะเห็นว่าเป็น REST ทั้งหมด เช่น `PATCH /api/admin/services/:id` = แก้บางช่องของบริการเล่มนั้น

**ดูของจริง:** เปิด DevTools (F12) แท็บ Network บนเว็บคู่มือนี้ แล้วกด "เข้าใจการ์ดนี้แล้ว" ท้ายการ์ด จะเห็นคำขอ `PUT /api/progress` วิ่งออกไป (เว็บคู่มือนี้ใช้รูปแบบ body ที่สั้นกว่า Requirement เพราะทำก่อนมี Requirement แต่หลัก REST เหมือนกัน)

ลองคิด: "คืนหนังสือ" ควรเป็น `DELETE /api/loans/7` หรือ `PATCH /api/loans/7` ที่ใส่วันคืน ประวัติการยืมยังต้องใช้ไหม

## ลองเอง

**โจทย์:** ห้องสมุดเพิ่มระบบจองหนังสือล่วงหน้า เขียนรายการ API (ดูเล่มที่จองได้, จอง, ยกเลิกการจอง, ดูการจองของฉัน) เป็น `METHOD /path` พร้อม status ตอนสำเร็จ และ status ตอน "เล่มนี้มีคนจองไปแล้ว"

<Hint level={1}>เริ่มจากหาคำนาม: ระบบนี้มี "ของ" กี่อย่าง แต่ละอย่างคือ URL หนึ่งกลุ่ม</Hint>
<Hint level={2}>"การจอง" เป็นของสิ่งหนึ่ง จอง = สร้างมัน ยกเลิก = ลบหรือเปลี่ยนสถานะมัน ส่วน "ของฉัน" ไม่ต้องมี id ใน URL เพราะ server รู้ว่าเราเป็นใครจากการ login</Hint>
<Hint level={3}>เล่มถูกจองแล้ว ไม่ใช่ server พัง และไม่ใช่ข้อมูลผิดรูปแบบ แต่ "ขัดกับสิ่งที่มีอยู่" ดูตาราง 4xx อีกที</Hint>
