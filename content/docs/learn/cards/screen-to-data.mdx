## ความหมาย

คือการไล่ดู wireframe ทีละชิ้น แล้วถามว่า **"ข้อความหรือปุ่มนี้ เอาข้อมูลมาจากไหน"** ผลที่ได้คือรายการข้อมูลที่ระบบต้องมี แยกเป็น 3 แบบ: **เก็บไว้** (มีคอลัมน์ในตาราง), **คำนวณเอา** (ได้จากข้อมูลที่เก็บไว้แล้ว) และ **ข้อความคงที่ของหน้าจอ** (คำบนปุ่ม ไม่ต้องอยู่ในฐานข้อมูล)

**นึกภาพ:** ดูเมนูร้านอาหารแล้วเขียนรายการวัตถุดิบที่ต้องซื้อ ทุกจานในเมนูต้องมีวัตถุดิบในรายการ ถ้าจานไหนไม่มี แปลว่าลืมซื้อ หรือต้องเอาจานนั้นออกจากเมนู

## ที่มา

ถ้าออกแบบตารางจากความรู้สึก ("ห้องสมุดน่าจะมีชื่อหนังสือ ผู้แต่ง ISBN สำนักพิมพ์...") จะได้ 2 ปัญหาพร้อมกัน: คอลัมน์ที่ไม่มีหน้าจอไหนใช้ (ต้องกรอก seed และดูแลไปเปล่าๆ) และคอลัมน์ที่หน้าจอต้องใช้แต่ลืมสร้าง ซึ่งมักรู้ตัววันที่เขียนหน้าเว็บ ตอนนั้นต้องกลับไปแก้ schema, ทำ migration ใหม่ และแก้ seed การเริ่มจากหน้าจอทำให้ตารางมีเท่าที่ใช้จริง และรู้ตั้งแต่วันที่ 1

## การใช้งาน

**1. ไล่ wireframe ทีละชิ้น แล้วจดลงตาราง** ตัวอย่างจากหน้า `/books` และ `/books/:id` ในการ์ด [Wireframe](/learn/cards/wireframe)

| ชิ้นบนหน้าจอ | ข้อมูล | แบบ | มาจาก |
|---|---|---|---|
| ชื่อหนังสือในแต่ละแถว | `title` | เก็บไว้ | ตาราง `books` |
| ป้าย "ยืมได้ / ถูกยืมอยู่" | ว่างไหม | **คำนวณ** | มีแถวใน `loans` ของเล่มนี้ที่ `returned_at` ยังว่างไหม |
| กดแถวแล้วไปหน้าเล่มนั้น | `id` | เก็บไว้ | `books.id` (ใส่ใน `/books/:id`) |
| ช่องค้นหา | คำที่พิมพ์ | ไม่เก็บ | ส่งเป็น `?q=` ไปถาม API |
| ปุ่ม "ค้น", "ก่อนหน้า", "ถัดไป" | | ข้อความคงที่ | เขียนในโค้ดหน้าจอได้ |
| แท่งเทาบรรทัดที่ 2 ในหน้ารายละเอียด (ตั้งใจให้เป็นผู้แต่ง) | `author` | เก็บไว้ | **ยังไม่มีในตาราง** |

**2. ข้อมูลที่ "คำนวณได้" อย่าเก็บซ้ำ** ป้ายสถานะดูเหมือนต้องมีคอลัมน์ `available` แต่ถ้าเก็บไว้ ทุกครั้งที่ยืมหรือคืน ต้องจำไปแก้คอลัมน์นี้ด้วย ลืมสักครั้ง หนังสือจะ "ถูกยืมอยู่" ตลอดไปทั้งที่คืนแล้ว การ์ด [แบ่งชั้น](/learn/cards/layers) จึงคำนวณ `available` จาก `loans` ทุกครั้งที่ถาม ถามตัวเองทุกคอลัมน์ว่า **"ค่านี้หาได้จากของที่เก็บอยู่แล้วไหม"** ถ้าได้ ไม่ต้องเก็บ

**3. แถวที่ "ยังไม่มี" ต้องตัดสินใจ 1 ใน 2 ทาง** อย่าปล่อยไว้

- เพิ่มคอลัมน์ `author` ในตาราง `books` (ต้องแก้ seed ด้วย) หรือ
- เอาบรรทัดผู้แต่งออกจาก wireframe ถ้าผู้ใช้ไม่ได้ใช้ค้นหรือตัดสินใจจากมัน

ห้องสมุดบิตในการ์ดช่วง Coding เลือกทางที่ 2 เพื่อให้ตารางเล็ก ตารางจึงมีแค่ `id`, `title`, `created_at` ([Drizzle](/learn/cards/drizzle-orm)) ไม่มีทางไหนถูกเสมอ ที่ผิดคือรู้ตัววันที่ 7 ตอนเขียนหน้าเว็บ

**4. รวมเป็นรายการต่อตาราง** เอาคอลัมน์ "มาจาก" มารวมกัน จะได้โครงตารางคร่าวๆ ที่ใช้ต่อในการ์ด [ER diagram](/learn/cards/er-diagram)

| ตาราง | คอลัมน์ | หน้าจอที่ใช้ |
|---|---|---|
| `books` | `id`, `title`, `created_at` (คอลัมน์ "เพิ่มเมื่อ" ที่หลังบ้าน) | `/books`, `/books/:id`, `/admin/books` |
| `loans` | `book_id`, `member_id` (ยืมอยู่กับใคร), `returned_at` (ใช้คำนวณป้าย), `due_at` | ป้ายสถานะ, รายงานเกินกำหนด |
| `members` | `id`, `name` | บันทึกการยืม (story 5) |
| `librarians` | `email`, `password_hash`, `name` | `/admin/login` (story 3) ไม่มีหน้าไหนแสดง `password_hash` แต่ต้องเก็บไว้ตรวจรหัส |

**ควรได้:** ตารางชิ้นบนหน้าจอของทุกหน้าใน wireframe ที่ไม่มีแถวไหนช่อง "มาจาก" ว่าง และรายการต่อตารางที่ทุกคอลัมน์ชี้ได้ว่าหน้าจอไหนใช้

## ทริคที่แนะนำ

1. **ไล่หลังบ้านด้วย ไม่ใช่แค่หน้าบ้าน:** หน้าจัดการมักต้องการข้อมูลที่หน้าบ้านไม่โชว์ เช่น สถานะ "เปิด/ปิดการแสดงผล" หรือ "ลำดับการแสดง" ซึ่งหน้าบ้านใช้แค่กรองและเรียง ไม่ได้แสดงออกมา ถ้าไล่แค่หน้าบ้านจะไม่เจอคอลัมน์พวกนี้
2. **จดด้วยว่าเรียงและกรองด้วยอะไร:** "รายการใหม่สุดก่อน" แปลว่าต้องมี `created_at` ที่เรียงได้ "กรองตามหมวด" แปลว่าต้องมี [foreign key](/glossary#foreign-key) (คอลัมน์ที่เก็บ id ของหมวด) ไปหมวด การเรียงและกรองไม่โผล่เป็นข้อความบนจอ จึงพลาดง่ายที่สุด
3. **ข้อความที่เจ้าของร้านแก้ได้ = ข้อมูล ข้อความที่ไม่มีใครแก้ = โค้ด:** หัวข้อ Hero ที่เจ้าของร้านเปลี่ยนเองได้ต้องอยู่ในฐานข้อมูล แต่คำบนปุ่ม "ส่ง" เขียนในโค้ดได้ ถามทีละข้อความว่า "ใครเปลี่ยนมันได้บ้าง"

## ปรับไปใช้จริง

**ในงาน STARTER:** [Requirement หน้า 4](/api/files/requirement.pdf#page=4) (ต้อง login) บอกว่า "ทุกข้อความ รูป และรายการบนหน้าบ้าน ต้องดึงจาก API ห้าม hardcode (ยกเว้นข้อความ UI เช่น ปุ่ม "ส่ง")" ซึ่งก็คือทริคข้อ 3 Requirement หน้า 7 ให้ตารางขั้นต่ำ 6 ตารางมาแล้ว งานของเราจึงเป็น **การตรวจกลับ**: ไล่ wireframe ทั้ง 3 หน้าและหลังบ้าน แล้วดูว่าทุกชิ้นมีคอลัมน์รองรับ และมีชิ้นไหนที่ธุรกิจของเราต้องการเพิ่ม (Requirement อนุญาตให้เพิ่มฟิลด์ได้ แต่ห้ามตัด) ลองดูตัวอย่าง: "ข้อความติดต่อที่ยังไม่อ่านเป็นตัวหนา" (หน้า 5) ใช้คอลัมน์ `is_read` ของ `contact_messages`

**เว็บคู่มือนี้:** หน้า "ความคืบหน้าของน้อง" ในหลังบ้านพี่เลี้ยงแสดงว่าแต่ละคนผ่านกี่บทแล้ว ตัวเลขนี้ไม่มีคอลัมน์ของตัวเอง แต่นับจากแถวในตาราง `progress` ทุกครั้งที่เปิดหน้า เหตุผลเดียวกับ `available` ของห้องสมุด ดูตารางได้ที่ [server/db/schema.ts บน GitHub](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/server/db/schema.ts)

ลองคิด: Dashboard ของ STARTER ต้องโชว์ "จำนวนข้อความที่ยังไม่อ่าน" (หน้า 5) ควรมีคอลัมน์ `unread_count` ในตาราง `site_settings` ไหม ถ้ามี จะพังได้ตอนไหน

## ตัวเลือกอื่นที่คล้ายกัน

| วิธี | เริ่มจาก | เหมาะกับ |
|---|---|---|
| **จากหน้าจอ (การ์ดนี้)** | wireframe ทีละชิ้น | เว็บที่หน้าจอชัดแล้ว เช่น STARTER |
| จากคำนามใน story | ขีดเส้นใต้คำนามใน user story (สมาชิก, หนังสือ, การยืม) แล้วทำเป็นตาราง | ตอนยังไม่มีหน้าจอ ได้ภาพรวมเร็วแต่มักได้คอลัมน์เกิน |
| จากข้อมูลเดิมของลูกค้า | ไฟล์ Excel หรือสมุดที่ลูกค้าใช้อยู่ | งานที่ย้ายระบบเก่า ต้องเก็บทุกอย่างที่มีอยู่แล้ว |

## ลองเอง

**โจทย์:** ทำตาราง "ชิ้นบนหน้าจอ → ข้อมูล" ของหน้า Home และ `/admin/services` ในงาน STARTER จาก wireframe ที่วาดในโจทย์ของการ์ด Wireframe แล้วเทียบกับตารางในหน้า 7 ของ Requirement

<Hint level={1}>เริ่มจาก Hero: หัวข้อใหญ่, ข้อความรอง, รูปพื้นหลัง, ปุ่ม แต่ละชิ้นถามว่า "เจ้าของร้านแก้ได้ไหม" ถ้าได้ ต้องอยู่ในฐานข้อมูล แล้วหาว่าอยู่ตารางไหนในหน้า 7</Hint>
<Hint level={2}>"บริการเด่น 3 รายการ" บนหน้า Home ไม่ได้แปลว่ามีตารางบริการเด่นแยก ลองหาคอลัมน์ใน `services` ที่ทำให้เลือกได้ว่ารายการไหนเด่น และคอลัมน์ที่บอกลำดับ ส่วนตาราง `/admin/services` ที่ "กรองตามหมวด" ต้องใช้คอลัมน์ไหน</Hint>
<Hint level={3}>ตรวจก่อนส่ง: ไม่มีแถวไหนที่ช่อง "มาจาก" ว่าง, ทุกค่าที่ "คำนวณ" เขียนได้ว่าคำนวณจากอะไร, ไม่มีคอลัมน์ที่เก็บค่าที่คำนวณได้ และทุกคอลัมน์ที่เพิ่มเกินหน้า 7 มีเหตุผลจาก brief ของตัวเอง</Hint>
