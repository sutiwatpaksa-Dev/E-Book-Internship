## ความหมาย

หน้าเว็บขอข้อมูลจาก API ด้วย `fetch` ระหว่างรอและเมื่อได้ผล หน้าจอต้องมี **3 สถานะเสมอ: [กำลังโหลด](/glossary#loading-state) / โหลดพัง / สำเร็จ** และโค้ดเรียก API อยู่ใน **ไฟล์กลางที่เดียว** ไม่กระจายอยู่ในทุกชิ้นส่วน

**นึกภาพ:** สั่งอาหารผ่านแอป หน้าจอบอกตลอดว่า "กำลังเตรียม" "ส่งไม่ได้ ร้านปิด" หรือ "ถึงแล้ว" ถ้าหน้าจอนิ่งเฉยๆ เราจะกดสั่งซ้ำ หรือคิดว่าแอปพัง

จับคู่: "กำลังเตรียม" = สถานะกำลังโหลด · "ส่งไม่ได้ ร้านปิด" = สถานะโหลดพัง · "ถึงแล้ว" = สถานะสำเร็จ · ตัวแอปที่คุยกับร้านให้ = ไฟล์กลาง `src/api/client.ts`

```text
ชิ้นส่วนหน้า /books
   │ เรียกฟังก์ชันในไฟล์กลาง
   ▼
src/api/client.ts
   │ fetch("/api/books")
   ▼
server
   │
   ├──► ยังไม่ตอบ
   │    แสดง "กำลังโหลด..."
   ├──► ตอบ error หรือติดต่อไม่ได้
   │    แสดงข้อความ + ปุ่มลองใหม่
   └──► ได้ข้อมูล
        แสดงรายการ
```

จุดที่ไม่ตรง: แอปสั่งอาหารบอกสถานะให้เอง แต่ `fetch` ไม่บอก ต้องเขียนเองว่าตอนนี้อยู่สถานะไหน และ `fetch` ถือว่า server ตอบ `404` หรือ `500` เป็น "สำเร็จ" ด้วย (เพราะติดต่อได้) ไฟล์กลางจึงต้องดูผลเองแล้วโยน error (ข้อ 1)

## ที่มา

บนเครื่องเรา API ตอบใน 5 มิลลิวินาที เลยลืมทำหน้า "กำลังโหลด" พอขึ้นเว็บจริงและผู้ใช้อยู่บนเน็ตมือถือ หน้าจอว่างเปล่า 3 วินาที คนคิดว่าเว็บพัง หรือ API ตอบ error แล้วหน้าเว็บขาวทั้งหน้า ส่วนการเขียน `fetch` ทุกชิ้นส่วน พอวันหนึ่งต้องเพิ่ม header หรือเปลี่ยนที่อยู่ API ต้องตามแก้ทุกไฟล์

## การใช้งาน

### ตั้งค่าครั้งแรก: ให้หน้าเว็บคุยกับ API ได้ (proxy)

ตอนพัฒนามี 2 โปรแกรมรันพร้อมกัน: หน้าเว็บ (Vite, port 5173) และ API (Hono, port 3000) ต่างคน "ต่างบ้าน" browser จะไม่ยอมให้หน้าเว็บอ่านคำตอบจากบ้านอื่นง่ายๆ (เรื่อง [CORS](/glossary#cors)) วิธีที่ง่ายที่สุดคือให้ Vite เป็นคนกลาง ([proxy](/glossary#proxy-dev)): หน้าเว็บขอ `/api/...` ที่ Vite แล้ว Vite ส่งต่อให้ Hono

เพิ่ม `server` ใน `client/vite.config.ts` แล้วรีสตาร์ท `bun run dev`

```ts
export default defineConfig({
  plugins: [react(), tailwindcss()],
  server: {
    proxy: { "/api": "http://localhost:3000" },   // คำขอที่ขึ้นต้นด้วย /api ส่งต่อให้ server
  },
});
```

**ควรเห็น:** เปิด server ไว้ (`bun run dev` ใน `server/`) แล้วเปิด `http://localhost:5173/api/books` ได้ JSON เดียวกับเปิดที่ port 3000

### 1. ชั้นเรียก API อยู่ไฟล์เดียว

รู้จัก URL, รูปแบบคำตอบ `{ success, data }` / `{ success: false, error }` (ดูการ์ด [HTTP และ REST](/learn/cards/http-rest)) และการส่ง cookie

```ts
// src/api/client.ts
type ApiResponse<T> =
  | { success: true; data: T }
  | { success: false; error: { code: string; message: string; details?: Record<string, string[]> } };

export class ApiError extends Error {
  status: number;                                // status จาก server เช่น 401 = ยังไม่ได้ login
  details?: Record<string, string[]>;            // error รายช่องจาก Zod ใช้ในการ์ดฟอร์ม
  constructor(message: string, status: number, details?: Record<string, string[]>) {
    super(message);
    this.status = status;
    this.details = details;
  }
}

export async function request<T>(path: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(`/api${path}`, { credentials: "same-origin", ...init });
  const body = (await res.json().catch(() => null)) as ApiResponse<T> | null;
  if (!body) throw new ApiError(`ผิดพลาด (${res.status})`, res.status);   // ไม่ได้ JSON กลับมา เช่น server ดับ
  if (!body.success) throw new ApiError(body.error.message, res.status, body.error.details);
  return body.data;                                                   // ชิ้นส่วนได้แค่ data ไม่ต้องแกะเอง
}

export const jsonBody = (method: string, data: unknown): RequestInit => ({
  method,
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(data),
});
```

อ่านทีละส่วน (syntax ใหม่ของ TypeScript ทบทวนพื้นฐานได้ที่[บท TypeScript](/04-typescript)):

- **`<T>`** (generic) คือช่องว่างของ type ที่คนเรียกเติมเอง `request<Book[]>("/books")` แปลว่า "data ที่ได้คือ `Book[]`" ฟังก์ชันเดียวจึงใช้ได้ทุก endpoint และ editor ยังรู้ type ของผล
- **`ApiResponse<T>`** บอกว่าคำตอบมีได้ 2 หน้าตา (`|` = หรือ) พอเช็ก `body.success` แล้ว TypeScript รู้เองว่าเป็นแบบไหน จึงอ่าน `body.data` หรือ `body.error` ได้ถูกตัว
- **`class ApiError extends Error`** สร้าง error ชนิดใหม่ที่เป็น `Error` ทุกอย่าง (`throw` / `catch` ได้ปกติ) แต่มีช่อง `status` (เลข status ของคำตอบ ใช้แยกว่า "ยังไม่ได้ login" กับ "server ดับ") และ `details` เพิ่ม ส่วน `super(message)` คือเรียกตัวสร้างของ `Error` ให้ตั้งข้อความก่อน แล้วค่อยเก็บของเราเพิ่ม
- **`as ApiResponse<T> | null`** บอก TypeScript ว่า "เชื่อเถอะ JSON นี้หน้าตาแบบนี้" เพราะ TypeScript ตรวจของที่มาจาก server ตอนรันไม่ได้ เราจึงรับรองเอง

```ts
// src/api/books.api.ts · ไฟล์ละเรื่อง
import type { Book } from "../types/book";
import { jsonBody, request } from "./client";

export const booksApi = {
  list: () => request<Book[]>("/books"),
  get: (id: number) => request<Book>(`/books/${id}`),
  create: (data: { title: string }) => request<Book>("/books", jsonBody("POST", data)),
};
```

### 2. ชิ้นส่วนสนใจแค่ 3 สถานะ

แก้ `src/pages/books-page.tsx` จากการ์ด Component ให้ดึงเองแทนรับ props

```tsx
import { useEffect, useState } from "react";
import { booksApi } from "../api/books.api";
import { BookCard } from "../components/book-card";
import type { Book } from "../types/book";

export function BooksPage() {
  const [books, setBooks] = useState<Book[] | null>(null);    // null = ยังโหลดไม่เสร็จ
  const [error, setError] = useState("");

  useEffect(() => {
    let ignore = false;                       // ออกจากหน้าก่อนโหลดเสร็จ → ไม่ต้องอัปเดตแล้ว
    booksApi.list()
      .then((list) => !ignore && setBooks(list))
      .catch((e: Error) => !ignore && setError(e.message));
    return () => { ignore = true; };
  }, []);

  if (error) return <p role="alert">โหลดไม่สำเร็จ: {error}</p>;
  if (!books) return <p>กำลังโหลด...</p>;
  if (books.length === 0) return <p>ยังไม่มีหนังสือ</p>;
  return (
    <ul className="grid grid-cols-1 gap-4 md:grid-cols-2">
      {books.map((b) => <li key={b.id}><BookCard book={b} /></li>)}
    </ul>
  );
}
```

แล้วใน `App.tsx` เปลี่ยนเป็น `<BooksPage />` (ไม่ต้องส่ง `books` แล้ว ลบ array ตายตัวทิ้ง)

**ควรเห็น:** แวบหนึ่งขึ้น "กำลังโหลด..." แล้วเป็นรายการหนังสือจากฐานข้อมูลจริง ลองปิด server แล้วรีเฟรช ต้องเห็นข้อความ "โหลดไม่สำเร็จ"

## ทริคที่แนะนำ

1. **ลองช้าและลองพังทุกครั้ง:** DevTools → Network → เลือก **Slow 4G** แล้วรีเฟรช ต้องเห็น "กำลังโหลด" ลองปิด API แล้วรีเฟรช ต้องเห็นข้อความ error ไม่ใช่หน้าขาว
2. **"ว่าง" เป็นสถานะที่ 4 ที่ลืมบ่อย** รายการว่างควรบอกว่าทำอะไรต่อได้ ("ยังไม่มีหนังสือ เพิ่มเล่มแรก") ไม่ใช่พื้นที่ว่างเปล่า
3. **ใช้ข้อความ error จาก API ตรงๆ** API ที่ทำตามการ์ด[จัดการ error](/learn/cards/error-handling) ส่ง `error.message` ภาษาไทยที่บอกว่าต้องทำอะไรมาแล้ว ไม่ต้องเขียนข้อความใหม่ฝั่งหน้าเว็บ

## ปรับไปใช้จริง

**ในโจทย์ฝึกงาน** (ตัวอย่างจาก STARTER)**:** Requirement ให้มีโฟลเดอร์ `client/src/api/` ("fetch wrapper") ตรงกับไฟล์ `client.ts` ข้างบน และเกณฑ์ Frontend ข้อ "Loading/Error state ครบทุกหน้า" มี 15 คะแนน หน้าไหนขาวตอนโหลดหรือตอน API พัง เสียคะแนนทันที ส่วน `credentials` ที่ใส่ไว้ จะได้ใช้ในช่วง Login ตอน cookie ต้องติดไปกับทุกคำขอ

**เว็บคู่มือนี้:** มีกติกาว่า **component ไม่เรียก `fetch` เอง** ทุกคำขอผ่าน [src/api/client.ts](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/src/api/client.ts) + ไฟล์แยกตามเรื่อง (เว็บนี้อ่าน error แบบสั้น `body.error` เพราะทำก่อนมี Requirement)

ลองคิด: ปุ่มที่กดแล้วส่งคำขอ (เช่น "ยืม") ต้องมีสถานะอะไรบ้างระหว่างรอ และถ้าผู้ใช้กดรัวๆ จะเกิดอะไร

## ตัวเลือกอื่นที่คล้ายกัน

| วิธี | ช่วยอะไรเพิ่ม | ระดับ |
|---|---|---|
| **`fetch` + `useEffect` + ชั้น `src/api/` (ทีมใช้)** | ไม่ต้องติดตั้งเพิ่ม เห็นทุกขั้น | ใช้ทุกงาน |
| TanStack Query | เก็บผลไว้ใช้ซ้ำ ดึงใหม่เอง ลองใหม่เมื่อพัง | ควรรู้จัก เมื่อหน้าเว็บดึงข้อมูลหลายจุด |
| SWR | แนวเดียวกับ TanStack Query ตัวเล็กกว่า | รู้ว่ามี |
| ดึงฝั่ง server (Next.js Server Component, loader ของ React Router) | ข้อมูลมาพร้อมหน้าแรก ไม่ต้องมีหน้า "กำลังโหลด" ตอนเปิด | รู้ว่ามี |

## ลองเอง

**โจทย์:** เพิ่มปุ่ม "ลบ" ในกล่องหนังสือแต่ละเล่ม ที่เรียก `DELETE /api/books/:id` (จากโจทย์ข้อ 2 ของการ์ด [แบ่งชั้น](/learn/cards/layers)) ระหว่างส่ง ปุ่มกดซ้ำไม่ได้ ลบสำเร็จแล้วเล่มนั้นหายจากรายการ ลบไม่สำเร็จต้องเห็นข้อความจาก API

<Hint level={1}>เพิ่มฟังก์ชัน `remove` ใน `books.api.ts` ก่อน ลองเรียกจาก Console ของ browser ให้ได้ผลก่อนไปทำหน้าจอ (ใช้ `jsonBody` ไม่ได้เพราะไม่มี body ส่งแค่ `{ method: "DELETE" }`)</Hint>
<Hint level={2}>ปุ่มต้องรู้ว่า "กำลังส่ง" อยู่ไหม นั่นคือ state อีกตัว ใช้คู่กับ `disabled` ส่วนการลบเกิดเพราะผู้ใช้กด จึงอยู่ใน `onClick` ไม่ใช่ `useEffect`</Hint>
<Hint level={3}>หลังลบสำเร็จมี 2 ทาง: ดึงรายการใหม่ทั้งหมด หรือกรองเล่มนั้นออกจาก state เอง ลองคิดว่าทางไหนพลาดยากกว่าถ้ามีคนอื่นเพิ่มหนังสือพร้อมกัน</Hint>
