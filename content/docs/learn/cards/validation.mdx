## ความหมาย

ทุกอย่างที่ส่งเข้ามาทาง API **เชื่อไม่ได้** จนกว่าจะตรวจ [Zod](/glossary#zod) ให้เราเขียน **[schema](/glossary#schema-zod)** บอกว่าข้อมูลควรหน้าตาแบบไหน แล้วเอาข้อมูลจริงไปเทียบ ผ่านแล้วได้ข้อมูลที่สะอาดพร้อม type ไม่ผ่านก็ได้รายการว่าผิดช่องไหน

**นึกภาพ:** พนักงานตรวจรับของหน้าโกดัง ถือใบรายการ (schema) เทียบของที่มาส่งทีละช่อง ของไม่ครบหรือผิดชนิดก็ส่งคืนพร้อมบอกว่าผิดตรงไหน ไม่ปล่อยเข้าโกดัง (ฐานข้อมูล)

## ที่มา

type ของ TypeScript หายไปตอนรัน มันช่วยได้แค่โค้ดที่เราเขียนเอง ช่วยไม่ได้กับ JSON ที่คนอื่นส่งมา และคนยิง API ตรงๆ ข้ามหน้าเว็บได้เสมอ ส่ง `title` เป็นตัวเลข ส่งค่าว่าง หรือส่งข้อความยาวล้านตัวอักษรก็ได้ ถ้าไม่ตรวจ ของพวกนี้จะไปพังในฐานข้อมูลหรือโผล่บนหน้าเว็บคนอื่น Zod เขียนครั้งเดียว ได้ทั้งตัวตรวจตอนรันและ type ตอนเขียนโค้ด

## การใช้งาน

### ตั้งค่าครั้งแรก

```bash
cd server
bun add zod
```

### 1. เขียน schema `server/src/validators/book.validator.ts`

```ts
import { z } from "zod";

export const newBookSchema = z.object({
  title: z.string().trim().min(1, "ต้องมีชื่อหนังสือ").max(200),
});

export type NewBook = z.infer<typeof newBookSchema>;   // { title: string } ได้ type ไม่ต้องเขียนซ้ำ
```

### 2. ใช้ใน route (ต่อจากการ์ด [Hono](/learn/cards/hono))

```ts
import { z } from "zod";
import { newBookSchema } from "../validators/book.validator";

bookRoutes.post("/", async (c) => {
  // body ไม่ใช่ JSON → ได้ null → ไม่ผ่าน schema (ไม่ปล่อยให้กลายเป็น 500)
  const parsed = newBookSchema.safeParse(await c.req.json().catch(() => null));
  if (!parsed.success) {
    return fail(c, 400, "VALIDATION_ERROR", "ข้อมูลไม่ถูกต้อง", z.flattenError(parsed.error).fieldErrors);
  }
  const book = { id: books.length + 1, title: parsed.data.title, available: true };   // parsed.data ผ่านการตรวจแล้ว
  books.push(book);
  return ok(c, book, 201);
});
```

**ควรเห็น:** ส่ง `{ "title": "" }` ได้ `400`

```json
{"success":false,"error":{"code":"VALIDATION_ERROR","message":"ข้อมูลไม่ถูกต้อง","details":{"title":["ต้องมีชื่อหนังสือ"]}}}
```

ส่ง `{ "title": " ฮอบบิท 2 " }` ได้ `201` และชื่อถูกตัดช่องว่างหัวท้ายเป็น `"ฮอบบิท 2"` ให้ก่อนบันทึก (วิธียิงคำขอ `POST` ดูการ์ด [ยิงทดสอบ API](/learn/cards/api-testing))

`details` บอกเป็นรายช่อง หน้าเว็บเอาไปขึ้นใต้ช่องที่ผิดได้ทันที (ดูการ์ด [ฟอร์ม](/learn/cards/react-forms))

## ทริคที่แนะนำ

1. **ใช้ `safeParse` ไม่ใช่ `parse`:** `parse` โยน error ถ้าไม่มีใครจับจะกลายเป็น `500` ทั้งที่คนส่งเป็นฝ่ายผิด
2. **ใส่ `max` ให้ข้อความและรายการเสมอ** กันคนส่งของใหญ่มาถมฐานข้อมูล (Requirement กำหนดข้อความติดต่อไม่เกิน 1,000 ตัวอักษร)
3. **Zod ตรวจ "รูปแบบ" ส่วน "กฎ" ที่ต้องดูฐานข้อมูลอยู่ใน service:** "ชื่อห้ามว่าง" เป็นรูปแบบ แต่ "สมาชิกยืมได้ไม่เกิน 3 เล่ม" ต้องนับในฐานข้อมูลก่อน (ดูการ์ด [แบ่งชั้น](/learn/cards/layers))

## ปรับไปใช้จริง

**ในงาน STARTER:** Requirement บอกว่า "ทุก request body/query ผ่าน Zod ที่ backend เสมอ (validate frontend อย่างเดียวไม่นับ)" และ Zod ได้ 25 คะแนนในหมวด Backend/API เก็บ schema ไว้ใน `server/src/validators/` ตามโครงโฟลเดอร์ และ `pages.content` ที่เป็น [jsonb](/glossary#jsonb) ก็ต้องมี schema คุมหน้าตาทุกครั้งที่บันทึก

**เว็บคู่มือนี้:** ดู [server/validators/progress.validator.ts บน GitHub](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/server/validators/progress.validator.ts) link ถูกบังคับด้วย regex ให้หน้าตาเป็น `/ชื่อ-บท` เท่านั้น ส่วน "มีบทนี้จริงไหม" ไปเช็กต่อใน service ตรงกับทริคข้อ 3

ลองคิด: schema ตอน "สร้าง" กับตอน "แก้บางช่อง" (`PATCH`) ควรต่างกันตรงไหน (ลองค้น `.partial()` ในเอกสาร Zod)

## ตัวเลือกอื่นที่คล้ายกัน

Hono มีตัวช่วย `zValidator` (แพ็กเกจ `@hono/zod-validator`) ที่ตรวจให้ก่อนเข้า handler สั้นกว่า แต่คำขอต้องมี header `Content-Type: application/json` ไม่งั้นได้ object ว่าง และต้องตั้งค่าเพิ่มถ้าอยากให้คำตอบตอนไม่ผ่านเป็นรูปแบบเดียวกับ Requirement

## ลองเอง

**โจทย์:** เขียน schema สมัครสมาชิกห้องสมุด: ชื่อ (บังคับ), อีเมล (ไม่บังคับ แต่ถ้ากรอกต้องถูกรูปแบบ), เบอร์โทรตัวเลข 9–10 หลัก แล้วยิงข้อมูลผิดทีละช่อง `details` ต้องบอกช่องที่ผิดถูกต้อง

<Hint level={1}>แต่ละช่องคือ 1 บรรทัดใน `z.object({...})` ลองหาในเอกสาร Zod ว่ามีตัวตรวจอีเมลสำเร็จรูปไหม</Hint>
<Hint level={2}>เบอร์โทรใช้ `.regex()` คิดรูปแบบเป็นคำพูดก่อน: "ตัวเลขล้วน 9 ถึง 10 ตัว ไม่มีอย่างอื่น" แล้วค่อยแปลงเป็น regex</Hint>
<Hint level={3}>"ไม่บังคับ" ใช้ `.optional()` แต่ระวัง ช่องอีเมลในฟอร์มที่ไม่กรอกมักส่งมาเป็น `""` (ข้อความว่าง) ไม่ใช่ไม่ส่ง ลองยิงทั้งสองแบบแล้วดูผล</Hint>
