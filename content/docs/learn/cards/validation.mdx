## ความหมาย

ทุกอย่างที่ส่งเข้ามาทาง API เป็นของ **ที่เชื่อไม่ได้** จนกว่าจะตรวจ Zod ให้เราเขียน **schema** (หน้าตาที่ข้อมูลควรเป็น) แล้วเอาข้อมูลจริงไปเทียบ ผ่านได้ข้อมูลที่สะอาดพร้อม type ไม่ผ่านได้รายการว่าผิดช่องไหน

## ที่มา

type ของ TypeScript หายไปตอนรัน มันช่วยได้แค่โค้ดที่เราเขียนเอง แต่ช่วยไม่ได้กับ JSON ที่คนอื่นส่งมา คนยิง API ตรงๆ ด้วย `curl` ข้ามหน้าเว็บได้เสมอ ส่ง `title` เป็นตัวเลข ส่งค่าว่าง หรือส่งข้อความยาวล้านตัวอักษร ถ้าไม่ตรวจ ของพวกนี้จะไปพังในฐานข้อมูลหรือโผล่บนหน้าเว็บคนอื่น Zod เขียนครั้งเดียวได้ทั้งตัวตรวจตอนรันและ type ตอนเขียนโค้ด ไม่ต้องเขียนซ้ำสองที่

## การใช้งาน

```ts
// server/validators/book.validator.ts
import { z } from "zod";

export const newBookSchema = z.object({
  title: z.string().trim().min(1, "ต้องมีชื่อหนังสือ").max(200),
  year: z.number().int().min(1400).optional(),
});

export type NewBook = z.infer<typeof newBookSchema>;   // { title: string; year?: number }
```

```ts
// ใน route
bookRoutes.post("/", async (c) => {
  // body ไม่ใช่ JSON → ได้ null → ไม่ผ่าน schema (ไม่ปล่อยให้ระบบตอบ 500)
  const parsed = newBookSchema.safeParse(await c.req.json().catch(() => null));
  if (!parsed.success) {
    const details = parsed.error.issues.map((i) => `${i.path.join(".")}: ${i.message}`);
    return c.json({ error: "ข้อมูลไม่ถูกต้อง", details }, 400);
  }
  const book = await bookService.create(parsed.data);   // ตรงนี้ parsed.data เป็น NewBook แล้ว
  return c.json(book, 201);
});
```

ส่ง `{"title": ""}` จะได้ `400` กับ `"details": ["title: ต้องมีชื่อหนังสือ"]` ส่วน `" ฮอบบิท "` จะถูกตัดช่องว่างหัวท้ายเป็น `"ฮอบบิท"` ให้ก่อนบันทึก

## ทริคที่แนะนำ

1. **ใช้ `safeParse` ไม่ใช่ `parse`:** `parse` โยน error ถ้าไม่มีใครจับ จะกลายเป็น `500` ทั้งที่ผิดที่คนส่ง
2. **ใส่ `max` ให้ข้อความและ array เสมอ** กันคนส่งของใหญ่มาถมฐานข้อมูล (เว็บนี้รับ link ไม่เกิน 80 ตัวอักษร และนำเข้าทีละไม่เกิน 100 รายการ)
3. **Zod ตรวจ "รูปแบบ" ส่วน "กฎ" อยู่ใน service:** "ชื่อห้ามว่าง" เป็นรูปแบบ แต่ "สมาชิกยืมได้ไม่เกิน 3 เล่ม" ต้องดูฐานข้อมูล จึงเป็นงานของ service (ดูการ์ดแบ่งชั้น)

## ปรับไปใช้จริง

เว็บคู่มือนี้เก็บ schema ไว้ใน `server/validators/` แยกจาก route เปิด `progress.validator.ts` จะเห็น link ถูกบังคับด้วย regex ให้หน้าตาเป็น `/ชื่อ-บท` เท่านั้น แต่ "มีบทนี้จริงไหม" ไปเช็กต่อใน service ซึ่งตรงกับทริคข้อ 3

Hono มีตัวช่วย `zValidator` (แพ็กเกจ `@hono/zod-validator`) ที่ตรวจให้ก่อนเข้า handler แล้วอ่านผลด้วย `c.req.valid("json")` สั้นกว่า แต่คำขอต้องมี header `Content-Type: application/json` ไม่งั้นจะได้ object ว่าง เว็บนี้เลือกเขียน `safeParse` เองเพื่อคุมข้อความ error เป็นภาษาไทยได้ทุกตัว

ลองคิด: schema ตอน "สร้าง" กับตอน "แก้บางช่อง" ควรต่างกันตรงไหน (ลองค้น `.partial()` ในเอกสาร Zod)

## ลองเอง

**โจทย์:** เขียน schema สำหรับสมัครสมาชิกห้องสมุด: ชื่อ, อีเมล, เบอร์โทรไทย 10 หลักขึ้นต้นด้วย 0 และปีเกิดที่ทำให้อายุอย่างน้อย 7 ขวบ แล้วลองยิงข้อมูลผิดทีละช่อง ต้องได้ข้อความที่บอกช่องที่ผิดถูกต้อง

<Hint level={1}>แต่ละช่องคือ 1 บรรทัดใน `z.object({...})` ลองหาในเอกสาร Zod ว่ามีตัวตรวจอีเมลสำเร็จรูปไหม</Hint>
<Hint level={2}>เบอร์โทรใช้ `.regex()` คิดรูปแบบเป็นคำพูดก่อน: "0 ตามด้วยตัวเลขอีก 9 ตัว ไม่มีอย่างอื่น" แล้วค่อยแปลงเป็น regex</Hint>
<Hint level={3}>ปีที่ "ทำให้อายุ 7 ขวบ" ขึ้นกับปีปัจจุบัน ต้องคำนวณจาก `new Date().getFullYear()` ไม่ใช่เขียนเลขตายตัว</Hint>
