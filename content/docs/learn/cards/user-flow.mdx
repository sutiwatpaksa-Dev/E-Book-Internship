## ความหมาย

[User flow](/glossary#user-flow) คือ **ลำดับการกดและหน้าจอ** ที่ผู้ใช้ผ่านเพื่อทำงาน 1 อย่างให้เสร็จ รวมทั้ง **ทางแยก** เมื่อมีอะไรผิดพลาด ส่วน **สถานะของหน้าจอ** คือหน้าตาของหน้าเดียวกันในแต่ละสภาพ: กำลังโหลด ผิดพลาด ไม่มีข้อมูล และมีข้อมูล

**นึกภาพ:** แผนผังทางหนีไฟในตึก ไม่ได้วาดแค่ทางเดินปกติ แต่บอกด้วยว่าถ้าประตูนี้ปิด ให้ไปทางไหน ถ้าไม่มีป้ายบอกตอนประตูปิด คนจะยืนงงอยู่หน้าประตู

| แผนผังหนีไฟ | หน้าเว็บ |
|---|---|
| ทางเดินปกติจากห้องถึงทางออก | flow หลัก: ทุกอย่างเรียบร้อย ทำงานเสร็จ |
| ประตูที่อาจปิดอยู่ | จุดที่พังได้: ยังไม่ login, กรอกผิด, server ล่ม |
| ป้าย "ประตูปิด ไปทางซ้าย" | ข้อความบนหน้าจอ + ปุ่มที่พาไปต่อ |

จุดที่ไม่ตรง: แผนผังหนีไฟไม่มีช่วง "รอ" แต่หน้าเว็บมี ระหว่างรอข้อมูลจาก server หน้าจอต้องบอกว่ากำลังโหลด ช่วงนี้จึงต้องคิดเพิ่มเอง

หน้าเดียวมีได้ 4 สภาพ ทุกหน้าที่ดึงข้อมูลต้องออกแบบครบทั้ง 4:

```text
เปิดหน้า /books
   │
   ▼
กำลังโหลด
   │
   ├──► ผิดพลาด
   │    บอกว่าเกิดอะไร + ปุ่มลองใหม่
   │
   ├──► ไม่มีข้อมูล
   │    บอกว่ายังว่าง + ทางไปต่อ
   │
   └──► มีข้อมูล
        แสดงรายการ
```

## ที่มา

Wireframe ในการ์ดก่อนวาดหน้าจอตอนที่ **ทุกอย่างเรียบร้อย** ข้อมูลมาครบ ผู้ใช้กรอกถูก แต่ของจริงไม่ได้เป็นแบบนั้นเสมอ เน็ตมือถือช้า server ล่ม ผู้ใช้กรอกผิด ยังไม่ได้ login ถ้าไม่ได้คิดไว้ก่อน โค้ดจะทำแบบที่ง่ายที่สุดให้เอง คือ **จอขาว** หรือข้อความ error ภาษาเครื่องที่ผู้ใช้อ่านไม่ออก และผู้ใช้ไม่รู้ว่าต้องทำอะไรต่อ

## การใช้งาน

**1. เขียน flow ของงานหลัก** 1 flow ต่อ story ที่ "ต้องมี" เขียนเป็นลูกศรก็พอ ทางหลักอยู่บรรทัดบน ทางแยกย่อหน้าลงไปใต้ขั้นที่แยกออก

ตัวอย่าง story 4 ของห้องสมุด "บรรณารักษ์เพิ่มหนังสือ" (ตรงกับที่การ์ด [หน้าจัดการข้อมูล](/learn/cards/crud-ui) สร้าง)

1. เปิด `/admin/books`
   - ยังไม่ login → ไปหน้า `/admin/login` แล้ว **จำไว้ว่ามาจากหน้าไหน**
2. กรอกอีเมลและรหัสผ่าน → กด "เข้าสู่ระบบ"
   - ผิด → อยู่หน้าเดิม ขึ้น "อีเมลหรือรหัสผ่านไม่ถูกต้อง" ช่องอีเมลยังมีค่าเดิม
3. กลับมาที่ `/admin/books` เอง (ไม่ใช่หน้าแรกของหลังบ้าน)
4. กด "เพิ่มหนังสือ" → ฟอร์มเปิด → กรอกชื่อ → กด "บันทึก" → ปุ่มเปลี่ยนเป็น "กำลังบันทึก..." และกดซ้ำไม่ได้
   - ชื่อว่าง → ข้อความใต้ช่อง ไม่ส่งไป server
   - server ตอบ error → ข้อความใต้ช่อง ฟอร์มยังเปิดอยู่ **ชื่อที่กรอกไว้ยังอยู่** แก้แล้วกดใหม่ได้
5. ฟอร์มปิด ตารางโหลดใหม่ เห็นหนังสือเล่มใหม่

ขั้น 1 ที่ "จำไว้ว่ามาจากหน้าไหน" คือสิ่งที่การ์ด [หน้าหลังบ้านที่ต้อง login](/learn/cards/protected-routes) ส่ง `state.from` ไปให้หน้า login ถ้าไม่ได้เขียนไว้ใน flow มักไม่มีใครทำ แล้วบรรณารักษ์ต้องกดเมนูหาหน้าเดิมเองทุกครั้งที่ login

**2. ทุกหน้าที่ดึงข้อมูล ออกแบบ 4 สถานะ** (การ์ด [ดึงข้อมูลจาก API](/learn/cards/data-fetching) เขียนโค้ดของทั้ง 4 แบบ)

| สถานะ | `/books` แสดงอะไร | ถ้าไม่ได้ออกแบบไว้ |
|---|---|---|
| กำลังโหลด | "กำลังโหลด..." หรือกล่องเทาเท่ารายการ | จอว่าง 3 วินาทีบนเน็ตมือถือ ผู้ใช้คิดว่าเว็บพัง |
| ผิดพลาด | "โหลดไม่สำเร็จ" + บอกให้ลองใหม่ | จอขาว หรือ error ภาษาอังกฤษ |
| ไม่มีข้อมูล | "ไม่พบหนังสือที่ชื่อมีคำว่า ..." | รายการว่างเปล่า ผู้ใช้ไม่รู้ว่าค้นผิดหรือโหลดยังไม่เสร็จ |
| มีข้อมูล | รายการตาม wireframe | |

การ์ด data-fetching ทำครบ 4 แบบแต่หน้านั้นยังไม่มีช่องค้นหา ข้อความว่างจึงเป็น "ยังไม่มีหนังสือ" พอเพิ่มช่องค้นหา ข้อความต้องเปลี่ยนตาม เพราะ "ไม่มีหนังสือเลย" กับ "ค้นแล้วไม่เจอ" ให้ผู้ใช้ทำต่อคนละอย่าง

และอีก 2 แบบที่ไม่ได้มาจากการโหลด: **ที่อยู่ที่ไม่มีจริง** (`/abc`) ได้หน้า "ไม่พบหน้านี้" และ **ข้อมูลที่ไม่มีจริง** (`/books/99`) ได้ "ไม่พบหนังสือ" พร้อมลิงก์กลับรายการ

**3. ปุ่มที่ส่งข้อมูลมี 3 สภาพ:** ปกติ → กำลังส่ง (กดซ้ำไม่ได้ เพื่อไม่ให้บันทึกซ้ำ 2 แถว) → สำเร็จหรือผิดพลาด (บอกผล และบอกว่าทำอะไรต่อ)

**ควรได้:** flow ของทุก story ที่ "ต้องมี" และตาราง 4 สถานะของทุกหน้าที่ดึงข้อมูล เขียนข้างภาพ wireframe

## ทริคที่แนะนำ

1. **ทุกทางแยกต้องมีทางกลับ:** ทุกครั้งที่เขียน "ผิด → ..." ให้ตอบต่อว่าผู้ใช้ทำอะไรต่อได้ (กดลองใหม่, แก้ช่องที่ผิด, ลิงก์กลับรายการ) error ที่ไม่บอกทางไปต่อ คือทางตันที่ผู้ใช้ต้องปิดเว็บ
2. **เขียนข้อความ error ตั้งแต่ตอนออกแบบ:** ถ้าปล่อยให้คิดตอนเขียนโค้ด จะได้ข้อความที่คนเขียนโค้ดเข้าใจ เช่น "Request failed 500" ข้อความที่ดีบอก **เกิดอะไร** และ **ทำอะไรต่อ** เช่น "บันทึกไม่สำเร็จ ลองกดอีกครั้ง ข้อมูลที่กรอกไว้ยังอยู่"
3. **นับจำนวนขั้นของงานที่ทำบ่อย:** บรรณารักษ์เพิ่มหนังสือวันละหลายสิบเล่ม ทุกขั้นที่ตัดได้ประหยัดเวลาเขาทุกวัน เช่น ขั้น 5 ของการ์ด crud-ui ปิดฟอร์มหลังบันทึก ถ้าเปลี่ยนเป็นล้างช่องแล้วเปิดฟอร์มค้างไว้ บรรณารักษ์จะกรอกเล่มต่อไปได้เลยโดยไม่ต้องกด "เพิ่มหนังสือ" ทุกเล่ม (ลองทำเป็นโจทย์หลังจบการ์ด crud-ui)

## ปรับไปใช้จริง

**ในงาน STARTER:** [Requirement หน้า 4](/api/files/requirement.pdf?sec=public) (ต้อง login) เขียนไว้ว่า **สถานะที่ต้องมีทุกหน้า** คือ Loading, Error เมื่อ API ล่ม "ไม่ใช่หน้าขาว" และหน้า 404 ส่วนฟอร์มติดต่อ "ระหว่างส่ง ปุ่มต้อง disable + แสดง loading ส่งสำเร็จแสดงข้อความขอบคุณและล้างฟอร์ม" ซึ่งก็คือ flow ข้อ 3 ข้างบน หน้า 5 บอกว่าเข้า `/admin/*` โดยไม่ login ต้องเด้งกลับหน้า login และ session หมดอายุใน 1 วัน ตาม Timeline (หน้า 11) วันที่ 9 คือวันทำ loading/error state และ Review รอบที่ 2 ทั้งระบบ ถ้าออกแบบไว้ตั้งแต่วันที่ 1 วันที่ 9 แค่ไล่เช็ก ไม่ต้องรื้อหน้าที่ทำเสร็จแล้ว

**เว็บคู่มือนี้:** กล่องแชท "ถามพี่เลี้ยง" มีสถานะ "กำลังโหลด…" และสถานะว่าง 2 แบบที่ข้อความต่างกัน: "ยังไม่มีเรื่อง" กับ "ไม่มีเรื่องในหมวดนี้" (ตอนกรองหมวดอยู่) เพราะวิธีไปต่อของสองกรณีไม่เหมือนกัน ดูใน [src/components/chat-panel.tsx บน GitHub](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/src/components/chat-panel.tsx)

ลองคิด: เจ้าของร้านกรอกฟอร์มแก้รายละเอียดบริการยาวๆ อยู่ แล้ว session หมดอายุพอดีก่อนกดบันทึก ตาม flow ที่ดี ควรเกิดอะไรกับข้อความที่พิมพ์ไว้

## ตัวเลือกอื่นที่คล้ายกัน

| วิธี | ข้อดี | ข้อเสีย |
|---|---|---|
| **ลูกศรเป็นข้อความ (การ์ดนี้)** | เร็ว เขียนใน `NOTES.md` ได้ เห็นทางแยกชัด | ไม่เห็นหน้าจอ ต้องเปิดคู่กับ wireframe |
| Flowchart ([draw.io](https://www.drawio.com), FigJam) | เห็นทางแยกเป็นภาพ | วาดนานกว่า แก้ยากกว่าเมื่อ flow เปลี่ยน |
| Storyboard | วาด wireframe ทีละจอเรียงกันเหมือนการ์ตูน | ชัดที่สุดสำหรับลูกค้า / งานเยอะที่สุด |
| Prototype กดได้ (Figma, Penpot) | ให้คนลองกดก่อนมีโค้ด | ต้องทำหน้าจอทุกสถานะ เหมาะกับงานที่ใหญ่กว่า STARTER |

## ลองเอง

**โจทย์:** เขียน flow ของ "ลูกค้าส่งฟอร์มติดต่อ" ในงาน STARTER ให้ครบทุกทางแยก แล้วทำตาราง 4 สถานะของหน้า About/Services (รายการบริการที่กรองตามหมวดได้)

<Hint level={1}>เริ่มจากทางหลัก 4–5 ขั้นก่อน แล้วถามทีละขั้นว่า "ขั้นนี้พังได้แบบไหนบ้าง" ทั้งผู้ใช้ทำผิดและระบบพัง</Hint>
<Hint level={2}>ฟอร์มติดต่อมีด่านกันสแปม 5 ครั้งต่อ 10 นาที (Requirement หน้า 10) ครั้งที่ 6 ผู้ใช้ต้องเห็นอะไร ส่วนหน้ารายการบริการ ถ้ากรองหมวดแล้วไม่มีบริการเลย ต่างจากร้านที่ยังไม่มีบริการสักรายการยังไง</Hint>
<Hint level={3}>ตรวจก่อนส่ง: ทุกบรรทัด "ผิด → ..." บอกว่าผู้ใช้ทำอะไรต่อได้, ทุกข้อความเขียนเป็นภาษาที่ลูกค้าอ่านเข้าใจ, ข้อมูลที่ผู้ใช้กรอกไม่หายในทางแยกไหนเลย และตาราง 4 สถานะไม่มีช่องว่าง</Hint>
