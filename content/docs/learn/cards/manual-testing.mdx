## ความหมาย

คือการทดสอบตาม **รายการที่เขียนไว้ก่อน** ไม่ใช่คลิกเล่นไปเรื่อยๆ แต่ละข้อในรายการเรียกว่า **[test case](/glossary#test-case)** บอก 2 อย่าง: **ทำอะไร** (ขั้นที่ทำตามได้ทุกครั้ง) และ **ต้องเห็นอะไร** (ผลที่ตัดสินได้ว่าผ่านหรือไม่ผ่าน) รายการทั้งหมดเรียกว่าแผนทดสอบ (test plan)

**นึกภาพ:** ตรวจบ้านก่อนรับโอน ช่างตรวจถือใบรายการ เปิดก๊อกทุกห้อง กดสวิตช์ทุกตัว ติ๊กว่าผ่านหรือไม่ผ่าน ไม่ได้เดินดูว่า "โดยรวมก็สวยดี" ใบเดียวกันใช้ตรวจซ้ำได้หลังผู้รับเหมาแก้งาน

จับคู่: ใบรายการของช่างตรวจ = test plan · "เปิดก๊อกห้องน้ำชั้น 2" = ขั้นที่ทำของ test case · "น้ำไหล ไม่ซึม" = สิ่งที่ต้องเห็น · ติ๊กผ่าน/ไม่ผ่าน = ผลของแต่ละข้อ

จุดที่ไม่ตรง: บ้านตรวจครั้งเดียวก่อนรับโอน แต่เว็บต้องตรวจซ้ำ **ทุกครั้งที่แก้โค้ด** เพราะแก้จุดหนึ่งอาจไปพังอีกจุดที่เคยผ่านแล้ว และหน้าเว็บมีหลายสภาพที่บ้านไม่มี เช่น จอมือถือ ยังไม่ได้ login เน็ตช้า ใบรายการจึงต้องมีข้อของสภาพพวกนี้ด้วย

## ที่มา

คนเขียนโค้ดรู้ว่าต้องกดตรงไหน จึงมักกดแต่ทางที่ถูก แล้วสรุปว่า "ใช้ได้แล้ว" แต่ผู้ใช้จริงกรอกช่องว่าง กดปุ่มซ้ำ เปิดลิงก์เก่าที่ไม่มีแล้ว การคลิกเล่นมีอีก 2 ปัญหา: ไม่มีใครรู้ว่าลองอะไรไปแล้วบ้าง และพอแก้บั๊กเสร็จ ก็ไม่รู้ว่าต้องลองอะไรซ้ำ

ข่าวดีคือเกณฑ์ว่าเสร็จที่เขียนไว้ในการ์ด [User story](/learn/cards/user-stories) และ 4 สถานะในการ์ด [User flow](/learn/cards/user-flow) คือแผนทดสอบที่เขียนไปแล้วครึ่งหนึ่ง การ์ดนี้แปลงมันเป็นรายการที่ทำตามได้

## การใช้งาน

**1. แปลงเกณฑ์ว่าเสร็จเป็น test case** เกณฑ์ 1 ข้อ = test case อย่างน้อย 1 ข้อ เขียนเป็นขั้นที่คนอื่นทำตามได้ ไม่ต้องถามเรา ตัวอย่างจาก story 3 และ 4 ของห้องสมุดบิต (หน้าจอจากการ์ด [หน้าหลังบ้านที่ต้อง login](/learn/cards/protected-routes) และ [หน้าจัดการข้อมูล](/learn/cards/crud-ui))

| # | story | ทำ | ต้องเห็น |
|---|---|---|---|
| T1 | 3 | ยังไม่ login เปิด `/admin/books` ตรงๆ | ถูกพาไปหน้า login |

| T4 | 4 | กด "เพิ่มหนังสือ" เว้นชื่อว่าง กด "บันทึก" | ขึ้น "กรอกชื่อหนังสือ" ไม่มีแถวใหม่ในตาราง |
| T5 | 4 | กรอกชื่อเป็นช่องว่างล้วน 3 ตัว กด "บันทึก" | ผลเหมือน T4 |
| T6 | 4 | เพิ่มเล่ม "zz ทดสอบ" แล้วเปิด `/books` ในอีกแท็บ | "zz ทดสอบ" ขึ้นแถวแรกในหลังบ้าน และอยู่ในรายการ `/books` |

ชื่อขึ้นต้น `zz` ทำให้รู้ทันทีว่าเป็นข้อมูลทดสอบ ลบทิ้งได้ไม่ต้องคิด

story 5 (ยืมเกิน 3 เล่ม) ยังไม่มีหน้าจอ ทดสอบผ่าน API ด้วยวิธีในการ์ด [ยิงทดสอบ API](/learn/cards/api-testing) ก็นับเป็นทดสอบด้วยมือเหมือนกัน: สมาชิก 1 ยืมค้างครบ 3 เล่มอยู่แล้วจากการ์ด [แบ่งชั้น](/learn/cards/layers) ยืมให้อีก 1 เล่มต้องได้ `409` กับ `LOAN_LIMIT` (ถ้าล้างฐานไปแล้ว ยืมให้ครบ 3 ก่อน แล้วค่อยยืมเล่มที่ 4)

**2. เพิ่มทางพังที่เกณฑ์ไม่ได้เขียนไว้** ทุกฟอร์มและทุกหน้าที่ดึงข้อมูล ลอง 6 อย่างนี้เสมอ

| ลองอะไร | ทำยังไง | หน้าที่ดีควรเป็นยังไง |
|---|---|---|
| ค่าว่างและช่องว่างล้วน | เว้นทุกช่อง / พิมพ์ช่องว่าง | บอกใต้ช่องที่ผิด ไม่บันทึก |
| ยาวเกิน | วางข้อความยาว 300 ตัวในช่องชื่อ (สร้างได้ใน DevTools แท็บ Console: พิมพ์ `copy("ก".repeat(300))` กด Enter แล้ววาง) | บอกเป็นภาษาไทยว่ายาวเกิน ไม่ใช่ error 500 |
| กดซ้ำเร็วๆ | กด "บันทึก" รัว 3 ครั้ง | ปุ่มเป็น "กำลังบันทึก..." กดไม่ได้ ได้แถวเดียว |
| กำลังโหลดช้า | DevTools แท็บ Network เลือก **Slow 4G** แล้วรีเฟรช | เห็น "กำลังโหลด..." ไม่ใช่จอว่าง |
| server ล่ม | ปิด server (กด `Ctrl+C` ใน Terminal ที่รัน) แล้วรีเฟรชหน้า | ขึ้นข้อความว่าผิดพลาด ไม่ใช่จอขาว · หน้าหลังบ้านที่ทำตามการ์ด [กันหน้าที่ต้อง login](/learn/cards/protected-routes) จะเด้งไปหน้า login แทน เพราะ `.catch(() => setState("out"))` นับทุก error ว่า "ยังไม่ได้ login" จดเป็นบั๊ก แล้วแก้ตามโค้ดใต้ตาราง |
| ของที่ไม่มีจริง | เปิด `/books/99` และ `/abc` | "ไม่พบหนังสือ" และ "ไม่พบหน้านี้" เมนูด้านบนยังกดกลับได้ |

`Ctrl+C` ใช้หยุด server ได้ทั้ง Windows และ Mac (บน Mac ก็เป็น `Ctrl` ไม่ใช่ `Cmd`)

**แก้บั๊ก server ล่ม** ใน `client/src/components/require-librarian.tsx`: ถือว่า "ยังไม่ได้ login" เฉพาะเมื่อ server ตอบ `401` จริง (`status` มาจาก `ApiError` ในการ์ด [ดึงข้อมูลจาก API](/learn/cards/data-fetching)) ที่เหลือคือ "ติดต่อไม่ได้"

```tsx
import { ApiError } from "../api/client";   // เพิ่มบนสุด

const [state, setState] = useState<"checking" | "in" | "out" | "error">("checking");

authApi.me().then(() => setState("in")).catch((e) => setState(e instanceof ApiError && e.status === 401 ? "out" : "error"));

if (state === "error") return <p className="p-8">ติดต่อ server ไม่ได้ ลองรีเฟรชอีกครั้ง</p>;   // วางเหนือ return สุดท้าย
```

**ควรเห็น:** ปิด server แล้วรีเฟรช `/admin/books` ขึ้น "ติดต่อ server ไม่ได้" ไม่เด้งไปหน้า login (Vite ตอบ `502` เมื่อ server ดับ ไม่ใช่ `401` ลองแล้ว) เปิด server กลับแล้วรีเฟรช เห็นตารางเหมือนเดิม

**ถ้าทำตามการ์ดช่วง Coding มาครบ จะเจอบั๊กจริงอย่างน้อย 1 ข้อตรงนี้:** ชื่อยาว 300 ตัวได้ข้อความ `Too big: expected string to have <=200 characters` เพราะ `.max(200)` ในการ์ด [ตรวจข้อมูลด้วย Zod](/learn/cards/validation) ไม่ได้ใส่ข้อความไทยไว้ และหน้าหลังบ้านแสดงข้อความจาก server ตรงๆ นี่คือเหตุผลที่ต้องลองทางพัง: คนเขียนไม่เคยวาง 300 ตัว จึงไม่เคยเห็น จดเป็นรายงานบั๊ก (แบบข้อ 4) แล้วแก้ด้วย `.max(200, "ชื่อยาวเกิน 200 ตัวอักษร")`

**3. ดู 3 ขนาดจอ** เปิด DevTools (`F12` บน Windows, `Cmd+Option+I` บน Mac) แล้วกดปุ่มรูปมือถือ หรือ `Ctrl+Shift+M` / `Cmd+Shift+M` พิมพ์ความกว้าง 375, 768 และ 1280 ทีละขนาด ทุกหน้าต้องไม่มีแถบเลื่อนแนวนอนของทั้งหน้า ตารางยาวเลื่อนได้ในกรอบของมันเอง และปุ่มกดด้วยนิ้วได้ (สูงอย่างน้อย 44px) วัดได้โดยกดปุ่มลูกศรมุมซ้ายบนของ DevTools แล้วชี้ที่ปุ่ม จะขึ้นขนาด เช่น `64 × 40` ข้อนี้หน้า [หน้าจัดการข้อมูล](/learn/cards/crud-ui) จะไม่ผ่าน: ปุ่มส่วนใหญ่ใช้ `py-2` สูงราว 40px ปุ่มแบ่งหน้าใช้ `py-1` ส่วน "แก้" กับ "ลบ" เป็นแค่ตัวหนังสือ จดเป็นบั๊ก แล้วแก้ด้วยคลาส `min-h-11` (44px)

**4. จดผลลงไฟล์** สร้าง `TESTING.md` ไว้ที่ root ของโปรเจกต์ (ข้าง `NOTES.md`) เป็นตารางจากข้อ 1–3 เพิ่มคอลัมน์ "ผล" กับวันที่ ทุกรอบที่ทดสอบให้จดว่าผ่านหรือไม่ผ่าน ข้อที่ไม่ผ่านเขียนเป็น **รายงานบั๊ก** แบบนี้ (ตัวอย่างรูปแบบ ถ้าทำตามการ์ด crud-ui ปุ่มถูกปิดระหว่างบันทึกอยู่แล้ว อาจไม่เจอบั๊กนี้)

> - **เรื่อง:** กด "บันทึก" รัวๆ แล้วได้หนังสือซ้ำ 2 เล่ม
> - **ทำซ้ำได้โดย:** `/admin/books` → "เพิ่มหนังสือ" → กรอก "zz ซ้ำ" → กด "บันทึก" 3 ครั้งเร็วๆ
> - **ต้องเห็น:** ได้ 1 เล่ม ปุ่มกดไม่ได้ระหว่างบันทึก
> - **เห็นจริง:** ได้ "zz ซ้ำ" 2 แถว
> - **เครื่อง:** Chrome บน Windows 11, จอ 1280 · แนบรูป หรือรูปแท็บ Network ที่เห็น `POST` 2 ครั้ง

**ควรได้:** `TESTING.md` ที่มี test case ครบทุกเกณฑ์ของ story ที่ "ต้องมี" พร้อมทางพังข้อ 2 และ 3 ขนาดจอ คนอื่นหยิบไปทำตามได้โดยไม่ต้องถามเรา

## ทริคที่แนะนำ

1. **เขียน test case ก่อนเขียนโค้ด:** ทำต่อจากเกณฑ์ว่าเสร็จได้ตั้งแต่วันที่ 1 ตอนเขียนโค้ดจะรู้ว่าต้องรองรับกรณีไหนบ้าง ถ้าเขียนหลังโค้ดเสร็จ เรามักเขียนตามสิ่งที่โค้ดทำได้ ไม่ใช่สิ่งที่ผู้ใช้ต้องการ
2. **ให้คนอื่นทดสอบ แล้วเราห้ามพูด:** คนเขียนมองไม่เห็นจุดพังของตัวเอง เพราะรู้ว่าปุ่มไหนห้ามกด ให้เพื่อนทำตาม `TESTING.md` แล้วเราจดเฉพาะสิ่งที่เพื่อนเห็นจริง ถ้าเพื่อนต้องถามว่า "กดตรงไหน" แปลว่า test case ข้อนั้นเขียนไม่ชัด
3. **แก้บั๊กเสร็จ ลองซ้ำทั้งหน้า ไม่ใช่ข้อเดียว:** การแก้ตรงหนึ่งทำให้อีกตรงพังได้ (เรียกว่า [regression](/glossary#regression)) ข้อไหนที่ต้องลองซ้ำทุกรอบและตัดสินด้วยค่า (ได้ `409` ไหม, ได้กี่แถว) ให้เครื่องทำแทน ในการ์ด [เทสต์อัตโนมัติด้วย bun test](/learn/cards/unit-testing) ส่วนเรื่องที่ต้องใช้ตาคน (อ่านง่ายไหม, ปุ่มเด่นพอไหม) ยังต้องใช้มือ

## ปรับไปใช้จริง

**ในงาน STARTER:** ตาม Timeline ([Requirement หน้า 11](/api/files/requirement.pdf#page=11), ต้อง login) วันที่ 9 คือวันตรวจความเรียบร้อยทั้งระบบและ Review รอบที่ 2 ซึ่งต้องใช้แผนทดสอบนี้ตรงๆ:
- Loading, Error และหน้า 404 ของทุกหน้า (หน้า 4)
- 3 ขนาดจอ 375 / 768 / 1280 และตารางหลังบ้านที่เลื่อนในกรอบ (หน้า 10)
- ฟอร์มติดต่อส่งได้ 5 ครั้งต่อ 10 นาทีต่อ IP (หน้า 10): ส่งครั้งที่ 6 ต้องโดนกัน

หน้า 12 มีข้อที่ **ไม่ผ่านทันที** 3 ข้อ ใส่เป็น test case บนสุดของ `TESTING.md`:
- เรียก admin API โดยไม่ login ได้
- รหัสผ่านไม่ hash: เปิดตาราง `admins` ใน pgAdmin แล้วต้องไม่เห็นรหัสจริง
- รันตาม README ไม่ขึ้น: ให้เพื่อน clone ใหม่แล้วทำตาม README ทีละบรรทัด

Demo สด (หน้า 12) มีขั้น "แก้ข้อมูลในหลังบ้านให้ดูว่าหน้าบ้านเปลี่ยน" คือ test case แบบ T6 ลองก่อนวัน demo ทุกครั้ง

**เว็บคู่มือนี้:** ก่อนออกทุกเวอร์ชัน เปิดหน้าที่แก้บนจอ 375px แล้วไล่เช็กลิสต์ 3 ขนาดจอในข้อ 3 ข้างบน ปุ่มกรองในคลังการ์ดใช้คลาส `min-h-11` (44px) ตามเกณฑ์ปุ่มกดด้วยนิ้ว ดูใน [src/components/card-library.tsx บน GitHub](https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/src/components/card-library.tsx)

ลองคิด: เกณฑ์ "session หมดอายุใน 1 วัน" (หน้า 5) ทดสอบด้วยมือยังไงโดยไม่ต้องรอ 1 วัน

## ลองเอง

**โจทย์:** เขียน `TESTING.md` ของฟอร์มติดต่อในงาน STARTER (Requirement หน้า 4 และ 10) อย่างน้อย 10 test case ครอบคลุมทางปกติ ทางพังทุกช่อง และ rate limit แล้วให้เพื่อนทำตามโดยเราไม่พูด

<Hint level={1}>เริ่มจากทุกช่องในฟอร์ม แต่ละช่องมีกฎอะไรใน Requirement หน้า 10 (เบอร์โทร, ความยาวข้อความ) 1 กฎ = อย่างน้อย 2 test case: ค่าที่ผ่านพอดี และค่าที่เกินมา 1</Hint>
<Hint level={2}>อย่าลืมสิ่งที่เกิด "หลัง" กดส่ง: ปุ่มระหว่างส่ง, ข้อความขอบคุณ, ฟอร์มถูกล้าง และข้อความไปโผล่ในหลังบ้านจริงไหม (หน้า 5) ส่วน rate limit นับว่าครั้งที่เท่าไหร่ต้องโดนกัน และโดนแล้วหน้าจอบอกอะไร</Hint>
<Hint level={3}>ตรวจแผนของตัวเอง: ทุกข้อมีทั้ง "ทำ" และ "ต้องเห็น", ช่อง "ต้องเห็น" ตัดสินได้ทันทีว่าผ่านไหม (ไม่มีคำว่า "ถูกต้อง" หรือ "ใช้ได้" เฉยๆ) และเพื่อนทำครบทุกข้อโดยไม่ต้องถามสักครั้ง</Hint>
