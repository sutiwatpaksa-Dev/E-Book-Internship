## ความหมาย

คือการแตก story และของที่ออกแบบไว้ เป็น **งานชิ้นเล็กที่ทำเสร็จได้ไม่เกินครึ่งวัน** แต่ละชิ้นมีบรรทัด **"เสร็จเมื่อ"** ที่ตรวจได้จริง แล้วเรียงตามว่าชิ้นไหนต้องมาก่อน และลงวันที่จะทำ

**นึกภาพ:** สูตรทำกับข้าว ไม่ได้เขียนว่า "ทำแกงเขียวหวาน" บรรทัดเดียว แต่เขียนว่า หั่นไก่ → ผัดพริกแกงกับกะทิ → ใส่ไก่จนสุก → ใส่มะเขือ ทุกขั้นรู้ว่าเสร็จเมื่อไร (ไก่สุก) และรู้ว่าขั้นไหนข้ามไม่ได้

จับคู่: แกงทั้งหม้อ = story 1 ข้อ · แต่ละขั้นในสูตร = งานชิ้นเล็ก · "ไก่สุก" = บรรทัด "เสร็จเมื่อ" · ขั้นที่ข้ามไม่ได้ = งานที่ชิ้นอื่นต้องพึ่ง

จุดที่ไม่ตรง: สูตรอาหารบอกเวลาแน่นอน แต่การประมาณเวลางานโค้ดพลาดได้เสมอ ชิ้นงานจึงต้องเล็กพอให้รู้ตัวเร็วว่าช้า และแจ้งได้ภายในวันนั้น

ลำดับหลักของงานในระบบ คือทำของที่ถูกพึ่งก่อน:

```text
ตาราง + migration
   │ API ต้องมีที่เก็บข้อมูลก่อน
   ▼
API (repository → service → route)
   │ หน้าเว็บต้องมี API ให้เรียก
   ▼
หน้าเว็บ
```

## ที่มา

"ทำหลังบ้าน" ไม่ใช่งาน เพราะไม่รู้ว่าเริ่มตรงไหน และไม่รู้ว่าเสร็จไปแล้วกี่ส่วน ถ้าวางแผนเป็นชิ้นใหญ่ ทุกวันจะรู้สึกว่า "ใกล้เสร็จแล้ว" จนถึงวันสุดท้ายที่รู้ว่ายังเหลือครึ่งหนึ่ง ซึ่งสายเกินกว่าพี่เลี้ยงจะช่วยได้ งานชิ้นเล็กที่มีเกณฑ์ "เสร็จเมื่อ" ทำให้ตอบได้ทุกเย็นว่า **วันนี้ตรงแผนไหม** และถ้าไม่ตรง ก็รู้ตั้งแต่วันแรกที่หลุด

## การใช้งาน

**1. แตก story ตามชั้นของระบบ** ตัวอย่าง story 5 ของห้องสมุด "บรรณารักษ์บันทึกการยืม" แต่ละชิ้นตรงกับการ์ดช่วง Coding 1 ใบ (repository คือชั้นที่คุยกับฐานข้อมูล service คือชั้นที่เก็บกฎของงาน อธิบายในการ์ดแบ่งชั้น ตอนนี้ยังไม่ต้องเข้าใจ อ่านตารางนี้อีกรอบหลังจบการ์ดนั้น)

| # | งาน | เสร็จเมื่อ | การ์ด |
|---|---|---|---|
| 1 | ตาราง `loans` + migration | เห็นตาราง `loans` ใน pgAdmin มีคอลัมน์ครบตาม ER diagram | [Drizzle](/learn/cards/drizzle-orm), [Migration](/learn/cards/migration) |
| 2 | repository: นับเล่มที่ยืมค้าง, สร้างการยืม | ไม่มีเส้นแดงใน VS Code · ข้อนี้ยังลองจริงไม่ได้จนกว่าจะมี route ในข้อ 3 จึงควรวางข้อ 2–3 ไว้ช่วงเดียวกัน | [แบ่งชั้น](/learn/cards/layers) |
| 3 | service: กฎ "ยืมได้ไม่เกิน 3 เล่ม" + route `POST /api/loans` + ตรวจด้วย Zod | ยิงแล้วได้ `201` และส่ง body ผิดได้ `400` | แบ่งชั้น, [Zod](/learn/cards/validation) |
| 4 | แปลงรหัส error เป็น status ตามสัญญา | ยืมเล่มที่ 4 ได้ `409 LOAN_LIMIT` ไม่ใช่ `500` (ตอนนี้ยืมเล่มเดิมซ้ำได้ เพราะยังไม่มีกฎในข้อ 5) | [จัดการ error](/learn/cards/error-handling) |
| 5 | กฎ "เล่มที่ยังไม่คืน ยืมซ้ำไม่ได้" (เกณฑ์ข้อ 3 ของ story 5) | ยืมเล่มที่ถูกยืมอยู่ได้ `409` · seed ต้องมีหนังสืออย่างน้อย 4 เล่ม ข้อ 4 จึงยังทดสอบได้ | โจทย์ 1 ของการ์ดแบ่งชั้น |
| 6 | ยิงทดสอบครบทุกแถวในสัญญา | ทุกแถวในสัญญาของการ์ด [ออกแบบรายการ API](/learn/cards/api-design) ได้ status ตรง | [ยิงทดสอบ API](/learn/cards/api-testing) |
| 7 | หน้าบันทึกการยืมในหลังบ้าน | กรอกสมาชิกกับหนังสือแล้วบันทึกได้ ยืมเกินขึ้นข้อความภาษาคน | ไม่มีการ์ดทำให้ ลองทำเองหลังจบการ์ด [หน้าจัดการข้อมูล](/learn/cards/crud-ui) |

บรรทัด "เสร็จเมื่อ" เป็นสิ่งที่ **เห็นได้** (เห็นในจอ, ได้ status นี้) ไม่ใช่ความรู้สึก ("เขียนโค้ดเสร็จแล้ว") และหลายบรรทัดมาจากเกณฑ์ของ story และสัญญา API ที่เขียนไว้แล้ว

**2. ชิ้นไหนเกินครึ่งวัน ให้แตกอีก** ถามทีละชิ้นว่า "ถ้าเริ่มเช้านี้ เที่ยงเสร็จไหม" ถ้าไม่แน่ใจ ส่วนใหญ่ยังใหญ่ไป และถ้าเขียนบรรทัด "เสร็จเมื่อ" ไม่ออก แปลว่ายังไม่รู้ว่างานนี้คืออะไร ให้กลับไปดู story หรือถามก่อน

**3. เรียงตามสิ่งที่ถูกพึ่ง** งานที่ชิ้นอื่นต้องใช้มาก่อน: ตาราง → API → หน้าเว็บ ข้อ 3 ของตารางข้างบนทำไม่ได้ถ้ายังไม่มีข้อ 1 ส่วนข้อ 7 ทำหน้าตาก่อนได้ แต่ต่อ API จริงไม่ได้จนกว่าข้อ 3 เสร็จ

**4. ลงวัน แล้วเทียบทุกเย็น** เย็นวันไหนมีงานของวันนั้นยังไม่เสร็จ ใช้ข้อความแจ้งหลุดแผน 4 บรรทัดในการ์ด [ขอบเขตงาน](/learn/cards/scope-questions) ภายในวันนั้น

**ควรได้:** รายการงานของทั้ง 10 วันที่ทุกชิ้นไม่เกินครึ่งวัน มีบรรทัด "เสร็จเมื่อ" และลงวันไว้ เก็บใน `NOTES.md` หรือ GitHub Issues

## ทริคที่แนะนำ

1. **งานแรกของทุกวัน คืองานที่งานอื่นรอ:** ถ้าเช้าวันที่ 2 เริ่มจาก seed ก่อน migration เสร็จ ทั้งวันจะติด งานที่ถูกพึ่งมากที่สุดทำตอนสมองสดที่สุด
2. **อย่าวางงานใหม่ในวันสุดท้าย:** Timeline ให้วันที่ 10 เป็นวันแก้ตาม review และเตรียมนำเสนอ ถ้าแผนมีงานใหม่ในวันที่ 10 แปลว่าแผนไม่มีที่ให้หลุดเลย ซึ่งงานจริงหลุดเสมอ
3. **1 งาน = 1 commit:** พองานเล็กพอ ข้อความ commit ก็เขียนง่าย ("เพิ่ม POST /api/loans พร้อมกฎยืมไม่เกิน 3 เล่ม") และถ้าพังก็ย้อนกลับได้ทีละชิ้น วิธีเขียนข้อความ commit อยู่ในบทเดิม [Git ข้อ 5](/01-git#5-ข้อความ-commit-ที่ดี)

## ปรับไปใช้จริง

**ในงาน STARTER:** Timeline ([Requirement หน้า 11](/api/files/requirement.pdf?sec=timeline), ต้อง login) บอกงานรายวัน คอลัมน์ "งานต้องเสร็จ" ของมันคือบรรทัด "เสร็จเมื่อ" ระดับวัน เช่น วันที่ 4 "เรียก admin API โดยไม่ login แล้วได้ 401" และบอกลำดับไว้ว่า ฐานข้อมูล → API → หน้าบ้าน → หลังบ้าน **เพราะน้องถนัด backend จาก Todo มาแล้ว** Checklist (หน้า 14–15) แตกแต่ละวันเป็นข้อย่อยให้แล้ว งานของเราคือแตกข้อย่อยที่ยังใหญ่เกินครึ่งวันต่อ เช่น "Admin API ครบ: dashboard/settings/pages/services/categories/messages" เป็นชิ้นละกลุ่ม Timeline กับ Checklist วางวันที่ 5–6 ไม่ตรงกัน ให้ถามพี่เลี้ยงก่อนลงวัน (การ์ด [อ่าน Requirement](/learn/cards/reading-requirements)) ส่วนโบนัส (หน้า 13) วางไว้หลังของบังคับเสร็จหมดแล้วเท่านั้น

**เว็บคู่มือนี้:** การเพิ่มการ์ดขั้น Problem และ Design ไม่ได้ออกเป็นงานก้อนเดียว แต่แตกเป็นเวอร์ชันละชิ้นที่ใช้ได้ในตัว: v2.0.23 การ์ดขั้น Problem 4 ใบ, v2.0.24 การ์ด Design 3 ใบแรก, v2.0.25 อีก 3 ใบ ทุกชิ้นตรวจและขึ้นเว็บทดลองได้ก่อนเริ่มชิ้นถัดไป ดูได้ใน [ประวัติการอัปเดต](/changelog)

ลองคิด: ถ้าวันที่ 3 ใช้เวลากับ Zod นานจนวันที่ 4 เริ่มช้าครึ่งวัน ควรตัดอะไรออกจากแผน หรือควรย้ายอะไร และต้องบอกใครก่อน

## ตัวเลือกอื่นที่คล้ายกัน

| ที่เก็บรายการงาน | ข้อดี | ข้อเสีย |
|---|---|---|
| **เช็กลิสต์ใน `NOTES.md`** | อยู่ใน repo เดียวกับโค้ด ไม่ต้องสมัครอะไร | พี่เลี้ยงต้องเปิดไฟล์ดูเอง ไม่มีแจ้งเตือน |
| GitHub Issues + Projects | ผูกงานกับ commit ได้ (`fixes #12`) มีบอร์ด ต้องทำ/กำลังทำ/เสร็จ | ต้องตั้งค่าบอร์ด เปิด Issue ทีละใบ |
| Trello / Notion | ลากการ์ดง่าย ทีมที่ไม่ใช่โปรแกรมเมอร์ใช้ได้ | แยกจากโค้ด ต้องคอยอัปเดตสองที่ |
| กระดาษโน้ตติดผนัง | เห็นทั้งแผนตลอดเวลา | ทำงานจากที่อื่นแล้วไม่เห็น พี่เลี้ยงตามไม่ได้ |

## ลองเอง

**โจทย์:** แตกวันที่ 3 ของงาน STARTER (Public API) เป็นงานชิ้นละไม่เกินครึ่งวัน พร้อมบรรทัด "เสร็จเมื่อ" ทุกชิ้น แล้วเรียงลำดับ

<Hint level={1}>เริ่มจาก Checklist วันที่ 3 (หน้า 14): endpoint 5 ทาง, Zod ทุก endpoint, รูปแบบคำตอบตาม spec และทดสอบด้วย Postman/Httpie ลองถามว่าข้อไหนต้องมีก่อนข้ออื่น</Hint>
<Hint level={2}>ตัวช่วยตอบ `ok` / `fail` (การ์ด [Hono](/learn/cards/hono)) และตัวจับ error กลาง (การ์ด [จัดการ error](/learn/cards/error-handling)) ใช้กับทุก endpoint จึงควรเป็นงานชิ้นแรก ส่วน 5 endpoint แบ่งตามที่ซับซ้อน: `GET /api/settings` อ่านแถวเดียว เร็ว แต่ `GET /api/services?category=&featured=` มีเงื่อนไขกรอง</Hint>
<Hint level={3}>ตรวจก่อนส่ง: ทุกชิ้นตอบได้ว่า "เริ่มเช้า เที่ยงเสร็จ", ทุกบรรทัด "เสร็จเมื่อ" เป็นสิ่งที่เห็นได้ (status, ข้อมูลในจอ) และงานทั้งหมดรวมกันแล้วไม่เกิน 2 ช่วง (เช้า + บ่าย) ถ้าเกิน แปลว่าวันที่ 3 แน่นเกินไป ให้เข้ารายการคำถามกับพี่เลี้ยง</Hint>
