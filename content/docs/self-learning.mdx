## เรื่องเล่า

สัปดาห์แรก บิตถามพี่ไบต์วันละ 15 ครั้ง ทุกครั้งพี่ไบต์ตอบได้ใน 1 นาที บิตรู้สึกว่าเร็วดี
สัปดาห์ที่สาม พี่ไบต์ไปประชุมลูกค้าทั้งวัน บิตติด error ตัวเดียวตั้งแต่เช้าถึงเย็น

วันรุ่งขึ้นพี่ไบต์มาดู แล้วไม่ได้ตอบ แต่ถามกลับ 3 ข้อ
1. *"error บอกว่าอะไร อ่านให้พี่ฟังหน่อย"*
2. *"ถ้าเอาคำว่า `ECONNREFUSED` ไปค้นใน docs ของ Node เจออะไร"*
3. *"ครั้งสุดท้ายที่มันยังทำงานได้ เราเปลี่ยนอะไรไป"*

บิตตอบข้อ 2 เสร็จก็รู้คำตอบเอง: ลืมเปิด container ของฐานข้อมูล
พี่ไบต์: *"15 คำตอบต่อวันของพี่ ช่วยบิตได้ 15 ครั้ง แต่ 3 คำถามนี้ช่วยบิตได้ทุกครั้งที่เหลือ"*

## 0. ทำไมต้องหาเองเป็น

ไม่ใช่เพราะพี่ไม่อยากตอบ แต่เพราะ
- **คำตอบหมดอายุ วิธีหาไม่หมดอายุ** เล่มนี้เองก็เจอมาแล้ว: Express 4 → 5, Zod 3 → 4, Tailwind v3 → v4, TypeScript 7 ที่ไม่โหลด `@types/*` ให้เอง คำตอบที่จำมาปีที่แล้วอาจผิดปีนี้ แต่คนที่เปิด changelog เป็นจะรู้ทันที
- **คนที่ช่วยเราไม่ได้อยู่ตลอด** ตอนตีสองที่ระบบลูกค้าล่ม คนที่อยู่หน้าจอคือเรา
- **ความเข้าใจเกิดตอนหาเอง** คำตอบที่มีคนยื่นให้จะลืมในสัปดาห์เดียว คำตอบที่เราเดินไปเจอเองจะจำได้ว่า "หาที่ไหน" และนั่นคือสิ่งที่ใช้ซ้ำได้

> **บทนี้ไม่ได้เปลี่ยนกฎเรื่อง AI ของทีม** (กฎยังเป็นตามหน้าแรกและ [บทที่ 16](/16-ai-pairing)) บทนี้คือทักษะพื้นฐานที่ใช้ได้ทั้งตอนมีและไม่มี AI และเป็นวิธีเดียวที่จะ **ตรวจได้ว่าคำตอบของ AI ถูกหรือเปล่า** ถ้าเปิดเอกสารทางการไม่เป็น ก็แยกไม่ออกว่า AI ตอบตามเวอร์ชันที่เราใช้หรือเวอร์ชันเก่า

> **เคล็ดลับ:** พี่ๆ Dev ก็ใช้บทนี้เหมือนกัน ข้อ 2–9 คือสิ่งที่คนทำงานมาหลายปีทำทุกวันจนเป็นนิสัย ส่วนข้อ 13 เขียนให้พี่เลี้ยงโดยตรง

## 2. อ่าน error ให้จบ แล้วดึง "ส่วนที่ค้นได้"

### 2.1 บรรทัดไหนสำคัญ

error ยาวไม่ได้แปลว่ายาก ส่วนใหญ่ต้องการแค่ 2–3 บรรทัด แต่ต้อง **อ่านให้ถึงบรรทัดเหล่านั้น**

| เจอแบบนี้ | อ่านตรงไหน | ทำไม |
|---|---|---|
| stack trace (`at ...` หลายบรรทัด) | บรรทัดแรก = **เกิดอะไร** · บรรทัด `at` แรกที่เป็นไฟล์ของเรา = **เกิดที่ไหน** | บรรทัดของ `node_modules` / `node:internal` คือทางที่โค้ดเดินผ่าน ไม่ใช่ต้นเหตุ ([บทที่ 9 ข้อ 2](/09-debugging#2-อ่าน-stack-trace)) |
| มี `[cause]:` หรือ `Caused by:` | **อ่านส่วน cause** ด้วยเสมอ | error ชั้นนอกมักเป็นคำกว้างๆ (`fetch failed`) ต้นเหตุจริงอยู่ข้างใน |
| error ของ `tsc` หลายบรรทัด (`is not assignable ...` ซ้อนกัน) | บรรทัดแรก + **บรรทัดสุดท้าย** | บรรทัดแรกบอกภาพรวม บรรทัดล่างสุดบอกว่าช่องไหนที่ไม่ตรงจริงๆ ([บทที่ 4 ข้อ 13](/04-typescript#13-อ่าน-error-ให้เป็น)) |
| npm / bun install พัง | หา `ERR!` / `error:` บรรทัดแรก และรหัส `E...` | ข้อความหลังจากนั้นมักเป็นผลต่อเนื่อง ([บทที่ 3](/03-node-yarn-bun)) |
| หน้าเว็บขาว ไม่มีอะไรขึ้น | DevTools > Console บรรทัดแดงบนสุด | error ฝั่งหน้าเว็บไม่ขึ้นใน terminal ([บทที่ 9 ข้อ 8](/09-debugging#8-ทัวร์-devtools-ใน-browser-ทีละแท็บ)) |
| API ตอบ 500 | **log ของ server** ไม่ใช่ browser | browser เห็นแค่ว่า "server พัง" ส่วนเหตุผลอยู่ฝั่ง server |

### 2.2 ลองกับของจริง: `[cause]` ที่คนส่วนใหญ่อ่านไม่ถึง

สร้างไฟล์ `fetch-error.mjs` ในโฟลเดอร์ทดลอง (`.mjs` = บอก Node ว่าไฟล์นี้ใช้ `import`/`await` ระดับบนสุดได้ โดยไม่ต้องมี `package.json`)
```js
const res = await fetch("http://localhost:3999/laptops");   // port นี้ไม่มีใครรอรับ
console.log(res.status);
```
```bash
node fetch-error.mjs
```
**ควรเห็น** (ตัดบางบรรทัด · ทดสอบกับ Node 26)
```
[TypeError: fetch failed] {
  [cause]: AggregateError [ECONNREFUSED]:
      at internalConnectMultiple (node:net:1426:18)
      ...
    code: 'ECONNREFUSED',
    [errors]: [
      Error: connect ECONNREFUSED ::1:3999
      ...
      Error: connect ECONNREFUSED 127.0.0.1:3999
```
ถ้าอ่านแค่บรรทัดแรกจะได้ `fetch failed` ซึ่งกว้างมาก (เน็ตหลุด? URL ผิด? server ล่ม?) แต่ส่วน `[cause]` บอกชัดว่า **`ECONNREFUSED` = ไปถึงเครื่องแล้ว แต่ไม่มีโปรแกรมไหนรอที่ port 3999** และบอกด้วยว่าลองทั้ง `::1` (IPv6) และ `127.0.0.1` (IPv4) แล้ว

ลองรันไฟล์เดียวกันด้วย Bun
```bash
bun fetch-error.mjs
```
**ควรเห็น** (ทดสอบกับ Bun 1.4)
```
TypeError: Unable to connect. Is the computer able to access the url?
  path: "http://localhost:3999/laptops",
 errno: 0,
  code: "ConnectionRefused"
```
ข้อความต่างกัน แต่ความหมายเดียวกัน นี่คือเหตุผลที่ต้อง **รู้ว่าตัวเองใช้ runtime อะไร** ก่อนค้น (ข้อ 4) เพราะคำตอบของ Node อาจใช้คำคนละคำกับของ Bun

### 2.3 ดึงส่วนที่ค้นได้ ตัดส่วนที่เป็นของเรา

ก่อนเอาไปค้น ให้แยก error เป็น 2 กอง

| ✅ เก็บไว้ (คนทั้งโลกเจอเหมือนกัน) | ❌ ตัดทิ้ง (มีแค่เครื่องเรา) |
|---|---|
| ชื่อ error: `TypeError`, `SyntaxError`, `ZodError` | path ในเครื่อง: `/Users/bit/project/src/...` |
| รหัส: `TS2345`, `ECONNREFUSED`, `EADDRINUSE`, `ERR_MODULE_NOT_FOUND`, `23505` (Postgres) | ชื่อตัวแปร ชื่อตาราง ชื่อไฟล์ของเรา |
| ประโยคหลักที่คงที่: `is not assignable to parameter of type` | ค่าเฉพาะ: id, port ที่เราตั้ง, เวลา, token |
| ชื่อ library + เวอร์ชัน: `drizzle-orm 0.45`, `zod 4` | ข้อมูลลูกค้าจริง (ห้ามเอาไปวางที่ไหนเลย บทที่ 9 ข้อ 7.1) |

ตัวอย่าง
```
src/routes/laptops.ts:12:15 - error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
```
คำค้นที่ดี: `TS2345 "is not assignable to parameter of type"` หรือแค่ `TS2345` ก็พอ (รหัสของ TypeScript ค้นได้ตรงมาก)

> **รหัส error คือของขวัญ** ระบบที่ดีใส่รหัสไว้ให้ค้นได้ตรงๆ เช่น Node มีหน้ารวม [Node.js Errors](https://nodejs.org/docs/latest/api/errors.html) (ค้น `ECONNREFUSED`, `ERR_MODULE_NOT_FOUND` ในหน้านั้น), PostgreSQL มี [ตารางรหัส error](https://www.postgresql.org/docs/current/errcodes-appendix.html) (`23505` = `unique_violation`), JavaScript มี [หน้ารวม error ของ MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Errors)

## 3. ทำให้เกิดซ้ำแบบเล็กที่สุด (Minimal reproduction)

**ทำไม:** บั๊กในโปรเจกต์จริงมีของอื่นปนเยอะ (DB, auth, router, state) ถ้าตัดของที่ไม่เกี่ยวออกจนเหลือ 5–10 บรรทัดที่ยังพังอยู่ จะเกิด 3 อย่าง
1. **บ่อยครั้งเจอคำตอบระหว่างตัด** เพราะพอตัดชิ้นหนึ่งแล้วหาย = ต้นเหตุอยู่ในชิ้นนั้น (หารครึ่งแบบ [บทที่ 9 ข้อ 1.1](/09-debugging#11-แต่ละขั้นทำอะไรจริงๆ))
2. ทดลองแก้ได้เร็ว รันไฟล์เดียวไม่ต้องเปิดทั้งระบบ
3. ถ้าต้องถามคนหรือเปิด issue คนอ่านเข้าใจใน 30 วินาที

**ขั้นตอน**
1. สร้างไฟล์ใหม่ในโฟลเดอร์ทดลอง (ไม่ใช่ในโปรเจกต์จริง)
2. ใส่เฉพาะสิ่งที่คิดว่าเกี่ยว แทนข้อมูลจาก DB/API ด้วยค่าที่เขียนตายตัวในไฟล์
3. รันแล้วดูว่ายังพังแบบเดิมไหม ถ้าไม่พัง แปลว่าของที่ตัดออกมีส่วนเกี่ยว ใส่กลับทีละชิ้น
4. ตัดต่อจนตัดอะไรออกอีกไม่ได้โดยที่บั๊กไม่หาย

ตัวอย่าง: หน้ารายการโน้ตบุ๊กแสดงราคารวมเป็น `"015001200"` แทน `2700` แทนที่จะไล่ทั้ง React + API ให้ลองเขียนแค่
```js
// repro.mjs
const laptops = [{ price: "1500" }, { price: "1200" }];   // จำลองข้อมูลจาก API (ราคาเป็นข้อความ)
console.log(laptops.reduce((sum, l) => sum + l.price, 0));
```
**ควรเห็น**
```
015001200
```
พังแบบเดียวกันในไฟล์ 2 บรรทัด → ตัด React, API, DB ออกจากผู้ต้องสงสัยได้หมด เหลือแค่ "ราคามาเป็น string" ซึ่งพาไปสู่คำถามที่ถูก: *"API ส่งราคาเป็น string เพราะอะไร และควรแปลง/ตรวจที่ไหน"* (คำตอบ: ตรวจด้วย Zod ตอนรับข้อมูล [บทที่ 4 ข้อ 11](/04-typescript#11-ข้อจำกัด-typescript-ไม่ได้ตรวจข้อมูลตอนรัน))

## 4. ถามเครื่องก่อนถามคน

โปรแกรมส่วนใหญ่ **บอกวิธีใช้ตัวเองได้** และบอกสถานะของเครื่องเราได้แม่นกว่าคนที่ไม่ได้นั่งหน้าเครื่องเรา

| อยากรู้ | คำสั่ง | ได้อะไร |
|---|---|---|
| คำสั่งนี้มีตัวเลือกอะไร | `<คำสั่ง> --help` เช่น `bun create vite --help`, `docker run --help`, `npx tsc --help` | รายการตัวเลือกของ **รุ่นที่ติดตั้งอยู่จริง** (ตรงกว่าบทความในเน็ต) |
| คำสั่งย่อยของ git | `git log -h` (สั้น) / `git log --help` (คู่มือเต็ม) | `-h` สรุปในหน้าจอ / `--help` เปิดคู่มือ (กด `q` ออก) |
| คู่มือคำสั่งระบบ (Mac/Linux/Git Bash) | `man ls` | คู่มือเต็ม กด `/` เพื่อค้นในหน้า, `q` ออก |
| ใช้รุ่นอะไรอยู่ | `node -v`, `bun -v`, `npm -v`, `git --version`, `docker --version` | เลขรุ่น ต้องใช้ทุกครั้งที่ค้นหรือถาม |
| library ตัวนี้ติดตั้งรุ่นไหน | `npm ls zod` | รุ่นที่ติดตั้งจริงใน `node_modules` (ไม่ใช่แค่ที่เขียนใน `package.json`) |
| ใครดึง library นี้มา | `npm explain esbuild` | สายว่า package ไหนต้องการมัน |
| รุ่นล่าสุดคืออะไร | `npm view zod version` | รุ่นล่าสุดบน npm (เทียบกับที่เราใช้) |

## 7. Changelog, Release notes และ Migration guide

**ใช้เมื่อ:** โค้ดจากบทความ/คู่มือ/เพื่อน ใช้กับเครื่องเราไม่ได้ ทั้งที่ "พิมพ์ตามเป๊ะ" ต้นเหตุมักเป็น **รุ่นไม่ตรง**

1. หาว่าเราใช้รุ่นไหน: `npm ls <ชื่อ>`
2. หาว่าโค้ดที่ copy มาเขียนสำหรับรุ่นไหน (ดูวันที่ หรือสังเกต syntax)
3. เปิด **Release notes** (มักอยู่ที่ `github.com/<เจ้าของ>/<ชื่อ>/releases`) หรือหน้า **Migration / Upgrade guide** ของเอกสาร แล้วค้นคำว่า **breaking** ในหน้านั้น

ตัวอย่างที่เจอจริงในเล่มนี้

| เครื่องมือ | เปลี่ยนอะไร | ถ้าไม่รู้จะเจอ |
|---|---|---|
| TypeScript 7 | ไม่โหลด `@types/*` ให้เอง ต้องใส่ `"types": ["node"]` | `TS2591: Cannot find name 'process'` ทั้งที่ติดตั้งแล้ว ([บทที่ 4](/04-typescript#9-ลงมือ-โปรเจกต์-typescript-ตั้งแต่ศูนย์)) |
| Zod 3 → 4 | ข้อความ error และบาง API เปลี่ยน | ผลไม่ตรงกับบทความเก่า |
| Tailwind v3 → v4 | ตั้งค่าด้วย CSS แทน `tailwind.config.js` | ทำตามบทความเก่าแล้วคลาสไม่ทำงาน |
| create-vite 9 | ถามเรื่อง linter และ "install and start now?" | สับสนตอนสร้างโปรเจกต์ ([บทที่ 11](/11-react#2-ลงมือ-สร้างโปรเจกต์)) |

> **นิสัยของมืออาชีพ:** ก่อนอัปเกรด library ตัวใหญ่ เปิด release notes อ่านหัวข้อ breaking changes ก่อนเสมอ ใช้เวลา 5 นาทีแต่ประหยัดได้ทั้งวัน

## 8. เปิดดูโค้ดและ type ของ library ใน `node_modules`

`node_modules` ไม่ใช่กล่องดำ ทุกอย่างที่เรา import มาเป็นไฟล์ที่เปิดอ่านได้ และ **type (`.d.ts`) คือเอกสารที่ตรงกับรุ่นที่ติดตั้งแน่นอน 100%**

**วิธีใน VS Code**
- **เอาเมาส์ชี้** ที่ชื่อฟังก์ชัน → เห็น type ที่รับและคืน
- **Go to Definition**: `F12` หรือ `⌘/Ctrl + คลิก` ที่ชื่อ → เปิดไฟล์ type ของ library ตรงบรรทัดนั้น
- **Peek**: `Option/Alt + F12` ดูในกรอบเล็กโดยไม่เปลี่ยนไฟล์

 **ลองเลย** ในไฟล์ `src/zod-demo.ts` ของบทที่ 4 กด `⌘/Ctrl + คลิก` ที่คำว่า `safeParse` จะเปิดไฟล์ประมาณ `node_modules/zod/v4/classic/schemas.d.ts` และเห็นบรรทัด
```ts
safeParse(data: unknown, params?: core.ParseContext<core.$ZodIssue>): parse.ZodSafeParseResult<core.output<this>>;
```
อ่านได้ว่า: รับ `data` เป็น **`unknown`** (อะไรก็ได้ เพราะหน้าที่ของมันคือตรวจของที่ยังไม่รู้) และคืนผลที่มีชนิดตาม schema (`output<this>`) ไม่ต้องอ่านเข้าใจทุกตัวอักษร แค่ได้ 2 ข้อนี้ก็ตอบคำถามว่า "ส่ง string ตรงๆ ได้ไหม" ได้แล้ว

**ที่อื่นใน `node_modules/<ชื่อ>/` ที่ควรรู้**
| ไฟล์ | ได้อะไร |
|---|---|
| `package.json` | รุ่นที่ติดตั้งจริง (`"version"`), ลิงก์เอกสาร (`"homepage"`), repo |
| `README.md` | วิธีใช้ฉบับย่อของรุ่นนั้น |
| `*.d.ts` | type ของทุกฟังก์ชัน หลายตัวมี comment อธิบายและตัวอย่างอยู่ในนั้น |

> **อ่านได้ แต่ห้ามแก้** ไฟล์ใน `node_modules` ถูกลบและติดตั้งใหม่ทุกครั้งที่ `install` และไม่ขึ้น Git แก้ตรงนั้นเท่ากับแก้บนเครื่องเราเครื่องเดียว

## 9. GitHub issues: ดูว่ามีคนเจอก่อนเราไหม

ถ้า error ดูเหมือนมาจากข้างใน library (stack trace มีแต่ `node_modules`) หรือเพิ่งเกิดหลังอัปเกรด มีโอกาสที่คนอื่นเจอแล้ว

1. เข้า repo ของ library (ลิงก์อยู่ใน `package.json` หรือหน้า npm) → แท็บ **Issues**
2. ลบ `is:open` ออกจากช่องค้นหา (ให้รวม **ที่ปิดแล้ว** ด้วย เพราะ issue ที่ถูกแก้แล้วจะถูกปิด และมักบอกว่าแก้ในรุ่นไหน) แล้วพิมพ์ส่วนที่ค้นได้ของ error เช่น `is:issue ECONNREFUSED` ([วิธีค้นของ GitHub](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests))
3. อ่าน **คำตอบของ maintainer** (มีป้าย Member/Owner/Collaborator) ก่อนคอมเมนต์ทั่วไป
4. ถ้าเจอว่าเป็นบั๊กที่แก้แล้วในรุ่นใหม่ → อัปเกรด (อ่าน release notes ก่อน ข้อ 7) / ถ้ายังไม่แก้ → ดูว่ามี workaround ไหม

> **เคล็ดลับ:** เจอ issue ที่ตรงกับเราแล้ว **กด แทนการคอมเมนต์ "+1"** คอมเมนต์ "+1" ทำให้คนที่ติดตาม issue ได้แจ้งเตือนโดยไม่มีข้อมูลใหม่
> ถ้าคิดว่าเจอบั๊กใหม่ของ library ให้คุยกับพี่เลี้ยงก่อนเปิด issue และต้องมี minimal reproduction (ข้อ 3) เสมอ

## 10. เป็ดยางและการเขียนคำถาม

ก่อนถามใคร ลองอธิบายปัญหาให้เป็ดยางฟังทีละบรรทัด ([บทที่ 9 ข้อ 5](/09-debugging#5-rubber-duck-debugging)) หรือเขียนคำถามตามเทมเพลตให้ครบ 4 ช่อง
```
🎯 กำลังทำ:      (ทำอะไรอยู่ ไฟล์ไหน endpoint ไหน)
✅ คาดว่าจะได้:   (ผลที่ควรเป็น)
❌ ได้จริง:       (ผลจริง + error เต็มๆ เป็นข้อความ ไม่ใช่รูป)
🔍 ลองแล้ว:       (ลองอะไรไปแล้ว ได้ผลอะไร + ลิงก์เอกสาร/issue ที่อ่านแล้ว)
```
**ทำไมได้ผล:** การเขียน "คาดว่าจะได้" บังคับให้เราคิดว่าความจริงต่างจากที่คิดตรงไหน และการเขียน "ลองแล้ว" บังคับให้เห็นว่ายังไม่ได้ลองอะไร ครึ่งหนึ่งของคำถามจะไม่ถูกส่ง เพราะเจอคำตอบระหว่างเขียน

(เทมเพลตเต็มพร้อมตัวอย่างอยู่ที่ [บทที่ 9 ข้อ 6](/09-debugging#6-ถามคนอื่นยังไงให้ได้คำตอบเร็ว))

## 11. บันได time-box และการถามพี่เลี้ยง

**ทำไมต้องจับเวลา:** มีกับดัก 2 แบบที่ตรงข้ามกัน
- **ถามเร็วเกิน** (ยังไม่อ่าน error เลย) → ไม่ได้ฝึก และพี่ต้องถามกลับ 3 รอบกว่าจะเริ่มช่วยได้
- **ดื้อนานเกิน** (ติดทั้งวันเพราะเกรงใจ) → เสียเวลาทั้งวันกับเรื่องที่พี่ชี้ได้ในนาทีเดียว และอาจเป็นเรื่องที่น้องหาเองไม่ได้จริงๆ เช่น สิทธิ์เข้าระบบ ค่าใน `.env` ที่ไม่มีใครให้

บันไดในข้อ 1 อยู่ตรงกลางระหว่างสองกับดักนี้

**ถึงขั้นที่ 5 แล้วยังไม่เจอ:** ท้ายทุกบทมีกล่อง **"ติดตรงไหนในบทนี้ ถามพี่เลี้ยงได้"** (เห็นเมื่อ login แล้ว) วางคำถาม 4 ช่องจากข้อ 10 ลงไปได้เลย เห็นแค่เรากับพี่เลี้ยง และระบบจำไว้ว่าถามจากบทไหน คำตอบจะขึ้นที่กล่องเดิม และรวมไว้ที่หน้า [คำถามของฉัน](/questions)

> **เคล็ดลับ:** คำถามที่บอกว่า **ลองอะไรไปแล้ว** ได้คำตอบตรงและเร็วกว่า เพราะพี่ไม่ต้องเดาว่าน้องรู้อะไรแล้วบ้าง และพี่จะตอบที่ "ขั้นที่น้องติด" ได้ ไม่ต้องเริ่มจากศูนย์
> **ไม่ต้องรอ 30 นาที** ถ้าเป็นเรื่องที่น้องหาเองไม่ได้: ไม่มีสิทธิ์เข้าระบบ, ต้องใช้ค่าลับที่ไม่มีใครให้, หรือ **สงสัยว่าความลับรั่ว** (แจ้งทันที [บทที่ 10](/10-security))

## 12. สมุดบันทึกการเรียนรู้ (Learning log)

**ทำไม:** บั๊กส่วนใหญ่ที่เจอ จะกลับมาอีกในหน้าตาใหม่ ถ้าจดไว้ ครั้งที่สองจะใช้ 2 นาทีแทน 2 ชั่วโมง และเมื่อย้อนอ่านจะเห็น **รูปแบบ** ว่าตัวเองพลาดเรื่องไหนบ่อย (เช่น ลืม `await` 5 ครั้งในเดือนเดียว) ซึ่งเป็นข้อมูลที่ดีที่สุดว่าควรเรียนอะไรเพิ่ม

**เก็บที่ไหน:** ไฟล์ข้อความใน repo ส่วนตัว (เช่น `learning-log.md`) หรือโน้ตที่ค้นได้ สำคัญคือ **ค้นได้** และ **จดทันทีที่แก้เสร็จ** (ถ้ารอตอนเย็นจะลืมรายละเอียด)

**รูปแบบ 5 บรรทัด**
```
## 2026-10-23 · ECONNREFUSED ตอนเรียก API
อาการ:   fetch failed (cause: ECONNREFUSED 127.0.0.1:5432)
สาเหตุ:  ยังไม่ได้ docker compose up ฐานข้อมูล
หาเจอยังไง: อ่าน [cause] → ค้น ECONNREFUSED ในเอกสาร Node errors → docker compose ps
ครั้งหน้า: เห็น ECONNREFUSED = เช็คก่อนว่าปลายทางเปิดอยู่ไหม
```
บรรทัด **"หาเจอยังไง"** สำคัญที่สุด เพราะมันคือวิธีที่ใช้ซ้ำได้กับปัญหาอื่น ไม่ใช่แค่คำตอบของปัญหานี้

> **เคล็ดลับ:** ทุกสัปดาห์ เลือกบันทึก 1 เรื่องมาเล่าให้พี่เลี้ยงหรือเพื่อนฟัง 2 นาที ถ้าเล่าได้โดยไม่เปิดโน้ต แปลว่าเข้าใจจริง

## 13. สำหรับพี่เลี้ยงและ Dev: ตอบยังไงให้น้องเก่งขึ้น

ข้อนี้เขียนให้พี่ๆ ที่ตอบคำถามในกล่องท้ายบทและหน้า admin โดยตรง น้องอ่านได้ จะได้รู้ว่าพี่ตอบแบบนี้เพราะอะไร

### 13.1 เป้าหมายของการตอบ

ไม่ใช่ "ให้บั๊กนี้หาย" แต่คือ **"ให้น้องแก้บั๊กแบบนี้ได้เองครั้งหน้า"** ถ้าเราตอบด้วยโค้ดที่แก้แล้ว บั๊กหายเร็วที่สุด แต่น้องได้เรียนแค่ว่า "ติดเมื่อไหร่ ถามพี่" ซึ่งเป็นบทเรียนที่เราไม่อยากสอน

### 13.2 บันไดคำใบ้ (hint ladder)

ตอบทีละขั้นจากบนลงล่าง หยุดทันทีที่น้องไปต่อได้

| ขั้น | พี่ทำอะไร | ตัวอย่างคำตอบ |
|---|---|---|
| 0 | ถามว่าลองอะไรแล้ว (ถ้าคำถามไม่ได้บอก) | "error เต็มๆ ว่าอะไร ลองอะไรไปแล้วบ้าง" |
| 1 | ชี้ **ที่ที่ต้องดู** | "อ่านส่วน `[cause]` ของ error อีกที มันบอกอะไร" |
| 2 | ให้ **คำค้น / ลิงก์เอกสาร** | "ลองค้น `ECONNREFUSED` ในหน้า Node errors" + ลิงก์ |
| 3 | อธิบาย **แนวคิด** ที่ขาด | "`ECONNREFUSED` แปลว่าไปถึงเครื่องแต่ไม่มีใครรอที่ port นั้น ตอนนี้ DB เราอยู่ที่ไหน" |
| 4 | ให้ **ตัวอย่างที่คล้าย** (ไม่ใช่โค้ดของน้อง) | ตัวอย่าง 5 บรรทัดในโฟลเดอร์ทดลอง ให้น้องเอาไปปรับเอง |
| 5 | **นั่งทำด้วยกัน** (pair) น้องเป็นคนพิมพ์ | พี่พูดความคิดออกมาดังๆ ว่ากำลังดูอะไร เพราะอะไร |

> **เคล็ดลับ:** ขั้น 1–2 ใช้ได้กับ **คำถามส่วนใหญ่** และใช้เวลาพี่น้อยที่สุด ขั้น 5 ใช้เวลามากที่สุดแต่ได้ผลที่สุดกับเรื่องที่น้องติดซ้ำ

### 13.3 หลักการตอบ

- **ลิงก์เอกสารมากกว่าโค้ด** ลิงก์ไปที่หัวข้อในเล่มนี้ หรือหน้าเอกสารทางการตรงหัวข้อ (ข้อ 5.4) น้องจะได้รู้ว่า "คำตอบแบบนี้อยู่ที่ไหน"
- **บอกว่าพี่หาเจอยังไง** เช่น "พี่เห็นคำว่า `23505` เลยไปเปิดตารางรหัส error ของ Postgres" วิธีหาสำคัญกว่าคำตอบ
- **ถามกลับให้น้องสรุป** "แก้ได้แล้วลองเขียนใน learning log ว่าสาเหตุคืออะไร" (ข้อ 12)
- **ชมคำถามที่ดี** คำถามที่มี 4 ช่องครบ บอกให้รู้ว่าดีเพราะอะไร พฤติกรรมที่ถูกชมจะเกิดซ้ำ
- **อย่าตอบเรื่องที่ถามแค่ "มันพัง"** ให้ตอบกลับด้วยเทมเพลต 4 ช่องแทน (ไม่ใช่เพราะดุ แต่เพราะยังตอบไม่ได้จริงๆ)

### 13.4 เมื่อไหร่ควรให้คำตอบตรงๆ ทันที

บันไดคำใบ้ไม่ใช่กฎตายตัว ให้คำตอบตรงๆ เมื่อ
- **เรื่องสภาพแวดล้อม/สิทธิ์** ที่น้องหาเองไม่ได้ (บัญชี, ค่าลับ, VPN, สิทธิ์ repo)
- **ความปลอดภัย** เช่น ความลับรั่ว ต้องแก้ก่อนสอน
- **ไม่ใช่สิ่งที่บทกำลังสอน** เช่น ติดเรื่อง config ของ editor ตอนเรียนบท React ตอบแล้วให้น้องกลับไปเรียนเรื่องหลัก
- **น้องผ่านบันไดมาครบแล้ว** และคำถามบอกชัดว่าลองอะไรไป ตอบตรงพร้อมอธิบาย "ทำไม" ได้เลย

### 13.5 ตัวอย่างคำตอบในกล่องถาม

❌ *"แก้บรรทัด 12 เป็น `await db.select()...` ครับ"* (บั๊กหาย แต่น้องไม่รู้ว่าทำไม)

✅
```
ดูจาก error บรรทัดแรก: "Promise { <pending> }" แปลว่าตัวแปรได้ Promise แทนข้อมูลจริง
ลองหาในไฟล์ว่าตรงไหนเรียกฟังก์ชันที่เป็น async แต่ไม่ได้รอผล
อ่านประกอบ: บทที่ 4 โบนัส A (กล่อง ⚠️ ท้ายหัวข้อ) และบทที่ 9 ข้อ 9
ถ้าแก้ได้แล้ว ช่วยเล่ากลับมาสั้นๆ ว่าเจอที่บรรทัดไหน และทำไมมันถึงพัง
```

### 13.6 Dev เองก็ใช้บันไดเดียวกัน

บันไดในบทนี้ไม่ได้มีไว้สำหรับน้องเท่านั้น งานของ Dev ที่มีประสบการณ์ก็คือขั้น 1–4 ที่ทำเร็วขึ้นจนเป็นนิสัย: อ่าน release notes ก่อนอัปเกรด, ทำ minimal reproduction ก่อนเปิด issue ให้ library, อ่าน `.d.ts` แทนการเดา เวลาน้องเห็นพี่ทำสิ่งเหล่านี้ให้ดูจริงๆ (พูดออกมาว่ากำลังทำอะไร) ได้ผลกว่าการบอกให้ทำ

## เช็คความเข้าใจ

<details>
<summary>1. error บรรทัดแรกเขียนว่า `TypeError: fetch failed` อย่างเดียว ควรทำอะไรต่อก่อนค้น Google?</summary>

อ่านต่อให้ถึงส่วน `[cause]` เพราะ `fetch failed` เป็น error ชั้นนอกที่กว้างมาก ต้นเหตุจริง (เช่น `ECONNREFUSED`, `ENOTFOUND`, certificate) อยู่ใน cause และเป็นคำที่เอาไปค้นได้ตรงกว่า

</details>

<details>
<summary>2. จาก error `/Users/bit/shop/src/db.ts:8:3 - error TS2307: Cannot find module 'drizzle-orm' or its corresponding type declarations.` ควรค้นด้วยคำว่าอะไร และก่อนค้นควรรันคำสั่งไหน?</summary>

ค้น `TS2307 "Cannot find module"` (ตัด path ของเราทิ้ง) แต่ก่อนค้นให้รัน `npm ls drizzle-orm` ก่อน ถ้าขึ้น `(empty)` แปลว่ายังไม่ได้ติดตั้งในโปรเจกต์นี้ แก้ได้ทันทีโดยไม่ต้องค้นเลย

</details>

<details>
<summary>3. Guide กับ API Reference ต่างกันยังไง และควรเปิดอันไหนเมื่อ "อยากรู้ว่า `useEffect` รับอะไร และ cleanup ทำงานตอนไหน"?</summary>

Guide อธิบายเป็นเรื่องว่าทำ X ยังไง ทำไม / Reference เป็นรายการฟังก์ชันพร้อม parameter และค่าที่คืน คำถามนี้รู้ชื่อฟังก์ชันแล้ว ถามเรื่องสิ่งที่รับและพฤติกรรม เปิด Reference (`react.dev/reference/react/useEffect`) ถ้ายังงงเรื่องแนวคิดค่อยถอยไปอ่าน Guide

</details>

<details>
<summary>4. เจอคำตอบใน Stack Overflow ปี 2020 ที่คะแนนสูงมาก แต่ใช้กับโปรเจกต์แล้วไม่ได้ น่าจะเพราะอะไร และควรไปดูที่ไหนต่อ?</summary>

น่าจะเป็นคนละรุ่นกับที่เราใช้ ให้เช็ครุ่นด้วย `npm ls` แล้วเปิด release notes / migration guide ของ library ค้นคำว่า breaking หรือดูเอกสารทางการรุ่นปัจจุบัน

</details>

<details>
<summary>5. ทำไมการเขียนคำถาม 4 ช่อง (ทำอะไร / คาดว่า / ได้จริง / ลองแล้ว) มักทำให้เจอคำตอบเองก่อนส่ง?</summary>

เพราะบังคับให้แยก "สิ่งที่คิด" กับ "สิ่งที่เกิดจริง" ออกจากกัน และบังคับให้เห็นว่ายังไม่ได้ลองอะไร เป็นเป็ดยางแบบเขียน

</details>

<details>
<summary>6. (สำหรับพี่เลี้ยง) น้องถามว่า "API ได้ 500 ครับ" อย่างเดียว ควรตอบยังไง?</summary>

ยังไม่ตอบวิธีแก้ ถามกลับตามขั้น 0 ของบันไดคำใบ้ พร้อมชี้ที่ดู เช่น "500 แปลว่า server พัง ลองเปิด log ของ server (terminal ที่รัน API หรือ `docker compose logs api`) แล้ววาง error เต็มๆ พร้อมบอกว่าส่งอะไรไป และลองอะไรไปแล้ว" แบบนี้น้องได้เรียนว่า 500 ต้องไปดูที่ไหนด้วย

</details>

1. **แก้ error 3 ตัวโดยใช้แค่เอกสารทางการ** สร้างแต่ละไฟล์ในโฟลเดอร์ทดลอง รัน อ่าน error แล้วหาคำอธิบายจาก **เอกสารทางการเท่านั้น** (ข้อ 5.4) จดใน learning log ว่า (ก) ส่วนที่ค้นได้คืออะไร (ข) ลิงก์ไหนให้คำตอบ (ค) แก้ยังไง
   - `err-a.mjs`: `const x = 1; x = 2;` (ใบ้: ค้นใน MDN หน้ารวม error)
   - `err-b.mjs`: `import { formatBaht } from "./money.mjs";` โดยที่ `money.mjs` มีแค่ `export default function formatBaht() {}` (ใบ้: ค้นใน MDN เรื่อง `import`)
   - `err-c`: เปิด terminal 2 หน้าต่าง รันคำสั่งเดียวกันนี้ในทั้งสองหน้าต่าง (ตัวแรกจะค้างไว้เป็น server ตัวที่สองจะพัง) `node -e "require('http').createServer().listen(3000)"` (ใบ้: ค้นรหัสในหน้า Node errors · เสร็จแล้วกด `Ctrl + C` ปิดตัวแรก)
2. **คั่นหน้าเอกสาร** สร้างโฟลเดอร์ bookmark ในเบราว์เซอร์ใส่ลิงก์จากตารางข้อ 5.4 ที่ตรงกับบทที่กำลังเรียน แล้วเปิดแต่ละอันหา **ช่องค้นหา** และ **ตัวเลือกเวอร์ชัน** ให้เจอ (บางเว็บไม่มีตัวเลือกเวอร์ชัน จดไว้ว่าเว็บไหน)
3. **อ่าน type แทนการเดา** ในโปรเจกต์ `ts-basic` ใช้ Go to Definition ตอบว่า (ก) `z.coerce.number()` รับ input เป็นชนิดอะไร (ข) `JSON.parse` คืนชนิดอะไร (ค) ทำไมข้อ (ข) ถึงทำให้บทที่ 4 แนะนำให้ประกาศผลเป็น `unknown`
4. **Learning log สัปดาห์แรก** จดอย่างน้อย 3 รายการตามรูปแบบข้อ 12 แล้วเลือก 1 รายการเล่าให้พี่เลี้ยงฟัง

<details>
<summary> แนวเฉลยข้อ 1 และ 3 (ลองเองก่อนค่อยเปิด)</summary>

- `err-a`: `TypeError: Assignment to constant variable.` → MDN หน้า "TypeError: invalid assignment to const" อธิบายว่า `const` ห้ามกำหนดค่าใหม่ ใช้ `let` ถ้าต้องเปลี่ยนค่า
- `err-b`: `SyntaxError: The requested module './money.mjs' does not provide an export named 'formatBaht'` → MDN หน้า `import` อธิบายว่า default import ไม่มี `{}` แก้เป็น `import formatBaht from "./money.mjs"`
- `err-c`: `Error: listen EADDRINUSE: address already in use :::3000` → Node errors หน้า Common system errors อธิบาย `EADDRINUSE` = port ถูกใช้อยู่ ปิดตัวเดิมหรือเปลี่ยน port
- ข้อ 3: (ก) `z.coerce.number()` ฝั่ง input เป็น `unknown` (รับอะไรก็ได้ แล้วแปลงเป็นตัวเลขก่อนตรวจ) (ข) `JSON.parse(text: string, ...): any` (ค) `any` ปิดการตรวจทั้งหมด ถ้าเอาผลไปใช้ต่อ TS จะไม่เตือนอะไรเลย ประกาศเป็น `unknown` จึงบังคับให้ตรวจ (ด้วย Zod) ก่อนใช้

## ผ่านด่าน

- [ ] อ่าน error ได้ถึงส่วน `[cause]` และบอกได้ว่าบรรทัดไหน "เกิดอะไร" บรรทัดไหน "เกิดที่ไหน"
- [ ] ดึงส่วนที่ค้นได้ออกจาก error และตัดส่วนที่เป็นของเราทิ้งได้
- [ ] ทำ minimal reproduction ของบั๊กให้เหลือไฟล์เดียวได้
- [ ] ใช้ `--help`, `npm ls`, `npm view`, `git status`, Go to Definition หาคำตอบก่อนค้นเน็ต
- [ ] เปิดเอกสารทางการของ stack ได้ทุกตัว แยก Guide กับ Reference ออก และเลือกเวอร์ชันให้ตรง
- [ ] ค้นด้วยข้อความ error ในเครื่องหมายคำพูด และเช็ควันที่/รุ่นของคำตอบเสมอ
- [ ] ค้น GitHub issues รวมที่ปิดแล้วได้
- [ ] ใช้บันได time-box และเขียนคำถาม 4 ช่องก่อนถามในกล่องท้ายบท
- [ ] มี learning log อย่างน้อย 3 รายการ
- [ ] (พี่เลี้ยง) ตอบคำถามด้วยบันไดคำใบ้และลิงก์เอกสาร มากกว่าโค้ดสำเร็จ
