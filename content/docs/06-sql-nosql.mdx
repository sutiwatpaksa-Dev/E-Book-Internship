> **⚡ สรุป 30 วินาที**
> - ฐานข้อมูลมีหลาย **ประเภท** เพราะข้อมูลมีหลายหน้าตา และถูกใช้คนละแบบ ไม่มีตัวไหนเก่งทุกงาน
> - **Relational (SQL)** เก็บเป็นตารางที่เชื่อมกันด้วย key มีกฎเข้ม ไว้ใจได้เรื่องเงิน (ACID) งานส่วนใหญ่เริ่มที่กลุ่มนี้
> - **NoSQL** เป็นชื่อรวมของ 4 ตระกูล: **document, key-value, wide-column, graph** แต่ละตระกูลเก่งคนละโจทย์
> - ประเภทเฉพาะทางที่จะเจอในงานจริง: **search engine** (ค้นข้อความ), **vector database** (ค้นตามความหมาย งาน AI), **time-series** (ข้อมูลที่เรียงตามเวลา)
> - เลือกจาก "ข้อมูลหน้าตาแบบไหน ถูกอ่าน/เขียนยังไง ผิดพลาดได้แค่ไหน" ไม่ใช่จากความดัง · ไม่แน่ใจ → **เริ่มที่ PostgreSQL** (ทีมใช้)
> - ลงมือ: คำสั่ง SQL หลัก `SELECT` `INSERT` `UPDATE` `DELETE` `JOIN` `GROUP BY` · index · NULL (`IS NULL` ไม่ใช่ `= NULL`) · transaction

## 1. ปัญหา: ทำไมต้องมีฐานข้อมูล และทำไมมีหลายประเภท

เมื่อระบบจริงต้อง:
- ค้นข้อมูลหลักล้านแถวในเสี้ยววินาที ⚡
- ให้หลายคนบันทึกพร้อมกันโดยไม่ชน 👥
- กันข้อมูลผิด เช่น rental ของลูกค้าที่ไม่มีอยู่จริง 🛡️
- ไฟดับกลางทางแล้วข้อมูลไม่เสีย 🔌

นี่คืองานของ **Database** ไฟล์ Excel หรือไฟล์ JSON ธรรมดาทำ 4 ข้อนี้ไม่ได้ เพราะไม่มีใครคอยคุมว่าใครเขียนอะไรเมื่อไร

> 💡 **ฐานข้อมูลคือโปรแกรมที่รันอยู่ตลอดเวลา** (เรียกว่า **database server**) คล้ายร้านอาหารที่เปิดรอลูกค้า
> โค้ดของเรา (หรือเครื่องมืออย่าง `psql`) เป็น "ลูกค้า" ที่ **ส่งคำสั่ง** ไปหาแล้วรอคำตอบ
> ส่วนข้อมูลจริงถูกเก็บเป็นไฟล์ของ server ในเครื่อง/ใน Docker volume ไม่ได้อยู่ในโค้ดเรา
> (มีข้อยกเว้น เช่น SQLite ที่ไม่มี server แยก ทั้งฐานข้อมูลเป็นไฟล์เดียวที่แอปเปิดเอง)

**แล้วทำไมไม่มีฐานข้อมูลแบบเดียวที่ใช้ได้ทุกงาน?** เพราะโจทย์ต่างกันใน 3 เรื่อง

| คำถาม | ตัวอย่างคำตอบที่ต่างกัน |
|---|---|
| ข้อมูล **หน้าตา** แบบไหน | ตารางที่อ้างถึงกัน · เอกสารก้อนเดียวที่รูปร่างไม่เท่ากัน · คู่ "กุญแจ → ค่า" · เครือข่ายคนรู้จักกัน · ข้อความยาว · ตัวเลขจาก sensor ทุกวินาที |
| ถูก **อ่าน/เขียน** แบบไหน | ดึงตามกุญแจตัวเดียว · JOIN หลายตารางแล้วสรุปผล · ค้นคำในข้อความ · หา "ของที่คล้ายกัน" · เขียนเข้ามหาศาลแต่แทบไม่แก้ |
| **ผิดพลาด** ได้แค่ไหน และ **โต** แค่ไหน | เงิน/สต็อกผิดไม่ได้เลย · cache หายแล้วสร้างใหม่ได้ · ข้อมูลโตจนเครื่องเดียวรับไม่ไหว |

ฐานข้อมูลแต่ละประเภทถูกออกแบบมาให้เก่งกับคำตอบชุดหนึ่ง จึงแบ่งได้เป็น 3 กลุ่มใหญ่ในบทนี้

![NoSQL 4 ประเภท ได้แก่ Document, Key-Value, Wide-Column และ Graph พร้อมตัวอย่างและงานที่เหมาะ](/img/06-nosql-types.svg)
*ภาพนี้แสดง 4 ตระกูลของ NoSQL (กลุ่มที่ 2) · กลุ่มที่ 1 คือ Relational และกลุ่มที่ 3 คือฐานข้อมูลเฉพาะทาง*

| กลุ่ม | เก่งเรื่อง | อยู่ข้อ |
|---|---|---|
| 1. Relational (SQL) | ข้อมูลที่อ้างถึงกัน ต้องถูกต้องเสมอ | ข้อ 2 |
| 2. NoSQL (document, key-value, wide-column, graph) | รูปร่างยืดหยุ่น อ่านตามกุญแจเร็ว ขยายหลายเครื่อง ความสัมพันธ์ลึก | ข้อ 3 |
| 3. เฉพาะทาง (search, vector, time-series) | งานค้นและงานข้อมูลเฉพาะแบบ ที่สองกลุ่มแรกทำได้ไม่ดี | ข้อ 4 |

## 2. กลุ่มที่ 1: Relational Database (SQL)

**คืออะไร:** ฐานข้อมูลที่เก็บเป็น **ตาราง** คล้าย Excel แต่ **มีกฎเข้มงวด** และ **ตารางอ้างถึงกันได้** ("relational" มาจากคำว่า relation ในคณิตศาสตร์ ซึ่งหมายถึงตาราง)
**SQL** (อ่านว่า "เอส-คิว-แอล" หรือ "ซีควล") คือ **ภาษา** ที่ใช้สั่งฐานข้อมูลกลุ่มนี้ ทั้งสร้าง เพิ่ม ค้น แก้ ลบ คนจึงเรียกกลุ่มนี้สั้นๆ ว่า "SQL database"
💡 relational database = **ตู้เอกสารของสำนักงานที่มีระเบียบ** 🗂️ ทุกแฟ้มมีแบบฟอร์มเดียวกัน และอ้างถึงแฟ้มอื่นด้วยเลขที่ ไม่ถ่ายเอกสารซ้ำ

**ข้างในมีอะไร**

| คำ | ความหมาย | 💡 เทียบ Excel |
|---|---|---|
| **Table** | ตารางเก็บเรื่องเดียวกัน | 1 sheet |
| **Row** | 1 รายการ | 1 แถว |
| **Column** | คุณสมบัติ มีชนิดข้อมูลกำหนด | 1 คอลัมน์ (แต่ใส่มั่วไม่ได้) |
| **Schema** | โครงสร้าง: ตารางอะไร คอลัมน์อะไร ชนิดอะไร | หัวตารางที่ล็อกไว้ |
| **Primary Key (PK)** | คอลัมน์ระบุแถวแบบไม่ซ้ำ | เลขบัตรประชาชน 🪪 |
| **Foreign Key (FK)** | คอลัมน์ที่ชี้ไป PK ของอีกตาราง | การอ้างอิงเลขบัตรของคนอื่น |
| **Constraint** | กฎที่ฐานข้อมูลตรวจให้ทุกครั้ง เช่น `NOT NULL`, `UNIQUE`, `CHECK`, FK | การล็อกช่องไม่ให้กรอกผิด (Excel ทำได้แค่บางส่วน และข้ามได้ง่าย) |

![ภาพโครงสร้างตาราง customers แสดง column, row, cell และคอลัมน์ id ที่เป็น primary key](/img/06-table-anatomy.svg)
*ตาราง 1 ตาราง = หลายคอลัมน์ (แนวตั้ง) x หลายแถว (แนวนอน) · แต่ละคอลัมน์มีชนิดข้อมูลและกฎของตัวเอง*

**ตัวอย่าง: ร้านเช่าโน้ตบุ๊ค**

`customers`
| id (PK) | name | phone |
|---|---|---|
| 1 | สมชาย | 081-111-1111 |
| 2 | สมหญิง | 082-222-2222 |
| 3 | มานี | 083-333-3333 |

`rentals`
| id (PK) | customer_id (FK) | laptop | price_per_month |
|---|---|---|---|
| 1 | 1 | Lenovo T14 | 1500 |
| 2 | 1 | Dell 5420 | 1200 |
| 3 | 2 | HP 840 | 1300 |

`customer_id` ชี้ไปที่ `customers.id` → สมชายเช่า 2 เครื่อง สมหญิง 1 เครื่อง มานียังไม่เคยเช่า

> 💡 **ทำไมไม่เขียนชื่อลูกค้าซ้ำลงใน rentals เลย?**
> เพราะพอเปลี่ยนเบอร์ต้องตามแก้ทุกแถว (ปัญหาในเรื่องเล่า!) การเก็บแต่ละเรื่องไว้ **ที่เดียว** แล้วอ้างอิงกัน เรียกว่า **Normalization**
> และ FK ยังกันไม่ให้สร้าง rental ของลูกค้า id 99 ที่ไม่มีจริง

### Primary Key และ Foreign Key ต่างกันยังไง

| | Primary Key (PK) | Foreign Key (FK) |
|---|---|---|
| หน้าที่ | บอกว่า "แถวนี้คือใคร" | บอกว่า "แถวนี้เกี่ยวกับแถวไหนของอีกตาราง" |
| ซ้ำได้ไหม | **ไม่ได้** และห้ามว่าง | ซ้ำได้ (สมชายมีหลาย rental → `customer_id = 1` ซ้ำหลายแถว) |
| มีกี่ตัวต่อตาราง | 1 ชุดต่อตาราง (ชุดนั้นอาจมีหลายคอลัมน์รวมกัน เช่น `order_items` ในข้อ 7) | กี่ตัวก็ได้ |
| ตัวอย่าง | `customers.id` | `rentals.customer_id` |

เคล็ดลับเลือก PK: ใช้ **เลขรันอัตโนมัติ** (`id`) ที่ไม่มีความหมายทางธุรกิจ ไม่ควรใช้เบอร์โทรหรืออีเมลเป็น PK เพราะคนเปลี่ยนเบอร์/อีเมลได้ แต่ถ้าแก้ PK ทุกตารางที่อ้างถึงต้องแก้ตาม

### ความสัมพันธ์ 3 แบบ (ER Diagram)

| แบบ | ตัวอย่าง | ทำยังไงในตาราง |
|---|---|---|
| **1 : 1** | คน 1 คน ↔ บัตรประชาชน 1 ใบ | ใส่ FK ที่ฝั่งใดฝั่งหนึ่ง และสั่ง `UNIQUE` กันซ้ำ |
| **1 : N** (เจอบ่อยสุด) | ลูกค้า 1 คน → หลาย rental | ใส่ FK ที่ฝั่ง "N" (ตาราง rentals) |
| **N : M** | ออเดอร์มีหลายสินค้า สินค้าอยู่ในหลายออเดอร์ | ต้องมีตารางกลาง `order_items` ที่มี FK 2 ตัว |

![ER diagram แสดงความสัมพันธ์ 1:1, 1:N และ N:M พร้อมตารางกลาง](/img/06-er-diagram.svg)
*อ่านแผนภาพ ER: ขีดตั้ง | คือฝั่ง "1", ขา 3 แฉกคือฝั่ง "N (หลายแถว)" · N:M แตกเป็น 1:N สองเส้นผ่านตารางกลาง*

### Normalization ในภาษาคน

Normalization ไม่ได้ซับซ้อน มีหลักจำง่ายๆ 3 ข้อ:

1. **1 ช่องใส่ 1 ค่า** ห้ามยัดหลายค่าในช่องเดียว เช่น `laptop = 'T14, Dell, HP'` (ค้นและนับไม่ได้) → แยกเป็นหลายแถว
2. **1 เรื่อง 1 ตาราง** ข้อมูลของลูกค้าอยู่ใน `customers` ที่เดียว ที่อื่นอ้างด้วย `customer_id`
3. **ข้อมูลที่ซ้ำให้แยกตารางออกไป** ถ้าเห็นค่าเดิมๆ ซ้ำเต็มคอลัมน์ (ชื่อ/เบอร์ลูกค้าซ้ำในทุกแถว rental) แปลว่าควรแยก

```text
❌ ก่อน (ซ้ำ)                                  ✅ หลัง (แยกตาราง)
rentals                                        customers            rentals
id | customer_name | phone  | laptop          id | name | phone    id | customer_id | laptop
1  | สมชาย         | 081... | T14             1  | สมชาย | 081...  1  | 1           | T14
2  | สมชาย         | 081... | Dell                                 2  | 1           | Dell
(สมชายเปลี่ยนเบอร์ = ต้องแก้ทุกแถว)             (เปลี่ยนเบอร์ = แก้ที่เดียว)
```

> 💡 **ไม่ต้องจำชื่อ "รูปแบบปกติที่ 1/2/3 (1NF/2NF/3NF)"** ถ้ารักษา 3 ข้อข้างบนก็ถือว่า normalize พอใช้แล้ว
> บางกรณีเขาตั้งใจ **ซ้ำข้อมูลเพื่อความเร็ว** (denormalize) เช่น เก็บ `total` ของบิลไว้ในบิลเลย แต่ทำเมื่อรู้ว่าทำไมเท่านั้น

**อีกสองอย่างที่อยู่ข้างในทุกตัวของกลุ่มนี้** (ลงมือในข้อ 7–8)
- **Index:** สารบัญที่ทำให้ค้นเร็วโดยไม่ต้องไล่อ่านทุกแถว
- **Transaction (ACID):** มัดหลายคำสั่งให้ "สำเร็จทั้งหมดหรือไม่เกิดอะไรเลย" และกันคนทำพร้อมกันไม่ให้ชน นี่คือเหตุผลหลักที่ระบบเงิน/สต็อกเลือกกลุ่มนี้

**ในกลุ่มนี้มีใครบ้าง**

<ToolTable group="db-relational" />

ตารางนี้ไม่ได้ให้จำทุกตัว ดูแค่ช่อง **ระดับ**: 🟢 ทีมใช้ (ลงมือในบทนี้) · 🔵 ควรรู้จัก (เจอบ่อยในงานจริง) · ⚪ รู้ว่ามี (เจอแล้วบอกได้ว่าอยู่กลุ่มไหนก็พอ)

**ตัวในกลุ่มเหมือนกันตรงไหน ต่างกันตรงไหน**

| หัวข้อ | เหมือนกัน / ต่างกัน |
|---|---|
| แนวคิด | ✅ เหมือนกัน: ตาราง, PK/FK, constraint, JOIN, index, transaction เรียนครั้งเดียวใช้ได้ทุกตัว |
| ภาษา SQL | ✅ คำสั่งหลัก (`SELECT` `INSERT` `JOIN` `GROUP BY`) เหมือนกัน · ⚠️ รายละเอียดต่างกันบ้าง เช่น เลขรันอัตโนมัติ ชนิดข้อมูล JSON (ดูตารางเทียบใน [บทที่ 7](/07-mysql-postgres)) |
| รันแบบไหน | ส่วนใหญ่เป็น **server** ที่โค้ดต่อเข้าไป · SQLite เป็น **ไฟล์เดียวที่แอปเปิดเอง** ไม่มี server |
| ขยายเมื่อข้อมูลโต | ส่วนใหญ่ขยาย **แนวตั้ง** (เครื่องแรงขึ้น) และเพิ่ม **เครื่องสำเนาไว้อ่าน** (read replica) ได้ · กลุ่ม **distributed SQL** (เช่น CockroachDB) กระจายข้อมูลไปหลายเครื่องให้เอง |
| ค่าใช้จ่าย | PostgreSQL, MySQL, MariaDB, SQLite ใช้ฟรี · SQL Server, Oracle มีรุ่นที่ต้องซื้อ license |

> 🤔 **"SQL ขยายไม่ได้ ต้องใช้ NoSQL" จริงไหม?** ไม่จริงทั้งหมด เครื่องเดียวที่ตั้งค่าดีรับงานได้มากกว่าที่คนส่วนใหญ่คิด และเพิ่ม read replica ช่วยรับงานอ่านได้ ปัญหา "ใหญ่เกินเครื่องเดียว" เกิดกับระบบขนาดใหญ่มากเท่านั้น งานส่วนใหญ่ที่เราจะเจอไม่ถึงจุดนั้น

## 3. กลุ่มที่ 2: NoSQL (4 ตระกูล)

**คืออะไร:** **NoSQL** ("Not only SQL") = ชื่อเรียกรวมของฐานข้อมูลที่ **ไม่ได้เก็บเป็นตารางที่อ้างถึงกัน** ไม่ใช่ผลิตภัณฑ์เดียว และไม่ได้แปลว่า "ห้ามใช้ SQL"
**เกิดมาทำไม:** ช่วงที่เว็บใหญ่ๆ มีผู้ใช้หลักร้อยล้าน ข้อมูลโตจนเครื่องเดียวรับไม่ไหว และรูปร่างข้อมูลเปลี่ยนเร็วจนการแก้ schema ทุกครั้งเป็นภาระ จึงเกิดฐานข้อมูลที่ยอม **ลดกฎบางอย่าง** (เช่น JOIN, schema ตายตัว) เพื่อแลกกับ **ขยายไปหลายเครื่องง่าย** หรือ **อ่านตามกุญแจเร็วมาก**

**ข้างในมีอะไร: 4 ตระกูล**

| ประเภท | เก็บแบบไหน | 💡 เปรียบเทียบ | ตัวอย่าง | ใช้กับ |
|---|---|---|---|---|
| **Document** | เอกสาร JSON | แฟ้ม 1 แฟ้มต่อ 1 เรื่อง 📁 | MongoDB, Firestore | ข้อมูลรูปร่างหลากหลาย อ่านเป็นก้อน |
| **Key-Value** | กุญแจ → ค่า | ตู้ล็อกเกอร์ รู้เลขตู้เปิดได้ทันที 🔑 | Redis, Valkey | cache, session, ตัวนับ |
| **Wide-Column** | แถวที่แบ่งกลุ่มตามกุญแจ กระจายไปหลายเครื่อง | สมุดหลายเล่มแยกตามหมวด แต่ละหน้าจดไม่เหมือนกัน | Cassandra | log, IoT ข้อมูลเขียนเข้ามหาศาล |
| **Graph** | จุด (node) และเส้นเชื่อม (relationship) | แผนผังความสัมพันธ์ 🕸️ | Neo4j | เครือข่ายเพื่อน, ระบบแนะนำ, ตรวจโกง |

**ตระกูล Document:** ข้อมูลชุดเดียวกับข้อ 2 ในแบบ Document
```json
{
  "_id": "665f...",
  "name": "สมชาย",
  "phone": "081-111-1111",
  "rentals": [
    { "laptop": "Lenovo T14", "pricePerMonth": 1500 },
    { "laptop": "Dell 5420",  "pricePerMonth": 1200 }
  ]
}
```
rental **ฝังอยู่ในเอกสารลูกค้าเลย (embed)** ดึงครั้งเดียวได้ครบ ไม่ต้อง JOIN แลกกับการที่ข้อมูลเดียวกันอาจไปซ้ำอยู่หลายเอกสาร (เช่น ชื่อรุ่นเครื่อง)

> 💡 **Embed หรือ Reference?**
> - **Embed:** ข้อมูลที่อ่านพร้อมกันเสมอและไม่โตไม่จำกัด เช่น ที่อยู่ลูกค้า
> - **Reference (เก็บแค่ id):** ข้อมูลที่ใช้หลายที่ หรือโตเรื่อยๆ เช่น ประวัติสั่งซื้อหลายพันรายการ (MongoDB จำกัดขนาด 1 เอกสารไว้ที่ 16 MiB)

**ตระกูล Key-Value:** "ตั้งค่า / อ่านค่า" ตามชื่อกุญแจ ไม่มีตาราง ไม่มี JOIN ตัวอย่าง Redis
```text
SET session:abc123 "user-1" EX 3600     # เก็บ session 1 ชั่วโมงแล้วหายเอง
GET session:abc123                       # ได้ "user-1" ทันที (เร็วมาก เพราะอยู่ใน RAM)
```
เพราะข้อมูลหลักอยู่ใน RAM จึงเร็ว ค่าเริ่มต้นของ Redis บันทึกลงดิสก์เป็นรอบๆ (snapshot) ถ้าไฟดับ ข้อมูลที่เขียนหลังรอบล่าสุดจะหาย (เปิดโหมด AOF ที่จดทุกการเขียนได้ แต่แลกกับความเร็ว) งานที่เหมาะจึงเป็นข้อมูลที่ "หายแล้วสร้างใหม่ได้"

**ตระกูล Wide-Column:** ข้อมูลถูกแบ่งกลุ่มด้วย **partition key** แล้วกระจายไปเก็บหลายเครื่อง แต่ละตัวจัดเครื่องต่างกัน: **Cassandra** ให้ทุกเครื่องเท่าเทียมกัน (ไม่มีเครื่องหลัก) เครื่องหนึ่งพังระบบยังทำงานต่อได้ ส่วนตัวอื่นในตระกูลเดียวกัน เช่น HBase และ Google Bigtable มีเครื่องควบคุมกลางคอยแบ่งงาน (จึงอย่าเหมาว่า "wide-column = ไม่มีเครื่องหลัก" ให้ดูเอกสารของตัวที่ใช้) ภาษาที่ใช้ (CQL ของ Cassandra) หน้าตาคล้าย SQL แต่ **ไม่มี JOIN** ต้องออกแบบตาราง **ตามคำถามที่จะถาม** เช่น "log ของเครื่อง X วันนี้" ไม่ใช่ตามความสัมพันธ์ของข้อมูล

**ตระกูล Graph:** เก็บ "ความสัมพันธ์" เป็นข้อมูลหลัก คำถามอย่าง "เพื่อนของเพื่อนของบิตที่ชอบเกมเดียวกัน" ใน SQL ต้อง JOIN ตัวเองหลายชั้น แต่ใน graph คือการเดินตามเส้น ตัวอย่างภาษา Cypher ของ Neo4j
```text
MATCH (bit:Person {name: 'บิต'})-[:FRIEND]->()-[:FRIEND]->(fof)
RETURN fof.name
```

**ในกลุ่มนี้มีใครบ้าง**

<ToolTable group="db-nosql" />

**เหมือนกับ SQL ตรงไหน ต่างกันตรงไหน**

| หัวข้อ | Relational (SQL) | NoSQL |
|---|---|---|
| รูปแบบ | ตาราง | เอกสาร / key-value / wide-column / graph |
| Schema | ตายตัว เปลี่ยนต้อง migrate (บทที่ 8) | ยืดหยุ่น เพิ่ม field ได้เลย (หลายตัวเปิดกฎตรวจเพิ่มได้ เช่น schema validation ของ MongoDB) |
| ความสัมพันธ์ | JOIN เก่งมาก | มัก embed ไว้ด้วยกัน (graph เป็นข้อยกเว้น เก่งเรื่องความสัมพันธ์ที่สุด) |
| ความถูกต้อง | ACID เต็มรูปแบบ มี FK/CHECK ช่วย | ต่างกันมากแต่ละตัว บางตัวมี transaction (MongoDB, DynamoDB) บางตัวยอมให้ข้อมูลตรงกันช้าลงนิดหนึ่งเพื่อแลกความเร็ว · กฎหลายอย่างกลายเป็นหน้าที่โค้ดเรา |
| การขยาย | แนวตั้งเป็นหลัก + read replica | หลายตัวออกแบบมาขยายแนวนอน (เพิ่มเครื่อง) ตั้งแต่ต้น |
| ภาษา query | SQL คำสั่งหลักเหมือนกันทุกยี่ห้อ | แต่ละยี่ห้อมีวิธีของตัวเอง |
| เหมาะกับ | เงิน, สต็อก, POS, ERP, การจอง | cache, session, log, แชท, ข้อมูลรูปร่างไม่แน่นอน |

> 💡 **ขยายแนวตั้ง vs แนวนอน:** แนวตั้ง = เปลี่ยนเป็นเครื่องที่แรงขึ้น (ง่าย แต่มีเพดาน) · แนวนอน = เพิ่มจำนวนเครื่องแล้วแบ่งข้อมูลกัน (ไม่มีเพดาน แต่ยาก เพราะต้องตอบให้ได้ว่า "ถ้าสองเครื่องเห็นข้อมูลไม่ตรงกันชั่วขณะ จะเอาตามใคร") ฐานข้อมูลที่ยอมให้ "ตรงกันในไม่ช้า" เรียกว่า **eventual consistency** ใช้ได้กับยอดไลก์ แต่ใช้ไม่ได้กับยอดเงิน

> ⚠️ **ความเชื่อเก่าที่ยังเจอในเน็ต:** "NoSQL ไม่มี transaction" ไม่จริงแล้วสำหรับหลายตัว (MongoDB มี transaction หลายเอกสารตั้งแต่รุ่น 4.0) และ "SQL เก็บข้อมูลยืดหยุ่นไม่ได้" ก็ไม่จริง PostgreSQL มีคอลัมน์ `JSONB` ([บทที่ 7](/07-mysql-postgres#-ชนิดข้อมูลพิเศษ)) เส้นแบ่งระหว่างกลุ่มเริ่มจางลง จึงต้องเลือกจากโจทย์ ไม่ใช่จากป้ายชื่อ

## 4. กลุ่มที่ 3: ฐานข้อมูลเฉพาะทาง (Search, Vector, Time-series)

สองกลุ่มแรกเป็น "ที่เก็บข้อมูลหลัก" ส่วนกลุ่มนี้เกิดมาเพราะมีงานบางแบบที่ทั้งตารางและเอกสารทำได้ไม่ดี มักใช้ **คู่กับฐานข้อมูลหลัก** โดยคัดลอกข้อมูลมาจากฐานหลักอีกที

**ข้างในมีอะไร: 3 ประเภทที่จะเจอบ่อย**

**① Search engine: ค้นข้อความแบบที่คนพิมพ์จริง**
- **ปัญหา:** `WHERE name LIKE '%โน้ตบุ๊ค%'` ต้องไล่อ่านทุกแถว ช้าเมื่อข้อมูลเยอะ และหา "notebook", "โน๊ตบุ๊ก" (สะกดต่าง) หรือเรียงผลตามความเกี่ยวข้องไม่ได้
- **แนวคิดข้างใน:** **inverted index** คือ สารบัญท้ายหนังสือ 📚 จดว่า "คำนี้อยู่ในเอกสารไหนบ้าง" พอค้นคำ ก็เปิดสารบัญแทนการอ่านทุกหน้า แล้วให้คะแนนว่าเอกสารไหนเกี่ยวข้องที่สุด บางตัวยอมให้พิมพ์ผิดได้ด้วย
- **ตัวอย่าง:** ช่องค้นหาสินค้า, ค้น log ของระบบ

**② Vector database: ค้นตาม "ความหมาย"**
- **ปัญหา:** ผู้ใช้ถามว่า "เครื่องเบาๆ ไว้พกไปเรียน" แต่ในข้อมูลเขียนว่า "น้ำหนัก 1.1 กก. เหมาะกับนักศึกษา" ไม่มีคำไหนตรงกันเลย search engine แบบคำจึงหาไม่เจอ
- **แนวคิดข้างใน:** ใช้โมเดล AI แปลงข้อความ (หรือรูป) เป็น **embedding** คือชุดตัวเลขยาวๆ ที่แทนความหมาย ข้อความที่ความหมายใกล้กันจะได้ตัวเลขใกล้กัน แล้วฐานข้อมูลหา **"จุดที่ใกล้ที่สุด"** (nearest neighbor) ให้ มีวิธีทำ index แบบประมาณ (เช่น HNSW) เพื่อให้เร็วโดยยอมพลาดบ้างเล็กน้อย
- **ตัวอย่าง:** แชตบอตที่ตอบจากเอกสารบริษัท (เรียกว่า RAG), ค้นสินค้าที่คล้ายกัน

**③ Time-series database: ข้อมูลที่เรียงตามเวลา**
- **ปัญหา:** sensor ส่งค่าอุณหภูมิทุกวินาที หรือ server ส่งค่า CPU ทุก 10 วินาที ข้อมูลเขียนเข้าตลอด แทบไม่ถูกแก้ และคำถามมักเป็น "ค่าเฉลี่ยรายชั่วโมงของสัปดาห์ที่แล้ว"
- **แนวคิดข้างใน:** แบ่งเก็บข้อมูลเป็นช่วงเวลาให้อัตโนมัติ (เช่น ก้อนละสัปดาห์) ค้นช่วงเวลาไหนก็เปิดแค่ก้อนนั้น และลบข้อมูลเก่าทั้งก้อนได้ง่าย
- **ตัวอย่าง:** dashboard ดูสุขภาพ server, ข้อมูล IoT, ราคาหุ้น

> 💡 **ยังมีอีกประเภทที่อาจเจอ: ฐานข้อมูลวิเคราะห์ (OLAP / columnar)** เช่น ClickHouse เก็บข้อมูล **ทีละคอลัมน์** แทนทีละแถว ทำให้คำถามแบบ "ยอดขายรวมแยกตามเดือนของ 3 ปี" บนข้อมูลหลายร้อยล้านแถวเร็วมาก แต่ไม่เหมาะกับการแก้ทีละแถวแบบระบบหน้าร้าน

**ในกลุ่มนี้มีใครบ้าง**

<ToolTable group="db-specialized" />

**เหมือนกันตรงไหน ต่างกันตรงไหน**

| หัวข้อ | เหมือนกัน / ต่างกัน |
|---|---|
| บทบาท | ✅ ส่วนใหญ่เป็น **ฐานข้อมูลเสริม** ไม่ใช่ที่เก็บความจริงหลัก ถ้าข้อมูลในนี้เสีย ต้องสร้างใหม่จากฐานหลักได้ |
| สิ่งที่เก่ง | ต่างกันสิ้นเชิง: search = คำ · vector = ความหมาย · time-series = ช่วงเวลา |
| ทางเลือกที่อยู่ใน PostgreSQL | PostgreSQL ทำได้ทั้ง 3 อย่างระดับเริ่มต้น: **full-text search** มีในตัว · **pgvector** และ **TimescaleDB** เป็น extension ที่ติดตั้งเพิ่ม |

> 🎯 **หลักคิด:** ระบบเล็กถึงกลางมักเริ่มจากความสามารถใน PostgreSQL ก่อน เพราะได้ข้อมูลอยู่ที่เดียว ไม่ต้องคอยคัดลอกให้สองที่ตรงกัน แยกไปใช้ตัวเฉพาะทางเมื่อวัดแล้วว่าไม่พอจริง

## 5. เจอฐานข้อมูลใหม่ จัดกลุ่มเองได้

ทุกปีมีฐานข้อมูลใหม่ออกมา ไม่ต้องจำชื่อ ให้ถามคำถามเหล่านี้กับตัวที่เพิ่งเจอ (ดูจากหน้า "Introduction" หรือ "Data model" ในเอกสารของมัน)

| ถามว่า | ถ้าคำตอบคือ | อยู่กลุ่ม |
|---|---|---|
| มันเก็บข้อมูลเป็น **ตารางที่มี schema** และสั่งด้วย SQL ไหม | ใช่ มี FK และ transaction | Relational |
| มันเก็บเป็น **เอกสาร JSON** ไหม | ใช่ | Document |
| มันเน้น **ตั้ง/อ่านค่าตามกุญแจ** ส่วนใหญ่อยู่ใน RAM ไหม | ใช่ | Key-Value |
| มันแบ่งข้อมูลด้วย **partition key** กระจายหลายเครื่อง ไม่มี JOIN ไหม | ใช่ | Wide-Column |
| มันเก็บ **node กับเส้นเชื่อม** ไหม | ใช่ | Graph |
| จุดขายคือ **ค้นข้อความ / ค้นด้วย vector / ข้อมูลตามเวลา** ไหม | ใช่ | เฉพาะทาง (search / vector / time-series) |

แล้วถามต่ออีก 2 ข้อที่มีผลกับงานจริง: **รับประกันความถูกต้องแค่ไหน** (มี transaction ไหม) และ **ขยายยังไง** (เครื่องเดียว / หลายเครื่อง / ผู้ให้บริการดูแลให้)

> 💡 **หลายตัวอยู่มากกว่า 1 กลุ่ม** (เรียกว่า **multi-model**) เช่น PostgreSQL เป็น relational แต่เก็บ JSON และค้นด้วย vector ได้ · DynamoDB เป็นทั้ง key-value และ document · Elasticsearch เป็น search engine ที่ค้นด้วย vector ได้ด้วย ให้ดูว่า **จุดแข็งหลัก** ของมันคืออะไร

**คำถามก่อนเลือก** (ไล่จากบนลงล่าง)
1. ข้อมูลเกี่ยวกับ **เงิน / สต็อก / การจอง** ที่ผิดไม่ได้ไหม? → **Relational (SQL)**
2. ข้อมูลมี **ความสัมพันธ์ซับซ้อน** (ลูกค้า-ออเดอร์-สินค้า-ใบแจ้งหนี้) และต้อง JOIN/สรุปผลบ่อยไหม? → **Relational (SQL)**
3. ต้องการแค่ **เก็บ-อ่านตามกุญแจเร็วๆ** และข้อมูลหายก็ไม่ร้ายแรง (cache, session, rate limit)? → **Key-Value (Redis/Valkey)**
4. ข้อมูลรูปร่างต่างกันมาก เปลี่ยนบ่อย และอ่านเป็นก้อนเดียว (เช่น เนื้อหา CMS, log เหตุการณ์)? → **Document** ก็เหมาะ (หรือคอลัมน์ `JSONB` ใน PostgreSQL ถ้าข้อมูลส่วนที่เหลือเป็นตาราง)
5. ต้อง **ค้นข้อความ** แบบช่องค้นหา / **ค้นตามความหมาย** / เก็บ **ข้อมูลตามเวลา** ปริมาณมาก? → ประเภท **เฉพาะทาง** (ลองของที่มีใน PostgreSQL ก่อน)
6. **ทีมดูแลไหวไหม?** ฐานข้อมูลทุกตัวที่เพิ่มเข้ามา = ต้อง backup, อัปเดต, เฝ้าดู และทำให้ข้อมูลตรงกันเพิ่มอีกหนึ่งที่

ถ้าข้อ 1 หรือ 2 ใช่ ไม่ต้องคิดมาก ใช้ SQL

> 🎯 **กลับไปที่เรื่องเล่า:** ปัญหาของร้านคือ "ข้อมูลซ้ำ" (แก้ด้วย normalization + FK) และ "สองคนเช่าเครื่องเดียวกัน" (แก้ด้วย transaction และเงื่อนไขในคำสั่ง ข้อ 8) ทั้งสองเรื่องเป็นจุดแข็งของกลุ่ม Relational คำตอบของบิตจึงยังไม่ใช่ MongoDB ไม่ใช่เพราะ MongoDB ไม่ดี แต่เพราะโจทย์นี้ต้องการกฎเข้ม

> **แนวทางของทีม:** ไม่แน่ใจ **เริ่มที่ SQL (PostgreSQL)** งานลูกค้าส่วนใหญ่ข้อมูลสัมพันธ์กัน ทีมใช้ PostgreSQL ผ่าน **Drizzle** (บทที่ 8)
> ระบบจริงมัก **ใช้หลายประเภทร่วมกัน** เช่น PostgreSQL เก็บข้อมูลหลัก + Redis เป็น cache โดยให้ฐานหลัก **เป็นแหล่งความจริงที่เดียว** ตัวอื่นเป็นสำเนาที่สร้างใหม่ได้

---

> 🔧 **จากนี้คือการลงมือ** เริ่มด้วย **PostgreSQL** (ตัวแทนกลุ่ม Relational ที่ทีมใช้) ในข้อ 7–8 แล้วลองตัวแทนกลุ่ม NoSQL 2 ตระกูลในข้อ 9 สังเกตว่าแนวคิดจากข้อ 2–3 (PK/FK, embed, กุญแจ) โผล่มาในคำสั่งทุกบรรทัด

## 7. 🔧 ลงมือ: SQL พื้นฐาน (PostgreSQL)

> 💡 SQL แบ่งเป็น 2 กลุ่มคำสั่ง: **สร้างโครงสร้าง** (`CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`) กับ **จัดการข้อมูล** (`INSERT`, `SELECT`, `UPDATE`, `DELETE`) ชื่อคำสั่งพิมพ์ตัวเล็ก/ใหญ่ก็ได้ ทีมเรานิยมพิมพ์ตัวใหญ่เพื่ออ่านง่าย และต้องจบทุกคำสั่งด้วย `;`

```bash
docker run -d --name pg -e POSTGRES_PASSWORD=secret -p 5432:5432 postgres:17
docker exec -it pg psql -U postgres
```
ควรเห็น prompt ของ psql
```text
psql (17.x)
Type "help" for help.

```
(คำสั่ง psql: `\dt` ดูตาราง · `\d ชื่อตาราง` ดูโครงสร้าง · `\q` ออก)
> 💡 ไม่ถนัด Terminal? ใช้โปรแกรม **DBeaver** ต่อที่ `localhost` port `5432` user `postgres` รหัส `secret` ได้ (เรื่องต่อ DB ด้วย GUI ดู [บทที่ 7](/07-mysql-postgres)) ส่วน Adminer จาก [บทที่ 2](/02-docker) จะ**ต่อกล่อง `pg` นี้ไม่ได้ตรงๆ** เพราะ Adminer อยู่ในกล่องของตัวเอง คำว่า `localhost` ในกล่อง Adminer หมายถึงตัว Adminer เอง และกล่อง `pg` ที่เปิดด้วย `docker run` ไม่ได้อยู่ใน network เดียวกับ compose ของบทที่ 2

### CREATE: สร้างตาราง
```sql
CREATE TABLE customers (
  id    SERIAL PRIMARY KEY,           -- เลขรันอัตโนมัติ 1, 2, 3...
  name  TEXT NOT NULL,                -- ห้ามว่าง
  phone TEXT UNIQUE                   -- ห้ามซ้ำ
);

CREATE TABLE rentals (
  id              SERIAL PRIMARY KEY,
  customer_id     INT NOT NULL REFERENCES customers(id),   -- FK
  laptop          TEXT NOT NULL,
  price_per_month INT NOT NULL CHECK (price_per_month > 0) -- กฎเพิ่มเติม
);
```
ควรเห็น
```text
CREATE TABLE
CREATE TABLE
```
ตรวจโครงสร้างด้วย `\d rentals` จะเห็น FK ที่เราตั้งไว้ในหัวข้อ `Foreign-key constraints`

> 💡 **`SERIAL` กับ `GENERATED ALWAYS AS IDENTITY`:** `SERIAL` เป็นทางลัดแบบเก่าของ PostgreSQL ที่ยังใช้ได้และเจอในตัวอย่างทั่วไป บทนี้ใช้เพราะพิมพ์สั้น ส่วนวิธีตามมาตรฐาน SQL คือ `id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` ซึ่ง [wiki ของ PostgreSQL](https://wiki.postgresql.org/wiki/Don't_Do_This#Don.27t_use_serial) แนะนำสำหรับงานใหม่ เพราะกันการใส่เลข id เองโดยไม่ตั้งใจ ผลลัพธ์ในบทนี้ออกมาเหมือนกันทั้งสองแบบ

ชนิดข้อมูลที่เจอบ่อย:

| ชนิด | เก็บอะไร | ตัวอย่าง |
|---|---|---|
| `INT` / `SERIAL` | จำนวนเต็ม / จำนวนเต็มรันเลขเอง | `1500` |
| `NUMERIC(10,2)` | ทศนิยมที่ต้องแม่น (เงิน) | `99.50` |
| `TEXT` | ข้อความยาวเท่าไรก็ได้ | `'สมชาย'` |
| `BOOLEAN` | จริง/เท็จ | `true` |
| `TIMESTAMPTZ` | วันเวลา (มี time zone) | `'2026-10-20 09:00+07'` |
| `DATE` | วันที่ | `'2026-10-20'` |

> ⚠️ **ห้ามเก็บเงินเป็น `FLOAT`** ทศนิยมแบบ float คลาดเคลื่อนได้ (0.1 + 0.2 ≠ 0.3) ใช้ `INT` (เก็บเป็นสตางค์) หรือ `NUMERIC`

### INSERT: เพิ่มข้อมูล
```sql
INSERT INTO customers (name, phone) VALUES
  ('สมชาย', '081-111-1111'), ('สมหญิง', '082-222-2222'), ('มานี', '083-333-3333');

INSERT INTO rentals (customer_id, laptop, price_per_month) VALUES
  (1, 'Lenovo T14', 1500), (1, 'Dell 5420', 1200), (2, 'HP 840', 1300);
```
ควรเห็น (เลข = จำนวนแถวที่เพิ่ม)
```text
INSERT 0 3
INSERT 0 3
```

💥 **ลองพังมันดู: ทำผิดกฎ**
```sql
INSERT INTO rentals (customer_id, laptop, price_per_month) VALUES (99, 'Mac', 2000);
INSERT INTO rentals (customer_id, laptop, price_per_month) VALUES (1, 'Mac', -5);
```
ควรเห็น
```text
ERROR:  insert or update on table "rentals" violates foreign key constraint "rentals_customer_id_fkey"
DETAIL:  Key (customer_id)=(99) is not present in table "customers".

ERROR:  new row for relation "rentals" violates check constraint "rentals_price_per_month_check"
DETAIL:  Failing row contains (5, 1, Mac, -5).
```
ฐานข้อมูล **ปฏิเสธข้อมูลผิดให้เอง** 🛡️ นี่คือจุดแข็งใหญ่ของ SQL
(สังเกต: `Failing row contains (5, ...)` แปลว่า id ถูกจองไปแล้ว 4 ตัว ทั้งที่แถวนั้นไม่ถูกบันทึก เลข `SERIAL` จึงอาจ "ข้าม" ได้ ไม่ใช่บั๊ก)

### SELECT: ดึงข้อมูล
```sql
SELECT * FROM customers;
SELECT name, phone FROM customers WHERE id = 1;
SELECT * FROM rentals WHERE price_per_month >= 1300 ORDER BY price_per_month DESC;
SELECT * FROM customers WHERE name LIKE 'สม%';      -- ขึ้นต้นด้วย "สม"
```
ควรเห็น (คำสั่งแรกกับคำสั่งที่ 3)
```text
 id |  name  |    phone
----+--------+--------------
  1 | สมชาย  | 081-111-1111
  2 | สมหญิง | 082-222-2222
  3 | มานี   | 083-333-3333
(3 rows)

 id | customer_id |   laptop   | price_per_month
----+-------------+------------+-----------------
  1 |           1 | Lenovo T14 |            1500
  3 |           2 | HP 840     |            1300
(2 rows)
```

**ตัวกรองและการเรียงที่ใช้บ่อย**

| คำสั่ง | ทำอะไร | ตัวอย่าง |
|---|---|---|
| `WHERE` | กรองแถว | `WHERE price_per_month >= 1300` |
| `AND` / `OR` | รวมเงื่อนไข | `WHERE price_per_month > 1000 AND customer_id = 1` |
| `IN (...)` | ตรงกับค่าใดค่าหนึ่ง | `WHERE customer_id IN (1, 2)` |
| `BETWEEN a AND b` | อยู่ในช่วง (รวมปลายทั้งสอง) | `WHERE price_per_month BETWEEN 1200 AND 1400` |
| `LIKE` | ค้นด้วยแพตเทิร์น `%` = กี่ตัวอักษรก็ได้ | `WHERE name LIKE 'สม%'` |
| `ORDER BY ... ASC/DESC` | เรียง น้อย→มาก / มาก→น้อย | `ORDER BY price_per_month DESC` |
| `LIMIT n` | เอาแค่ n แถวแรก | `LIMIT 2` |
| `OFFSET n` | ข้าม n แถวแรก (ใช้ทำแบ่งหน้า) | `LIMIT 10 OFFSET 20` |

```sql
-- 2 เครื่องที่ค่าเช่าแพงสุด
SELECT * FROM rentals ORDER BY price_per_month DESC LIMIT 2;
```
```text
 id | customer_id |   laptop   | price_per_month
----+-------------+------------+-----------------
  1 |           1 | Lenovo T14 |            1500
  3 |           2 | HP 840     |            1300
(2 rows)
```
> 💡 `LIMIT` ที่ไม่มี `ORDER BY` ลำดับไม่รับประกัน ถ้าจะ "เอา 3 อันดับแรก" ต้องมี `ORDER BY` เสมอ

### UPDATE / DELETE
```sql
UPDATE customers SET phone = '089-999-9999' WHERE id = 1;

-- ลองลบ: เพิ่มแถวทดลองก่อน แล้วลบเฉพาะแถวนั้น (ข้อมูลหลักของเราจะได้ไม่หาย)
INSERT INTO rentals (customer_id, laptop, price_per_month) VALUES (3, 'Temp', 999);
DELETE FROM rentals WHERE laptop = 'Temp';
```
ควรเห็น
```text
UPDATE 1
INSERT 0 1
DELETE 1
```
ตัวเลขหลัง `UPDATE`/`DELETE` คือ **จำนวนแถวที่โดนแก้/ลบ** ถ้าคาดว่า 1 แต่ได้ 500 แปลว่า WHERE กว้างเกินไป

> ⚠️ **`ROLLBACK` ช่วยได้เฉพาะเมื่อพิมพ์ `BEGIN;` ไว้ก่อน** psql ทำงานแบบ **autocommit** คือทุกคำสั่งถูกบันทึกถาวรทันทีที่จบ `;` ถ้าไม่ได้เปิด transaction ไว้ `ROLLBACK` จะไม่มีอะไรให้ย้อน:
> ```text
> postgres=# UPDATE rentals SET price_per_month = 1;
> UPDATE 3
> postgres=# ROLLBACK;
> WARNING:  there is no transaction in progress
> ROLLBACK
> ```
> ข้อมูลเปลี่ยนไปแล้วทั้ง 3 แถว (อย่าลองคำสั่งนี้กับข้อมูลที่ยังต้องใช้) นิสัยที่ปลอดภัยเวลาแก้ข้อมูลสำคัญด้วยมือคือ `BEGIN;` → `UPDATE ...` → ดูเลขจำนวนแถว → ถ้าถูกค่อย `COMMIT;` ถ้าผิด `ROLLBACK;` (เรื่อง transaction อยู่ข้อ 8)

> ⚠️ **ห้ามลืม `WHERE`!** ไม่มี WHERE = **แก้/ลบทุกแถว** มีคนทำ production พังด้วยเรื่องนี้มานับไม่ถ้วน 💀
> 💡 ทริค: เขียน `SELECT * FROM ... WHERE ...` ดูก่อนว่าได้แถวที่ต้องการ แล้วค่อยเปลี่ยนเป็น UPDATE/DELETE

💥 **ลองพังมันดู: ลบลูกค้าที่ยังมี rental อยู่**
```sql
DELETE FROM customers WHERE id = 1;
```
```text
ERROR:  update or delete on table "customers" violates foreign key constraint "rentals_customer_id_fkey" on table "rentals"
DETAIL:  Key (id)=(1) is still referenced from table "rentals".
```
FK กันไม่ให้ลบลูกค้าที่ยังมีรายการเช่าค้างอยู่ (ไม่งั้นจะเหลือ rental ที่ชี้ไปหาคนที่ไม่มีแล้ว)

### JOIN: รวมหลายตาราง

ข้อมูลที่แยกตารางไว้ (normalize) ต้องเอามา "ต่อกัน" ตอนดึง นั่นคือ `JOIN` โดยบอกว่าจับคู่ด้วยคอลัมน์ไหน (`ON`)
```sql
SELECT c.name, r.laptop, r.price_per_month
FROM rentals r
JOIN customers c ON c.id = r.customer_id;
```
(`r` และ `c` คือ **นามแฝง (alias)** ของตาราง พิมพ์สั้นลง)

ควรเห็น (มานีไม่โผล่ เพราะยังไม่มี rental ให้จับคู่)
```text
  name  |   laptop   | price_per_month
--------+------------+-----------------
 สมชาย  | Lenovo T14 |            1500
 สมชาย  | Dell 5420  |            1200
 สมหญิง | HP 840     |            1300
(3 rows)
```

![แผนภาพวงกลม Venn ของ INNER, LEFT, RIGHT และ FULL JOIN](/img/06-join-types.svg)
*JOIN 4 แบบ: ส่วนสีเขียวคือแถวที่ได้ในผลลัพธ์ · ที่ใช้บ่อยสุดคือ INNER (พิมพ์แค่ `JOIN`) และ LEFT*

- `JOIN` (= `INNER JOIN`) = เอาเฉพาะแถวที่จับคู่ได้
- `LEFT JOIN` = เอาทุกแถวจากตารางซ้าย แม้ไม่มีคู่ (ฝั่งขวาเป็น `NULL`)
- `RIGHT JOIN` = กลับด้านกับ LEFT (เอาทุกแถวจากตารางขวา) ในทางปฏิบัติสลับตำแหน่งตารางแล้วใช้ LEFT แทนได้ จึงเจอน้อย
- `FULL JOIN` = เอาทุกแถวทั้งสองฝั่ง

![การจับคู่แถวระหว่างตาราง a (id 1,2,3) กับตาราง b (id 2,3,4) และผลของ INNER, LEFT, FULL JOIN](/img/06-join-rows.svg)
*ลองมองเป็นการลากเส้นจับคู่แถวที่ `id` เท่ากัน: แถวที่ไม่มีเส้นโยงคือแถวที่ INNER ตัดทิ้ง แต่ LEFT/FULL เก็บไว้และเติม NULL*

```sql
SELECT c.name, r.laptop
FROM customers c
LEFT JOIN rentals r ON r.customer_id = c.id
ORDER BY c.id, r.id;
```
```text
  name  |   laptop
--------+------------
 สมชาย  | Lenovo T14
 สมชาย  | Dell 5420
 สมหญิง | HP 840
 มานี   |
(4 rows)
```
สังเกต: "มานี" ยังอยู่ แต่ `laptop` ว่าง (เป็น NULL) นี่คือต่างจาก INNER JOIN ที่มานีหายไป เราใช้ความต่างนี้หาคนที่ "ยังไม่เคย..." ได้
```sql
-- ลูกค้าที่ยังไม่เคยเช่า
SELECT c.name
FROM customers c
LEFT JOIN rentals r ON r.customer_id = c.id
WHERE r.id IS NULL;                -- ได้ "มานี"
```
```text
 name
------
 มานี
(1 row)
```

### GROUP BY: สรุปผล

**Aggregate function** = ฟังก์ชันที่ยุบหลายแถวเหลือค่าเดียว: `COUNT` (นับ) `SUM` (รวม) `AVG` (เฉลี่ย) `MIN` `MAX`
`GROUP BY` = จัดแถวเป็นกลุ่มก่อน แล้วคำนวณทีละกลุ่ม
```sql
SELECT c.name, COUNT(r.id) AS total_rentals, SUM(r.price_per_month) AS total_price
FROM customers c
LEFT JOIN rentals r ON r.customer_id = c.id
GROUP BY c.id, c.name;     -- ใส่ id ด้วย เพราะลูกค้าชื่อซ้ำกันได้ (สมชาย 2 คน ต้องไม่ถูกรวมเป็นคนเดียว)
```
```text
  name  | total_rentals | total_price
--------+---------------+-------------
 สมชาย  |             2 |        2700
 สมหญิง |             1 |        1300
 มานี   |             0 |
(3 rows)
```
(ลำดับแถวอาจต่างจากนี้ ถ้าอยากให้เรียงแน่นอนให้ใส่ `ORDER BY`)

สังเกต: มานี `COUNT` ได้ 0 แต่ `SUM` ได้ว่าง (NULL) ไม่ใช่ 0 (ดูเรื่อง NULL ด้านล่าง)

**`WHERE` กรองก่อนจัดกลุ่ม, `HAVING` กรองหลังจัดกลุ่ม**
```sql
-- ลูกค้าที่ค่าเช่ารวมเกิน 1300
SELECT c.name, SUM(r.price_per_month) AS total
FROM customers c
JOIN rentals r ON r.customer_id = c.id
GROUP BY c.id, c.name
HAVING SUM(r.price_per_month) > 1300;
```
```text
  name  | total
--------+-------
 สมชาย  |  2700
(1 row)
```
> 💡 จำง่ายๆ: เงื่อนไขของ "แถว" ใช้ `WHERE` · เงื่อนไขของ "ผลสรุป (SUM/COUNT)" ใช้ `HAVING`

### 🔧 Index: ทำให้ค้นเร็ว

ฐานข้อมูลที่ไม่มี index เวลา `WHERE email = '...'` ต้อง **ไล่อ่านทุกแถว** (เรียก *sequential scan*) เหมือนหาชื่อในสมุดที่ไม่เรียงตัวอักษร
**Index** คือ **สารบัญ** ที่ฐานข้อมูลเรียงไว้ให้ (โครงสร้างหลักเรียกว่า **B-tree**) ทำให้กระโดดไปถึงแถวที่ต้องการได้ในไม่กี่ก้าว

![เปรียบเทียบการไล่อ่านทุกแถว (seq scan) กับการค้นผ่าน index แบบ B-tree พร้อมเวลาที่วัดได้จริง](/img/06-index-lookup.svg)
*ซ้าย: ไม่มี index ต้องอ่านครบทุกแถว · ขวา: มี index ตัดตัวเลือกทิ้งทีละครึ่ง · ตัวเลขเวลาวัดจากเครื่องผู้เขียน ของเราอาจต่างกันแต่ "ลำดับความเร็ว" จะคล้ายกัน*

ลองวัดเองด้วยตาราง 200,000 แถว (ใช้ `generate_series` สร้างข้อมูลปลอมให้)
```sql
CREATE TABLE big (id SERIAL PRIMARY KEY, email TEXT NOT NULL);
INSERT INTO big (email) SELECT 'user' || g || '@mail.com' FROM generate_series(1, 200000) g;
ANALYZE big;

EXPLAIN ANALYZE SELECT * FROM big WHERE email = 'user150000@mail.com';
```
ควรเห็น (สังเกต `Seq Scan` และ `Rows Removed by Filter`)
```text
 Seq Scan on big  (cost=0.00..3774.00 rows=1 width=23) (actual time=6.865..9.526 rows=1 loops=1)
   Filter: (email = 'user150000@mail.com'::text)
   Rows Removed by Filter: 199999
 Planning Time: 0.084 ms
 Execution Time: 9.539 ms
```
ทีนี้สร้าง index แล้วลองใหม่
```sql
CREATE INDEX idx_big_email ON big (email);
ANALYZE big;
EXPLAIN ANALYZE SELECT * FROM big WHERE email = 'user150000@mail.com';
```
ควรเห็น
```text
 Index Scan using idx_big_email on big  (cost=0.42..8.44 rows=1 width=23) (actual time=0.025..0.026 rows=1 loops=1)
   Index Cond: (email = 'user150000@mail.com'::text)
 Planning Time: 0.091 ms
 Execution Time: 0.035 ms
```
เร็วขึ้นราว 270 เท่า (ตารางยิ่งใหญ่ ยิ่งต่างมาก) เก็บกวาดด้วย `DROP TABLE big;`

**กฎการใช้ index**

| | |
|---|---|
| ✅ ควรสร้าง | คอลัมน์ที่ใช้ใน `WHERE`, `JOIN ... ON`, `ORDER BY` บ่อยๆ เช่น `customer_id` (FK) หรือ `email` |
| ✅ ได้มาให้แล้ว | `PRIMARY KEY` และ `UNIQUE` สร้าง index ให้อัตโนมัติ |
| ❌ ไม่ใช่ยาวิเศษ | index **ทำให้ INSERT/UPDATE ช้าลงนิดหน่อย** และกินพื้นที่ จึงไม่ควรสร้างทุกคอลัมน์ |
| ⚠️ PostgreSQL ไม่สร้าง index ให้ FK | ต้องสร้างเองถ้าจะ `JOIN`/ค้นด้วยคอลัมน์ FK บ่อย (MySQL InnoDB สร้างให้) |

> 💡 ไม่แน่ใจว่า query ช้าเพราะอะไร ให้ใส่ `EXPLAIN ANALYZE` นำหน้า query แล้วดูว่าเป็น `Seq Scan` (ไล่ทั้งตาราง) หรือ `Index Scan`

### NULL: "ไม่มีค่า" ไม่เท่ากับ 0 หรือข้อความว่าง

`NULL` = **ไม่ทราบ / ไม่มีค่า** (เหมือนช่องที่ยังไม่ได้กรอกในฟอร์ม) ไม่ใช่ 0 และไม่ใช่ `''` เพราะ "ไม่ทราบ" เทียบกับอะไรก็ได้ผล "ไม่ทราบ" ตามไปด้วย จึงมีกับดัก:

```sql
SELECT NULL = NULL AS eq, NULL IS NULL AS isnull, 1 + NULL AS plus;
```
```text
 eq | isnull | plus
----+--------+------
    | t      |
```
- `NULL = NULL` ไม่ใช่ true (ได้ NULL) → ต้องใช้ **`IS NULL`** / **`IS NOT NULL`**
- เอา NULL ไปบวกลบ ได้ NULL

```sql
CREATE TABLE n (id INT, note TEXT);
INSERT INTO n VALUES (1, 'x'), (2, NULL), (3, 'y');

SELECT * FROM n WHERE note <> 'x';        -- กับดัก! แถวที่ note เป็น NULL หายไปด้วย
SELECT * FROM n WHERE note IS NULL;
SELECT COUNT(*) AS rows_, COUNT(note) AS notes FROM n;   -- COUNT(คอลัมน์) ไม่นับ NULL
SELECT COALESCE(note, '-') FROM n ORDER BY id;           -- COALESCE = ถ้า NULL ให้ใช้ค่าสำรอง
```
```text
 id | note
----+------
  3 | y
(1 row)

 id | note
----+------
  2 |
(1 row)

 rows_ | notes
-------+-------
     3 |     2
(1 row)

 coalesce
----------
 x
 -
 y
(3 rows)
```
**สรุปกับดัก NULL:** `= NULL` ใช้ไม่ได้ · `<> 'x'` ไม่รวมแถว NULL · `COUNT(*)` นับทุกแถว แต่ `COUNT(คอลัมน์)` ข้าม NULL · `SUM` ของแถวที่ว่างทั้งหมดได้ NULL ไม่ใช่ 0 (ใช้ `COALESCE(SUM(x), 0)`)
เก็บกวาด: `DROP TABLE n;`

### 🔧 ตารางกลางสำหรับ N : M

```sql
CREATE TABLE products (id SERIAL PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE orders   (id SERIAL PRIMARY KEY, customer TEXT NOT NULL);
CREATE TABLE order_items (
  order_id   INT NOT NULL REFERENCES orders(id),
  product_id INT NOT NULL REFERENCES products(id),
  qty        INT NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, product_id)          -- PK คู่: สินค้าเดิมในออเดอร์เดิมซ้ำไม่ได้
);
INSERT INTO products (name) VALUES ('กาแฟ'), ('ขนมปัง'), ('นม');
INSERT INTO orders (customer) VALUES ('บิต'), ('พี่ไบต์');
INSERT INTO order_items VALUES (1, 1, 2), (1, 2, 1), (2, 1, 1);

SELECT o.customer, p.name AS product, i.qty
FROM order_items i
JOIN orders   o ON o.id = i.order_id
JOIN products p ON p.id = i.product_id
ORDER BY o.id, p.id;
```
ควรเห็น
```text
 customer | product | qty
----------+---------+-----
 บิต      | กาแฟ    |   2
 บิต      | ขนมปัง  |   1
 พี่ไบต์   | กาแฟ    |   1
(3 rows)
```
JOIN ต่อกันได้หลายตาราง (3 ตารางข้างบน) 💥 ลองใส่ `INSERT INTO order_items VALUES (1, 1, 5);` จะได้ `duplicate key value violates unique constraint "order_items_pkey"` เพราะ PK คู่กันซ้ำ
เก็บกวาด: `DROP TABLE order_items, orders, products;`

### ⚠️ ทีเซอร์: SQL Injection

พอเราเริ่มเขียน SQL ในโค้ด จะมีโอกาส **เอาข้อความที่ผู้ใช้พิมพ์มาต่อเป็นคำสั่ง** เช่น `"SELECT * FROM customers WHERE name = '" + input + "'"`
ถ้าผู้ใช้พิมพ์ `' OR '1'='1` เงื่อนไขจะเป็นจริงเสมอ ได้ข้อมูลทุกแถว นี่คือ **SQL Injection** ช่องโหว่ที่เจอบ่อยที่สุดตัวหนึ่ง
วิธีกัน: **ห้ามต่อข้อความ ให้ส่งค่าเป็น parameter แยกจากคำสั่งเสมอ** (ORM ในบทที่ 8 ทำให้อัตโนมัติ) รายละเอียดอยู่ใน [บทที่ 10 ข้อ 4](/10-security)

> 🎮 อยากฝึกเพิ่มแบบเกม? ลอง **[SQLBolt](https://sqlbolt.com)** (ฝึกในเว็บทีละด่าน) หรือ **[SQL Murder Mystery](https://mystery.knightlab.com)** (ใช้ SQL สืบหาฆาตกร 🕵️)

## 8. Transaction และ ACID: ทำไม SQL ไว้ใจได้เรื่องเงิน

**สถานการณ์:** ลูกค้าเช่าเครื่อง ระบบต้องทำ 2 อย่าง
1. สร้างรายการเช่า
2. เปลี่ยนสถานะเครื่องเป็น "ถูกเช่า"

ถ้าทำข้อ 1 แล้ว **ไฟดับก่อนข้อ 2** → มีรายการเช่า แต่เครื่องยังโชว์ว่าว่าง → ข้อมูลขัดกันเอง

เพิ่มตารางเครื่องก่อน (ตัวอย่างนี้ใช้ต่อจากตารางในข้อ 7)
```sql
CREATE TABLE laptops (
  serial TEXT PRIMARY KEY,
  model  TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'available' CHECK (status IN ('available', 'rented'))
);
INSERT INTO laptops (serial, model) VALUES ('AS-01', 'Asus'), ('LN-01', 'Lenovo T14');
```

**Transaction** = มัดหลายคำสั่งเป็นก้อนเดียว **"สำเร็จทั้งหมด หรือไม่เกิดอะไรเลย"**
(ตัวอย่างนี้ใส่เลขเครื่องลงคอลัมน์ข้อความ `rentals.laptop` ตรงๆ ให้สั้น แบบที่ถูกคือ FK ไปที่ `laptops` ซึ่งออกแบบเต็มในบทที่ 8b)
```sql
BEGIN;
  INSERT INTO rentals (customer_id, laptop, price_per_month) VALUES (3, 'AS-01', 1100);
  UPDATE laptops SET status = 'rented' WHERE serial = 'AS-01';
COMMIT;       -- ยืนยัน (มีอะไรผิดพลาด → ROLLBACK ยกเลิกทั้งหมด)
```

![ผังการทำงานของ transaction: BEGIN, INSERT, UPDATE แล้ว COMMIT หรือ ROLLBACK เมื่อเกิด error](/img/06-transaction-flow.svg)
*ทุกคำสั่งระหว่าง BEGIN ถึง COMMIT เป็นก้อนเดียวกัน พังที่ขั้นไหนก็ย้อนกลับทั้งก้อน*

💥 **ลองพังมันดู:** ให้ขั้นที่ 2 ผิดกฎ แล้วดูว่าขั้นที่ 1 หายไปด้วยไหม
```sql
BEGIN;
  INSERT INTO rentals (customer_id, laptop, price_per_month) VALUES (1, 'LN-01', 1500);
  UPDATE laptops SET status = 'broken' WHERE serial = 'LN-01';   -- ERROR: violates check constraint
COMMIT;                                                          -- ได้ ROLLBACK แทน
SELECT count(*) FROM rentals WHERE laptop = 'LN-01';             -- 0: รายการเช่าก็ไม่ถูกบันทึก ✅
```
ควรเห็น
```text
BEGIN
INSERT 0 1
ERROR:  new row for relation "laptops" violates check constraint "laptops_status_check"
DETAIL:  Failing row contains (LN-01, Lenovo T14, broken).
ROLLBACK
 count
-------
     0
```

| | ชื่อ | ความหมาย | 💸 ตัวอย่างโอนเงิน A → B 500 บาท |
|---|---|---|---|
| **A** | Atomicity | ทั้งหมดหรือไม่มีเลย | หัก A แล้วต้องเพิ่ม B ห้ามหักแล้วเงินหาย |
| **C** | Consistency | ข้อมูลถูกกฎเสมอ | ยอดเงินห้ามติดลบ ผิดกฎ = ยกเลิก |
| **I** | Isolation | ทำพร้อมกันไม่ชน | กดโอน 2 เครื่องพร้อมกัน ต้องไม่หักซ้อน |
| **D** | Durability | บันทึกแล้วไม่หาย | COMMIT แล้วไฟดับ ข้อมูลยังอยู่ |

### ⚠️ 2 คนกดพร้อมกัน: transaction อย่างเดียวไม่พอ

ปัญหาในเรื่องเล่า (พนักงาน 2 คนปล่อยเช่าเครื่องเดียวกัน) **ไม่ใช่เรื่องไฟดับ** แต่เป็นเรื่อง **ทำพร้อมกัน** (เรียกว่า **race condition**)
```
 เวลา   พนักงาน A                          พนักงาน B
 10:00  ดู: AS-01 ว่าง ✅                    ดู: AS-01 ว่าง ✅
 10:01  เช่าให้ลูกค้า 1 (transaction ผ่าน)    เช่าให้ลูกค้า 2 (transaction ผ่าน)  😱
```
ทั้งสองคน "ดูแล้วว่าง" ก่อนอีกคนจะเปลี่ยนสถานะ แต่ละ transaction ถูกต้องในตัวเอง แต่ผลรวมผิด ต้องเพิ่มอย่างใดอย่างหนึ่ง:

![เส้นเวลาเปรียบเทียบพนักงาน A และ B เช่าเครื่องเดียวกันพร้อมกัน ก่อนและหลังแก้ด้วยเงื่อนไข status = available](/img/06-race-condition.svg)
*ครึ่งบน: ไม่ป้องกัน ได้ผลผิด · ครึ่งล่าง: ใส่เงื่อนไขในคำสั่ง UPDATE คนที่สองจะได้ 0 แถว*

**วิธีที่ 1: เปลี่ยนสถานะแบบมีเงื่อนไข** (ง่ายที่สุด แนะนำ)
```sql
UPDATE laptops SET status = 'rented' WHERE serial = 'AS-01' AND status = 'available';
-- UPDATE 1 = เราได้เครื่อง ทำขั้นต่อไป / UPDATE 0 = มีคนเช่าไปก่อนแล้ว → ROLLBACK แล้วบอกผู้ใช้
```
ฐานข้อมูลล็อกแถวนั้นระหว่างแก้ คนที่สองต้องรอ แล้วตรวจเงื่อนไขใหม่กับค่าล่าสุด (ตอนนี้เป็น `'rented'` แล้ว) จึงได้ `UPDATE 0` เสมอ

**วิธีที่ 2: ล็อกแถวไว้ก่อน (`SELECT ... FOR UPDATE`)**
```sql
BEGIN;
  SELECT status FROM laptops WHERE serial = 'AS-01' FOR UPDATE;  -- คนที่สองต้องรอตรงนี้จนคนแรกเสร็จ
  -- ถ้าเป็น 'available' ค่อย INSERT rentals + UPDATE laptops
COMMIT;
```
🧪 ลองเปิด psql 2 หน้าต่าง พิมพ์ `BEGIN;` + `SELECT ... FOR UPDATE` ทั้งคู่ จะเห็นหน้าต่างที่สองค้างรอจนหน้าต่างแรก `COMMIT`

> 💡 **สรุป:** transaction กัน "ทำไม่ครบ" / เงื่อนไขหรือการล็อกกัน "ทำซ้อนกัน" ระบบจริงต้องใช้ทั้งสองอย่าง (บทที่ 8 ข้อ 6 ทำ transaction เดียวกันนี้ผ่าน Drizzle)

## 9. 🔧 ลองเล่น NoSQL: MongoDB และ Redis

### MongoDB (ตระกูล Document)
```bash
docker run -d --name mongo -p 27017:27017 mongo:8.2
docker exec -it mongo mongosh
```
(ระบุรุ่น `8.2` ไว้ เพราะ MongoDB รุ่นใหม่กว่านั้นอาจเปิดไม่ขึ้นบน Docker Desktop บางรุ่น ดูข้อ 10)

```js
use shop
db.customers.insertOne({ name: "สมชาย", rentals: [{ laptop: "Lenovo T14", pricePerMonth: 1500 }] })
db.customers.insertOne({ name: "มานี", vip: true })
db.customers.find()
db.customers.find({ "rentals.laptop": "Lenovo T14" })
```
ควรเห็น (คำสั่ง `find()` แรก · ค่า `ObjectId` ของเราจะต่างจากนี้)
```text
[
  {
    _id: ObjectId('6ad9c07d6797c1578400b8d7'),
    name: 'สมชาย',
    rentals: [ { laptop: 'Lenovo T14', pricePerMonth: 1500 } ]
  },
  { _id: ObjectId('6ad9c07d6797c1578400b8d8'), name: 'มานี', vip: true }
]
```
(mongosh เป็นเครื่องมือทดลองที่พิมพ์แบบ JS ได้ ส่วนโค้ดในโปรเจกต์ยังต้องเป็น TypeScript)

สังเกต: "มานี" มี `vip` แต่ไม่มี `rentals` MongoDB ก็ยอม = **ยืดหยุ่น** 🤸 และไม่ต้องสร้าง collection `customers` ก่อนด้วย มันสร้างให้ตอนเพิ่มเอกสารแรก
แต่ก็แปลว่า **พิมพ์ชื่อ field ผิดก็ยอมเหมือนกัน** 😬

💥 **ลองพังมันดู: พิมพ์ชื่อ field ผิด**
```js
db.customers.insertOne({ nmae: "พิมพ์ผิด" })
```
ได้ `acknowledged: true` บันทึกผ่าน! ทั้งที่ไม่มีใครมีชื่อ field ว่า `nmae` เทียบกับ PostgreSQL ที่จะตอบ `column "nmae" of relation "customers" does not exist` ทันที

**แก้ได้ 2 ชั้น:** ตรวจในโค้ดก่อนบันทึก (Zod ซึ่งทีมใช้) และ/หรือให้ MongoDB ตรวจเองด้วย **schema validation**
```js
db.createCollection("laptops", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["serial", "model"],
    properties: { serial: { bsonType: "string" }, model: { bsonType: "string" } }
  } }
})
db.laptops.insertOne({ serial: "AS-01", model: "Asus" })      // ผ่าน
db.laptops.insertOne({ serail: "LN-01", model: "Lenovo" })    // สะกด serial ผิด
```
ควรเห็น (ตัวที่สอง)
```text
MongoServerError: Document failed validation
...
        missingProperties: [ 'serial' ]
```
ความยืดหยุ่นของ NoSQL จึง **เลือกได้** ว่าจะเข้มแค่ไหน แต่ต้องตั้งเอง ส่วน SQL เข้มเป็นค่าเริ่มต้น
เก็บกวาด: พิมพ์ `exit` แล้ว `docker rm -f mongo`

### Redis (ตระกูล Key-Value)
```bash
docker run -d --name redis -p 6379:6379 redis:8
docker exec -it redis redis-cli
```
```text
SET session:abc123 "user-1" EX 3600
GET session:abc123
TTL session:abc123
INCR visits:home
INCR visits:home
GET nothing
```
ควรเห็น
```text
OK
"user-1"
(integer) 3600
(integer) 1
(integer) 2
(nil)
```
- `TTL` = เหลือเวลากี่วินาทีก่อนกุญแจหายเอง เหมาะกับ session และ cache
- `INCR` = บวก 1 ให้แบบทีละคน (ไม่ชนกันแม้หลายคนกดพร้อมกัน) จึงใช้ทำตัวนับยอดวิว หรือจำกัดจำนวนครั้งที่เรียก API (rate limit)
- `GET` กุญแจที่ไม่มี ได้ `(nil)` ไม่ใช่ error

สังเกตว่าไม่มีคำว่า "ตาราง" หรือ "JOIN" เลย ถ้าอยากรู้ว่า "ลูกค้าคนไหนมี session อยู่บ้าง" Redis ตอบยาก นี่คือราคาที่แลกกับความเร็ว
เก็บกวาด: พิมพ์ `exit` แล้ว `docker rm -f redis`

## 10. ⚠️ ปัญหาที่เจอบ่อย (อาการ → สาเหตุ → วิธีแก้)

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| `port is already allocated` ตอน `docker run` | มีโปรแกรมอื่นใช้ port นั้นอยู่ (เช่น PostgreSQL ที่ติดตั้งในเครื่อง หรือ container เก่า) | ปิดตัวเก่า หรือเปลี่ยน port ฝั่งซ้าย เช่น `-p 5433:5432` (ดูบทที่ 7) |
| `Conflict. The container name "/pg" is already in use` | เคยสร้าง container ชื่อนี้ไว้แล้ว | ใช้ตัวเดิม `docker start pg` หรือลบแล้วสร้างใหม่ `docker rm -f pg` (ข้อมูลในนั้นหาย) |
| `FATAL:  role "root" does not exist` | สั่ง `psql` โดยไม่บอก user จึงใช้ชื่อ user ของเครื่องแทน | ใส่ `-U postgres` เสมอ |
| prompt เปลี่ยนเป็น `postgres-#` แล้วกด Enter ไม่มีอะไรเกิด | ลืม `;` ท้ายคำสั่ง psql จึงรอบรรทัดต่อ | พิมพ์ `;` แล้ว Enter (หรือ `Ctrl+C` เพื่อยกเลิกคำสั่งที่พิมพ์ค้าง) |
| `ERROR:  relation "customers" does not exist` | ยังไม่ได้สร้างตาราง, สะกดผิด, หรือลบ container แล้วสร้างใหม่ (ข้อมูลหาย) | `\dt` ดูว่ามีตารางอะไร แล้วสร้างใหม่ตามข้อ 7 |
| `ERROR:  column "สมชาย" does not exist` | ใช้ `"..."` ครอบข้อความ ใน SQL `"..."` คือชื่อคอลัมน์ ส่วนข้อความต้องใช้ `'...'` | `WHERE name = 'สมชาย'` |
| `current transaction is aborted, commands ignored until end of transaction block` | มี error เกิดขึ้นหลัง `BEGIN` ฐานข้อมูลจึงไม่รับคำสั่งต่อ (กันไม่ให้บันทึกครึ่งๆ กลางๆ) | สั่ง `ROLLBACK;` แล้วเริ่มใหม่ |
| ตาราง psql ที่มีภาษาไทยดูเบี้ยว | psql นับความกว้างของสระ/วรรณยุกต์ไทยไม่ตรงกับที่ Terminal แสดง | ปกติ ข้อมูลถูกต้อง ถ้าอยากดูสวยใช้ Adminer หรือ DBeaver |
| `MongoDB cannot start: Linux kernel versions ... have a known incompatibility` แล้ว container ดับเอง | MongoDB รุ่นใหม่เช็ครุ่น kernel ของ Linux ที่ Docker ใช้ แล้วปฏิเสธรุ่นที่มีปัญหาเข้ากันไม่ได้ ([SERVER-121912](https://jira.mongodb.org/browse/SERVER-121912)) | ใช้ `mongo:8.2` ตามข้อ 9 หรืออัปเดต Docker Desktop · ดูสาเหตุจริงด้วย `docker logs mongo` เสมอ |

> 💡 อาการ "container ดับเองทันที" แทบทุกครั้งมีคำอธิบายอยู่ใน `docker logs ชื่อ container` (บทที่ 2) อ่านบรรทัดท้ายๆ ก่อนค้นเน็ต

## 🧠 เช็คความเข้าใจ

<details>
<summary>1. ระบบ POS ร้านค้า ควรใช้ฐานข้อมูลประเภทไหน?</summary>

Relational (SQL) เพราะเกี่ยวกับเงินและสต็อก ต้องการ transaction/ACID และข้อมูลสัมพันธ์กันชัด (สินค้า, บิล, รายการในบิล)

</details>

<details>
<summary>2. เก็บ "สินค้าที่ดูล่าสุด 10 ชิ้น" ของผู้ใช้ ควรใช้อะไร?</summary>

Key-Value อย่าง Redis ต้องการความเร็ว ข้อมูลหายก็ไม่ร้ายแรง รูปแบบง่าย

</details>

<details>
<summary>3. ลืม WHERE ในคำสั่ง DELETE จะเกิดอะไร?</summary>

ลบทุกแถวในตาราง 💀 (ตารางยังอยู่ แต่ข้อมูลหายหมด)

</details>

<details>
<summary>4. ทำไม `WHERE note = NULL` ไม่เจอแถวที่ note ว่าง? ต้องเขียนยังไง?</summary>

เพราะ `NULL` แปลว่า "ไม่ทราบ" การเทียบ `= NULL` ได้ผลเป็น "ไม่ทราบ" ไม่ใช่ true ต้องเขียน `WHERE note IS NULL`

</details>

<details>
<summary>5. อยากได้รายชื่อลูกค้า "ทุกคน" พร้อมจำนวน rental (คนที่ไม่เคยเช่าก็ต้องโชว์ว่า 0) ควรใช้ JOIN แบบไหน?</summary>

`LEFT JOIN` จาก customers ไป rentals แล้ว `COUNT(r.id)` (ไม่ใช่ `COUNT(*)` เพราะจะนับแถว NULL เป็น 1) ถ้าใช้ INNER JOIN คนที่ไม่เคยเช่าจะหายไป

</details>

<details>
<summary>6. ตารางมี 5 ล้านแถว `WHERE email = ...` ช้า ควรทำอะไรก่อน?</summary>

ใส่ `EXPLAIN ANALYZE` ดูว่าเป็น Seq Scan ไหม ถ้าใช่ สร้าง index ที่คอลัมน์ `email` (`CREATE INDEX ... ON users (email)`) แล้ววัดใหม่

</details>

<details>
<summary>7. สินค้ากับออเดอร์ความสัมพันธ์แบบ N:M ต้องออกแบบตารางยังไง?</summary>

ต้องมีตารางกลาง (เช่น `order_items`) ที่มี FK ชี้ไป orders และ products อย่างละตัว (และเก็บ `qty` ได้) ไม่สามารถใส่ FK ตัวเดียวในตารางใดตารางหนึ่งได้

</details>

<details>
<summary>8. ลูกค้าอยากได้ช่องค้นหาสินค้าที่พิมพ์ "โน๊ตบุค" ก็ยังเจอ "โน้ตบุ๊ก" ควรใช้ประเภทไหน และเริ่มยังไง?</summary>

ประเภท search engine (เก่งเรื่องค้นคำ และหลายตัวยอมให้พิมพ์ผิดได้) แต่ถ้าสินค้ามีไม่มาก เริ่มจากความสามารถค้นข้อความที่มีใน PostgreSQL ก่อน เพราะข้อมูลอยู่ที่เดียว ค่อยแยกไปใช้ Meilisearch/Elasticsearch เมื่อวัดแล้วว่าไม่พอ (แล้วต้องมีวิธีคัดลอกข้อมูลจากฐานหลักไปให้ตรงกันเสมอ)

</details>

<details>
<summary>9. แชตบอตที่ตอบจากคู่มือบริษัท ต้องหาย่อหน้าที่ "ความหมายใกล้" กับคำถาม แม้ไม่มีคำตรงกัน ใช้อะไร?</summary>

vector database: แปลงทั้งคำถามและย่อหน้าเป็น embedding แล้วหาตัวที่ใกล้ที่สุด ถ้าใช้ PostgreSQL อยู่แล้ว เริ่มด้วย extension `pgvector` ได้

</details>

<details>
<summary>10. เจอฐานข้อมูลชื่อ "X" ที่เอกสารบอกว่า "stores data as nodes and relationships" อยู่กลุ่มไหน และเหมาะกับงานอะไร?</summary>

ตระกูล Graph ของกลุ่ม NoSQL เหมาะกับคำถามที่เดินตามความสัมพันธ์หลายชั้น เช่น เพื่อนของเพื่อน ระบบแนะนำ หรือหาเส้นทางเงินที่ผิดปกติ (ใช้คำถามในข้อ 5)

</details>

<details>
<summary>11. เพื่อนบอกว่า "MongoDB ไม่มี transaction ห้ามใช้กับงานเงิน" ถูกไหม?</summary>

ข้อมูลเก่า MongoDB มี transaction หลายเอกสารตั้งแต่รุ่น 4.0 แต่เหตุผลที่ยังเลือก SQL สำหรับงานเงินคือข้อมูลแบบนี้มักสัมพันธ์กันมาก ต้อง JOIN/สรุปผล และ SQL มี FK/CHECK ตรวจให้เป็นค่าเริ่มต้น ไม่ต้องตั้งเอง เลือกจากโจทย์ ไม่ใช่จากความเชื่อ

</details>

## ✏️ แบบฝึกหัด

เพิ่มข้อมูลให้มีลูกค้า 5 คน rental 8 รายการ แล้วเขียน SQL 3 ข้อ ใน `queries.sql` (ไฟล์บนเครื่องเรา) แล้วรันทั้งไฟล์ในกล่อง `pg`:
```bash
docker cp queries.sql pg:/queries.sql            # คัดลอกไฟล์จากเครื่องเราเข้าไปในกล่อง
docker exec -it pg psql -U postgres -f /queries.sql
```
(ต้อง `docker cp` ก่อนเพราะ psql รันอยู่ในกล่อง มองไม่เห็นไฟล์บนเครื่องเรา) แก้ไฟล์แล้วต้อง `docker cp` ซ้ำทุกครั้ง ผลที่ถูกของแต่ละข้อ: ข้อ 1 ได้ 1 แถวต่อลูกค้าที่มี rental, ข้อ 2 ได้เฉพาะลูกค้าที่ไม่มีแถวใน `rentals` เลย (ถ้าได้ 0 แถว ให้เช็คว่าข้อมูลมีลูกค้าที่ยังไม่เช่าจริงไหม), ข้อ 3 ได้ 3 แถวเรียงจากแพงไปถูก

1. ค่าเช่ารวมต่อเดือนของลูกค้าแต่ละคน
2. ลูกค้าที่ยังไม่เคยเช่า
3. เครื่องที่ค่าเช่าแพงที่สุด 3 อันดับ

โจทย์เสริม (ถ้ามีเวลา):
4. สร้าง index ที่ `rentals(customer_id)` แล้วอธิบายว่าทำไม JOIN ถึงได้ประโยชน์ **บอกไว้ก่อน:** ถ้าลอง `EXPLAIN SELECT * FROM rentals WHERE customer_id = 1;` กับข้อมูลแค่ 8 แถว จะยังเห็น `Seq Scan` แม้สร้าง index แล้ว ไม่ได้แปลว่า index พัง แต่ PostgreSQL คำนวณแล้วว่าตาราง 8 แถวอยู่ในหน้าดิสก์หน้าเดียว อ่านทั้งหน้ายังถูกกว่าไปเปิด index ก่อน (index จะคุ้มเมื่อข้อมูลเยอะแบบตาราง `big` ในข้อ 7) ถ้าอยากเห็นว่า index ใช้ได้จริง ให้สั่ง `SET enable_seqscan = off;` ก่อน `EXPLAIN` (เฉพาะทดลองเท่านั้น) จะเห็น `Index Scan using rentals_customer_id_idx`
5. หาลูกค้าที่ค่าเช่ารวมเกิน 2000 (ใช้ `HAVING`)
6. **จัดกลุ่มให้เป็น:** แอปร้านกาแฟมีข้อมูล 5 อย่าง: เมนูและราคา · บิลและแต้มสะสม · ตะกร้าสินค้าที่ยังไม่จ่าย · ช่องค้นหาเมนู · อุณหภูมิตู้เย็นทุก 1 นาที เขียนว่าแต่ละอย่างควรอยู่ฐานข้อมูลประเภทไหน **พร้อมเหตุผล 1 บรรทัด** แล้วสรุปว่าถ้าใช้ได้แค่ PostgreSQL ตัวเดียว จะทำแต่ละอย่างยังไง แล้วให้พี่เลี้ยงดู (ไม่มีคำตอบเดียวที่ถูก ที่สำคัญคือเหตุผล)
