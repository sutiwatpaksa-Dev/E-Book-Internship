> **⚡ สรุป 30 วินาที**
> - HTTP คือ **ภาษากลางที่ client กับ server ใช้คุยกัน**: ส่ง **request** ไป ได้ **response** กลับ · **Method** บอกว่าจะทำอะไร (`GET` ดู, `POST` สร้าง, `PATCH` แก้, `DELETE` ลบ) · **Status code** บอกผล (2xx สำเร็จ, 4xx client ผิด, 5xx server พัง)
> - บนภาษาเดียวกันนี้ มี **รูปแบบ API** หลายแบบ: REST, GraphQL, gRPC, tRPC และแบบ realtime (WebSocket, SSE) แต่ละแบบแก้ปัญหาต่างกัน ไม่มีแบบไหน "ดีที่สุด"
> - เครื่องมืออีก 2 กลุ่มที่ต้องแยกให้ออก: **ตัวเรียก/ทดสอบ API** (curl, ไฟล์ `.http`, Postman, Bruno, DevTools) กับ **framework ฝั่ง server** (Express, Hono, Fastify, NestJS …)
> - ทีมเราใช้ **REST + JSON บน Hono** · บทนี้ฝึกหลักการด้วย Express สร้าง **Laptop API ด้วย TypeScript** แล้วแพ็กใส่ Docker (บทที่ 8b ต่อยอดให้ใช้ฐานข้อมูลจริง)

## 📖 เรื่องเล่า

บิตเขียน API ตัวแรก ทุก endpoint ตอบกลับแบบนี้:

```
200 OK
{ "success": false, "message": "ไม่พบข้อมูล" }
```

พี่ไบต์ถาม: *"ถ้าทุกอย่างตอบ 200 แล้วแอปมือถือจะรู้ได้ยังไงว่าสำเร็จหรือพัง?"*
บิต: *"ก็...อ่าน message เอา?"*
พี่ไบต์: *"ถ้า message เป็นภาษาไทย แล้วทีมแอปเป็นคนญี่ปุ่นล่ะ?"* 😅

สัปดาห์ต่อมา บิตอ่านบทความหัวข้อ "เลิกใช้ REST ได้แล้ว ไปใช้ GraphQL" เลยถามพี่ไบต์:
*"ถ้าเปลี่ยนไปใช้ GraphQL ก็ไม่ต้องสนเรื่อง HTTP แล้วใช่ไหมครับ?"*
พี่ไบต์: *"แล้ว GraphQL ส่งข้อมูลผ่านอะไรล่ะ?"*
บิต: *"...ผ่าน GraphQL?"* 🤔

คำตอบคือ **GraphQL ก็ส่งผ่าน HTTP** (ปกติเป็น `POST` ไปที่ `/graphql`) บิตเอาของคนละชั้นมาเทียบกัน HTTP คือ **ภาษา** ส่วน REST กับ GraphQL คือ **รูปแบบการตั้งคำถาม** ที่ใช้ภาษานั้น อ่านบทนี้จบจะแยกได้ว่าอะไรอยู่ชั้นไหน และเจอชื่อใหม่เมื่อไหร่ก็จัดกลุ่มเองได้

> 🧭 **บทนี้เรียนแบบ "เข้าใจกลุ่มก่อน แล้วค่อยจับเครื่องมือ"** ข้อ 1–4 คือพื้นฐาน HTTP ที่ทุกรูปแบบใช้ร่วมกัน ข้อ 5–10 อธิบายเครื่องมือ 3 กลุ่ม (รูปแบบ API · ตัวเรียก/ทดสอบ · framework ฝั่ง server) ว่าแก้ปัญหาอะไร มีใครบ้าง เลือกยังไง ข้อ 11 เป็นต้นไปคือลงมือ ชื่อเครื่องมือเปลี่ยนได้ทุกปี แต่ HTTP กับปัญหาที่แต่ละกลุ่มแก้ยังเหมือนเดิม

## 1. ปัญหา 3 ข้อเวลาให้โปรแกรมคุยกัน

**ปัญหาที่ 1: ต้องมีภาษากลาง**
หน้าเว็บเขียนด้วย JavaScript แอปมือถือเขียนด้วย Swift หรือ Kotlin server เขียนด้วยอะไรก็ได้ ถ้าต่างคนต่างพูดภาษาตัวเองจะไม่มีใครเข้าใจกัน → ภาษากลางที่ทั้งโลกตกลงกันคือ **HTTP** (ข้อ 2–4)

**ปัญหาที่ 2: ภาษาเดียวกัน ยังต้องตกลง "รูปแบบ"**
พูดภาษาไทยเหมือนกัน แต่จดหมาย แบบฟอร์ม กับแชต ก็จัดหน้าไม่เหมือนกัน API ก็เช่นกัน ต้องตกลงว่า URL หมายถึงอะไร ข้อมูลส่งเป็นแบบไหน server ส่งหาเราเองได้ไหม → นี่คือกลุ่ม **รูปแบบ API** (ข้อ 5–6)

**ปัญหาที่ 3: ต้องมีเครื่องมือทั้งสองฝั่ง**
ฝั่งเรียกต้องมีอะไรสักอย่างแต่งคำขอแล้วส่งไป (ตอนพัฒนาเราใช้ **เครื่องมือเรียก/ทดสอบ API** ข้อ 7) ฝั่งรับต้องมีโปรแกรมเปิดรอคำขอ แยกว่าคำขอไหนไปทำอะไร (**framework ฝั่ง server** ข้อ 8)

```
 [client: หน้าเว็บ / แอป / curl / Postman]     ← กลุ่ม 2: ตัวเรียก/ทดสอบ
            │  ภาษา: HTTP (ข้อ 2–4)
            │  รูปแบบ: REST / GraphQL / ...      ← กลุ่ม 1: รูปแบบ API
            ▼
 [server: Express / Hono / ...]                ← กลุ่ม 3: framework
```

## 2. HTTP: การสั่งอาหารในร้าน

> 💡 **เปรียบเทียบ**
> - **Client** = ลูกค้า 🧑 · **Server** = ครัว 👨‍🍳 · **API** = เมนู 📜
> - **Request** = ใบสั่งอาหาร: สั่งอะไร (method + URL) · หมายเหตุ (headers) · รายละเอียด (body)
> - **Response** = อาหารที่มาเสิร์ฟ พร้อมบอกผล (status code): "ได้แล้วครับ" / "เมนูนี้หมด" / "ครัวไฟไหม้"

**API** (Application Programming Interface) คือ "เมนู" ที่โปรแกรมหนึ่งเปิดให้โปรแกรมอื่นสั่งงาน ส่วน **HTTP** คือ "ภาษา" ที่ใช้เขียนใบสั่งและตอบกลับ เว็บ แอปมือถือ และระบบหลังบ้านคุยกันด้วยภาษานี้เกือบทั้งหมด

### พิมพ์ URL แล้วกด Enter เกิดอะไรขึ้น (ฉบับย่อ)

![แผนภาพลำดับ เบราว์เซอร์ถาม DNS ต่อสายกับ server แล้วส่ง HTTP request](/img/05-url-journey.svg)
*3 ขั้น: หา IP จากชื่อ (DNS) → ต่อสาย (TCP, และ TLS ถ้าเป็น https) → คุย HTTP*

1. **DNS:** เครื่องรู้จักแค่เลข IP (เช่น `203.0.113.10`) จึงถาม "สมุดโทรศัพท์" ว่าชื่อ `api.shop.test` คือ IP อะไร
2. **TCP (+ TLS):** ต่อสายไปที่ IP นั้น ที่ port ที่กำหนด (ถ้าเป็น `https` จะเข้ารหัสสายด้วย)
3. **HTTP:** ส่ง request (`GET /laptops`) แล้วรอ response

ถ้าพิมพ์ `localhost:3000` ขั้น 1 ไม่ต้องทำ เพราะ `localhost` คือ "เครื่องตัวเอง" รายละเอียดของแต่ละขั้นอยู่ใน [บทที่ 17 (เน็ตเวิร์ก)](/17-network) และ [บทที่ 18 (โดเมนและ DNS)](/18-domain-dns) ตอนนี้แค่เข้าใจภาพรวมก็พอ

### Request มีอะไรบ้าง

![ส่วนประกอบของ HTTP request และ response](/img/05-request-response.svg)
*Request และ Response โครงสร้างเหมือนกัน: บรรทัดแรก (start line) · headers · บรรทัดว่าง · body*

```
POST /laptops?notify=true HTTP/1.1          ← method + path + query
Host: localhost:3000                        ← headers
Content-Type: application/json
Authorization: Bearer abc123

{ "brand": "Lenovo", "model": "T14" }       ← body
```
| ส่วน | หน้าที่ | ตัวอย่าง |
|---|---|---|
| **Method** | จะทำอะไร | `GET`, `POST` |
| **Path** | กับอะไร | `/laptops/5` |
| **Query** | ตัวเลือกเพิ่มเติม (หลัง `?`) | `?status=available&page=2` |
| **Headers** | ข้อมูลประกอบ | ชนิดข้อมูล, token ยืนยันตัวตน |
| **Body** | ข้อมูลที่ส่งไป (มักเป็น JSON) | `{ "brand": "Lenovo" }` |

### Response มีอะไรบ้าง
```
HTTP/1.1 201 Created                        ← status code
Content-Type: application/json              ← headers

{ "id": 7, "brand": "Lenovo", "model": "T14" }   ← body
```
บรรทัดแรกของ response เรียก **status line** ประกอบด้วย เวอร์ชัน HTTP · **เลข status** (ให้โปรแกรมอ่าน) · **ข้อความ status** (ให้คนอ่าน) โปรแกรมจึงควรตัดสินใจจาก **เลข** เสมอ ไม่ใช่จากข้อความ

> 💡 **HTTP ไม่จำอะไรเลย (stateless):** ทุก request เป็นเรื่องใหม่ server ไม่รู้ว่าคุณเคยมาแล้ว จึงต้องแนบ "บัตรประจำตัว" (cookie หรือ token) มากับทุก request ดูข้อ 13 และ [บทที่ 15](/15-auth)

> 🤓 **HTTP/1.1, HTTP/2, HTTP/3 ต่างกันยังไง?** ต่างกันที่ **วิธีขนส่ง** ไม่ใช่ความหมาย HTTP/1.1 ส่งเป็นข้อความแบบที่เห็นข้างบน HTTP/2 แปลงเป็น binary และส่งหลาย request พร้อมกันในสายเดียวได้ HTTP/3 เปลี่ยนไปวิ่งบน QUIC แทน TCP แต่ **method, status code, header ยังเป็นชุดเดียวกัน** (นิยามรวมอยู่ใน [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)) สิ่งที่เรียนในบทนี้จึงใช้ได้กับทุกเวอร์ชัน (HTTP/2 ส่งมาแค่เลข status ไม่มีข้อความอย่าง `OK` ต่อท้าย ([RFC 9113 ข้อ 8.3.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.3.2)) อีกเหตุผลที่ต้องดูเลข) ([MDN: Evolution of HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Evolution_of_HTTP))

### ส่วนประกอบของ URL

![ส่วนประกอบของ URL: โปรโตคอล โดเมน port path และ query](/img/05-url-anatomy.svg)
*URL = ที่อยู่ของสิ่งที่ขอ แยกเป็นส่วนๆ ได้*

| ส่วน | ตัวอย่าง | ความหมาย |
|---|---|---|
| โปรโตคอล | `https` | ใช้ภาษาอะไร (`https` = HTTP เข้ารหัส) |
| โดเมน | `shop.test` | ชื่อของเครื่อง server |
| port | `:3000` | ประตูของโปรแกรมในเครื่องนั้น (ถ้าไม่เขียน `http` = 80, `https` = 443) |
| path | `/laptops/5` | ของที่ขอ |
| query | `?status=rented&page=2` | ตัวเลือก คู่ `ชื่อ=ค่า` คั่นด้วย `&` |

**Path param กับ Query param ต่างกันยังไง**

| | Path param | Query param |
|---|---|---|
| หน้าตา | `/laptops/5` | `/laptops?status=rented` |
| ใช้บอก | **"ตัวไหน"** (ระบุสิ่งของ 1 ชิ้น) | **"แบบไหน"** (กรอง เรียง แบ่งหน้า) |
| จำเป็นไหม | จำเป็น ไม่มีก็คนละ URL | ไม่ใส่ก็ได้ ใช้ค่าเริ่มต้น |
| ตัวอย่าง | `GET /customers/3` | `GET /laptops?brand=Dell&page=2` |

> ⚠️ ตัวอักษรพิเศษและภาษาไทยใน URL ต้อง "เข้ารหัส" (เช่น ช่องว่างเป็น `%20`) เครื่องมืออย่าง `fetch` หรือ `URLSearchParams` ทำให้เอง อย่านำข้อความมาต่อสตริง URL เองโดยไม่เข้ารหัส

### JSON: รูปแบบข้อมูลที่ API ใช้ส่งกัน

**JSON** คือข้อความที่จัดรูปแบบให้ทุกภาษาโปรแกรมอ่านออก หน้าตาเหมือน object ของ JavaScript แต่ **เข้มงวดกว่า**
```json
{
  "id": 7,
  "brand": "Lenovo",
  "available": true,
  "note": null,
  "tags": ["pos", "rental"],
  "spec": { "ramGb": 16 }
}
```
| ชนิด | ตัวอย่าง |
|---|---|
| ข้อความ | `"Lenovo"` (ต้องใช้ **ฟันหนู `"` เท่านั้น**) |
| ตัวเลข | `7`, `3.14` |
| จริง/เท็จ | `true`, `false` |
| ไม่มีค่า | `null` |
| array | `["a", "b"]` |
| object | `{ "ramGb": 16 }` |

**กฎที่ทำให้ JSON พังบ่อยที่สุด:** ชื่อ key ต้องมี `"` ครอบ · ห้ามใช้ `'` · ห้ามมี comma ท้ายสุด (`[1, 2,]` ผิด) · ห้ามมี comment · `undefined` ไม่มีใน JSON

ลองดูตอนมันพัง (รัน `node -e` ใน Terminal ได้เลย):
```bash
node -e 'JSON.parse("{brand: \"Lenovo\"}")'
```
**ควรเห็น** (ข้อความอาจต่างเล็กน้อยตามเวอร์ชัน Node)
```
SyntaxError: Expected property name or '}' in JSON at position 1 (line 1 column 2)
```
ที่บอกว่า `position 1` เพราะ `brand` ไม่มี `"` ครอบ

### Headers ที่ต้องรู้จัก

Headers คือ "หมายเหตุหน้าใบสั่ง" เป็นคู่ `ชื่อ: ค่า`

| Header | ใช้ใน | บอกอะไร |
|---|---|---|
| `Content-Type` | request/response | **body นี้เป็นชนิดอะไร** เช่น `application/json` (JSON), `text/html`, `multipart/form-data` (อัปโหลดไฟล์) |
| `Accept` | request | client อยากได้ชนิดไหนกลับ เช่น `application/json` |
| `Authorization` | request | บัตรประจำตัว เช่น `Bearer eyJhbGci...` (token) |
| `Cookie` / `Set-Cookie` | request / response | ให้ server ฝากข้อมูลไว้ที่เบราว์เซอร์ แล้วเบราว์เซอร์ส่งกลับมาเองทุกครั้ง |
| `Access-Control-Allow-Origin` | response | อนุญาตเว็บอื่นเรียก API นี้จากเบราว์เซอร์ (CORS ดูข้อ 13) |
| `Content-Length` | ทั้งคู่ | body ยาวกี่ byte |

> 💡 **ข้อเดียวที่มือใหม่พลาดบ่อยที่สุด:** ส่ง JSON ต้องใส่ `Content-Type: application/json` เสมอ ไม่งั้น server ไม่รู้ว่าต้องอ่าน body เป็น JSON (ลองดูในหัวข้อ "ลองพังมันดู")

## 3. Method: บอกว่าจะทำอะไร

| Method | ทำอะไร | ตัวอย่าง | มี body? |
|---|---|---|---|
| `GET` | ดูข้อมูล | `GET /laptops` | ❌ |
| `POST` | สร้างใหม่ | `POST /laptops` | ✅ |
| `PATCH` | แก้บางส่วน | `PATCH /laptops/5` | ✅ |
| `PUT` | แทนที่ทั้งก้อน | `PUT /laptops/5` | ✅ |
| `DELETE` | ลบ | `DELETE /laptops/5` | ❌ |

> ⚠️ `GET` ต้อง **ไม่เปลี่ยนข้อมูล** เด็ดขาด เพราะ browser และระบบ cache อาจเรียกซ้ำเองได้ และ **ไม่ควรมี body** (ความหมายของ body ใน `GET` ไม่ได้นิยามไว้ บาง server ปฏิเสธเลย ตาม [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods/GET)) อยากส่งเงื่อนไขค้นหาให้ใส่ใน query

ยังมีอีก 2 method ที่เจอบ่อยแม้ไม่ได้เขียนเอง: **`HEAD`** = เหมือน `GET` แต่ขอแค่ headers ไม่เอา body · **`OPTIONS`** = ถามว่าทำอะไรได้บ้าง เบราว์เซอร์ใช้ถามก่อนเรื่อง CORS (ข้อ 13)

### สองคำที่ควรรู้: Safe และ Idempotent

![ตารางแสดงว่า method ไหน safe และ idempotent](/img/05-methods-safety.svg)
*Safe = เรียกแล้วไม่เปลี่ยนข้อมูล · Idempotent = เรียกซ้ำกี่ครั้งผลสุดท้ายเท่ากับเรียกครั้งเดียว*

- **Safe (ปลอดภัย):** แค่ดู ไม่เปลี่ยนอะไร → `GET` (รวมถึง `HEAD` และ `OPTIONS`) · method ที่ safe ทุกตัว idempotent ด้วยเสมอ
- **Idempotent (ยิงซ้ำผลเท่าเดิม):** `DELETE /laptops/5` สองครั้ง เครื่อง 5 ก็หายอยู่ดี (ครั้งที่สองอาจได้ `404` แต่ข้อมูลสุดท้ายเหมือนกัน) · `PUT` ใส่ค่าเดิมซ้ำก็ได้ผลเดิม
- **`POST` ไม่ idempotent:** ยิงสองครั้งได้ของใหม่สองชิ้น! นี่คือเหตุผลที่ปุ่ม "สั่งซื้อ" ควรถูกปิดหลังกดครั้งแรก ไม่งั้นเน็ตช้าแล้วลูกค้ากดซ้ำ จะได้ออเดอร์ซ้ำ
- **`PATCH`:** มาตรฐาน **ไม่รับประกัน** ว่า idempotent ขึ้นกับวิธีเขียน ("ตั้งสถานะเป็น rented" ซ้ำได้ผลเดิม แต่ "เพิ่มจำนวน +1" ซ้ำไม่ได้ผลเดิม) ([MDN: PATCH](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods/PATCH))

> 💡 **ทำไมต้องสนใจ?** เน็ตหลุดกลางทางแล้วระบบ/ผู้ใช้ "ลองใหม่" ถ้าเป็น method ที่ idempotent ก็ลองใหม่ได้ปลอดภัย ส่วน `POST` ต้องระวังเป็นพิเศษ

**PUT ต่างจาก PATCH ยังไง:** `PUT` = ส่งข้อมูล **ครบทั้งก้อน** ไปแทนของเดิม (ช่องที่ไม่ส่ง = หาย) · `PATCH` = ส่ง **เฉพาะช่องที่จะแก้** ส่วนใหญ่ในงานจริงใช้ `PATCH`

## 4. Status code: บอกผลลัพธ์

จำแค่หลักแรกก่อน:

![กลุ่มของ HTTP status code 2xx 3xx 4xx 5xx](/img/05-status-families.svg)
*เห็นเลขขึ้นต้นด้วยอะไร ก็รู้ทันทีว่าใครต้องแก้*

| กลุ่ม | ความหมาย | 💡 ในร้านอาหาร |
|---|---|---|
| **2xx** ✅ | สำเร็จ | "อาหารมาแล้วครับ" |
| **3xx** ↪️ | ไปเอาที่อื่น หรือใช้ของเดิมที่มีอยู่ (`304 Not Modified`) | "ร้านย้ายสาขาแล้ว" / "จานเดิมที่โต๊ะยังกินได้" |
| **4xx** 🙅 | **client ผิด** | "เมนูนี้ไม่มีครับ" / "สั่งไม่ครบ" |
| **5xx** 🔥 | **server พัง** | "ครัวไฟไหม้" |

ที่ใช้บ่อยจริงๆ:

| Code | ชื่อ | ใช้เมื่อ |
|---|---|---|
| `200` | OK | ดู/แก้สำเร็จ |
| `201` | Created | สร้างสำเร็จ (`POST`) |
| `204` | No Content | ลบสำเร็จ ไม่มีอะไรส่งกลับ |
| `400` | Bad Request | ข้อมูลที่ส่งมาผิดรูปแบบ |
| `401` | Unauthorized | ยังไม่ได้ login / token ผิด ("คุณเป็นใคร?") |
| `403` | Forbidden | login แล้วแต่ไม่มีสิทธิ์ ("รู้ว่าเป็นใคร แต่ห้ามเข้า") |
| `404` | Not Found | ไม่พบสิ่งที่ขอ |
| `409` | Conflict | ขัดกับสถานะปัจจุบัน เช่น เครื่องถูกเช่าไปแล้ว |
| `500` | Internal Server Error | โค้ด server พัง |

### เลือก status ยังไง: ถามตัวเองตามลำดับ

| คำถาม | ตอบ |
|---|---|
| สำเร็จไหม? | `200` ดู/แก้ · `201` สร้างใหม่ · `204` สำเร็จแต่ไม่มีอะไรให้ส่งกลับ (เช่น ลบ) |
| client ส่งมาผิดรูป/ข้อมูลไม่ครบ? | `400` (เช่น JSON พัง, ลืมช่อง, อีเมลไม่ถูกรูปแบบ) |
| ไม่ได้ login? | `401` |
| login แล้วแต่ไม่มีสิทธิ์? | `403` |
| ไม่มีของที่ขอ? | `404` |
| ของมีอยู่ แต่ทำตามสั่งไม่ได้เพราะสถานะตอนนี้? | `409` (เช่น เช่าเครื่องที่ถูกเช่าอยู่) |
| ขอถี่เกินไป? | `429 Too Many Requests` |
| ฝั่งเราเขียนพลาด/ฐานข้อมูลล่ม? | `500` (หรือ `502`/`503` ถ้า server หลังบ้านไม่พร้อม) |

> 💡 **`400` กับ `422` ต่างกันยังไง?** `400` = ส่งมาผิดรูป (อ่านไม่ออก) · `422 Unprocessable Content` = อ่านออก แต่ข้อมูลไม่ผ่านกติกา (เช่น ราคาติดลบ) บางทีมแยกใช้ทั้งสองตัว **ทีมเราใช้ `400` ทั้งสองกรณี** (ให้ `details` บอกว่าช่องไหนผิด) เพื่อให้จำง่าย ขอแค่ทุก endpoint ทำเหมือนกัน

> ⚠️ **ห้ามส่ง `200` แล้วเขียนว่า `"success": false`** แบบเรื่องเล่าของบิต เพราะระบบกลาง เช่น monitor, cache, หน้าเว็บ ดูแค่เลข status

> 🤓 **เกร็ด:** มีเว็บ **[http.cat](https://http.cat)** ที่ทำรูปแมวประกอบทุก status code 🐱 และมี code `418 I'm a teapot` จริงๆ เกิดจากมุกวันเมษาหน้าโง่ปี 1998

## 5. กลุ่มที่ 1: รูปแบบ API (ตกลงกันว่าจะคุยแบบไหน)

**คืออะไร:** ข้อตกลงว่าคำขอกับคำตอบหน้าตาแบบไหน URL หมายถึงอะไร ข้อมูลส่งเป็นอะไร และใครเริ่มคุยก่อน
💡 HTTP = **ภาษาไทย** 🗣️ รูปแบบ API = **รูปแบบเอกสาร** (จดหมาย แบบฟอร์ม แชต) ภาษาเดียวกันแต่จัดหน้าคนละแบบ เหมาะกับงานคนละอย่าง

**ข้างในทุกรูปแบบ ตอบคำถาม 4 ข้อนี้**
1. **ส่งผ่านอะไร:** HTTP ธรรมดา · HTTP/2 · หรือสายที่เปิดค้างไว้
2. **ข้อมูลหน้าตาแบบไหน:** JSON (ข้อความ คนอ่านได้) · Protocol Buffers (binary เล็กกว่าแต่คนอ่านไม่ออก) · XML
3. **สัญญาอยู่ที่ไหน:** ใครบอกว่ามีคำสั่งอะไร รับและตอบอะไร เช่น เอกสาร OpenAPI · GraphQL schema · ไฟล์ `.proto` · type ของ TypeScript
4. **ใครเริ่มคุย:** client ถามแล้ว server ตอบ (request-response) หรือ server ส่งมาเองได้ (realtime)

### แต่ละแบบเกิดมาแก้ปัญหาอะไร

**REST: ใช้ของที่ HTTP มีให้ครบ** แนวคิดมาจากวิทยานิพนธ์ของ Roy Fielding ปี 2000 ([ต้นฉบับ](https://roy.gbiv.com/pubs/dissertation/top.htm)) มอง URL เป็น **สิ่งของ** (`/laptops/5`) แล้วใช้ method เป็นคำกริยา ผลลัพธ์บอกด้วย status code ข้อดีคือ **อะไรที่พูด HTTP เป็นก็เรียกได้** ทั้ง browser, curl, ทุกภาษา และใช้ cache ของ HTTP ได้ (ข้อ 6 ลงรายละเอียด) ในงานจริงคำว่า "REST API" มักหมายถึง API ที่ใช้ HTTP + JSON + URL แบบสิ่งของ แม้จะไม่ได้ทำครบทุกข้อในต้นฉบับ ([MDN: REST](https://developer.mozilla.org/en-US/docs/Glossary/REST))

**GraphQL: ให้ client เลือกเองว่าอยากได้ช่องไหน** สมมติหน้าจอหนึ่งต้องโชว์เครื่อง + คนที่เช่า + ประวัติการเช่า แบบ REST อาจต้องยิง 3 ครั้ง และแต่ละครั้งได้ช่องที่ไม่ใช้ติดมาด้วย GraphQL แก้ด้วยการมี **URL เดียว** (ปกติ `/graphql`) แล้ว client ส่ง query บอกรูปร่างที่อยากได้
```
POST /graphql
{ "query": "{ laptop(id: 5) { brand status renter { name } } }" }
```
ได้กลับมาเท่าที่ขอพอดี ราคาที่ต้องจ่าย: cache แบบ HTTP ยากขึ้น ต้องคุมไม่ให้ใคร query ลึกจนเครื่องหนัก และ **error บางแบบยังตอบ `200`** ต้องอ่านช่อง `errors` ในคำตอบ ([graphql.org: Serving over HTTP](https://graphql.org/learn/serving-over-http/))

**gRPC: ให้ service คุยกันเร็วและ type ตรงกันข้ามภาษา** เขียน "สัญญา" ไว้ในไฟล์ `.proto` แล้วให้เครื่องมือสร้างโค้ด client และ server ให้ทุกภาษา (server เป็น Go, client เป็น Java ก็ได้) ข้อมูลเป็น Protocol Buffers วิ่งบน HTTP/2 รองรับการส่งข้อมูลต่อเนื่อง (streaming) ทั้งสองทาง เหมาะกับ service หลังบ้านคุยกันเอง แต่ **browser เรียกตรงไม่ได้** ต้องผ่าน [gRPC-Web](https://grpc.io/docs/platforms/web/basics/) ([gRPC: Core concepts](https://grpc.io/docs/what-is-grpc/core-concepts/))
```proto
service LaptopService {
  rpc GetLaptop (GetLaptopRequest) returns (Laptop);
}
```

**tRPC (และ RPC แบบอื่น): เรียก server เหมือนเรียกฟังก์ชัน** RPC = Remote Procedure Call คิดเป็น "ฟังก์ชัน" แทน "สิ่งของ" tRPC เหมาะเมื่อ **หน้าเว็บและ server เป็น TypeScript ทั้งคู่** เรียกฟังก์ชันฝั่ง server แล้วได้ type ตรงกันทันที ไม่ต้องเขียน schema แยกหรือ generate โค้ด แลกกับการที่ client ภาษาอื่นใช้ประโยชน์จาก type ไม่ได้ ([tRPC docs](https://trpc.io/docs)) Hono ก็มีแนวคิดคล้ายกัน ([Hono RPC](https://hono.dev/docs/guides/rpc): server ส่งออก type ของแอป แล้ว client `hc` ใช้ type นั้น) ข้างในยังเป็น endpoint HTTP ธรรมดาที่ curl เรียกได้

### Realtime: เมื่อ server ต้องเป็นฝ่ายเริ่มคุย

แบบข้างบนทั้งหมด **client ต้องถามก่อน** server ถึงตอบได้ ถ้าอยากรู้ทันทีว่ามีข้อความใหม่ทำยังไง?

| วิธี | ทำงานยังไง | 💡 เปรียบเทียบ | เหมาะกับ |
|---|---|---|---|
| **Polling** | client ถามซ้ำทุก N วินาที ("มีอะไรใหม่ไหม") | โทรถามร้านทุก 5 นาทีว่าอาหารเสร็จยัง | ไม่ต้องทันที เขียนง่ายสุด ใช้ REST เดิมได้ |
| **SSE** (Server-Sent Events) | client เปิด request ค้างไว้ server ทยอยส่งข้อความมาเรื่อยๆ **ทางเดียว** (`Content-Type: text/event-stream`) หลุดแล้ว browser ต่อใหม่เอง | ร้านมีจอเรียกคิว เรามองอย่างเดียว | แจ้งเตือน แสดงความคืบหน้า ข้อความที่ทยอยออกมา |
| **WebSocket** | เริ่มจาก HTTP แล้วขอ "อัปเกรด" (`101 Switching Protocols`) กลายเป็นสายเปิดค้าง **ส่งได้ทั้งสองทาง** | โทรศัพท์ที่ไม่วางสาย | แชต เกมหลายผู้เล่น แก้เอกสารพร้อมกัน |
| **Webhook** | server **ของคนอื่น** ยิง HTTP `POST` มาหา server เราเมื่อมีเหตุการณ์ | ร้านโทรมาบอกเองเมื่อของพร้อม | ระบบชำระเงิน แจ้งว่าจ่ายแล้ว (server คุยกับ server) |

แหล่งอ้างอิง: [MDN: Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events) · [MDN: WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API) · [MDN: Protocol upgrade](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Protocol_upgrade_mechanism)

> 💡 **เลือกแบบเบาที่สุดที่พอ:** สายที่เปิดค้างกินทรัพยากร server ต่อผู้ใช้ 1 คน ถ้าแค่ "ส่งทางเดียว" ใช้ SSE ก็พอ ถ้า "ช้าไป 10 วินาทีไม่เป็นไร" polling ง่ายและพังยากที่สุด WebSocket ใช้เมื่อต้องคุยสองทางถี่ๆ จริงๆ
>
> ⚠️ SSE บน HTTP/1.1 เบราว์เซอร์เปิดได้ประมาณ **6 สายต่อโดเมน** รวมทุกแท็บ (HTTP/2 ไม่ค่อยติดปัญหานี้) เปิดหลายแท็บแล้วหน้าเว็บค้างได้ ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events))

### ตัวในกลุ่มเหมือนกันตรงไหน ต่างกันตรงไหน

| หัวข้อ | REST | GraphQL | gRPC | tRPC | WebSocket / SSE |
|---|---|---|---|---|---|
| วิ่งบน HTTP ไหม | ✅ | ✅ (ปกติ `POST /graphql`) | ✅ HTTP/2 | ✅ | ✅ เริ่มจาก HTTP แล้วเปิดค้าง |
| URL หมายถึง | สิ่งของ (`/laptops/5`) | URL เดียวทั้งระบบ | ฟังก์ชันใน service | ฟังก์ชัน (procedure) | ช่องทางเดียวที่เปิดค้าง |
| ข้อมูล | JSON (ส่วนใหญ่) | JSON | Protocol Buffers | JSON | ตกลงกันเอง (มักเป็น JSON) |
| สัญญา | OpenAPI (ไม่บังคับ) | schema (บังคับ) | ไฟล์ `.proto` (บังคับ) | type ของ TypeScript | ตกลงกันเอง |
| บอกผลด้วย | HTTP status code | ช่อง `errors` (อาจได้ `200`) | status ของ gRPC เอง | แปลงเป็น HTTP status ให้ | ตกลงกันเอง |
| browser เรียกตรงได้ | ✅ | ✅ | ❌ ต้องผ่าน gRPC-Web | ✅ | ✅ |

> 🎯 **กลับไปที่เรื่องเล่า:** เกือบทุกรูปแบบในตารางวิ่งบน HTTP ทั้งนั้น ความรู้เรื่อง request, header, status, CORS ในบทนี้ใช้ได้หมด "เปลี่ยนจาก REST เป็น GraphQL" มีความหมาย (เปลี่ยนรูปแบบ) แต่ "เปลี่ยนจาก HTTP เป็น GraphQL" ไม่มีความหมาย

## 6. REST ละเอียด: ตั้งชื่อ endpoint ให้ทุกคนเดาได้

**REST** คือรูปแบบ API ที่นิยมที่สุด และเป็นแบบที่ทีมเราใช้ หลักง่ายๆ คือ **URL เป็นคำนาม (สิ่งของ) ส่วน method เป็นคำกริยา**

![แผนที่ REST: URL เป็นคำนาม method เป็นคำกริยา](/img/05-rest-map.svg)
*มี 2 ระดับหลัก: ทั้งกอง `/laptops` และชิ้นเดียว `/laptops/5` แต่ละระดับใช้ method ต่างกัน*

| ✅ ดี | ❌ ไม่ดี |
|---|---|
| `GET /laptops` | `GET /getAllLaptops` |
| `GET /laptops/5` | `GET /laptop?id=5&action=view` |
| `POST /laptops` | `POST /createLaptop` |
| `PATCH /laptops/5` | `POST /updateLaptop/5` |
| `DELETE /laptops/5` | `GET /deleteLaptop/5` 😱 |
| `GET /customers/3/rentals` | `GET /getRentalsByCustomer?cid=3` |
| `GET /laptops?status=available` | `GET /availableLaptops` |

**หลักจำ**
- ใช้ **พหูพจน์** (`/laptops`) และตัวพิมพ์เล็ก คั่นคำด้วย `-`
- ความสัมพันธ์ใช้ซ้อน: `/customers/3/rentals`
- ค้นหา/กรอง/แบ่งหน้าใช้ query: `?status=available&page=2`
- error ตอบรูปแบบเดียวกันทุกที่ เช่น `{ "error": "ข้อความ", "details": [...] }`

### Versioning: เปลี่ยน API โดยไม่ทำให้แอปเก่าพัง

แอปมือถือที่ลูกค้าติดตั้งไว้แล้วอัปเดตไม่พร้อมกัน ถ้าเราเปลี่ยนหน้าตา response แอปเก่าจะพัง วิธีที่นิยมคือ **ใส่เลขเวอร์ชันใน path**
```
GET /api/v1/laptops     ← แอปรุ่นเก่ายังใช้อยู่
GET /api/v2/laptops     ← รุ่นใหม่ เปลี่ยน response ได้
```
- เพิ่มช่องใหม่ใน response = ไม่ถือว่าทำลาย ไม่ต้องขึ้นเวอร์ชัน
- **ลบ/เปลี่ยนชื่อ/เปลี่ยนชนิด** ช่องเดิม = ต้องขึ้น `v2`
- งานเล็กที่มี client ของเราเองเจ้าเดียว (เช่น เว็บ + API ที่ deploy พร้อมกัน) เริ่มที่ `/api` เฉยๆ ก็พอ แต่ควรรู้แนวคิดนี้ไว้

### กรอง เรียง และแบ่งหน้า (filtering / sorting / pagination)

ถ้ามี 10,000 เครื่อง อย่าส่งกลับทั้งหมดในครั้งเดียว ให้ client บอกผ่าน query
```
GET /laptops?status=available                 ← กรอง
GET /laptops?sort=ramGb&order=desc            ← เรียง
GET /laptops?page=2&limit=20                  ← แบ่งหน้า: หน้าที่ 2 หน้าละ 20 รายการ
```
และ response ควรบอกข้อมูลสำหรับทำปุ่ม "หน้าถัดไป" ด้วย:
```json
{
  "items": [ { "id": 3, "brand": "B3", "status": "available" } ],
  "page": 1,
  "limit": 2,
  "total": 3
}
```
(ถ้าข้อมูลถูกเพิ่มบ่อยมากๆ มีวิธีขั้นสูงกว่า เรียก cursor pagination ตอนนี้รู้แค่ `page`/`limit` ก็พอ)

### รูปแบบ error ให้เหมือนกันทุก endpoint

client เขียนโค้ดจัดการ error ง่ายขึ้นมาก ถ้า error ทุกตัวหน้าตาเหมือนกัน เช่น
```json
{
  "error": "ข้อมูลไม่ถูกต้อง",
  "details": [ { "path": ["brand"], "message": "Too small: expected string to have >=1 characters" } ]
}
```
- `error` = ข้อความสั้นๆ ที่คนอ่านได้
- `details` = (ถ้ามี) บอกว่าช่องไหนผิดเพราะอะไร
- **ห้ามส่งรายละเอียดภายใน** เช่น stack trace, ข้อความ SQL, path ของไฟล์ ออกไปให้ client เก็บไว้ที่ log ฝั่ง server (บทที่ 10, 14)

> 💡 หน้าตาจะเป็นแบบไหนก็ได้ ขอแค่ **ทั้งระบบใช้แบบเดียวกัน** (บทที่ 14 ใช้โครงที่ห่อชั้นนอกเป็น `{ success, error: { code, message, details } }` ซึ่งใช้หลักคิดเดียวกัน) และต้องส่ง **status code ที่ถูกต้องควบคู่เสมอ**
>
> 🤓 มีมาตรฐานกลางด้วยชื่อ **Problem Details** ([RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)) ใช้ `Content-Type: application/problem+json` และช่อง `type`, `title`, `status`, `detail`, `instance` ถ้าเจอ API ของคนอื่นตอบแบบนี้ จะได้รู้ว่าเป็นรูปแบบมาตรฐาน ไม่ใช่ของแปลก

## 7. กลุ่มที่ 2: เครื่องมือเรียกและทดสอบ API

**คืออะไร:** โปรแกรมที่ช่วย **แต่งใบสั่ง HTTP ส่งไป แล้วโชว์คำตอบให้ดู** ใช้ตอนลอง API ก่อนมีหน้าเว็บ ตอนหาบั๊กว่าพังที่หน้าเว็บหรือที่ server และตอนลองเอกสาร API ของคนอื่น
💡 = **โทรสั่งอาหารเองโดยไม่ต้องผ่านพนักงานหน้าร้าน** ถ้าโทรสั่งตรงแล้วครัวทำได้ แปลว่าปัญหาอยู่ที่หน้าร้าน (หน้าเว็บ) ไม่ใช่ครัว (server)

**ข้างในทุกตัวมีของเหมือนกัน**
1. ช่องใส่ **method + URL, headers, body** (ส่วนประกอบเดียวกับข้อ 2)
2. แสดง **status, headers, body** ที่ได้กลับมา
3. **ตัวแปร** เช่น `baseUrl`, token ให้สลับเครื่อง dev / server จริงได้โดยไม่แก้ทุก request
4. **เก็บ request เป็นชุด** (collection) ไว้รันซ้ำ

ต่างกันแค่ 2 เรื่อง: **หน้าตา** (พิมพ์คำสั่ง / เขียนไฟล์ข้อความ / คลิกในแอป) และ **request ถูกเก็บที่ไหน** (ไฟล์ใน repo ที่อยู่ใน Git / บัญชี cloud ของแอป)

**ในกลุ่มนี้มีใครบ้าง**

ระดับ: 🟢 ทีมใช้ (ลงมือในบทนี้) · 🔵 ควรรู้จัก · ⚪ รู้ว่ามี

**ตัวในกลุ่มเหมือนกันตรงไหน ต่างกันตรงไหน**

| หัวข้อ | curl | ไฟล์ `.http` (REST Client) | แอป (Postman, Bruno, Hoppscotch) | DevTools ของ browser |
|---|---|---|---|---|
| แต่ง request เอง | ✅ พิมพ์ | ✅ เขียนไฟล์ | ✅ คลิก | ⚠️ ส่วนใหญ่ใช้ **ดู** สิ่งที่หน้าเว็บส่ง |

## 8. กลุ่มที่ 3: Framework ฝั่ง server

**คืออะไร:** library ที่เปิด port รอรับ HTTP request แล้วส่งต่อให้ฟังก์ชันของเรา (เรียกว่า **handler**) ตาม method + path จากนั้นช่วยส่ง response กลับ
💡 = **พนักงานรับออเดอร์** ดูใบสั่งแล้วส่งให้พ่อครัวที่ถูกคน เราเขียนแค่ "พ่อครัว" (handler)

runtime (Node, Bun) เปิด server ได้เองอยู่แล้ว แต่ต้องแยก path เอง อ่าน body เอง ตั้ง header เอง framework ทำส่วนซ้ำๆ นี้ให้

**ข้างในทุกตัวมี 4 อย่าง**
1. **Router:** จับคู่ method + path → handler (`GET /laptops/:id` → ฟังก์ชันหาเครื่อง)
2. **ตัวอ่าน request:** path param, query, headers, body ที่เป็น JSON
3. **Middleware:** โค้ดที่ทำก่อน/หลังทุก request เช่น เขียน log, ใส่ header CORS, ตรวจ token
4. **ตัวช่วยตอบ + จัดการ error:** ตั้ง status, ส่ง JSON, จุดรวมจับ error ที่หลุดมา

หน้าตาโค้ดต่างกันนิดเดียว เพราะทำ 4 อย่างเดียวกัน
```ts
// Express (บทนี้)
app.get("/laptops/:id", (req, res) => { res.json({ id: req.params.id }); });

// Hono (บทที่ 14 · ทีมใช้)
app.get("/laptops/:id", (c) => c.json({ id: c.req.param("id") }));
```
(ตารางเทียบทีละบรรทัดอยู่ใน [บทที่ 14](/14-hono-api))

**ในกลุ่มนี้มีใครบ้าง** (ฝั่ง JavaScript / TypeScript)

<ToolTable group="api-framework" />

ระดับ: 🟢 ทีมใช้ (Hono ลงมือในบทที่ 14) · 🔵 ควรรู้จัก (Express คือตัวที่บทนี้ใช้ฝึก) · ⚪ รู้ว่ามี

**ตัวในกลุ่มเหมือนกันตรงไหน ต่างกันตรงไหน**

| หัวข้อ | เหมือนกัน / ต่างกัน |
|---|---|
| แนวคิด | ✅ เหมือนกัน: router + middleware + handler + error handler |
| รันบน runtime ไหน | ⚠️ ต่างกัน: Express, Fastify, NestJS, Koa เขียนมาเพื่อ Node (Bun บอกว่า library HTTP หลักของ Node [ควรรันได้โดยไม่ต้องแก้](https://bun.com/docs/guides/ecosystem/express)) · Hono, Elysia ใช้มาตรฐานเว็บ (`Request` / `Response`) จึงย้าย runtime ได้ |
| ตรวจข้อมูลที่ส่งมา | Express / Koa ไม่มีในตัว ใส่ Zod เอง (บทนี้) · Fastify ใช้ JSON Schema ในตัว · Elysia มี `t` ในตัวและรับ Zod ได้ · Hono ทีมเราใช้คู่กับ Zod (บทที่ 14) |
| ขนาดโครง | Express, Hono, Koa, Fastify เล็ก เลือกโครงโฟลเดอร์เอง · NestJS โครงใหญ่ มีกฎว่าโค้ดต้องอยู่ตรงไหน (module, controller, provider) เหมาะทีมใหญ่ |

## 9. เจอเครื่องมือใหม่ จัดกลุ่มเองได้

ทุกปีมีชื่อใหม่ ไม่ต้องจำ ให้ถาม 3 ข้อนี้

| ถามว่า | ถ้าใช่ |
|---|---|
| มันบอกว่า **คำขอกับคำตอบต้องหน้าตาแบบไหน** (มีคำว่า spec, protocol, query language, schema) | **รูปแบบ API** (กลุ่ม 1) |
| มันมีปุ่ม/คำสั่ง **"ส่ง request"** แล้วโชว์ status กับ body ให้ดู | **ตัวเรียก/ทดสอบ** (กลุ่ม 2) |
| มันมีคำสั่งแบบ `app.get("/path", handler)` แล้ว **เปิด port รอรับ** | **framework ฝั่ง server** (กลุ่ม 3) |

บางตัวคร่อมกลุ่ม เช่น **tRPC** เป็นทั้งรูปแบบ (RPC) และ library ที่ติดตั้งทั้งสองฝั่ง · **Postman** เป็นตัวเรียกเป็นหลัก แต่ทำเอกสารและ server ปลอม (mock) ได้ด้วย ไม่เป็นไร ให้ถามว่า **"งานหลักของมันคืออะไร"**

**ไม่ใช่แค่ JavaScript** ทุกภาษามี framework ฝั่ง server ที่ทำ 4 อย่างเดียวกัน (router, ตัวอ่าน request, middleware, error handler) ส่วนรูปแบบ API และตัวเรียก/ทดสอบใช้ร่วมกันได้ทุกภาษา เพราะคุยกันด้วย HTTP

| ภาษา | Framework ฝั่ง server ที่เจอบ่อย |
|---|---|
| JavaScript / TypeScript | Express, Hono, Fastify, NestJS, Elysia |
| Python | FastAPI, Django, Flask |
| PHP | Laravel, Symfony |
| Go | `net/http` (มาในตัว), Gin, Echo |
| Java / Kotlin | Spring Boot |
| C# | ASP.NET Core |
| Ruby | Ruby on Rails, Sinatra |

> 💡 API ที่เขียนด้วย Python เรียกด้วย curl หรือไฟล์ `.http` ได้เหมือนกันทุกอย่าง เพราะเครื่องมือกลุ่ม 2 ไม่สนว่าฝั่ง server เขียนด้วยอะไร สนแค่ว่าพูด HTTP ถูกไหม

## 10. เลือกยังไง และทีมเราใช้อะไร

**คำถาม 4 ข้อก่อนเลือกรูปแบบ API**
1. **มี API เดิมอยู่แล้วไหม?** ถ้ามี ใช้รูปแบบเดิม การมีสองแบบในระบบเดียวเพิ่มงานให้ทุกคน
2. **ใครเป็นคนเรียก?** คนนอก/หลายภาษา/ไม่รู้ว่าจะเป็นใคร → แบบที่ใครก็เรียกได้ (REST) · เราเขียนเองทั้งสองฝั่ง → มีทางเลือกมากขึ้น
3. **server ต้องเป็นฝ่ายเริ่มคุยไหม?** ไม่ต้อง → request-response · ต้อง → เลือก polling / SSE / WebSocket ตามตารางในข้อ 5
4. **ทีมคุ้นและเครื่องมือรองรับไหม?** ตัวเลือกที่เก่งกว่านิดหน่อย ไม่คุ้มถ้าทั้งทีมต้องเรียนใหม่

| สถานการณ์ | มักเลือก | เพราะ |
|---|---|---|
| เว็บ แอปมือถือ หรือให้บริษัทอื่นเรียก | **REST + JSON** | ทุกภาษาทุกเครื่องมือเรียกได้ ใช้ status code และ cache ของ HTTP เต็มที่ |
| หลายหน้าจอ หลาย client อยากได้ข้อมูลซ้อนกันคนละรูปแบบ | GraphQL | client เลือกช่องเอง ลดการยิงหลายครั้ง |
| service หลังบ้านจำนวนมากคุยกันเอง หลายภาษา | gRPC | สัญญาเข้ม สร้างโค้ดให้ทุกภาษา ข้อมูลเล็ก |
| หน้าเว็บ + server เป็น TypeScript ใน repo เดียว ไม่มีคนนอกเรียก | tRPC หรือ Hono RPC | type ตรงกันทั้งสองฝั่งโดยไม่ต้องเขียนสัญญาแยก |
| server ต้องแจ้งเตือน client ทางเดียว | SSE | ง่ายกว่า WebSocket ต่อใหม่เองเมื่อหลุด |
| คุยสองทางถี่ๆ (แชต เกม) | WebSocket | สายเดียวเปิดค้าง ส่งได้ทั้งสองทาง |

> **แนวทางของทีม Blicktech**
> - **API ของทีมเป็น REST + JSON** สร้างด้วย **Hono บน Bun** ตรวจข้อมูลด้วย **Zod** ([บทที่ 14](/14-hono-api), งาน STARTER)
> - **บทนี้ฝึกด้วย Express** เพราะมีตัวอย่างในเน็ตมากที่สุด หลักการ (route, middleware, status code) ใช้กับ Hono ได้ทั้งหมด (เหตุผลเต็มอยู่ใน [บทที่ 3](/03-node-yarn-bun))
> - **ทดสอบ API ในคู่มือนี้** ใช้ไฟล์ `.http` (REST Client ติดตั้งไว้ตั้งแต่บทที่ 0) เพราะเก็บใน Git ได้ และใช้ `curl` เมื่ออยู่บน server หรืออยากเห็น header ละเอียด
> - **GraphQL, gRPC, WebSocket** รู้ไว้ให้จัดกลุ่มเป็นและอ่านโค้ดคนอื่นออก ถ้างานไหนดูเหมือนต้องใช้ คุยกับพี่เลี้ยงก่อนเลือก

---

> 🔧 **จากนี้คือการลงมือ** สร้าง REST API ด้วย Express แล้วเรียกด้วยเครื่องมือกลุ่ม 2 ทั้ง 3 แบบ (ไฟล์ `.http`, `curl`, DevTools) สังเกตว่าทุกเครื่องมือเห็น request/response หน้าตาเดียวกับข้อ 2

## 11. 🔧 ลงมือ: สร้าง Laptop API

**ขั้นที่ 1: เตรียมโปรเจกต์**
```bash
mkdir laptop-api && cd laptop-api
npm init -y
npm install express zod
npm install -D typescript tsx @types/node @types/express
```
ใส่ `tsconfig.json`, `"type": "module"` และ `scripts` (`dev`, `build`, `start`, `typecheck`) ตามหัวข้อ "โปรเจกต์ TypeScript ตั้งแต่ศูนย์" ใน [บทที่ 4](/04-typescript)
(ทดสอบกับ `express` 5 และ `zod` 4 · Express 5 ต้องใช้ Node 18 ขึ้นไป)

**ขั้นที่ 2: เขียน `src/index.ts`**
```ts
import express from "express";
import { z } from "zod";

const app = express();
app.use(express.json());              // ให้ Express อ่าน body ที่เป็น JSON ได้

// ----- ข้อมูล (เก็บใน memory ไปก่อน บทที่ 8b จะย้ายไปฐานข้อมูล) -----
const LaptopInput = z.object({
  brand: z.string().min(1),
  model: z.string().min(1),
  serial: z.string().min(1),
});
type Laptop = z.infer<typeof LaptopInput> & { id: number; status: "available" | "rented" };

const laptops: Laptop[] = [];
let nextId = 1;

// ----- endpoint -----
app.get("/health", (_req, res) => {
  res.json({ status: "ok" });
});

app.get("/laptops", (_req, res) => {
  res.json(laptops);
});

app.get("/laptops/:id", (req, res) => {
  const laptop = laptops.find((l) => l.id === Number(req.params.id));
  if (!laptop) {
    res.status(404).json({ error: "ไม่พบเครื่องนี้" });
    return;
  }
  res.json(laptop);
});

app.post("/laptops", (req, res) => {
  const parsed = LaptopInput.safeParse(req.body);
  if (!parsed.success) {
    res.status(400).json({ error: "ข้อมูลไม่ถูกต้อง", details: parsed.error.issues });
    return;
  }
  const laptop: Laptop = { id: nextId++, status: "available", ...parsed.data };
  laptops.push(laptop);
  res.status(201).json(laptop);
});

app.delete("/laptops/:id", (req, res) => {
  const index = laptops.findIndex((l) => l.id === Number(req.params.id));
  if (index === -1) {
    res.status(404).json({ error: "ไม่พบเครื่องนี้" });
    return;
  }
  laptops.splice(index, 1);
  res.status(204).end();
});

app.listen(3000, () => console.log("🚀 API on http://localhost:3000"));
```
อ่านโค้ดทีละส่วน:
- `app.get("/laptops/:id", ...)` : `:id` คือ **path param** ค่าที่ส่งมาอยู่ใน `req.params.id` (เป็นข้อความเสมอ จึงต้อง `Number(...)`)
- `req.body` คือ body ที่ client ส่งมา ต้องผ่าน `express.json()` ก่อนถึงจะเป็น object
- `safeParse` คือ Zod ตรวจ body (เรื่อง "TypeScript ไม่ได้ตรวจข้อมูลตอนรัน" ใน [บทที่ 4](/04-typescript)) ผิดก็ตอบ `400` · type ของ TypeScript หายไปตอนรัน ข้อมูลจากเน็ตจึงต้องตรวจด้วยโค้ดจริงเสมอ
- ทุกจุดที่ตอบเสร็จใช้ `return;` เพื่อไม่ให้โค้ดตอบซ้ำสองรอบ

- บรรทัด `@baseUrl = ...` คือตัวแปร เรียกใช้ด้วย `{{baseUrl}}` ตอนย้ายไปทดสอบ server จริง แก้ที่เดียว
- เว้น **บรรทัดว่าง** ระหว่าง headers กับ body (เหมือนโครงสร้าง HTTP ที่เห็นข้างบน)

**ควรเห็น** (ตอนกด Send ที่ "เพิ่มเครื่อง") ฝั่งขวาแสดง

### ทดสอบด้วย `curl` (ไม่ต้องลงอะไรเพิ่ม)

`curl` เป็นโปรแกรมใน Terminal ที่ส่ง request ได้ ใช้ได้ในเครื่อง server จริงที่ไม่มีหน้าจอด้วย
```bash
curl -i -s http://localhost:3000/laptops/99
```
(`-i` = แสดง status line และ headers ด้วย · `-s` = ซ่อนแถบความคืบหน้า)

**ควรเห็น** (บางบรรทัด เช่น `Date`, `ETag` จะต่างกัน)
```
HTTP/1.1 404 Not Found
X-Powered-By: Express
Content-Type: application/json; charset=utf-8
Content-Length: 57
...

{"error":"ไม่พบเครื่องนี้"}
```
สร้างเครื่องด้วย `POST`:
```bash
curl -s -X POST http://localhost:3000/laptops \
  -H "Content-Type: application/json" \
  -d '{"brand":"Lenovo","model":"T14","serial":"PF-001"}'
```
**ควรเห็น**
```
{"id":1,"status":"available","brand":"Lenovo","model":"T14","serial":"PF-001"}
```
| ตัวเลือก | ความหมาย |
|---|---|
| `-X POST` | เลือก method (ถ้าไม่ใส่ = `GET`) |
| `-H "ชื่อ: ค่า"` | ใส่ header (ใส่ได้หลายอัน) |
| `-d '...'` | ใส่ body |
| `-i` | แสดง status + headers ของ response |
| `-v` | แสดงทุกขั้นตอน (DNS, ต่อสาย, request, response) เหมาะตอนหาสาเหตุ |
| `-s -o /dev/null -w "%{http_code}\n"` | ไม่แสดง body แสดงแค่เลข status |
| `--json '...'` | ทางลัด: ใส่ body + `Content-Type: application/json` + `Accept: application/json` ให้ในครั้งเดียว (curl 7.82 ขึ้นไป) |

> 💡 ทางเลือกอื่นในกลุ่มเดียวกัน (ข้อ 7): **Postman**, **Bruno**, **Hoppscotch**, **Thunder Client** ทำงานเหมือนกัน แค่คลิกแทนพิมพ์ ไฟล์ `.http` ได้เปรียบตรงที่ **เก็บใน Git ได้** ให้เพื่อนร่วมทีมรันตามได้

### ส่องด้วย DevTools ของ browser

1. เปิด http://localhost:3000/laptops ใน Chrome (หรือ Edge, Firefox)
2. กด **F12** → แท็บ **Network** → กด reload หน้า
3. คลิกแถว `laptops` ดูแท็บ **Headers** (method, status, headers ทั้งขาไปขากลับ) และ **Response** (body)
4. คลิกขวาที่แถวนั้น → **Copy → Copy as cURL** แล้ววางใน Terminal รันได้ทันที

**ควรเห็น:** ในแท็บ Headers มี `Request Method: GET` และ `Status Code: 200 OK` ส่วน Response เป็น JSON array ของเครื่อง (ถ้ายังไม่ได้เพิ่มเครื่องจะเป็น `[]`)

สังเกตว่า request ที่ browser ส่งมี header มากกว่าที่เราพิมพ์เองใน curl มาก (`User-Agent`, `Accept-Language` …) นี่คือเหตุผลที่บางบั๊ก "เปิดใน browser พัง แต่ curl ไม่พัง" ให้ Copy as cURL มาเทียบทีละ header

### ขั้นต่อยอด: ดัก route ที่ไม่มี และ error ที่หลุดมา

ตอนนี้ถ้าเรียก path ที่ไม่มี หรือ JSON พัง Express จะตอบเป็นหน้า **HTML** (ไม่ใช่ JSON) ซึ่งทำให้ client งง เพิ่มโค้ด 2 ชุดนี้ **ต่อท้ายสุดของไฟล์ ก่อน `app.listen`**
```ts
// ----- ท้ายสุด: จัดการ route ที่ไม่มี และ error ที่หลุดมา -----
app.use((_req, res) => {
  res.status(404).json({ error: "ไม่พบเส้นทางนี้" });
});

app.use((err: unknown, _req: express.Request, res: express.Response, _next: express.NextFunction) => {
  if (err instanceof SyntaxError) {
    res.status(400).json({ error: "JSON ไม่ถูกต้อง" });   // body ที่ส่งมาไม่ใช่ JSON
    return;
  }
  console.error(err);                                     // รายละเอียดเก็บไว้ที่ log ไม่ส่งให้ client
  res.status(500).json({ error: "ระบบขัดข้อง ลองใหม่อีกครั้ง" });
});
```
ลองทดสอบ (ใช้ `PUT /laptops` ซึ่งเราไม่ได้ทำ และส่ง JSON พัง)
```bash
curl -s -i -X PUT http://localhost:3000/laptops | sed -n '1p;$p'
curl -s -i -X POST http://localhost:3000/laptops -H "Content-Type: application/json" -d '{brand: Lenovo}' | sed -n '1p;$p'
```
**ควรเห็น**
```
HTTP/1.1 404 Not Found
{"error":"ไม่พบเส้นทางนี้"}
HTTP/1.1 400 Bad Request
{"error":"JSON ไม่ถูกต้อง"}
```
> 💡 ฟังก์ชันที่มี **4 parameter** (`err, req, res, next`) คือ error handler ของ Express ต้องมีครบ 4 ตัวแม้ไม่ใช้ `next` ไม่งั้น Express ไม่รู้ว่าเป็นตัวจัดการ error
>
> 💡 ใน **Express 5** ถ้า handler เป็น `async` แล้ว `await` พัง (promise ถูก reject) Express ส่ง error มาที่ตัวจัดการนี้ให้เอง ไม่ต้องเขียน `try/catch` ทุก handler (Express 4 ทำไม่ได้ ตัวอย่างเก่าในเน็ตจึงมี `try/catch` เต็มไปหมด) ([Express: Migrating to 5](https://expressjs.com/en/guide/migrating-5.html)) บทที่ 8b จะได้ใช้ตอนต่อฐานข้อมูล

### 💥 ลองพังมันดู
รันคำสั่งเหล่านี้ (ก่อนเพิ่มโค้ดต่อยอดข้างบนก็ได้ จะเห็นว่าอะไรเปลี่ยน) แล้วดูว่า status และ body เป็นอะไร

**1. ส่ง body ที่ไม่ใช่ JSON**
```bash
curl -s -i -X POST http://localhost:3000/laptops -H "Content-Type: application/json" -d '{brand: Lenovo}'
```
ก่อนเพิ่มตัวดัก error จะได้ `HTTP/1.1 400 Bad Request` พร้อมหน้า **HTML** มี `SyntaxError: Expected property name or '}' in JSON at position 1 ...` (ซึ่งรั่วชื่อไฟล์ในเครื่อง server ออกมาด้วย จึงควรดักแบบข้างบน)

**2. ลืมใส่ `Content-Type: application/json`**
```bash
curl -s -i -X POST http://localhost:3000/laptops -d '{"brand":"A","model":"B","serial":"C"}'
```
**ควรเห็น**
```
HTTP/1.1 400 Bad Request
...
{"error":"ข้อมูลไม่ถูกต้อง","details":[{"expected":"object","code":"invalid_type","path":[],"message":"Invalid input: expected object, received undefined"}]}
```
(`curl -d` ใส่ `Content-Type: application/x-www-form-urlencoded` ให้เอง `express.json()` จึงไม่อ่าน body ทำให้ `req.body` เป็น `undefined`)

**3. ส่ง `serial` เป็นตัวเลข**
```bash
curl -s -X POST http://localhost:3000/laptops -H "Content-Type: application/json" -d '{"brand":"A","model":"B","serial":123}'
```
**ควรเห็น**
```
{"error":"ข้อมูลไม่ถูกต้อง","details":[{"expected":"string","code":"invalid_type","path":["serial"],"message":"Invalid input: expected string, received number"}]}
```
**4. ปิด server (Ctrl+C) แล้วเรียกอีกครั้ง**
```bash
curl http://localhost:3000/laptops
```
**ควรเห็น**
```
curl: (7) Failed to connect to localhost port 3000 after 1 ms: Couldn't connect to server
```
(ตัวเลข ms และถ้อยคำอาจต่างเล็กน้อยตามเวอร์ชัน curl) นี่คือ "ไม่มีใครรอรับสายอยู่" ไม่ใช่ error ของโค้ดเรา และ **ไม่มี status code** เพราะยังไม่ได้คุย HTTP กันเลย (ใน Node จะเห็นเป็น `ECONNREFUSED`)

## 13. CORS และ Cookie/Token: ของที่เบราว์เซอร์เกี่ยวข้อง

### CORS อธิบายแบบง่าย

ลองนึกภาพ: หน้าเว็บของเรา (`localhost:5173`) พยายามเรียก API ที่อยู่ `localhost:3000` เบราว์เซอร์ถือว่านี่คือ **"คนละเว็บ" (คนละ origin)** (origin = โปรโตคอล + โดเมน + port) ค่าเริ่มต้นของเบราว์เซอร์คือ **ไม่ยอมให้โค้ดของเว็บหนึ่งอ่านคำตอบจากอีก origin** (ไม่งั้นเว็บแปลกปลอมจะแอบอ่านข้อมูลบัญชีธนาคารที่คุณ login ค้างไว้ได้) ยกเว้น server ของ origin นั้นบอกว่าอนุญาต

คำขอแบ่งเป็น 2 แบบ ([MDN: CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS))
- **คำขอธรรมดา** (`GET`/`HEAD`/`POST` ที่ส่งแบบฟอร์มหรือข้อความล้วน ไม่มี header พิเศษ): ส่งไปเลย แต่ถ้า server ไม่ตอบ header อนุญาต เบราว์เซอร์จะ **ไม่ให้โค้ดอ่านคำตอบ**
- **คำขออื่นๆ** (ส่ง JSON, มี `Authorization`, ใช้ `PATCH`/`DELETE`): เบราว์เซอร์ **"ถามก่อน"** ด้วย `OPTIONS` (เรียกว่า **preflight**) ได้รับอนุญาตแล้วจึงส่งคำขอจริง API แบบ JSON ส่วนใหญ่จึงเจอ preflight

![ลำดับ CORS preflight: เบราว์เซอร์ส่ง OPTIONS ถามก่อน server ตอบอนุญาต แล้วจึงส่งคำขอจริง](/img/05-cors-preflight.svg)
*เบราว์เซอร์ส่ง OPTIONS (preflight) ถามก่อน server ตอบ header อนุญาต เบราว์เซอร์จึงส่งคำขอจริง*

- **CORS (Cross-Origin Resource Sharing)** = กติกาที่ **server** บอกเบราว์เซอร์ว่า "เว็บ origin ไหนเรียกฉันได้" ผ่าน header `Access-Control-Allow-Origin`
- **คนที่บล็อกคือเบราว์เซอร์** ไม่ใช่ server (curl, Postman, แอปมือถือ ไม่มีเรื่อง CORS)
- **ที่แก้คือฝั่ง server** (ใส่ header) ไม่ใช่ฝั่งหน้าเว็บ ห้ามแก้ด้วยการปิดความปลอดภัยของเบราว์เซอร์หรือใส่ `*` ทุกที่ (อนุญาตให้ทุกเว็บ) ในงานจริงที่มี login (ดู [บทที่ 10](/10-security)) และถ้าคำขอแนบ cookie มาด้วย เบราว์เซอร์ **ไม่ยอมรับ `*`** ต้องระบุ origin ตรงตัว
- **CORS ไม่ได้กันทุกอย่าง:** คำขอธรรมดายังไปถึง server ได้ (แค่อ่านคำตอบไม่ได้) การกันเว็บอื่นแอบส่งคำสั่งแทนผู้ใช้ (CSRF) เป็นอีกเรื่องหนึ่ง อยู่ใน [บทที่ 10](/10-security)

ลองดู header ที่ server ตอบตอนเบราว์เซอร์ถาม preflight (ตัวอย่างเขียน middleware เองให้เห็นกลไก งานจริงใช้ library เช่น `cors` ของ Express หรือ middleware ของ Hono ใน [บทที่ 14](/14-hono-api))
```ts
app.use((req, res, next) => {
  res.setHeader("Access-Control-Allow-Origin", "http://localhost:5173");
  res.setHeader("Access-Control-Allow-Methods", "GET,POST,PATCH,DELETE");
  res.setHeader("Access-Control-Allow-Headers", "Content-Type,Authorization");
  if (req.method === "OPTIONS") { res.status(204).end(); return; }   // ตอบ preflight
  next();
});
```
```bash
curl -s -i -X OPTIONS http://localhost:3000/laptops \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type"
```
**ควรเห็น**
```
HTTP/1.1 204 No Content
X-Powered-By: Express
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Methods: GET,POST,PATCH,DELETE
Access-Control-Allow-Headers: Content-Type,Authorization
...
```
> 💡 ใน dev ที่หน้าเว็บกับ API คนละ port วิธีที่ง่ายกว่าคือให้ dev server ของหน้าเว็บ **proxy** `/api` ไปหา API ทำให้เบราว์เซอร์เห็นเป็น origin เดียวกัน (บทที่ 14)

### Cookie กับ Token (พรีวิว)

HTTP ไม่จำว่าคุณคือใคร จึงต้องแนบ "บัตร" ไปกับทุก request มี 2 แบบหลัก

| | Cookie | Token (เช่น JWT) |
|---|---|---|
| เก็บที่ | เบราว์เซอร์เก็บให้อัตโนมัติ | โค้ดฝั่ง client เก็บเอง |
| ส่งยังไง | เบราว์เซอร์แนบ header `Cookie` ให้เอง | โค้ดใส่ header `Authorization: Bearer ...` เอง |
| server ตั้งค่าด้วย | header `Set-Cookie` | ส่ง token กลับใน body |
| ใช้เด่นกับ | เว็บในเบราว์เซอร์ | API ที่มีหลาย client (มือถือ ฯลฯ) |
| ระวัง | CSRF, ต้องตั้ง `HttpOnly`/`Secure` | ถ้าเก็บผิดที่โดนขโมยได้ (XSS) |

รายละเอียดการทำ login จริงอยู่ใน [บทที่ 15](/15-auth) ตอนนี้จำแค่ว่า **บัตรเดินทางผ่าน header**

## 14. 📚 อ่านเอกสาร API ให้เป็น

เวลาต้องเรียก API ของคนอื่น (เช่น ระบบชำระเงิน, แผนที่) เปิดเอกสารแล้วหา 6 อย่างนี้ตามลำดับ

| หาอะไร | ตัวอย่าง |
|---|---|
| 1. **Base URL** | `https://api.example.com/v1` |
| 2. **การยืนยันตัวตน** | ใส่ `Authorization: Bearer <API_KEY>` (ขอ key ที่ไหน) |
| 3. **Endpoint ที่ต้องใช้** | `GET /laptops` , `POST /laptops` |
| 4. **Parameters** | path param, query param (อะไรจำเป็น/ไม่จำเป็น) |
| 5. **Request body** | ช่องไหนจำเป็น ชนิดอะไร ตัวอย่าง JSON |
| 6. **Response + error** | ตัวอย่างผลสำเร็จ และ status/รูปแบบ error ที่เป็นไปได้ |

**ทำตามนี้:** copy ตัวอย่าง `curl` ในเอกสารมาลองใน Terminal หรือแปลงเป็นไฟล์ `.http` ก่อน เห็นผลจริงแล้วค่อยเขียนโค้ด และมักมีเอกสารแบบ **OpenAPI/Swagger** ที่กด "Try it out" ลองยิงบนหน้าเว็บได้เลย

> ⚠️ **API key = รหัสผ่านของระบบ** ห้าม commit ลง Git (เก็บในไฟล์ `.env` ตาม [บทที่ 10](/10-security))

| อาการ | เกิดจากอะไร | วิธีแก้ |
|---|---|---|
| Console ในเบราว์เซอร์ขึ้น `blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource` | หน้าเว็บคนละ origin กับ API แต่ server ไม่บอกว่าอนุญาต | แก้ **ฝั่ง server** ให้ส่ง `Access-Control-Allow-Origin` (และตอบ `OPTIONS`) หรือใช้ proxy ตอน dev ดูข้อ 13 |

| `415 Unsupported Media Type` | ส่ง body เป็นชนิดที่ server ไม่รับ (เช่น ส่งข้อความล้วนแต่ API รับ JSON) | ส่ง `Content-Type: application/json` พร้อม body เป็น JSON จริง · (Express ที่เราทำจะไม่ตอบ 415 แต่จะมอง body ว่าว่างแล้วตอบ `400`) |

| `400` แต่ในทีมอื่นใช้ `422` | ข้อมูลอ่านออกแต่ผิดกติกา | ไม่ใช่บั๊ก แค่ตกลงกันในทีม ทีมเราใช้ `400` ทั้งสองกรณี |
| `401` / `403` | `401` ยังไม่ login/ token ผิดหรือหมดอายุ · `403` login แล้วแต่ไม่มีสิทธิ์ | เช็ค header `Authorization` ว่าส่งไปจริงและถูกต้อง · เช็คสิทธิ์ของบัญชี |
| `500 Internal Server Error` | โค้ด **server** พังระหว่างทำงาน (client ไม่ผิด) | เปิด **log ของ server** (ใน Terminal ที่รันอยู่) ดู error และ stack trace แล้วแก้โค้ด อย่าเดาจากฝั่ง client |

| แก้โค้ดแล้ว API ยังตอบแบบเก่า | server ตัวเก่ายังรันอยู่ หรือเรียกผิด port | หยุดของเก่า (`Ctrl+C`) แล้วรันใหม่ · เช็ค port |
| หน้าเว็บพัง แต่ยิงด้วย curl / `.http` ได้ปกติ | หน้าเว็บส่ง request ไม่เหมือนที่เราคิด (ลืม header, URL ผิด, cookie ไม่ติด) หรือติด CORS | เปิด DevTools → Network ดู request ที่ส่งจริง แล้ว **Copy as cURL** มาเทียบกับคำสั่งที่ใช้ได้ทีละ header |
| เรียก GraphQL API ได้ `200` แต่ไม่มีข้อมูล | GraphQL ส่ง error ในช่อง `errors` ของ body ได้ แม้ status เป็น `200` | อ่านช่อง `errors` ทุกครั้ง อย่าดูแค่ status (ข้อ 5) |

## 🧠 เช็คความเข้าใจ

<details>
<summary>1. ลูกค้าส่งฟอร์มมาโดยไม่กรอกเบอร์โทร ควรตอบ status อะไร?</summary>

`400 Bad Request` เพราะข้อมูลที่ client ส่งมาไม่ครบ

</details>

<details>
<summary>2. ยืมเครื่องที่ถูกยืมไปแล้ว ควรตอบอะไร?</summary>

`409 Conflict` คำขอถูกรูปแบบ แต่ขัดกับสถานะปัจจุบันของข้อมูล

</details>

<details>
<summary>3. `401` กับ `403` ต่างกันยังไง?</summary>

401 = ไม่รู้ว่าเป็นใคร (ยังไม่ login) / 403 = รู้ว่าเป็นใคร แต่ไม่มีสิทธิ์ทำสิ่งนี้

</details>

<details>
<summary>4. ทำไม `GET /deleteLaptop/5` อันตราย?</summary>

GET ควรเป็นการดูอย่างเดียว browser, bot หรือระบบ preview ลิงก์อาจเรียก URL นี้เองโดยไม่ตั้งใจ แล้วข้อมูลถูกลบ

</details>

<details>
<summary>5. `/laptops/5` กับ `/laptops?status=rented` ส่วนที่ต่างกันเรียกว่าอะไร ใช้ต่างกันยังไง?</summary>

`5` คือ path param ใช้ระบุ "ตัวไหน" (ของชิ้นเดียว) ส่วน `status=rented` คือ query param ใช้ "กรอง/เรียง/แบ่งหน้า" ของกลุ่ม

</details>

<details>
<summary>6. `POST` กับ `PUT` ต่างกันเรื่อง idempotent ยังไง?</summary>

`PUT /laptops/5` ส่งซ้ำกี่ครั้งผลสุดท้ายเท่าเดิม (idempotent) ส่วน `POST /laptops` ส่งซ้ำ = สร้างเครื่องใหม่ซ้ำ จึงต้องระวังปุ่มที่ถูกกดซ้ำ

</details>

<details>
<summary>7. เบราว์เซอร์ฟ้อง CORS error แต่เรียกด้วย curl ได้ปกติ แปลว่าอะไร และต้องแก้ที่ไหน?</summary>

server ทำงานปกติ แต่ไม่ได้ส่ง `Access-Control-Allow-Origin` ที่อนุญาต origin ของหน้าเว็บ เบราว์เซอร์เป็นตัวบล็อก (curl ไม่มีกลไกนี้) ต้องแก้ที่ **server** ให้ส่ง header นั้น (หรือใช้ proxy ตอน dev)

</details>

<details>
<summary>8. ส่ง JSON ไปแต่ `req.body` เป็น `undefined` ตรวจอะไรเป็นอย่างแรก?</summary>

เช็คว่ามี `app.use(express.json())` และ client ส่ง header `Content-Type: application/json` ครบหรือไม่

</details>

<details>
<summary>9. เพื่อนบอกว่า "โปรเจกต์นี้เลิกใช้ HTTP แล้ว เปลี่ยนเป็น GraphQL" ประโยคนี้ผิดตรงไหน?</summary>

GraphQL เป็น **รูปแบบ API** ที่วิ่งบน HTTP (ปกติ `POST /graphql`) ไม่ใช่สิ่งที่มาแทน HTTP ที่ถูกคือ "เปลี่ยนจาก REST เป็น GraphQL" เรื่อง header, CORS, token ยังใช้เหมือนเดิม

</details>

<details>
<summary>10. หน้าเว็บต้องโชว์ความคืบหน้าการประมวลผลไฟล์ที่ server ส่งมาเรื่อยๆ ผู้ใช้ไม่ต้องส่งอะไรกลับ ควรใช้อะไร เพราะอะไร?</summary>

**SSE** เพราะข้อมูลไหลทางเดียวจาก server → client วิ่งบน HTTP ธรรมดา และเบราว์เซอร์ต่อใหม่เองเมื่อหลุด WebSocket ก็ทำได้แต่หนักเกินจำเป็น (เปิดสองทางทั้งที่ใช้ทางเดียว) ถ้าช้าไปหลายวินาทีไม่เป็นไร polling ก็พอ

</details>

<details>
<summary>11. Bruno, Hono, gRPC อยู่กลุ่มไหนบ้าง?</summary>

**Bruno** = ตัวเรียก/ทดสอบ API (มีปุ่มส่ง request) · **Hono** = framework ฝั่ง server (มี `app.get(...)` เปิด port รอรับ) · **gRPC** = รูปแบบ API (กำหนดว่าคำขอ/คำตอบหน้าตาแบบไหนผ่านไฟล์ `.proto`)

</details>

<details>
<summary>12. ทำไมทีมเลือก REST สำหรับ API ของเว็บ แทนที่จะใช้ gRPC ที่ข้อมูลเล็กและเร็วกว่า?</summary>

browser เรียก gRPC ตรงไม่ได้ (ต้องผ่าน gRPC-Web) และ REST เรียกได้จากทุกเครื่องมือทุกภาษา ใช้ status code กับ cache ของ HTTP ได้เต็มที่ ทดสอบด้วย curl หรือไฟล์ `.http` ได้ทันที ข้อดีเรื่องความเร็วของ gRPC เห็นชัดตอน service หลังบ้านคุยกันจำนวนมาก ซึ่งไม่ใช่โจทย์ของเว็บทั่วไป

</details>

## ✏️ แบบฝึกหัด

เพิ่ม `PATCH /laptops/:id` (แก้ brand/model ได้บาง field ใช้ `LaptopInput.partial()`) และ `GET /laptops?status=available` ทดสอบด้วยไฟล์ `.http` ให้ครบทั้งกรณีสำเร็จและกรณี error

เพิ่มเติม (ถ้าอยากไปไกลกว่านี้)
- เพิ่ม `?page=` และ `?limit=` ให้ `GET /laptops` แล้วตอบรูปแบบ `{ items, page, limit, total }`
- ให้ทุก error ใช้รูปแบบ `{ error, details? }` เหมือนกัน (รวม 404 ของ route ที่ไม่มี และ 500)
- เขียนไฟล์ `.http` ที่เก็บ request ทุกแบบรวมถึง `@baseUrl` และกรณีพัง เช่น JSON ผิด, ลืม `Content-Type`
- เปิดเว็บที่ใช้ประจำ (เช่น เว็บข่าว) แล้วดูแท็บ Network หา request ที่ตอบเป็น JSON 1 ตัว จดว่า method, status, `Content-Type` เป็นอะไร และเดาว่าเว็บนั้นใช้รูปแบบ API แบบไหน (URL เป็นสิ่งของ = REST · ยิงไป `/graphql` = GraphQL)

**ฝึกจัดกลุ่ม:** ค้นชื่อเหล่านี้ทีละตัวในเว็บทางการ แล้วบอกว่าอยู่กลุ่มไหน (รูปแบบ API / ตัวเรียก-ทดสอบ / framework ฝั่ง server) ด้วยคำถามในข้อ 9: **HTTPie**, **FastAPI**, **Socket.IO**, **Insomnia**, **AdonisJS**

## ✅ ผ่านด่าน

- [ ] แยกได้ว่า HTTP (ภาษา) กับ REST / GraphQL / gRPC (รูปแบบ) อยู่คนละชั้น และบอกได้ว่าแต่ละรูปแบบแก้ปัญหาอะไร
- [ ] เลือกได้ว่างานไหนใช้ polling, SSE หรือ WebSocket พร้อมเหตุผล
- [ ] จัดกลุ่มเครื่องมือที่ไม่เคยเห็นได้ว่าเป็นรูปแบบ API, ตัวเรียก/ทดสอบ หรือ framework ฝั่ง server
- [ ] อธิบายส่วนประกอบของ request/response ได้ (start line, headers, body)
- [ ] อธิบายส่วนประกอบของ URL, path param และ query param ได้
- [ ] เลือก method และ status code ได้ถูก รู้ว่า `GET` ห้ามเปลี่ยนข้อมูล
- [ ] ตั้งชื่อ endpoint แบบ REST ได้ และตอบ error รูปแบบเดียวกัน

- [ ] สร้าง API ด้วย TS + Zod และรันใน Docker ได้
