> ประมาณ 4 ชั่วโมง · ต้องผ่านก่อน: บทที่ 10, 13 และ 14 · ใช้: Hono, `Bun.password`, React Router

> **สรุป 30 วินาที**
> - เก็บรหัสผ่านแบบ **hash** (แปลงทางเดียว ย้อนกลับไม่ได้ ไม่ใช่การเข้ารหัส) ด้วย `Bun.password`
> - login สำเร็จ → server ออก **บัตรผ่าน (JWT)** ใส่ไว้ใน **cookie แบบที่โค้ดในหน้าเว็บอ่านไม่ได้** (`httpOnly`) ใช้ได้ 1 วัน
> - มี **ด่านตรวจ (middleware)** หน้าทุก `/api/admin/...` ไม่มีบัตรหรือบัตรหมดอายุ → ตอบ `401`
> - login ผิดตอบข้อความเดียว **"อีเมลหรือรหัสผ่านไม่ถูกต้อง"** ห้ามบอกว่าผิดช่องไหน
> - หน้าเว็บพาคนที่ยังไม่ login ไปหน้า login ก็จริง แต่ **ตัวกันจริงคือ server**

## เรื่องเล่า

บิตทำหน้า `/admin` เสร็จ ซ่อนปุ่มไว้อย่างดี พี่ไบต์เปิด Terminal แล้วพิมพ์:
```bash
curl -X DELETE http://localhost:3000/api/admin/categories/1
```
หมวดหายไปทั้งหมวด บิต: *"แต่พี่ยังไม่ได้ login เลยนะ!"*
พี่ไบต์: *"server ไม่รู้หรอกว่าเราซ่อนปุ่มไว้ server ต้องถามเองทุกครั้งว่า 'คุณเป็นใคร'"*

> **ระวัง:** นี่คือ 1 ใน 3 ข้อที่ทำให้งาน STARTER **ไม่ผ่านทันที**: *เรียก API หลังบ้านได้โดยไม่ต้อง login*

## 1. login ทำงานยังไง

![ลำดับตอน login: เบราว์เซอร์ส่งอีเมลและรหัสผ่าน server หาบัญชีแล้วเทียบ hash ตรงก็ออกบัตรผ่านใน Set-Cookie ไม่ตรงตอบ 401](/img/15-login-sequence.svg)
*ลำดับขั้นของการ login ตั้งแต่กดปุ่มจนได้บัตรผ่าน*

> **นึกภาพ:** สายรัดข้อมือเข้างานคอนเสิร์ต ตรวจบัตรครั้งเดียวที่ประตู แล้วได้สายรัดข้อมือ เดินเข้าโซนไหนก็แค่โชว์สายรัด ไม่ต้องโชว์บัตรประชาชนทุกครั้ง

**ทำไมเก็บบัตรใน cookie แบบ `httpOnly` ไม่ใช่ localStorage** (ทบทวน [บทที่ 10](/10-security#3-authentication-vs-authorization))
| | localStorage | cookie แบบ `httpOnly` |
|---|---|---|
| โค้ดในหน้าเว็บอ่านได้ไหม | ✅ ได้ → ถ้าคนร้ายแอบใส่โค้ดลงหน้าเว็บได้ บัตรถูกขโมยทันที | ❌ ไม่ได้ |
| ต้องแนบบัตรเองทุกครั้งไหม | ต้องเขียนโค้ดแนบเอง | เบราว์เซอร์แนบให้เอง |
| กันเว็บอื่นแอบส่งคำขอแทนเรา | ไม่ช่วย | `SameSite=Lax` กันได้ส่วนใหญ่ แต่ไม่ครบ ต้องมีด่านตรวจ CSRF เพิ่ม ([ข้อ 4](#ด่านกันคำขอปลอมจากเว็บอื่น-csrf)) |

**ตั้งค่า cookie แต่ละตัวทำอะไร**
| ตั้งค่า | ทำอะไร |
|---|---|
| `HttpOnly` | โค้ดในหน้าเว็บอ่าน cookie นี้ไม่ได้ |
| `SameSite=Lax` | ถ้าเว็บ **คนละโดเมนหลัก** พยายามส่ง `POST` / `PATCH` / `DELETE` มาที่เว็บเรา เบราว์เซอร์จะไม่แนบ cookie ไปให้ (แต่โดเมนย่อยของโดเมนเดียวกัน เช่น `blog.example.com` ยังแนบ ดูข้อ 4) |
| `Secure` | ส่ง cookie เฉพาะตอนเป็น `https://` (เปิดตอนขึ้นระบบจริง ตอนพัฒนาในเครื่องใช้ `http://` จึงปิดไว้) |
| `Max-Age=86400` | หมดอายุใน 1 วัน (86,400 วินาที) ตามที่งาน STARTER กำหนด |
| `Path=/` | ใช้ได้ทุกหน้าของเว็บ |

![เปรียบเทียบ localStorage ที่โค้ดแปลกปลอมอ่านได้ กับ cookie แบบ HttpOnly ที่อ่านไม่ได้ พร้อมค่าที่ตั้งใน cookie](/img/15-cookie-flags.svg)
*ถ้าเก็บบัตรใน localStorage โค้ดแปลกปลอมอ่านได้ แต่ cookie แบบ HttpOnly อ่านไม่ได้*


สุ่มกุญแจลับยาวๆ ไว้เซ็นบัตรผ่าน (Mac/Linux/Git Bash)

Git Bash บน Windows มี `openssl` มาให้แล้ว ถ้าเครื่องไหนพิมพ์แล้วขึ้น `command not found` ใช้ Bun ที่ติดตั้งไว้แล้วสุ่มแทน ได้ผลแบบเดียวกัน

```
ADMIN_EMAIL=admin@bitcafe.local
ADMIN_PASSWORD=<รหัสผ่านทดสอบ อย่างน้อย 12 ตัว>
```

ดูในฐานข้อมูล (สั่งในโฟลเดอร์ `bit-cafe`)

**ควรเห็น**

```
---------------------+--------------------------------
```

## 3. ออกบัตร + ตรวจบัตร

บัตรผ่าน (JWT) มี 3 ส่วนต่อกันด้วยจุด และอ่านได้แต่แก้ไม่ได้

![โครงสร้างของ JWT: header, payload และ signature อ่านข้างในได้แต่ถ้าแก้ลายเซ็นจะไม่ตรง](/img/15-jwt-anatomy.svg)
*JWT ไม่ได้เข้ารหัส ใครก็อ่านข้างในได้ แค่เซ็นชื่อกันแก้ จึงห้ามใส่ข้อมูลลับ*

`src/auth/session.ts` ออกบัตรผ่าน และอ่านบัตรผ่าน
```ts
import { sign, verify } from "hono/jwt";
import { env } from "../env";

export const SESSION_COOKIE = "session";
const ONE_DAY = 60 * 60 * 24;

export const sessionCookieOptions = {
  httpOnly: true,
  secure: env.NODE_ENV === "production",
  sameSite: "Lax",
  path: "/",
  maxAge: ONE_DAY,
} as const;

export function createSessionToken(adminId: number): Promise<string> {
  return sign({ sub: String(adminId), exp: Math.floor(Date.now() / 1000) + ONE_DAY }, env.JWT_SECRET, "HS256");
}

// คืน adminId ถ้า token ถูกต้องและยังไม่หมดอายุ / ไม่งั้นคืน null
export async function readSessionToken(token: string): Promise<number | null> {
  try {
    const payload = await verify(token, env.JWT_SECRET, "HS256");   // ตรวจลายเซ็น + exp ให้เอง
    const id = Number(payload.sub);
    return Number.isInteger(id) ? id : null;
  } catch {
    return null;
  }
}
```

`src/middleware/require-admin.ts` ด่านตรวจหน้า API หลังบ้าน
```ts
import { createMiddleware } from "hono/factory";
import { getCookie } from "hono/cookie";
import { readSessionToken, SESSION_COOKIE } from "../auth/session";
import { AppError } from "../http/response";

export type AdminEnv = { Variables: { adminId: number } };

export const requireAdmin = createMiddleware<AdminEnv>(async (c, next) => {
  const token = getCookie(c, SESSION_COOKIE);
  const adminId = token ? await readSessionToken(token) : null;
  if (!adminId) throw new AppError(401, "UNAUTHORIZED", "กรุณาเข้าสู่ระบบ");

  c.set("adminId", adminId);     // route ถัดไปใช้ c.get("adminId") ได้
  await next();
});
```

## 4. เข้าระบบ / ออกจากระบบ / ถามว่าเป็นใคร

`src/routes/auth.ts` (2 ที่อยู่นี้ **ไม่ต้อง** login ก่อน)
```ts
import { Hono } from "hono";
import { deleteCookie, setCookie } from "hono/cookie";
import { eq } from "drizzle-orm";
import { z } from "zod";
import { db } from "../db";
import { admins } from "../db/schema";
import { createSessionToken, SESSION_COOKIE, sessionCookieOptions } from "../auth/session";
import { AppError, ok, parse } from "../http/response";
import { rateLimit } from "../middleware/rate-limit";

const LoginInput = z.object({ email: z.email(), password: z.string().min(1) });

// hash หลอก: ใช้ตอนไม่พบอีเมล ให้เวลาตอบพอๆ กับกรณีรหัสผิด คนร้ายจะเดาไม่ได้ว่าอีเมลไหนมีจริง
const DUMMY_HASH = await Bun.password.hash("not-a-real-password");

export const authRoutes = new Hono();

authRoutes.post("/login", rateLimit({ limit: 10, windowMs: 15 * 60 * 1000 }), async (c) => {
  const body = parse(LoginInput, await c.req.json().catch(() => null));

  const [admin] = await db.select().from(admins).where(eq(admins.email, body.email.toLowerCase()));
  const valid = await Bun.password.verify(body.password, admin?.passwordHash ?? DUMMY_HASH);
  if (!admin || !valid) {
    throw new AppError(401, "INVALID_CREDENTIALS", "อีเมลหรือรหัสผ่านไม่ถูกต้อง");   // ข้อความเดียวทุกกรณี
  }

  setCookie(c, SESSION_COOKIE, await createSessionToken(admin.id), sessionCookieOptions);
  return ok(c, { id: admin.id, email: admin.email, name: admin.name });
});

authRoutes.post("/logout", (c) => {
  deleteCookie(c, SESSION_COOKIE, { path: "/" });
  return ok(c, null);
});
```

`src/routes/admin.ts` (ทุกที่อยู่ในไฟล์นี้ต้อง login ก่อน)
```ts
import { Hono } from "hono";
import { count, desc, eq } from "drizzle-orm";
import { z } from "zod";
import { db } from "../db";
import { admins, categories, contactMessages, services } from "../db/schema";
import { AppError, ok, parse } from "../http/response";
import type { AdminEnv } from "../middleware/require-admin";

const IdParam = z.object({ id: z.coerce.number().int().positive() });
const MessageUpdate = z.object({ isRead: z.boolean() });

export const adminRoutes = new Hono<AdminEnv>();

adminRoutes.get("/me", async (c) => {
  const [admin] = await db
    .select({ id: admins.id, email: admins.email, name: admins.name })
    .from(admins)
    .where(eq(admins.id, c.get("adminId")));
  if (!admin) throw new AppError(401, "UNAUTHORIZED", "กรุณาเข้าสู่ระบบ");    // ถูกลบบัญชีไปแล้ว
  return ok(c, admin);
});

adminRoutes.get("/dashboard", async (c) => {
  const unread = await db.$count(contactMessages, eq(contactMessages.isRead, false));
  const totalServices = await db.$count(services);
  const latest = await db.select().from(contactMessages).orderBy(desc(contactMessages.createdAt)).limit(5);
  return ok(c, { unread, totalServices, latest });
});

// เปลี่ยนสถานะอ่านแล้ว/ยังไม่อ่าน ใช้ PATCH ไม่ใช่ GET เพราะ GET ต้องไม่เปลี่ยนข้อมูล (บทที่ 5)
adminRoutes.patch("/messages/:id", async (c) => {
  const { id } = parse(IdParam, c.req.param());
  const body = parse(MessageUpdate, await c.req.json().catch(() => null));
  const [message] = await db
    .update(contactMessages)
    .set({ isRead: body.isRead })
    .where(eq(contactMessages.id, id))
    .returning();
  if (!message) throw new AppError(404, "NOT_FOUND", "ไม่พบข้อความนี้");
  return ok(c, message);
});

adminRoutes.delete("/categories/:id", async (c) => {
  const { id } = parse(IdParam, c.req.param());
  const [used] = await db.select({ n: count() }).from(services).where(eq(services.categoryId, id));
  if (used && used.n > 0) {
    throw new AppError(409, "CATEGORY_IN_USE", `ยังมีบริการ ${used.n} รายการในหมวดนี้ ย้ายหรือลบก่อน`);
  }
  const [deleted] = await db.delete(categories).where(eq(categories.id, id)).returning();
  if (!deleted) throw new AppError(404, "NOT_FOUND", "ไม่พบหมวดนี้");
  return ok(c, deleted);
});
```

`src/index.ts` ประกอบเข้าด้วยกัน **เขียนทับทั้งไฟล์ของบทที่ 14** (ของเดิมยังอยู่ครบ เพิ่มบรรทัด ⓪–③ และกรณี 403 ใน `onError` ซึ่งอธิบายในหัวข้อ CSRF ถัดไป)
```ts
import { Hono } from "hono";
import { logger } from "hono/logger";
import { csrf } from "hono/csrf";
import { HTTPException } from "hono/http-exception";
import { env } from "./env";
import { AppError } from "./http/response";
import { requireAdmin } from "./middleware/require-admin";
import { publicRoutes } from "./routes/public";
import { authRoutes } from "./routes/auth";
import { adminRoutes } from "./routes/admin";

const app = new Hono();
app.use(logger());                                          // log ทุก request ใน terminal

// ⓪ ด่าน CSRF หน้าทุก /api/* ต้องมาก่อน route ทุกตัว (ข้อ 4)
app.use("/api/*", csrf({ origin: env.APP_ORIGIN }));

app.get("/api/health", (c) => c.json({ status: "ok" }));
app.route("/api", publicRoutes);
app.route("/api/admin", authRoutes);         // ① login / logout ประกาศก่อน
app.use("/api/admin/*", requireAdmin);       // ② ทุก /api/admin/* ที่ประกาศหลังบรรทัดนี้ต้องผ่าน middleware
app.route("/api/admin", adminRoutes);        // ③ endpoint ที่ต้อง login

app.notFound((c) =>
  c.json({ success: false, error: { code: "NOT_FOUND", message: "ไม่พบ endpoint นี้", details: {} } }, 404),
);

app.onError((err, c) => {
  if (err instanceof AppError) {
    return c.json({ success: false, error: { code: err.code, message: err.message, details: err.details } }, err.status);
  }
  if (err instanceof HTTPException && err.status === 403) {   // ด่าน csrf ปฏิเสธ
    return c.json({ success: false, error: { code: "FORBIDDEN", message: "คำขอนี้ไม่ได้มาจากหน้าเว็บของเรา", details: {} } }, 403);
  }
  console.error(err);                                       // stack trace อยู่ใน log ของเราเท่านั้น
  return c.json(
    { success: false, error: { code: "INTERNAL_ERROR", message: "เกิดข้อผิดพลาดในระบบ", details: {} } },
    500,
  );
});

export default { port: env.PORT, fetch: app.fetch };
```
> **เคล็ดลับ:** `app.route("/api", publicRoutes)` มี **บรรทัดเดียว** ถ้าเผลอแปะซ้ำ (เช่นก๊อปส่วนใหม่ไปต่อท้ายไฟล์เดิม) Hono จะลงทะเบียน route ชุดเดียวกันสองรอบ และ middleware ในชุดนั้น (เช่น `rateLimit` ของฟอร์มติดต่อ) จะทำงานสองครั้งต่อคำขอ ส่งครั้งเดียวนับเป็นสอง
> **ลำดับบรรทัดสำคัญมาก:** Hono ทำงานตามลำดับที่เขียน คำขอ `/api/admin/login` เจอบรรทัด ① ก่อนและตอบกลับเลย จึงไม่ต้องผ่านด่านตรวจ ② ถ้าสลับลำดับ จะไม่มีใคร login ได้เลย

![คำขอ login ถูกตอบก่อนถึงด่าน requireAdmin ส่วนคำขออื่นต้องผ่านด่าน ไม่ผ่านได้ 401](/img/15-middleware-gate.svg)
*คำขอ login ไม่ผ่านด่าน แต่คำขออื่นของ /api/admin ต้องผ่าน requireAdmin ก่อนถึงโค้ดที่ทำงานจริง*

### ด่านกันคำขอปลอมจากเว็บอื่น (CSRF)

**ปัญหา:** cookie ถูกแนบ **อัตโนมัติ** ทุกครั้งที่เบราว์เซอร์ส่งคำขอไปเว็บเรา ไม่ว่าคำขอนั้นจะเริ่มจากหน้าไหน ถ้าเจ้าของร้าน login ค้างไว้ แล้วเผลอเปิดเว็บของคนร้าย หน้านั้นสั่งเบราว์เซอร์ให้ส่ง `DELETE /api/admin/services/3` มาที่เว็บเราได้ เบราว์เซอร์แนบบัตรผ่านไปให้ server เห็นบัตรถูกต้องก็ลบให้ การโจมตีแบบนี้เรียกว่า **CSRF** (Cross-Site Request Forgery แปลว่าปลอมคำขอข้ามเว็บ)

> **นึกภาพ:** คนร้ายเขียนใบสั่งจ่ายเงินแล้วยื่นให้เราถือเข้าธนาคาร พนักงานเห็นหน้าเรา (บัตรผ่าน) ก็ทำให้ โดยไม่ได้ถามว่าใบสั่งนี้ใครเขียน ด่าน CSRF คือการถามว่า "ใบสั่งนี้เขียนจากหน้าเว็บของเราหรือเปล่า"

**`SameSite=Lax` กันได้แค่ไหน**
| คำขอมาจาก | `SameSite=Lax` แนบ cookie ไหม | ปลอดภัยไหม |
|---|---|---|
| เว็บคนละโดเมน เช่น `evil.com` ส่ง `POST` / `DELETE` | ❌ ไม่แนบ | ✅ |
| โดเมนย่อยของเราเอง เช่น `blog.bitcafe.example` (เบราว์เซอร์นับเป็น "site เดียวกัน") | ✅ แนบ | ถ้าโดเมนย่อยนั้นถูกเจาะ หรือเป็นของคนอื่นที่เช่าโดเมนย่อยไป ก็ยิงมาได้ |
| คลิกลิงก์จากเว็บอื่นมาหน้าเรา (`GET` ทั้งหน้า) | ✅ แนบ | ✅ ถ้า `GET` ไม่เคยแก้ข้อมูล (กฎข้อนี้สำคัญ: อะไรที่เปลี่ยนข้อมูลต้องเป็น `POST` / `PATCH` / `DELETE`) |

อีกจุดคือ `c.req.json()` ของ Hono **ไม่ดู Content-Type** คำขอแบบ `text/plain` ที่ฟอร์ม HTML ธรรมดาส่งได้ (ไม่ต้องขออนุญาต CORS ก่อน) จึงถูกอ่านเป็น JSON ได้เหมือนกัน ด่านเดียวจึงไม่พอ

**วิธีแก้:** ด่าน `csrf` ของ Hono คือบรรทัด ⓪ ใน `src/index.ts` ด้านบน
```ts
app.use("/api/*", csrf({ origin: env.APP_ORIGIN }));
```
อยู่หน้าทุก `/api/*` และก่อน `app.route` ทุกบรรทัด เพราะ Hono ทำงานตามลำดับที่เขียน ถ้าวางไว้ทีหลัง route ที่ตอบไปแล้วจะไม่เคยผ่านด่านนี้ ส่วนกรณี `HTTPException` 403 ใน `onError` ต้องอยู่ **ก่อน** `console.error(err)` เพราะด่าน `csrf` ปฏิเสธด้วยการ throw `HTTPException` (ไม่ใช่ `AppError` ของเรา) ถ้าไม่ดักไว้ จะตกไปถึงบรรทัดสุดท้ายแล้วกลายเป็น 500 "เกิดข้อผิดพลาดในระบบ" ทั้งที่ไม่มีอะไรพัง

**ด่านนี้ตรวจอะไร** (ตรวจเฉพาะคำขอที่เปลี่ยนข้อมูลได้ คือไม่ใช่ `GET` / `HEAD` / `OPTIONS` และมี Content-Type แบบที่ฟอร์ม HTML ส่งได้ หรือไม่มี Content-Type เลย)
1. header `Sec-Fetch-Site` ที่เบราว์เซอร์ใส่ให้เอง (โค้ดหน้าเว็บปลอมไม่ได้) ถ้าเป็น `same-origin` = มาจากหน้าเว็บเราเอง ผ่าน
2. ถ้าข้อ 1 ไม่ผ่าน ดู header `Origin` ว่าตรงกับ `APP_ORIGIN` ไหม ตรงก็ผ่าน
3. ไม่ผ่านทั้งสองข้อ ตอบ `403`

> **ทำไมต้องบอก `origin` เอง:** ถ้าไม่ใส่ Hono จะเทียบ `Origin` กับที่อยู่ที่ server เห็นตัวเอง ซึ่งไม่เคยตรงในโปรเจกต์เรา ตอนพัฒนา proxy ของ Vite แบบเขียนสั้น (`"/api": "http://localhost:3000"`) ตั้ง `changeOrigin: true` ให้เอง จึงเปลี่ยน header `Host` เป็น `localhost:3000` server เลยเห็นตัวเองเป็น `http://localhost:3000` แต่เบราว์เซอร์ส่ง `Origin: http://localhost:5173` และตอนขึ้นระบบจริง Caddy คุยกับ server ด้วย `http://` แต่เบราว์เซอร์ส่ง `https://` (ทดสอบแล้วกับ Vite 8: ผ่าน proxy แบบเขียนสั้น server เห็น `Host: localhost:3000` และคำขอ `POST` แบบ `text/plain` ที่มี `Origin: http://localhost:5173` แต่ไม่มี `Sec-Fetch-Site` ได้ 403 ถ้าไม่ใส่ `origin`) เบราว์เซอร์รุ่นใหม่ยังผ่านด้วย `Sec-Fetch-Site` แต่เราไม่ควรให้ความปลอดภัยพึ่งด่านเดียว

> **แล้วคำขอแบบ `application/json` จากเว็บอื่นล่ะ ทำไมด่านปล่อยผ่าน?** เพราะเบราว์เซอร์จะไม่ยอมส่ง JSON ข้ามเว็บจนกว่าจะถาม server ก่อน (CORS preflight) และ API เราไม่ได้เปิด CORS ไว้ เบราว์เซอร์จึงหยุดคำขอนั้นเอง ด่าน `csrf` เลยดูแลเฉพาะช่องที่ CORS ไม่ได้กัน ถ้าวันหนึ่งเปิด CORS ให้ทุกเว็บ ช่องนี้จะเปิดทันที

### ลองด้วยคำสั่ง curl
```bash
# ① ไม่ login → ต้องได้ 401
curl -i http://localhost:3000/api/admin/me

# ② login ผิด → 401 ข้อความเดียวกันทั้งอีเมลผิดและรหัสผิด
curl -i -H "Content-Type: application/json" \
  -d '{"email":"admin@bitcafe.local","password":"wrong"}' \
  http://localhost:3000/api/admin/login

# ③ login ถูก → 200 + Set-Cookie (เก็บ cookie ลงไฟล์ด้วย -c)
curl -i -c cookies.txt -H "Content-Type: application/json" \
  -d '{"email":"admin@bitcafe.local","password":"<ADMIN_PASSWORD>"}' \
  http://localhost:3000/api/admin/login

# ④ ส่ง cookie กลับไป (-b) → 200
curl -i -b cookies.txt http://localhost:3000/api/admin/me

# ⑤ ลบหมวดที่ยังมีบริการ → 409 (curl ไม่ใช่เบราว์เซอร์ ไม่ใส่ Origin ให้ เราจึงใส่เองแทนหน้าเว็บ)
curl -i -b cookies.txt -X DELETE -H "Origin: http://localhost:5173" \
  http://localhost:3000/api/admin/categories/1

# ⑥ แกล้งเป็นเว็บคนร้าย: มีบัตรผ่านถูกต้อง แต่ Origin เป็นเว็บอื่น → 403
curl -i -b cookies.txt -X DELETE -H "Origin: https://evil.example" \
  http://localhost:3000/api/admin/categories/1
```
 ดูบรรทัด `Set-Cookie` ในข้อ ③ ต้องมีคำว่า `HttpOnly` และ `SameSite=Lax`

ข้อ ⑥ ควรเห็น
```
HTTP/1.1 403 Forbidden
...
{"success":false,"error":{"code":"FORBIDDEN","message":"คำขอนี้ไม่ได้มาจากหน้าเว็บของเรา","details":{}}}
```
> **เคล็ดลับ:** ข้อ ⑤ ถ้าลืม `-H "Origin: ..."` จะได้ `403` แบบเดียวกับข้อ ⑥ เพราะคำขอ `DELETE` ที่ไม่มีทั้ง `Origin` และ `Sec-Fetch-Site` ด่านพิสูจน์ไม่ได้ว่ามาจากหน้าเว็บเรา ส่วน login ข้อ ②③ ผ่านได้เพราะส่งเป็น `application/json` (เหตุผลอยู่ในกล่อง ด้านบน) ทั้งนี้ด่าน `csrf` อยู่ก่อน `requireAdmin` คำขอที่ไม่มี `Origin` จึงได้ `403` ก่อนจะได้ไปถึง `401`

### ยังไม่ login → พาไปหน้า login
![RequireAuth มี 3 สถานะ: checking, in, out ถ้าได้ 401 พาไปหน้า login แล้วกลับมาหน้าเดิม](/img/15-require-auth.svg)
*RequireAuth เช็คกับ server ว่ายัง login อยู่ไหม แล้วแสดงหน้าหรือพาไปหน้า login*

`client/src/components/require-auth.tsx`
```tsx
import { useEffect, useState, type ReactNode } from "react";
import { Navigate, useLocation } from "react-router";
import { getMe } from "../api/auth";

export default function RequireAuth({ children }: { children: ReactNode }) {
  const location = useLocation();
  const [state, setState] = useState<"checking" | "in" | "out">("checking");

  useEffect(() => {
    getMe()
      .then(() => setState("in"))
      .catch(() => setState("out"));
  }, [location.pathname]);                       // เช็คใหม่ทุกครั้งที่เปลี่ยนหน้า (session อาจหมดอายุ)

  if (state === "checking") return <p className="p-8">กำลังตรวจสอบสิทธิ์... ⏳</p>;
  if (state === "out") return <Navigate to="/admin/login" replace state={{ from: location.pathname }} />;
  return <>{children}</>;
}
```

### หน้า login
`client/src/pages/admin/login-page.tsx`
```tsx
import { useState, type SubmitEvent } from "react";
import { useLocation, useNavigate } from "react-router";
import { login } from "../../api/auth";

export default function LoginPage() {
  const navigate = useNavigate();
  const location = useLocation();
  const from = (location.state as { from?: string } | null)?.from ?? "/admin";

  const [email, setEmail] = useState("");
  const [password, setPassword] = useState("");
  const [error, setError] = useState<string | null>(null);
  const [sending, setSending] = useState(false);

  async function onSubmit(e: SubmitEvent<HTMLFormElement>) {
    e.preventDefault();
    setSending(true);
    setError(null);
    try {
      await login(email, password);
      navigate(from, { replace: true });          // กลับไปหน้าที่ตั้งใจจะเข้าตอนแรก
    } catch (err) {
      setError(err instanceof Error ? err.message : "เข้าสู่ระบบไม่สำเร็จ");
    } finally {
      setSending(false);
    }
  }

  return (
    <form onSubmit={onSubmit} className="mx-auto mt-24 max-w-sm space-y-4 rounded-2xl bg-white p-8 shadow">
      <title>เข้าสู่ระบบหลังบ้าน</title>
      <h1 className="text-2xl font-bold">เข้าสู่ระบบ</h1>
      <input type="email" autoComplete="username" placeholder="อีเมล" value={email}
        onChange={(e) => setEmail(e.target.value)} className="w-full rounded border p-2" />
      <input type="password" autoComplete="current-password" placeholder="รหัสผ่าน" value={password}
        onChange={(e) => setPassword(e.target.value)} className="w-full rounded border p-2" />
      {error && <p className="text-sm text-red-600">{error}</p>}
      <button disabled={sending} className="w-full rounded bg-brand py-2 text-white disabled:opacity-50">
        {sending ? "กำลังเข้าสู่ระบบ..." : "เข้าสู่ระบบ"}
      </button>
    </form>
  );
}
```

```tsx
}
```
ทำไม `admin/login` อยู่ **นอก** `RequireAuth`: ถ้าอยู่ข้างใน คนที่ยังไม่ login จะถูกส่งไปหน้า login ซึ่งก็ต้อง login ก่อนอีก วนไม่จบ

**ควรเห็น** (`bun run dev` ทั้งสองฝั่ง): เปิด `/admin/services` ตอนยังไม่ login → ถูกพาไปหน้า "เข้าสู่ระบบ" → login ด้วย `ADMIN_EMAIL` / `ADMIN_PASSWORD` → กลับมาที่ "จัดการบริการ" (หน้าที่ตั้งใจเข้าตอนแรก) → กด "สรุป" เห็น `ข้อความที่ยังไม่อ่าน: 0 · บริการทั้งหมด: 3` → กด "ออกจากระบบ" กลับไปหน้า login และกดย้อนกลับก็เข้าไม่ได้แล้ว

### เปิดอ่านข้อความแล้วเปลี่ยนเป็น "อ่านแล้ว"
ในหน้าข้อความ ตอนเจ้าของร้านกดเปิดข้อความไหน ให้หน้าเว็บส่ง `PATCH` ไปบอก server
```ts
await api(`/api/admin/messages/${id}`, { method: "PATCH", body: JSON.stringify({ isRead: true }) });
```

![เทียบการให้ GET เปลี่ยนสถานะอ่านแล้วเอง ซึ่งผิด กับการใช้ PATCH ที่ถูก](/img/15-message-read.svg)
*GET ต้องดูอย่างเดียว การเปลี่ยนสถานะอ่านแล้วต้องใช้ PATCH*

 ทำไมไม่ให้ `GET` เปลี่ยนสถานะให้เองเลย? เพราะ `GET` ต้องเป็นการดูอย่างเดียว (บทที่ 5) ระบบอื่นอาจเรียก `GET` เองโดยไม่มีใครตั้งใจ เช่น ตัวโหลดหน้าล่วงหน้าของเบราว์เซอร์ แล้วข้อความจะกลายเป็นอ่านแล้วทั้งที่เจ้าของร้านยังไม่เห็น

### บัตรหมดอายุระหว่างใช้งาน
แก้ `api()` ในไฟล์ `client/src/api/client.ts` เปลี่ยนบรรทัด `if (!body.success) throw ...` เป็น:
```ts
  if (!body.success) {
    // บัตรหมดอายุระหว่างใช้งาน → ส่งกลับไป login (ยกเว้น login เอง และ /me ที่ RequireAuth ใช้ถาม)
    if (res.status === 401 && path.startsWith("/api/admin") && path !== "/api/admin/login" && path !== "/api/admin/me") {
      window.location.assign("/admin/login");
    }
    throw new ApiError(res.status, body.error.code, body.error.message, body.error.details);
  }
```
ทำไมยกเว้น 2 ที่อยู่:
- `/api/admin/login`: รหัสผิดได้ 401 ถ้าส่งไปหน้า login ใหม่ ข้อความ "อีเมลหรือรหัสผ่านไม่ถูกต้อง" จะหายไปก่อนผู้ใช้ทันอ่าน
- `/api/admin/me`: `RequireAuth` ใช้ถามว่า login อยู่ไหม และได้ 401 เป็นเรื่องปกติทุกครั้งที่ยังไม่ login มันจัดการเองอยู่แล้วด้วย `<Navigate state={{ from }}>` ที่จำหน้าเดิมไว้ ถ้าไม่ยกเว้น `window.location.assign` จะโหลดหน้าใหม่ทั้งหน้า สิ่งที่จำไว้ใน `state` หายหมด login เสร็จแล้วไปตกที่ `/admin` แทนหน้าที่ตั้งใจเข้า (ทดสอบแล้ว: ไม่ยกเว้น `/me` เปิด `/admin/services` ตอนยังไม่ login จะเรียก `window.location.assign` 1 ครั้ง ยกเว้นแล้วเป็น 0 ครั้ง)

ส่วน API หลังบ้านตัวอื่น เช่น `/api/admin/dashboard` ถ้าได้ 401 แปลว่าบัตรหมดอายุ **ระหว่าง** ใช้งาน จึงส่งไป login ได้เลย

![บัตรใช้ได้ 1 วัน หมดอายุแล้วได้ 401 และหน้าเว็บพาไป login ส่วนออกจากระบบคือลบ cookie](/img/15-session-expiry.svg)
*เส้นเวลาของบัตรผ่าน และสิ่งที่เกิดขึ้นตอนกดออกจากระบบ*

## 6. เช็คความปลอดภัยของระบบ login

- [ ] ตาราง `admins` ไม่มีรหัสผ่านจริง มีแต่ `password_hash`
- [ ] กุญแจลับ `JWT_SECRET` ยาว 32 ตัวขึ้นไป สุ่มจริง อยู่ในไฟล์ `.env` เท่านั้น (ไม่ขึ้น Git)
- [ ] เรียก `/api/admin/...` ทุกตัวโดยไม่มี cookie ได้ `401` (ลองให้ครบทุกตัว)
- [ ] login ผิดได้ข้อความเดียวกัน ไม่ว่าอีเมลผิดหรือรหัสผิด
- [ ] หน้า login จำกัดจำนวนครั้งที่ลองได้
- [ ] cookie มี `HttpOnly`, `SameSite=Lax` และตอนขึ้นระบบจริงมี `Secure`
- [ ] มีด่าน `csrf({ origin: env.APP_ORIGIN })` หน้า `/api/*` ส่ง `DELETE` ที่มี `Origin: https://evil.example` แล้วได้ `403` และตอนขึ้นระบบจริงตั้ง `APP_ORIGIN` เป็นโดเมนจริง
- [ ] ไม่มี `GET` ตัวไหนเปลี่ยนข้อมูล (เพราะ `SameSite=Lax` ยังแนบ cookie ให้ `GET` จากเว็บอื่น)
- [ ] ไม่มีโค้ดไหนเก็บบัตรผ่านไว้ใน localStorage
- [ ] ออกจากระบบแล้ว เรียก `/api/admin/me` ได้ `401`

> **ข้อจำกัดของบัตรผ่านแบบนี้:** ออกจากระบบ = ลบ cookie ในเครื่องเรา แต่ถ้ามีคนก๊อปบัตรไปก่อน บัตรนั้นยังใช้ได้จนหมดอายุ (1 วัน) ระบบที่ต้องเตะผู้ใช้ออกทันที จะเก็บรายการคนที่ login อยู่ไว้ที่ server แทน ([บทที่ 10](/10-security#login-แล้ว-server-จำเราได้ยังไง-session-vs-jwt))

## เช็คความเข้าใจ

<details>
<summary>1. ทำไมกันคนไม่ได้ login ที่หน้าเว็บอย่างเดียวไม่พอ?</summary>

โค้ดหน้าเว็บอยู่ในเครื่องของผู้ใช้ แก้หรือข้ามได้ และใครก็ส่งคำขอตรงไปที่ API ด้วย curl ได้ ตัวตัดสินจริงต้องเป็นด่านตรวจที่ server

</details>

<details>
<summary>2. ทำไมตอนหาอีเมลไม่เจอ ยังต้องเทียบรหัสผ่านกับรหัสหลอกอีก?</summary>

การเทียบรหัสผ่านใช้เวลานาน (ตั้งใจให้ช้า) ถ้าหาอีเมลไม่เจอแล้วตอบทันที คนร้ายจับเวลาได้ว่าอีเมลไหนมีบัญชีจริง การเทียบกับรหัสหลอกทำให้ทุกกรณีใช้เวลาพอๆ กัน

</details>

<details>
<summary>3. บัตรผ่าน (JWT) ถูกเข้ารหัสไหม ใส่อะไรลงไปได้บ้าง?</summary>

ไม่ได้เข้ารหัส แค่เซ็นชื่อกันแก้ ใครก็อ่านข้างในได้ จึงใส่ได้แค่ข้อมูลที่ไม่ลับ เช่น เลขบัญชีกับเวลาหมดอายุ

</details>

<details>
<summary>4. ถ้าหน้าเว็บอยู่ `shop.com` แต่ API อยู่ `api-shop.com` จะเกิดอะไรกับ cookie?</summary>

เบราว์เซอร์ถือว่าเป็นคนละเว็บ cookie แบบ `SameSite=Lax` จะไม่ถูกแนบไป ต้องตั้งค่าข้ามเว็บเพิ่มหลายอย่าง ซึ่งยุ่งและเสี่ยงกว่า จึงควรให้ API อยู่ชื่อเว็บเดียวกันที่ `/api` ([บทที่ 20](/20-deploy-vps), [บทที่ 22](/22-deploy-managed))

</details>

<details>
<summary>5. มี `SameSite=Lax` แล้ว ทำไมยังต้องมีด่าน `csrf` อีก?</summary>

`SameSite` นับโดเมนย่อยทั้งหมดเป็น site เดียวกัน ถ้าโดเมนย่อยไหนถูกเจาะ ก็ส่งคำขอพร้อม cookie มาได้ ด่าน `csrf` ตรวจละเอียดกว่า คือดูว่ามาจาก **หน้าเว็บเราเท่านั้น** (`Sec-Fetch-Site: same-origin` หรือ `Origin` ตรง `APP_ORIGIN`) หลักคิดคือความปลอดภัยควรมีหลายชั้น ชั้นหนึ่งพลาด อีกชั้นยังกันอยู่

</details>

## แบบฝึกหัด

ทำหน้าจัดการร้านของ Bit Café: หน้า login, หน้าสรุป (จำนวนข้อความที่ยังไม่อ่าน + ข้อความล่าสุด 5 ข้อความ), หน้าข้อความ (ที่ยังไม่อ่านเป็นตัวหนา กดเปิดแล้วส่ง `PATCH` ให้เป็นอ่านแล้ว) และปุ่มออกจากระบบ จากนั้นเขียนไฟล์ `.http` ที่เรียก API หลังบ้านทุกตัวโดยไม่ login แล้วได้ `401` ครบทุกตัว (ใส่ `Origin: http://localhost:5173` ทุกคำขอ ไม่งั้นคำขอที่ไม่ได้ส่ง JSON เช่น `DELETE` และ logout จะโดนด่าน `csrf` ตอบ `403` ก่อน) และเพิ่มอีก 1 คำขอที่ใส่ `Origin` ของเว็บอื่นแล้วได้ `403`
