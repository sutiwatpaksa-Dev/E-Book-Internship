> **สรุป 30 วินาที**
> - พิมพ์ชื่อเว็บแล้วเกิด 4 ขั้น: **หาที่อยู่** จากชื่อเว็บ → **ต่อสาย** ไปที่เครื่องนั้น → **ตรวจบัตร** ว่าเป็นเว็บจริง (ถ้าเป็น https) → **ส่งคำขอ** แล้วรับคำตอบ
> - **IP** = บ้านเลขที่ของเครื่อง / **Port** = เลขห้องในเครื่อง / **Firewall** = ยามหน้าตึก
> - `localhost` กับ `0.0.0.0` ไม่เหมือนกัน เรื่องนี้ทำให้ขึ้นเว็บพังบ่อยที่สุด
> - ใช้คำสั่ง `curl -v`, `dig`, `ping` ดูทีละขั้นว่าพังตรงไหน

## เรื่องเล่า

บิตขึ้นเว็บครั้งแรก เปิดในเครื่องตัวเองได้ แต่ส่งลิงก์ให้ลูกค้าแล้วลูกค้าเปิดไม่ได้
บิตลองปิดเปิด server 3 รอบ ลบกล่อง Docker ทิ้งแล้วสร้างใหม่ ก็ยังไม่ได้

พี่ไบต์ถามคำถามเดียว: *"เปิดไม่ได้แบบไหน? หาเว็บไม่เจอ, ต่อไม่ติด, หรือต่อติดแต่ขึ้น error?"*
บิตตอบไม่ได้ เพราะไม่รู้ว่า **การเปิดเว็บ 1 ครั้งมีหลายขั้น** และแต่ละขั้นพังคนละแบบ

## ฝึกด่าน 7 ฟรีได้แค่ไหน

ด่าน 7 (บทที่ 17–23) พูดถึง "เครื่องเช่า" กับ "ชื่อเว็บจริง" ซึ่งเสียเงินทั้งคู่ แต่ **ความเข้าใจเกือบทั้งหมดฝึกได้ฟรี** เพราะสิ่งที่เราเรียนจริงๆ คือ *ลำดับขั้นและเหตุผล* (ชื่อ → IP → ประตู → ใบรับรอง → โปรแกรม) ซึ่งเหมือนกันทุกตัวอักษร ไม่ว่าเครื่องจะอยู่ในศูนย์ข้อมูลที่สิงคโปร์ หรืออยู่ในโน้ตบุ๊คของเราเอง ต่างกันแค่ "ใครบนโลกมองเห็นเครื่องนั้น"

| บท | ฝึกฟรีด้วยอะไร | ส่วนที่ต้องใช้ของจริง (เสียเงิน) |
|---|---|---|
| 17 เน็ตเวิร์ก | ทั้งบท: เครื่องตัวเอง + เว็บจริงเว็บไหนก็ได้ | ไม่มี |
| 18 ชื่อเว็บ | `dig` / `nslookup` กับเว็บจริง, จำลองชื่อเว็บด้วยไฟล์ `hosts` และชื่อ `*.localhost` ([บทที่ 18 ข้อ 4](/18-domain-dns#4-ตรวจว่าชื่อเว็บชี้ถูก)), บัญชี Cloudflare แบบ Free | จดชื่อเว็บจริง (จ่ายรายปี) |
| 19 เครื่องเช่า | **VM ในเครื่องเรา** ด้วย Multipass (ฟรี ใช้ได้ทั้ง Mac / Windows 10–11 รวม Home / Linux) หรือ UTM (Mac) ทำได้ครบทุกข้อ ส่วนกล่อง Docker ที่เปิด SSH ใช้ฝึกเฉพาะเรื่องกุญแจและบัญชี | VPS จริงที่มี IP สาธารณะ (จ่ายรายเดือน) |
| 20 ขึ้นเว็บ | **ทั้งระบบ** บนเครื่องตัวเองหรือใน VM ด้วย `DOMAIN=bitcafe.localhost` ([บทที่ 20 ข้อ 9](/20-deploy-vps#9-ซ้อมทั้งบทบนเครื่องตัวเอง-ฟรี)) | ใบรับรองจาก Let's Encrypt (ต้องมีชื่อเว็บจริง + เครื่องที่คนทั้งโลกต่อถึง) และการเปิดจากมือถือ / แชร์ลง LINE |
| 21 CI/CD | งานตรวจ (`check`) บน GitHub Actions ฟรีสำหรับ repo สาธารณะ และ `deploy.sh` รันเองบน VM | งาน `deploy` ที่เครื่องกลาง SSH เข้าไป ต้องมีเครื่องที่ GitHub ต่อถึง (VPS) |
| 22 บริการสำเร็จรูป | **ทั้งบท** ด้วยแผนฟรีของ Vercel + Render + Neon ได้ **ลิงก์สาธารณะจริง** (`*.vercel.app`) ที่ส่งให้ใครเปิดก็ได้ | ข้อ 6 ใส่ชื่อเว็บของตัวเอง (ต้องมีชื่อเว็บ) และงานลูกค้าจริงต้องใช้แผนเสียเงิน |
| 23 เปิดใช้จริง | สำรอง / ซ้อมกู้ / cron บนเครื่องตัวเองหรือ VM, เฝ้าเว็บด้วย UptimeRobot แผนฟรีกับลิงก์จากบทที่ 22 | ไม่มี (ส่วนที่เป็นของลูกค้าจริงทำตอนมีงานจริง) |

**เส้นทางฟรีที่แนะนำ:** 17 → 18 (เข้าใจ + `dig` + `hosts`) → 19 บน Multipass → 20 บน VM หรือเครื่องตัวเอง → 21 งานตรวจบน GitHub + `deploy.sh` บน VM → **22 ได้ลิงก์สาธารณะจริง** → 23 ซ้อมสำรองและกู้บน VM + เฝ้าลิงก์ของบทที่ 22

> **ใครจ่ายค่าเครื่องเช่าและชื่อเว็บ?** คู่มือนี้ไม่ได้กำหนด ถ้าแบบฝึกหัดข้อไหนต้องใช้ของจริง ให้ **ถามพี่เลี้ยง / บริษัท** ว่ามีเครื่องฝึก หรือชื่อย่อยของบริษัทให้ใช้ไหม และ **ก่อนกรอกบัตรใดๆ ในหน้าสมัครบริการ ให้ถามก่อนทุกครั้ง** (แผนฟรีบางเจ้าขอบัตรไว้ แล้วคิดเงินอัตโนมัติเมื่อใช้เกิน)

## 1. เปิดเว็บ 1 ครั้งเกิดอะไรขึ้น

![4 ขั้นของการเปิดเว็บ: หาที่อยู่ ต่อสาย ตรวจบัตร ส่งคำขอ พร้อมอาการเมื่อพังแต่ละขั้น](/img/17-four-steps.svg)
*เปิดเว็บ 1 ครั้งผ่าน 4 ขั้นเรียงกัน ถ้าขั้นไหนพังจะเห็นข้อความต่างกัน*

> **นึกภาพ: ไปส่งพัสดุ**
> ① เปิดสมุดหาบ้านเลขที่จากชื่อร้าน / ② เดินไปถึงหน้าตึกและมีคนเปิดประตู / ③ ตรวจบัตรว่าเป็นร้านจริงไม่ใช่ร้านปลอม / ④ ยื่นใบสั่งของ

**อาการ → พังที่ขั้นไหน**
| สิ่งที่เห็น | ขั้น | สาเหตุที่เจอบ่อย |
|---|---|---|
| `DNS_PROBE_FINISHED_NXDOMAIN`, `Could not resolve host` | ① หาที่อยู่ | ยังไม่ได้ตั้งชื่อเว็บ, พิมพ์ชื่อผิด, ชื่อเว็บเพิ่งตั้งยังไม่มีผลทั่วโลก |
| `Connection timed out` | ② ต่อสาย | ยามบล็อก, IP ผิด, เครื่องปิดอยู่ |
| `Connection refused` | ② ต่อสาย | ถึงเครื่องแล้ว แต่ **ไม่มีโปรแกรมรอรับที่ประตูนั้น** |
| `Your connection is not private`, `SSL certificate problem` | ③ ตรวจบัตร | ยังไม่มีใบรับรอง, ใบหมดอายุ, ชื่อบนใบไม่ตรง |
| `502 Bad Gateway` | ④ ส่งคำขอ | ประตูหน้า (เช่น Caddy) ส่งต่อให้โปรแกรมข้างในไม่ได้ (โปรแกรมล่ม / ชื่อผิด) |
| `404` / `500` | ④ ส่งคำขอ | ถึงโปรแกรมของเราแล้ว ปัญหาอยู่ในโค้ด |


สองอาการของขั้น ② ที่คนสับสนบ่อยที่สุดคือ `refused` กับ `timed out` ดูภาพนี้

![เปรียบเทียบ Connection refused (มีคนตอบว่าไม่มีใครรับ) กับ Connection timed out (เงียบไม่มีใครตอบ)](/img/17-refused-timeout.svg)
*refused = ไปถึงเครื่องแล้วโดนปฏิเสธทันที / timed out = ส่งไปแล้วเงียบ รอจนหมดเวลา*

## 2. IP: บ้านเลขที่ของเครื่อง

| ชนิด | ตัวอย่าง | ใช้ได้ที่ไหน |
|---|---|---|
| **IP ภายใน (private)** | `192.168.1.25`, `10.0.0.5`, `172.17.0.2` | ในบ้าน / ออฟฟิศ / ในเครือข่ายของ Docker เท่านั้น |
| **IP สาธารณะ (public)** | `203.0.113.10` | ทั้งโลกเห็น เครื่องเช่า (VPS) จะได้ IP แบบนี้ |
| **ตัวเอง (loopback)** | `127.0.0.1` (`localhost`) | เครื่องตัวเองเท่านั้น |
| **IPv6** | `2001:db8::1` | IP รุ่นใหม่ ยาวกว่า มีพอให้ทุกอุปกรณ์ในโลก |

![IP ภายในของอุปกรณ์ในบ้านออกอินเทอร์เน็ตผ่านเราเตอร์ที่มี IP สาธารณะ 1 ตัว](/img/17-nat.svg)
*อุปกรณ์ในบ้านใช้ IP ภายใน เราเตอร์แปลงเป็น IP สาธารณะตัวเดียวเวลาออกเน็ต*
 นี่คือเหตุผลที่ลูกค้าเปิด `http://192.168.1.25:5173` ไม่ได้: IP นี้ใช้ได้เฉพาะใน Wi-Fi บ้านเรา

> **ลองเอง (ฟรี):** เปิด `bun run dev` ของหน้าเว็บ (บทที่ 11) แล้วให้มือถือที่ต่อ **Wi-Fi เดียวกัน** เปิด `http://<IP ในวง Wi-Fi>:5173` จะเปิดไม่ได้ ทั้งที่อยู่บ้านเดียวกัน เพราะ Vite รอรับแค่ `localhost` เป็นค่าเริ่มต้น (ดูข้อ 3 เรื่อง `localhost` กับ `0.0.0.0`) ลองใหม่ด้วย `bun run dev --host` Vite จะพิมพ์บรรทัด `Network: http://192.168.x.x:5173/` เพิ่มขึ้นมา คราวนี้มือถือเปิดได้ แต่ลูกค้าที่อยู่นอกบ้านก็ยังเปิดไม่ได้อยู่ดี เพราะ IP ภายในใช้ได้แค่ใน Wi-Fi นี้

```bash
curl -4 ifconfig.me       # IP สาธารณะที่โลกเห็นเรา
ipconfig getifaddr en0    # Mac: IP ในวง Wi-Fi  (Windows: ipconfig / Linux: ip addr)
```

## 3. Port: เลขห้องในเครื่อง และ "ใครรออยู่ในห้องนี้"

**Port** = เลขช่องทาง 0–65535 ในเครื่องเดียวกัน โปรแกรมหนึ่งใช้ได้หลายห้อง แต่ห้องหนึ่งมีเจ้าของได้คนเดียว

![IP คือเลขของตึก port คือเลขห้อง ในเครื่องเช่าเครื่องเดียวมีหลายห้องที่แต่ละโปรแกรมรออยู่](/img/17-port-rooms.svg)
*IP บอกว่าเครื่องไหน port บอกว่าโปรแกรมไหนในเครื่องนั้น*

| Port | ใช้กับ | ตั้งในบท |
|---|---|---|
| `22` | SSH (เข้าเครื่องเช่า) | 19 |
| `80` | เว็บแบบ http | 20 (Caddy) |
| `443` | เว็บแบบ https | 20 (Caddy) |
| `3000` | API ของเรา | 14 |
| `5173` | Vite ตอนพัฒนาหน้าเว็บ | 11 |
| `5432` | ฐานข้อมูล PostgreSQL | 2, 14 |

**ดูว่าใครใช้ห้องไหนอยู่**
```bash
lsof -i :3000                # Mac
sudo ss -tlnp                # Linux (server): รายการ port ที่มีโปรแกรมฟังอยู่ทั้งหมด
netstat -ano | findstr :3000 # Windows: เลขท้ายบรรทัดคือ PID แล้วดูชื่อด้วย tasklist /FI "PID eq <PID>"
```

### `localhost` ไม่เหมือน `0.0.0.0` (สำคัญมาก)
เวลาโปรแกรม "รอรับ" ที่ห้องไหน ต้องบอกด้วยว่า **รับจากใครบ้าง**
| รอรับที่ | ใครเรียกได้ |
|---|---|
| `127.0.0.1` / `localhost` | เฉพาะโปรแกรมในเครื่องเดียวกัน (หรือในกล่อง Docker เดียวกัน) |
| `0.0.0.0` | ทุกคนที่เข้ามาถึงเครื่องนี้ รวมถึงกล่อง Docker อื่น |

![เปรียบเทียบ server รอรับที่ 127.0.0.1 (Caddy เรียกไม่ถึง ได้ 502) กับ 0.0.0.0 (เรียกถึง)](/img/17-bind-address.svg)
*127.0.0.1 ในแต่ละกล่องหมายถึงกล่องนั้นเอง กล่องอื่นจึงเรียกไม่ถึง*
 Bun (ที่ Hono ใช้) รอรับที่ `0.0.0.0` อยู่แล้วโดยไม่ต้องตั้ง แต่เครื่องมือบางตัวรอรับแค่ `localhost` ต้องตั้งเอง

## 4. การส่งข้อมูล และทำไมต้อง HTTPS

| | ทำอะไร | นึกภาพ |
|---|---|---|
| **TCP** | ส่งข้อมูลแบบรับประกันว่าถึงครบ และเรียงลำดับถูก | ส่งพัสดุลงทะเบียน มีเซ็นรับ |
| **UDP** | ส่งเร็ว แต่ไม่รับประกัน | ตะโกนบอก ได้ยินก็ดี ไม่ได้ยินก็แล้วไป (วิดีโอคอล, เกม) |
| **HTTP** | ภาษาที่เบราว์เซอร์คุยกับ server (บทที่ 5) | ใบสั่งของ |
| **HTTPS** | HTTP ที่ใส่ซองปิดผนึก + ตรวจบัตรผู้รับ | ใบสั่งของในซองปิดผนึก |

ตอนเบราว์เซอร์ต่อสายกับ server (ขั้น ② และ ③) จะคุยกันตามลำดับนี้ ก่อนส่ง HTTP จริง

![ลำดับจับมือ TCP 3 ข้อความ แล้ว TLS ตรวจใบรับรองและตกลงกุญแจ ก่อนส่ง HTTP](/img/17-tcp-tls.svg)
*TCP จับมือให้ต่อสายติด TLS ตรวจบัตรและเข้ารหัส แล้วค่อยส่ง HTTP*

**ทำไมต้อง HTTPS ทุกเว็บ** (แม้เป็นแค่เว็บร้านกาแฟ)
- คนที่ใช้ Wi-Fi เดียวกัน แอบอ่านหรือแก้ข้อมูลที่ส่งแบบ http ได้ รวมถึง cookie login ของเจ้าของร้าน
- เบราว์เซอร์ขึ้นคำว่า "Not secure" ลูกค้าไม่กล้าใช้
- cookie ที่ตั้ง `Secure` ไว้ (บทที่ 15) จะไม่ถูกส่งเลยถ้าไม่ใช่ https

**ใบรับรอง (certificate)** = บัตรประชาชนของเว็บ ออกโดยหน่วยงานที่เบราว์เซอร์เชื่อถือ เช่น **Let's Encrypt** (ฟรี) อายุประมาณ 90 วัน ต้องต่ออายุเรื่อยๆ ซึ่ง Caddy ทำให้เอง (บทที่ 20)

---

## 5. Firewall: ยามหน้าตึก

**Firewall** = กฎว่าประตูไหนให้คนนอกเข้ามาได้

![ยามหน้าเครื่องเช่าเปิดให้ผ่านเฉพาะ port 22 80 443 และปิด 3000 กับ 5432](/img/17-firewall.svg)
*Firewall เปิดเฉพาะประตูที่จำเป็น ที่เหลือปิดหมด*
> **หลักการ:** ปิดไว้ก่อนทุกประตู แล้วเปิดเฉพาะที่จำเป็น ฐานข้อมูลที่เปิดประตู 5432 ให้คนนอก จะถูกโปรแกรมของคนร้ายเจอภายในไม่กี่ชั่วโมง

ยามมี 2 ชั้นที่ต้องรู้: **ยามของผู้ให้บริการเครื่องเช่า** (ตั้งในหน้าเว็บของเขา) และ **ยามในเครื่อง** (`ufw` บน Ubuntu) ตั้งในบทที่ 19

---

## 6. ประตูหน้าบานเดียว (Reverse proxy)

**Reverse proxy** = พนักงานต้อนรับที่ล็อบบี้ รับทุกคนแล้วพาไปห้องที่ถูก

![ผู้ใช้เข้าที่ Caddy port 443 แล้ว Caddy ส่ง /api ไปที่ server และอย่างอื่นไปไฟล์หน้าเว็บ](/img/17-reverse-proxy.svg)
*Caddy เป็นประตูหน้าบานเดียว แล้วแจกต่อให้โปรแกรมที่ถูกต้อง*
**ได้อะไร**
- เปิดประตูให้คนนอกแค่ 80/443 ที่เดียว
- จัดการ HTTPS ที่เดียว
- หน้าเว็บกับ API อยู่ **ชื่อเว็บเดียวกัน** → ระบบ login ด้วย cookie ใช้ง่าย ไม่ต้องตั้งค่าข้ามเว็บ (บทที่ 14–15)
- อัปเดตโปรแกรมข้างในได้ โดยลูกค้าไม่รู้สึกอะไร

## 7. ลงมือ: เครื่องมือดูทีละขั้น

```bash
# ① DNS: ชื่อนี้ชี้ไป IP อะไร
dig +short example.com              # Mac/Linux
nslookup example.com                # มีทุกระบบ รวม Windows (Git Bash / PowerShell)

# ② ต่อถึงเครื่องไหม
ping -c 3 example.com               # Windows ใช้ ping -n 3  (บาง server ปิด ping ไว้ ไม่ตอบไม่ได้แปลว่าเครื่องล่ม)
traceroute example.com              # Windows: tracert  (ดูเส้นทางผ่านกี่จุด)

# ②③④ ดูทุกขั้นในคำสั่งเดียว
curl -v https://example.com
```
อ่านผล `curl -v` ทีละบรรทัด:
```
* Host example.com:443 was resolved.            ← ① DNS ผ่าน
*   Trying 203.0.113.10:443...
* Connected to example.com (203.0.113.10) port 443   ← ② TCP ผ่าน
* SSL connection using TLSv1.3 ...
*  subject: CN=example.com                      ← ③ TLS ผ่าน ใบรับรองตรงชื่อ
> GET / HTTP/2                                   ← ④ request ที่เราส่ง
< HTTP/2 200                                     ← ④ response ที่ได้
```
บรรทัดไหนหายไป หรือขึ้น error = พังที่ขั้นนั้น

> **ใช้ Windows:** `dig` ไม่ได้มากับเครื่อง ใช้ `nslookup` แทนได้ทุกที่ในบทนี้ (`nslookup -type=NS example.com` = `dig NS example.com`) และพิมพ์ `curl` ใน **Git Bash** (บทที่ 0) เพราะใน Windows PowerShell 5.1 คำว่า `curl` คือคำสั่งอื่น (`Invoke-WebRequest`) ที่ไม่รู้จัก `-v` แบบนี้

```bash
curl -I https://example.com         # ดูแค่ header ของ response
curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" https://example.com   # status + เวลา
```

## เช็คความเข้าใจ

<details>
<summary>1. `Connection refused` กับ `Connection timed out` ต่างกันยังไง?</summary>

refused = ไปถึงเครื่องแล้ว แต่ไม่มีโปรแกรมรอรับที่ประตูนั้น (โปรแกรมไม่ได้เปิด หรือรอผิดประตู) / timed out = ไปไม่ถึง หรือไม่มีใครตอบเลย มักเป็นเพราะยามบล็อก หรือ IP ผิด

</details>

<details>
<summary>2. ทำไมกล่อง server ที่รอรับที่ `127.0.0.1` ทำให้ Caddy ได้ 502?</summary>

แต่ละกล่องมี "ตัวเอง" ของมันเอง `127.0.0.1` ในกล่อง server หมายถึงกล่อง server เท่านั้น Caddy ที่อยู่อีกกล่องจึงต่อไม่ถึง ต้องรอรับที่ `0.0.0.0`

</details>

<details>
<summary>3. ทำไมห้ามเปิดประตู 5432 ของฐานข้อมูลให้คนนอก?</summary>

โปรแกรมของคนร้ายตามหาประตูฐานข้อมูลตลอดเวลาแล้วลองเดารหัส ฐานข้อมูลควรคุยได้เฉพาะกับ API ในเครือข่ายภายในเท่านั้น

</details>

<details>
<summary>4. เว็บขึ้น `502 Bad Gateway` ควรดูอะไรก่อน?</summary>

ขั้นหาที่อยู่ ต่อสาย และตรวจบัตรผ่านหมดแล้ว (ไม่งั้นจะไม่เห็น 502) ปัญหาอยู่ระหว่าง Caddy กับโปรแกรมข้างใน: โปรแกรมล่มไหม (`docker compose ps`, `logs`), ชื่อกล่องหรือประตูใน Caddyfile ถูกไหม, โปรแกรมรอรับที่ `0.0.0.0` ไหม

</details>

## แบบฝึกหัด

ใช้ `dig`, `curl -v` และ `curl -I` กับ 3 เว็บ: เว็บธนาคาร, เว็บข่าว และ `http://` (ไม่มี s) ของเว็บใดเว็บหนึ่ง จดว่าแต่ละเว็บ: IP อะไร, ใบรับรองออกโดยใคร, ได้เลขบอกผลอะไร และ `http://` ถูกพาไปที่ไหน
