> **⚡ สรุป 30 วินาที**
> - **บริการสำเร็จรูป (managed)** = มีคนดูแลเครื่อง ระบบปฏิบัติการ HTTPS ให้ เราแค่ส่งโค้ดขึ้น Git

## 1. เช่าเครื่องเอง vs ใช้บริการสำเร็จรูป

| | 🖥️ เช่าเครื่องเอง (บทที่ 19–21) | ☁️ บริการสำเร็จรูป (บทนี้) |
|---|---|---|
| ใครอัปเดตความปลอดภัยของเครื่อง | เรา | ผู้ให้บริการ |
| HTTPS | Caddy ทำให้ (ตั้งครั้งเดียว) | ได้เองอัตโนมัติ |
| ขึ้นระบบ | เราเขียนขั้นตอนอัตโนมัติเอง | ส่งงานขึ้น Git แล้วขึ้นระบบเอง + ได้ **เว็บทดลองของทุกคำขอรวมงาน** |
| ค่าใช้จ่าย | เท่าเดิมทุกเดือน ถูกถ้าวางหลายเว็บในเครื่องเดียว | แผนฟรีใช้ฝึกและโชว์งานได้ แต่ **เว็บลูกค้าต้องใช้แผนเสียเงิน** (เช่น Vercel Pro) และจ่ายเพิ่มตามการใช้งาน |
| ปรับแต่งได้ | ทุกอย่าง | เท่าที่บริการเปิดให้ |
| ข้อเสีย | ต้องรู้เรื่องดูแลเครื่อง | แผนฟรีหลับเมื่อไม่มีคนใช้, ย้ายไปที่อื่นทีหลังเหนื่อย |
| ได้เรียนรู้ | ลึกเรื่องเครือข่าย, Linux, Docker | เร็ว เน้นที่ตัวแอป |

![เปรียบเทียบว่าใครดูแลแต่ละชั้น ระหว่างเช่าเครื่องเองกับบริการสำเร็จรูป](/img/22-vps-vs-managed.svg)
*บริการสำเร็จรูปยกงานเครื่อง HTTPS และการขึ้นระบบให้ผู้ให้บริการ เหลือแค่โค้ดแอปที่เรายังต้องดูแลเอง*

> 💡 ไม่มีแบบไหน "ดีกว่า" เสมอ dev ที่ดี **อธิบายข้อดีข้อเสียให้ลูกค้าเลือกเองได้**

## 3. 🔧 ฐานข้อมูล: Neon

1. สมัคร neon.tech → **Create project** → เลือก **Singapore** (ใกล้ไทย) → PostgreSQL 17
2. ก๊อป **ที่อยู่สำหรับต่อฐานข้อมูล** (connection string) หน้าตาแบบนี้
   ```
   postgresql://<user>:<password>@<host>.neon.tech/<db>?sslmode=require
   ```
   `sslmode=require` = บังคับเข้ารหัสระหว่าง API กับฐานข้อมูล (อยู่คนละที่ ต้องเข้ารหัส)
3. สร้างตาราง + ข้อมูลตั้งต้น **จากเครื่องเรา** (ทำครั้งแรกครั้งเดียว)
   ```bash
   cd server
   DATABASE_URL='postgresql://...neon.tech/...?sslmode=require' JWT_SECRET='<สุ่ม 32 ตัวขึ้นไป>' bun run db:migrate
   DATABASE_URL='postgresql://...' JWT_SECRET='<สุ่ม>' ADMIN_EMAIL='owner@example.com' ADMIN_PASSWORD='<รหัส>' bun run seed
   ```
   ⚠️ คำสั่งที่มีรหัสผ่านจะค้างอยู่ในประวัติคำสั่งของ Terminal ให้ลบทิ้ง (`history -d`) หรือพิมพ์ช่องว่างนำหน้าคำสั่ง (ถ้าตั้งค่าให้ไม่จำคำสั่งที่ขึ้นต้นด้วยช่องว่างไว้)

> 💡 ใช้ที่อื่นแทนได้: **Supabase** (มี PostgreSQL + ของแถม), **Railway** (มีฐานข้อมูลในโปรเจกต์เดียวกับ API)

## 4. 🔧 ส่วนเบื้องหลัง (API): Render

1. render.com → **New → Web Service** → เชื่อมกับโปรเจกต์ใน GitHub
2. ตั้งค่า
   | ช่อง | ใส่ |
   |---|---|
   | Root Directory (โฟลเดอร์ที่ใช้) | `server` |
   | Runtime (วิธีรัน) | **Docker** (ใช้ `server/Dockerfile` จากบทที่ 20) |
   | Region (ที่ตั้งเครื่อง) | Singapore |
   | Health Check Path (ที่อยู่ไว้เช็คว่าปกติ) | `/api/health` |
3. **Environment Variables** (ค่าตั้งค่า แบบเดียวกับไฟล์ `.env`)
   | ชื่อ | ค่า |
   |---|---|
   | `DATABASE_URL` | ที่อยู่ฐานข้อมูลจาก Neon |
   | `JWT_SECRET` | ผลจาก `openssl rand -base64 48` |
   | `NODE_ENV` | `production` |
   | `PORT` | `3000` |
   | `TRUST_PROXY` | `true` (อ่านคำเตือนเรื่อง IP ด้านล่างก่อน) |
   | `APP_ORIGIN` | ที่อยู่หน้าเว็บที่ลูกค้าเปิดจริง เช่น `https://example.com` (ไม่ใช่ลิงก์ `onrender.com`) ด่านกัน CSRF ใช้เทียบว่าคำขอมาจากหน้าเว็บเรา ([บทที่ 15](./15-auth.md)) |
4. กด Deploy → ได้ลิงก์เช่น `https://bitcafe-api.onrender.com` ลอง `curl https://bitcafe-api.onrender.com/api/health`

![ค่าตั้งค่าอยู่ตรงไหน: Neon ให้ connection string ใส่ใน Render ส่วน vercel.json มีแค่ที่อยู่ API และเครื่องเรารัน migrate ครั้งแรก](/img/22-env-places.svg)
*ค่าลับอยู่ในช่อง Environment Variables ของบริการ ส่วน `vercel.json` มีแค่ที่อยู่ API ที่เปิดเผยได้*

**อัปเดตตารางครั้งต่อๆ ไป** เลือกทางใดทางหนึ่ง
- ตั้ง **Pre-Deploy Command** เป็น `bun run db:migrate` (ถ้าแผนที่ใช้มีให้) Render จะอัปเดตตารางก่อนสลับเป็นโค้ดใหม่ ลำดับเดียวกับบทที่ 20
- หรือให้ขั้นตอนอัตโนมัติในบทที่ 21 สั่ง `bun run db:migrate` ก่อนขึ้นระบบ ทางนี้ต้องทำเพิ่มให้ครบ เพราะ **Render ขึ้นระบบเองทันทีที่มีงานเข้า `main` โดยไม่รอใคร** ถ้าไม่ตั้ง โค้ดใหม่ที่ต้องใช้คอลัมน์ใหม่จะออนไลน์ก่อนตารางถูกอัปเดต แล้วพังจนกว่า migrate จะเสร็จ
  1. เก็บ `DATABASE_URL` ของ Neon เป็นค่าลับในระบบตรวจงาน (GitHub Secrets) ระบบตรวจงานยังไม่รู้จักฐานข้อมูลนี้
  2. Render → Settings → **Auto-Deploy = Off** ไม่ให้ขึ้นระบบเอง (ตัวเลือก "After CI Checks Pass" ยังไม่พอ เพราะรอแค่งานตรวจ ไม่ได้รอ migrate)
  3. ก๊อป **Deploy Hook** (ลิงก์ลับสำหรับสั่งขึ้นระบบ) จาก Render เก็บเป็นค่าลับ `RENDER_DEPLOY_HOOK`
  4. ใน `deploy` ของบทที่ 21 ให้ทำตามลำดับ: `bun run db:migrate` (ใช้ `DATABASE_URL` จากข้อ 1) → `curl -fsS -X POST "$RENDER_DEPLOY_HOOK"` เพื่อสั่ง Render ขึ้นโค้ดใหม่

  หลักคิดเดียวกับบทที่ 20: **ตารางต้องพร้อมก่อนโค้ดที่ใช้มัน** และ migrate ต้องเขียนแบบที่โค้ดเก่ายังทำงานได้ (เพิ่มคอลัมน์ได้ แต่อย่าลบคอลัมน์ที่โค้ดเก่ายังใช้ในรอบเดียวกัน)

![แผนฟรีหลับเมื่อไม่มีคนใช้ คนแรกที่เข้าต้องรอหลายสิบวินาที แล้วกลับมาเร็วปกติ](/img/22-cold-start.svg)
*ที่เรียกว่า cold start: คนแรกหลังช่วงหลับต้องรอให้เครื่องตื่นก่อน*

> ⚠️ **แผนฟรีของหลายบริการจะ "หลับ"** เมื่อไม่มีคนใช้สักพัก คนแรกที่เข้าหลังจากนั้นต้องรอหลายสิบวินาที ใช้โชว์งานได้ แต่ **เว็บลูกค้าจริงควรใช้แผนที่ไม่หลับ** และแจ้งลูกค้าเรื่องค่าใช้จ่ายตั้งแต่แรก
>
> ⚠️ **แผนฟรีไม่ได้แปลว่าใช้กับงานลูกค้าได้** แผน Hobby ของ Vercel ใช้ได้เฉพาะ **งานส่วนตัวที่ไม่ใช่เชิงพาณิชย์** ([เอกสาร Vercel](https://vercel.com/docs/plans/hobby) ณ ต.ค. 2569) เว็บร้านของลูกค้าคืองานเชิงพาณิชย์ ต้องใช้แผน Pro (คิดต่อคนในทีม) ก่อนเลือกบริการใดก็ตาม ให้อ่าน **เงื่อนไขการใช้งาน** ของแผนนั้นด้วย ไม่ใช่ดูแค่ราคา แล้วใส่ค่าใช้จ่ายรายเดือนไว้ในใบเสนอราคาตั้งแต่แรก
> 🔐 **คำเตือนเรื่องตัวจำกัดจำนวนครั้ง (rate limit) ในแบบนี้ ต้องอ่าน**
> ลิงก์ `onrender.com` ของ API **เรียกตรงได้โดยไม่ผ่าน Vercel** และเราไม่ได้คุม proxy ของ Render เองเหมือน Caddy ในบทที่ 20
> - ตั้ง `TRUST_PROXY=false`: server เห็น IP ของ proxy ของ Render เป็น IP เดียวกันหมดทุกคน → ทุกคนใช้โควตาร่วมกัน คนร้ายส่งรัวๆ แล้ว **ลูกค้าจริงส่งฟอร์มไม่ได้ และเจ้าของร้านถูกล็อก login**
> - ตั้ง `TRUST_PROXY=true`: ใช้ค่าท้ายสุดของ `X-Forwarded-For` ซึ่งปลอดภัย **เฉพาะเมื่อ proxy ของผู้ให้บริการเติม IP จริงต่อท้ายเสมอ** ถ้าไม่ใช่ คนร้ายใส่ header นี้เองแล้ว **หลบการจำกัดได้ทั้งหมด** รวมถึงหน้า login
>
> **ต้องทดสอบเองหลังขึ้นระบบ** ส่ง 6 ครั้งโดยปลอม IP ไม่ซ้ำกัน ครั้งที่ 6 ต้องได้ `429` ถ้าไม่ได้ = หลบได้ (ลบข้อความทดสอบในหน้าจัดการร้านทิ้งหลังลอง)
> ```bash
> for i in 1 2 3 4 5 6; do curl -s -o /dev/null -w "%{http_code}\n" -H "X-Forwarded-For: 10.0.0.$i" -H "Content-Type: application/json" -d '{"name":"test","phone":"0812345678","message":"test"}' https://bitcafe-api.onrender.com/api/contact; done
> ```
> **ทดสอบผ่านทางที่ลูกค้าใช้จริงด้วย** (ชื่อเว็บ → Vercel → Render) เพราะเป็นคนละเส้นทางกัน: ยิงตรงที่ `onrender.com` ด่านสุดท้ายก่อนถึง Render คือเครื่องเรา แต่ผ่าน Vercel ด่านสุดท้ายคือ **เครื่องของ Vercel** ค่าท้ายสุดของ `X-Forwarded-For` อาจกลายเป็น IP ของ Vercel แล้วลูกค้าทุกคนใช้โควตาร่วมกันโดยที่การทดสอบแรกไม่เห็น
> ```bash
> for i in 1 2 3 4 5 6; do curl -s -o /dev/null -w "%{http_code}\n" -H "X-Forwarded-For: 10.0.0.$i" -H "Content-Type: application/json" -d '{"name":"test","phone":"0812345678","message":"test"}' https://example.com/api/contact; done
> ```
> ผลที่ต้องได้: ครั้งที่ 6 ได้ `429` **และ** ลองส่งจากอีกเครือข่าย (เช่น เน็ตมือถือ) ทันทีหลังจากนั้นต้องยังได้ `201` ถ้าอีกเครือข่ายได้ `429` ด้วย = ทุกคนถูกนับเป็นคนเดียวกัน ตัวจำกัดใช้ไม่ได้ ให้ไปใช้ตัวจำกัดของผู้ให้บริการแทน (ย่อหน้าถัดไป)
> ถ้าหลบได้ หรือไม่อยากเสี่ยง: ปิดตัวจำกัดในโค้ด แล้วใช้ **ตัวจำกัดของผู้ให้บริการหรือ Cloudflare** (ตั้งกฎสำหรับ `/api/contact` และ `/api/admin/login`) แทน หน้า login ยังพอปลอดภัยเพราะ `Bun.password` ตั้งใจให้เดารหัสช้ามากอยู่แล้ว แต่ต้องตั้งรหัสผ่านยาวและเดายาก

สรุปคำเตือนข้างบนเป็นภาพ (เนื้อหาเดียวกัน ให้ยึดตามข้อความและผลทดสอบจริงเป็นหลัก)

![เปรียบเทียบ TRUST_PROXY เป็น false กับ true และวิธีทดสอบด้วยการส่ง 6 ครั้ง](/img/22-trust-proxy.svg)
*ตั้ง `false` ทุกคนใช้โควตาร่วมกัน ตั้ง `true` ปลอดภัยเฉพาะเมื่อ proxy เติม IP จริงต่อท้ายเสมอ จึงต้องทดสอบเองหลังขึ้นระบบ*

## 5. 🔧 หน้าเว็บ: Vercel

`client/vercel.json`
```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "rewrites": [
    { "source": "/api/:path*", "destination": "https://bitcafe-api.onrender.com/api/:path*" },
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
```
| กฎ | ทำอะไร |
|---|---|
| `/api/:path*` → Render | Vercel ส่งคำขอต่อให้ API แล้วส่งคำตอบ (รวม cookie) กลับมาในนามของ `example.com` |
| `/(.*)` → `/index.html` | ขอหน้าไหนก็ส่งหน้าหลักไป ให้ React เลือกหน้าเอง (แบบเดียวกับ `try_files` ในบทที่ 20) Vercel ดูไฟล์จริงก่อนเสมอ ไฟล์ใน `/assets` จึงไม่โดนกฎนี้ |

![ลำดับที่ Vercel ตัดสินคำขอ: กฎ /api ส่งไป Render, ไฟล์จริงส่งตรง, ที่เหลือได้ index.html](/img/22-rewrite-rules.svg)
*คำขอหนึ่งตัวถูกตัดสินจากบนลงล่าง จึงต้องวางกฎ `/api` ไว้บนสุด*

1. vercel.com → **Add New → Project** → เลือกโปรเจกต์จาก GitHub
2. **Root Directory** = `client` → Vercel รู้เองว่าเป็นเว็บ Vite (สั่ง `bun run build` แล้วเอาไฟล์จากโฟลเดอร์ `dist`)
3. กด **Deploy** → ได้ลิงก์เช่น `https://bit-cafe-xxxx.vercel.app`
4. ลอง: หน้าเว็บขึ้น, `/api/services` ได้ข้อมูล, รีเฟรช `/about` ไม่ 404, login หน้าจัดการร้านได้

**ของแถม:** ทุกคำขอรวมงาน (PR) จะได้ **เว็บทดลองแยก (Preview)** ส่งลิงก์ให้พี่เลี้ยงหรือลูกค้าดูก่อนรวมงานได้

![ทุก PR ได้เว็บทดลองแยก แต่เว็บทดลองและเว็บจริงใช้ API และฐานข้อมูลตัวจริงตัวเดียวกัน](/img/22-preview-deploys.svg)
*เว็บทดลองสะดวกในการดูงานก่อนรวม แต่ใช้ข้อมูลจริงร่วมกับเว็บจริง*

> ⚠️ เว็บทดลองทุกตัวส่งคำขอไปที่ API และฐานข้อมูล **ตัวจริง** (ตามไฟล์ `vercel.json`) ระวังการทดสอบที่ไปแก้ข้อมูลจริง ถ้างานใหญ่ขึ้นควรแยก API + ฐานข้อมูลสำหรับทดลอง

## 6. 🔧 ใส่ชื่อเว็บจริง

**Vercel:** Project → Settings → **Domains** → เพิ่ม `example.com` และ `www.example.com`
Vercel จะบอกว่าต้องเพิ่มบรรทัดไหนในสมุดชื่อเว็บ (ปกติเป็น **A** สำหรับชื่อหลัก และ **CNAME** สำหรับ `www`) → ไปเพิ่มใน Cloudflare (บทที่ 18) **ตามค่าที่หน้าจอ Vercel บอก** แบบเมฆสีเทา → รอขึ้นว่า Valid แล้ว HTTPS มาเอง

**(ไม่บังคับ) ชื่อย่อยให้ API:** Render → Settings → Custom Domains → `api.example.com` → เพิ่ม CNAME ตามที่ Render บอก แล้วแก้ปลายทางใน `vercel.json` เป็น `https://api.example.com/api/:path*`

ตรวจ

```bash
dig +short example.com
curl -I https://example.com/about                   # 200
curl -sS https://example.com/api/health             # {"status":"ok"}
curl -s -o /dev/null -w "%{http_code}\n" https://example.com/api/admin/me   # 401
```

## 7. ⚠️ ปัญหาที่เจอบ่อย

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| เรียก `/api/...` แล้วได้หน้าเว็บแทนข้อมูล | กฎ `/(.*)` อยู่ก่อนกฎ `/api` | ให้กฎ `/api/:path*` อยู่บนสุด |
| รีเฟรช `/about` แล้ว 404 | ไม่มีกฎส่งหน้าหลัก หรือวาง `vercel.json` ผิดโฟลเดอร์ | วาง `vercel.json` ใน `client/` |
| เปิดครั้งแรกช้ามาก | แผนฟรีหลับอยู่ | ใช้แผนที่ไม่หลับ / แจ้งลูกค้า |
| ต่อฐานข้อมูลไม่ได้ / ขึ้นเรื่อง certificate | ไม่มี `sslmode=require` หรือก๊อปที่อยู่ไม่ครบ | ก๊อปที่อยู่จาก Neon ให้ครบทั้งเส้น |
| login ผ่าน แต่ cookie ไม่ติด | หน้าเว็บเรียก `onrender.com` ตรงๆ | หน้าเว็บต้องเรียก `/api/...` เสมอ |
| Render ขึ้น error ตอนเปิด | ขาดค่าตั้งค่าตัวใดตัวหนึ่ง | ใส่ให้ครบตามข้อ 4 |

## 🧠 เช็คความเข้าใจ

<details><summary>1. ทำไมให้ Vercel ส่งต่อ <code>/api</code> ดีกว่าให้หน้าเว็บเรียก <code>onrender.com</code> ตรงๆ?</summary>

เบราว์เซอร์จะเห็นชื่อเว็บเดียว cookie login เป็นของ `example.com` ใช้แบบปลอดภัย (`SameSite=Lax`) ได้ ไม่ต้องตั้งค่าข้ามเว็บซึ่งยุ่งและเสี่ยงกว่า
</details>

<details><summary>2. ลูกค้างบน้อย อยากได้เว็บเร็ว และไม่มีคนดูแลเครื่อง ควรแนะนำแบบไหน? ข้อดีข้อเสียคืออะไร</summary>

บริการสำเร็จรูปเหมาะกว่า: ไม่ต้องดูแลเครื่อง ขึ้นระบบง่าย แต่เว็บจริงต้องใช้แผนที่ไม่หลับ ค่าใช้จ่ายขึ้นกับการใช้งาน และย้ายไปที่อื่นทีหลังต้องใช้แรง
</details>

<details><summary>3. เว็บทดลอง (Preview) มีประโยชน์และความเสี่ยงอะไร?</summary>

ประโยชน์: ทุกคำขอรวมงานมีเว็บให้ดูของจริงก่อนรวม / ความเสี่ยง: ถ้าเว็บทดลองใช้ API และฐานข้อมูลตัวจริง การทดสอบอาจไปแก้ข้อมูลจริงของลูกค้า
</details>
