# เขียนการ์ดความรู้

การ์ดคือหน่วยความรู้ 1 เรื่องในขั้น 7 ขั้น (`/learn`) เป้าหมายคือให้น้องที่เพิ่งจบงาน Todo (ตาราง 1 ตาราง, Prisma) เข้าใจ **ทำไม** ไม่ใช่ก๊อปโค้ด และพอทำตามครบทุกการ์ดแล้วต้องได้ระบบที่รันได้จริง

## ก่อนเขียน: อ่าน 3 อย่าง

1. **Requirement STARTER:** `Requirement โปรเจกต์ฝึกงาน เว็บไซต์ STARTER (Fullstack) (2).pdf` ที่ root ของ repo (17 หน้า) **ลิงก์ไป PDF ใช้ชื่อหัวข้อ** `/api/files/requirement.pdf?sec=<key>` (เช่น `?sec=api`, `?sec=timeline` · รายการ key ดูที่หลังบ้าน "โจทย์และตั้งค่า") ห้ามใช้ `#page=N` เพราะแต่ละรุ่นได้โจทย์คนละชิ้น หัวข้อเดียวกันอยู่คนละหน้า (มีเทสต์ตรวจ) · เลขหน้าที่เขียนเป็นตัวหนังสือใช้ตามโปรแกรมเปิด PDF ของ STARTER ส่วนที่ต้องเปิดดูทุกครั้ง:
   - stack: React+TS (Vite), Tailwind, React Router, Bun+Hono, Drizzle, Zod, PostgreSQL+pgAdmin, JWT ใน httpOnly cookie, `Bun.password`
   - โครงโฟลเดอร์ `client/src/{pages,components,api,types}` และ `server/src/{routes,db,validators,middleware}`
   - รายการ API (หน้า 8–9) รูปแบบคำตอบ (หน้า 9) และ status ที่ใช้: 200 201 400 401 404 409 500
   - หัวข้อ "ควรศึกษาก่อน" ของแต่ละวัน (หน้า 16–17) ใช้กำหนดค่า `starter` ของการ์ด
   - PDF มีจุดขัดกัน: Timeline หน้า 11 บอกวันที่ 5 = Layout+Home แต่ Checklist หน้า 14–15 บอกวันที่ 5 = Review และวันที่ 6 = Layout ให้ใช้ตาม Checklist
2. **`src/data/learn.ts`:** ลำดับการ์ด, `part`, `needs`, `starter` การ์ดที่อยู่ใน `needs` ต้องมาก่อนในรายการเสมอ (มีเทสต์ตรวจ)
3. **การ์ดข้างเคียง:** การ์ดใหม่ต้องต่อโค้ดจากการ์ดก่อนหน้าได้ ห้ามสร้างรูปแบบใหม่ที่ขัดกัน

## แม่แบบ 8 ส่วน (ห้ามข้าม)

| ส่วน | ต้องมี |
|---|---|
| ความหมาย | **คำอธิบายทั่วไป** 1–2 ประโยคแบบไม่มีศัพท์ ("พูดง่ายๆ คือ...") ก่อนนิยามจริง + **"นึกภาพ:"** เปรียบกับเรื่องใกล้ตัว + **ภาพตัวอย่าง 1 ภาพ** ถ้าเรื่องมีการไหลหรือหลายชิ้นต่อกัน + ลิงก์ glossary ตอนศัพท์โผล่ครั้งแรก (ดู "ทำให้นึกภาพออก") |
| ที่มา | ปัญหาที่ทำให้เรื่องนี้เกิดขึ้น (ไม่มีมันจะเจ็บยังไง) เล่าเป็นเหตุการณ์ที่น้องเจอได้จริง เช่น "รีเฟรชหน้าแล้ว login หลุด" ไม่ใช่หลักการลอยๆ |
| การใช้งาน | **"ตั้งค่าครั้งแรก"** ถ้ามีการติดตั้ง · **บอกก่อนโค้ดทุกก้อนว่าจะทำอะไรและทำไม** (1–2 ประโยค) · โค้ดมีชื่อไฟล์เต็มตามโครงใน Requirement · หลังโค้ดอธิบายบรรทัดที่สำคัญทีละจุด · **"ควรเห็น:"** ผลที่ต้องได้ทุกขั้น |

| ตัวเลือกอื่นที่คล้ายกัน | `<ToolTable group>` (ตรวจกับเอกสารทางการแล้ว) หรือตาราง markdown |

| อ่านเพิ่ม | ลิงก์บทเดิมที่ละเอียดกว่า |

## ทำให้นึกภาพออก

น้องที่ไม่มีพื้นฐานติดตรงที่ "อ่านทุกคำแล้วแต่ยังไม่เห็นภาพ" ทุกการ์ดต้องมี 3 อย่างนี้ เลือกใช้ให้เหมาะกับเรื่อง:

1. **คำอธิบายทั่วไป (พูดภาษาคน):** อธิบายเรื่องนั้นแบบที่เล่าให้คนนอกวงการฟังได้ ก่อนใช้ศัพท์ใดๆ เช่น "migration คือไฟล์บันทึกว่าแก้ตารางอะไรไปบ้าง เรียงตามลำดับ เครื่องอื่นจะได้แก้ตามได้เหมือนกัน" ถ้าต้องใช้ศัพท์ ให้แปลในวงเล็บครั้งแรก
2. **นึกภาพ (เปรียบเทียบ):** เลือกเรื่องในชีวิตจริงที่**โครงสร้างตรงกัน** ไม่ใช่แค่คล้ายกันผิวเผิน แล้วจับคู่ให้เห็นว่าชิ้นไหนคือชิ้นไหน เช่น "ร้านอาหาร: ลูกค้า = browser, พนักงานรับออเดอร์ = API, ครัว = ฐานข้อมูล" และ**บอกจุดที่เปรียบเทียบไม่ตรง**ถ้ามี (กันน้องเข้าใจผิดต่อ) · ใช้เรื่องเดียวกันตลอดการ์ด อย่าเปลี่ยนเปรียบเทียบกลางทาง
3. **ภาพตัวอย่าง:** ใช้เมื่อเรื่องมี "การไหล" (คำขอวิ่งผ่านหลายชิ้น), "ลำดับ" (ขั้นตอนก่อน-หลัง) หรือ "ความสัมพันธ์" (ตารางโยงกัน) ถ้าเล่าเป็นคำแล้วต้องจำหลายชิ้นในหัว แปลว่าต้องมีภาพ เลือกตามขนาด:
   | แบบ | ใช้เมื่อ | วิธี |
   |---|---|---|
   | แผนภาพตัวอักษร | ลูกศร 2–6 กล่อง, โครงโฟลเดอร์ | กล่อง ` ```text ` ใช้ `──►` `│` `├─` (ตัวอย่าง: ข้อ 2 ใน `vercel-deployment.mdx`) |
   | ภาพ SVG | ภาพหลักของการ์ดที่ซับซ้อนกว่านั้น หรือต้องใช้สีแยกส่วน | ไฟล์ `public/img/cards/<slug>-<เรื่อง>.svg` ใช้แบบเดียวกับ `public/img/14-request-path.svg`: `role="img"` + `aria-label` + `<title>` + `<desc>`, ฟอนต์ `'IBM Plex Sans Thai', Sarabun`, พื้นขาว (ใช้ได้ทั้งโหมดมืด), ตัวอักษรไม่ต่ำกว่า 14px, กว้าง `viewBox` 800 |
   | ภาพหน้าจอ / ผลลัพธ์ | "ควรเห็น" ที่เป็นหน้าจอ เช่น DevTools, pgAdmin | ถ้าไม่มีรูปจริง ให้ใช้ตารางหรือกล่อง `text` ที่คัดลอกผลจริงมา ห้ามวาดหน้าจอปลอม |

   ภาพ SVG ใส่ใน MDX แบบนี้ (คำบรรยายตัวเอียงบรรทัดถัดไป CSS จัดให้อยู่กลางใต้ภาพ):
   ```mdx
   ![ข้อความแทนภาพ บอกว่าภาพแสดงอะไร](/img/cards/jwt-cookie-flow.svg)
   *คำบรรยายสั้นๆ: ภาพนี้ให้ดูอะไร*
   ```
   **ภาพต้องมีคำอธิบายเป็นตัวหนังสือคู่กันเสมอ** คนที่ภาพโหลดไม่ขึ้นหรือใช้โปรแกรมอ่านหน้าจอต้องเข้าใจได้จากข้อความ ภาพไม่ใช่ที่เดียวที่มีเนื้อหา

ตรวจตัวเอง: ปิดโค้ดทั้งหมดแล้วอ่านแค่ข้อความกับภาพ น้องต้องอธิบายได้ว่าเรื่องนี้คืออะไร ทำไมต้องมี และชิ้นไหนต่อกับชิ้นไหน ถ้ายังทำไม่ได้ แปลว่าการ์ดสอนแค่วิธีก๊อป

## กติกาเนื้อหา

- **ตัวอย่างใช้ระบบห้องสมุด** (members / books / loans มี `due_at`, `returned_at`) จงใจไม่ใช้ของ STARTER เพื่อไม่สปอยงาน
- **รูปแบบคำตอบ API ตาม Requirement เสมอ:** `ok(c, data)` → `{ success: true, data }` และ `fail(c, status, CODE, message, details?)` → `{ success: false, error: { code, message, details } }` · ไม่ใช้ 204 (DELETE ตอบ 200) · error จาก Zod ใช้ `z.flattenError(error).fieldErrors`
- เว็บคู่มือนี้ตอบ `{ error: "..." }` แบบสั้น ถ้าอ้างโค้ดเว็บนี้ให้บอกว่าต่างจาก Requirement เพราะทำก่อน
- **คำสั่งใช้ Bun:** `bun add`, `bun add -d`, `bunx`, `bun run` ห้ามใช้ npm/npx ในการ์ด
- ทุกคำสั่ง Terminal ต้องใช้ได้ทั้ง Mac และ Windows **Git Bash** (กฎบท 0: Windows ใช้ Git Bash เท่านั้น) ห้ามสอนทาง PowerShell / `curl.exe` · ระวัง path ที่ขึ้นต้น `/` ใน Git Bash ถูกแปลง (ใช้ `MSYS_NO_PATHCONV=1`) และ `docker exec -it` ใน Git Bash อาจขึ้น not a TTY (คำสั่ง `-c` ไม่ต้อง `-it`)
- ห้ามใช้ของที่ยังไม่ได้สอน (เช่น `c.get("user")` ก่อนช่วง Login) ถ้าจำเป็นให้บอกตรงๆ ว่าเป็นทางลัดชั่วคราวและจะสอนในช่วงไหน
- ลิงก์ไฟล์ของเว็บนี้ใช้ `https://github.com/sutiwatpaksa-Dev/E-Book-Internship/blob/main/<path>` (repo เป็น public) ไฟล์ที่ยังอยู่แค่บน dev จะเปิดได้หลังขึ้น main
- ไทยง่ายๆ ประโยคสั้น ไม่ใช้ em dash
- **หัวข้อห้ามมีลิงก์** เช่น `### ใช้ใน route (ต่อจากการ์ด [Hono](...))` ทำให้เกิด `<a>` ซ้อน `<a>` (hydration error) ให้เขียนชื่อการ์ดในหัวข้อเป็นตัวหนังสือ แล้วใส่ลิงก์ในประโยคแรกใต้หัวข้อ (`src/lib/content-rules.test.ts` ตรวจให้)

## ตรวจก่อนส่ง (ทำจริง ห้ามเดา)

1. **รันโค้ดทุกชิ้นจริง** ในโปรเจกต์ทดลองที่ scratchpad (Postgres ใน Docker + `server/` Hono/Drizzle + `client/` Vite) ตามลำดับการ์ด: ติดตั้ง → migrate → seed → ยิง curl → `bun run build` ฝั่ง client แล้วเอาผลจริงไปใส่ "ควรเห็น"
2. ลิงก์ `/glossary#id` มี `id` นั้นใน `content/docs/glossary.mdx` · ลิงก์ `/learn/cards/x` มีไฟล์จริง · ลิงก์ GitHub มีไฟล์บน main หรือ dev
3. `bun test` (มีเทสต์ลำดับ `needs` และ `part`), `npm run typecheck`, `npm run build`
4. แคปหน้าการ์ดด้วย Chrome headless ดูหัวการ์ด (ป้าย STARTER, อ่านก่อน) และ sidebar · ถ้ามีภาพ ดูทั้งจอกว้าง จอมือถือ 375px (ตัวหนังสือในภาพยังอ่านออก) และโหมดมืด
5. เรียก agent `card-reader` (`.claude/agents/card-reader.md`) อ่านการ์ดที่เขียน/แก้ + การ์ดก่อนหน้าและถัดไปที่ต่อโค้ดกัน อย่าบอกเหตุผลของเราให้มันรู้ (ให้อ่านแบบน้องจริงๆ) แล้วแก้ตามข้อที่ยืนยันแล้ว ถ้า session นี้ยังไม่เห็น agent (สร้างระหว่าง session) ให้ใช้ general-purpose ที่สั่งให้อ่านไฟล์นั้นแล้วทำตาม

## ลงทะเบียนการ์ดใหม่

- เพิ่มใน `cards` ของ `src/data/learn.ts` (ตำแหน่งตาม `part` และ `needs`) และใส่ `topic` 1 หมวดจาก `topics` (plan / ux / db / api / auth / web / test) ซึ่งคลังการ์ดใช้กรองและแบ่งหัวข้อ ถ้าไม่เข้าหมวดไหนเลย ให้ถามผู้ใช้ก่อนเพิ่มหมวดใหม่ + ไฟล์ใน `meta.json` ของโฟลเดอร์ cards
- บทเดิมที่การ์ดแทนแล้ว ลบออกจาก `legacy` แต่**ไม่ลบไฟล์บทเดิม** (ถามผู้ใช้ก่อนเสมอ)
- ออกเวอร์ชันตาม skill `maintainer` (patch +0.0.1, changelog, tag, push dev)
